# Admin 주문 목록/상세 Controller + Mock JSON

`AdminOrderController.kt`를 신규 생성해 `/api/admin/v1/orders`(목록)와 `/api/admin/v1/orders/{orderId}`(상세) 두 엔드포인트를 `AdminHomeController` 패턴(생성자 주입 `MockLoader` + `mockLoader.load("admin", ...)` + `ResponseEntity.ok(data)`)으로 구현했다. 짝을 이루는 mock JSON 2개(`order__GET_admin_v1_orders.json`, `order__GET_admin_v1_orders_{order_id}.json`)는 DL §15/§16 스키마와 `IN_DELIVERY`(운송장 등록된 `PREPARING`) 표시규칙, 그리고 상세화면 3개 탭(CS·클레임/주문문의/변경이력)이 참조하는 `claims[]`/`inquiries[]`/`logs[]`를 채운다. force-cancel(§17)은 범위 밖으로 두었고 docs/와 프론트엔드는 손대지 않았다.

이번 패스는 이전 리뷰(review.md, 12:44 작성)에서 지적된 2건(claims[]의 `clamId` 오타, 한국어 레이블 값)이 이미 반영된 뒤의 상태를 다시 검토한 것이다. 상세 mock JSON 파일의 수정 시각(12:47:59)이 이전 리뷰 작성 시각(12:44:51)보다 늦어, 그 사이에 수정이 반영되었음을 파일시스템 타임스탬프로 확인했다(**confirmed**). 현재 파일을 직접 열어 `claimId`(영문 정식 필드명)와 `claimType: "RETURN"`/`status: "INSPECTING"`(DL 전역과 일치하는 영문 enum)로 바뀌어 있음을 확인했다.

Watch for: 새로 발견된 블로킹 이슈는 없다. 남아있는 것은 범위를 벗어나거나 정보성인 관찰뿐이다.

**Verdict**: APPROVED

## High-level view

Controller는 `AdminHomeController` 패턴을 정확히 따른다. 패키지(`com.runnshop.order.controller`), 클래스명(`AdminOrderController`), 생성자 주입 `MockLoader`, `mockLoader.load("admin", ...)` 호출, `ResponseEntity.ok(data)` 반환까지 모두 일치한다. 매핑 경로는 `/api/admin/v1/orders`와 `/api/admin/v1/orders/{orderId}`로 admin prefix만 쓰고 고객웹/입점사 prefix와 혼용되지 않는다. 쿼리 파라미터(`keyword/status/from/to/page/size`)는 선언만 하고 실제 필터링은 하지 않는데, 플랜에 명시된 의도적 범위축소다.

Mock 파일은 위치(`mock/admin/`)·파일명·응답 포맷(`{ "code": "SUCCESS", "data": {...} }`) 모두 규칙을 지킨다. 목록 mock은 7종 표시상태가 각 1건 이상 들어 있고 `summary`의 8개 카운트가 `orders[]` 실제 분포와 정확히 일치하며 `all(8) == totalCount(8) == len(orders)`다. `orders[]` 각 항목은 요구 필드 8개를 모두 갖춘다.

상세 mock은 §16 구조(`items/payment/shipping/history`)를 유지하면서 `claims[]`/`inquiries[]`/`logs[]`를 각 1건 이상 추가했다. 이전 패스에서 지적된 `clamId` 오타와 한국어 enum 값은 이미 `claimId`/`RETURN`/`INSPECTING`으로 수정되어 있다. `logs[]`는 `at/event/detail`로 통일되어 있고 항목 간 필드 중복은 없다. `IN_DELIVERY` 샘플(`ord-004`)은 목록·상세 양쪽에서 `trackingNumber`가 채워진 상태로 일관되게 "PREPARING + 운송장 등록 = IN_DELIVERY" 규칙을 반영한다.

빌드/실행 검증은 coder 기록과 독립적으로 Gradle 데몬 로그를 직접 열어 교차확인했다. `daemon-3795.out.log`에서 `compileKotlin` 계열 빌드가 두 차례 `BUILD SUCCESSFUL`(8s, 790ms)로 끝났고, `daemon-3161.out.log`에서 `bootRun`으로 Tomcat이 8080에서 기동된 뒤 27초 후 `DispatcherServlet`이 최초 요청에 반응해 지연초기화됐다(실제 HTTP 요청이 들어왔다는 흔적). 이후 `bootRun` 태스크는 exit code 143(SIGTERM, 수동 종료에 의한 정상적 흐름)으로 `BUILD FAILED`로 표기되지만 이는 포그라운드 서버 프로세스를 강제 종료할 때 Gradle이 항상 남기는 흔적이며, 그 직전까지 스택트레이스나 500 에러 로그는 없다. 두 mock JSON 파일은 `python3 -m json.tool`로 직접 파싱해 문법 유효성도 재확인했다(둘 다 통과).

force-cancel(POST `.../force-cancel`) 관련 코드는 `order/controller` 디렉터리 어디에도 없다. `docs/`에서 이번 작업으로 추적되는 변경은 없고(`DL-인터페이스명세/order.md`의 git diff는 이 작업보다 선행하는 무관한 변경), `apps/` 아래에도 변경 사항이 없다.

### 이전 패스 지적사항 재검증

이전 리뷰(review.md)는 `claims[]` 항목에 `clamId` 오타와 `claimType: "반품"`/`status: "처리중"` 한국어 값이 있다고 지적했다. 현재 파일(`order__GET_admin_v1_orders_{order_id}.json`)을 직접 열어 확인한 결과:

```json
"claims": [
  { "claimId": "CLM-20260628-001", "claimType": "RETURN", "status": "INSPECTING", "refundAmount": 147000, "extraShippingFee": 5000, "extraShippingFeeStatus": "PAID", "receivedAt": "2026-06-28 10:30" }
]
```

`claimId`로 수정되어 있고, `claimType`/`status` 모두 DL 전역(§10, §18~21 등)과 FE `Claim` 인터페이스가 쓰는 영문 enum(`RETURN`, `INSPECTING`)과 일치한다. 파일 수정 시각(12:47:59)이 이전 리뷰 작성 시각(12:44:51)보다 늦어 수정이 반영된 뒤의 상태임이 타임스탬프로 확인된다.

### 빌드/실행 검증 — 독립 교차확인

coder의 기록 자체를 재실행하지 않고, 로컬 Gradle 데몬 로그(`~/.gradle/daemon/8.8/daemon-3795.out.log`, `daemon-3161.out.log`)를 직접 읽어 확인했다. `currentDir=.../api/runNshop-api`에서 `compileKotlin` 빌드가 2회 `BUILD SUCCESSFUL`(8s, 그 다음 증분 790ms)로 끝났다. `bootRun`은 `Tomcat started on port 8080` → 27초 뒤 `DispatcherServlet` 지연초기화(최초 요청 수신 흔적) → 이후 exit 143(SIGTERM)으로 `BUILD FAILED` 표기. 이는 수동으로 포그라운드 서버를 종료할 때 Gradle이 항상 남기는 정상적인 흔적이며, 그 사이 스택트레이스나 500 에러는 없다. 응답 바디 내용은 액세스 로그에 남지 않으므로, 두 mock JSON은 별도로 `python3 -m json.tool`과 커스텀 파싱 스크립트로 직접 검증했다(문법 유효성, status 분포, summary 정합성 모두 통과).
