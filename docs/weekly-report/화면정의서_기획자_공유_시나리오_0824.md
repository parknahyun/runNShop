## 0. 이 문서를 쓰는 법

이 시나리오는 "설명 → 반응 유도 → 기록"을 반복하는 구조다. 발표자는 각 Step의 표·비교를 보여주고,
"질문" 박스를 그대로 던져 기획자의 실제 반응을 받는다. 반응은 별도 이슈 목록으로 옮겨 Step 6에서 취합한다.

목표는 두 가지다.
1. **설명**: 왜 PPT 한 장이던 화면정의서가 여러 md 문서로 쪼개졌는지, 그게 임의의 선택이 아니라
   산출물 간 의존관계(선행관계) 때문이라는 것을 이해시킨다.
2. **유도**: 이 전환이 기획자 실무에 실제로 어떤 불편/개선을 만드는지, 방어적 설명이 아니라
   솔직한 문제 제기를 받아낸다.

## Step 1. "지금까지 만들던 화면정의서, 뭐가 달라지나"

### 1-1. 기존 화면정의서(PPT) 8항목

| # | 항목 | 내용 |
|---|---|---|
| 1 | 화면 식별 정보 | 화면 ID, 화면명, 메뉴 경로, 접근 권한, 관련 화면 |
| 2 | 와이어프레임/목업 | 화면 레이아웃 이미지 |
| 3 | UI 요소 정의 | 번호 매칭 + 타입/기본값/필수여부/노출조건 |
| 4 | 이벤트/기능 정의 | 클릭·입력 시 동작, 화면 전환 규칙 |
| 5 | 데이터 정의 | 항목↔필드 매핑, 정렬/필터/페이징 |
| 6 | 유효성 검증 | 필수값·형식·에러 메시지 |
| 7 | 예외/에러 처리 | 데이터없음·로딩실패·권한없음 상태 화면 |
| 8 | 비고/정책 설명 | 기획 의도, 정책서 참조 |

### 1-2. 현 체계 대응 문서

| 화면정의서 항목 | runNshop 현 체계 대응 문서 |
|---|---|
| 1. 화면 식별 정보 | DD 메뉴구조도(IA) + **DN §0 메타블록**(화면ID·앱·접근권한·화면전환) |
| 2. 와이어프레임 | DN 화면레이아웃 |
| 3. UI 요소 정의 | DN "화면 구성" 표 |
| 4. 이벤트/화면 전환 | DK 세부유스케이스(행위 흐름) + DN 메타블록 "화면 전환" |
| 5. 데이터 정의(API 매핑) | DN "데이터 소스(API)" 컬럼 |
| 6. 유효성 검증 | DJ GWT + DL 인터페이스명세 에러 응답 (**DN은 링크만 보유**) |
| 7. 예외/에러 처리 | DN "상태별 UI" 표 + DJ GWT |
| 8. 정책/비고 | DK/DN 본문 REQ-ID 참조, 정책서 원본 |

> **강조 포인트**: 항목 1과 4는 최근 DN에 "화면정의서 메타블록"을 신설하면서 예전보다 한 곳에 모였다.
> 하지만 항목 6(유효성 검증)은 **의도적으로** DN에 옮기지 않고 DJ/DL 링크로만 연결해두었다 — 이 부분이
> Step 4에서 실제로 불편한지 확인이 필요한 지점이다.

> **질문 1**: PPT 한 장으로 보던 화면정의서가 지금처럼 문서 3~4개(DK/DN/DJ/DL)로 나뉜 것을 처음
> 보았을 때 어떤 인상이었나? 구체적으로 어떤 항목을 찾을 때 가장 헷갈렸나?

## Step 2. "왜 하나의 문서가 아니라 여러 산출물로 쪼개졌나"

산출물 흐름 문서(`AI활용_개발방법론_산출물_흐름.md`)의 핵심 원칙은 이렇다.

> **작성순서가 곧 실행순서** — "이걸 모르면 다음 걸 만들 수 없다"는 의존관계가 순서를 결정한다.

화면정의서에 담겼던 8항목을 하나씩 만들려면 실제로는 서로 다른 선행 정보가 필요하다.

| 만들어야 할 정보 | 이걸 먼저 알아야 함 | 그래서 담당 산출물 |
|---|---|---|
| 화면에서 어떤 행위가 일어나는가(항목4) | 상위 유스케이스(어떤 업무가 있는지) | DK 세부유스케이스 (선행: DC) |
| 화면에 뭘 표시하는가(항목2,3,5) | API가 무엇을 반환하는지 확정 | DN 화면레이아웃 (선행: DM 시퀀스) |
| 입력값이 틀렸을 때 뭐라고 하는가(항목6) | 에러 케이스가 전부 정의됨 | DJ GWT + DL 인터페이스명세 (선행: DE EARS) |

즉 "화면에서 뭘 하는가"와 "화면에서 뭘 보여주는가"와 "잘못 입력하면 어떻게 되는가"는
**서로 다른 시점에 확정되는 정보**다. DM(시퀀스)이 API 응답 구조를 확정하기 전에는 DN을 완성할 수 없고,
DE(EARS)가 예외 케이스를 정의하기 전에는 DJ/DL의 에러 규칙을 쓸 수 없다. PPT는 이 순서 제약이 없어서
한 파일에 다 적을 수 있었지만, 실제로는 그 정보들이 서로 다른 시점에 확정되다 보니 PPT 화면정의서도
매번 앞부분(레이아웃)은 먼저 그리고 뒷부분(검증규칙·에러메시지)은 나중에 채워 넣는 식으로 여러 번
고쳐 쓰는 문서였을 가능성이 크다 — 지금 체계는 그 "여러 번 고쳐 쓰는" 과정을 문서 단위로 나눈 것이다.

> **질문 2**: 실제로 PPT 화면정의서를 작성할 때, 레이아웃을 먼저 그리고 검증규칙·에러메시지는
> 나중에 API가 확정된 뒤 채워 넣은 경험이 있는가? 그 경우 PPT 파일을 몇 번이나 다시 열어 고쳤나?

## Step 3. "기획자는 지금 어디서 무엇을 하는가"

| 산출물 | 기획자 참여 방식 | 비고 |
|---|---|---|
| DC 상위유스케이스 | 리뷰어 | 업무 흐름이 맞는지 확인 |
| **DD 메뉴구조도(IA)** | **공동 저자** | 산출물 흐름 문서에 "기획자+개발자 협업"으로 명시된 유일한 구조설계 산출물 |
| **DK 세부유스케이스** | **주도 작성** | "버튼/화면 단위 행위 분해" — 화면 프로토타입을 입력으로 사용 |
| DL/DM (인터페이스명세/시퀀스) | 리뷰어 | DK에서 요구한 내용이 반영됐는지 확인 |
| **DN 화면레이아웃** | **공동 확인/보완** | 와이어프레임·메타블록의 화면전환·접근권한이 기획 의도와 맞는지 |

즉 기획자의 실무 동선은 **DD(공동저자) → DK(주도) → DN(공동확인)** 세 지점에 집중된다.
DC는 가볍게 리뷰만, DL/DM은 결과물이 DK 요구사항과 맞는지 확인하는 정도다.

> **질문 3**: 지금 이 참여 지점(DD/DK/DN) 중 실제로 가장 많은 시간을 쓰는 곳은 어디인가?
> 반대로 참여가 부족하다고 느끼는 지점(예: DL/DM 리뷰를 건너뛰어서 나중에 화면과 API가 안 맞았던 경험)이 있는가?

## Step 4. "실제로 불편해지는 지점" — 문제점 유도

여기서부터는 설명이 아니라 **문제 제기를 받는 구간**이다. 아래는 예상되는 불편 지점을 먼저 정리했다.
발표자는 이 목록을 "우리가 예상한 문제"로 제시하고, 기획자에게 "이 외에 실제로 겪은 다른 문제"를 묻는다.

### 4-1. 예상 문제 (사전 정리)

| 문제 | 구체적 상황 |
|---|---|
| 문서 3~4개를 오가야 함 | 화면 하나(예: 반품/교환 신청) 작업 시 DK(행위흐름)·DN(레이아웃)·DJ(검증규칙)·DL(에러코드)를 다 열어야 전체 그림이 보임 |
| 텍스트 ID 참조라 추적이 안 됨 | `REQ-ORD-058`처럼 텍스트로만 참조된 규칙은 grep 없이는 어디서 왔는지 못 찾음 (Foam 위키링크로 일부 보완했지만 도구 설치가 필요) |
| PPT의 "한 슬라이드=한 화면" 강점 상실 | PPT는 화면 하나를 인쇄해서 회의실에 붙여놓고 논의 가능했는데, md는 그런 "한 장 요약"이 안 됨 |
| 검증규칙이 DN에 없음 | 방금 결정한 대로 DN은 검증규칙을 링크만 걸어두므로, 화면만 보고는 "이 필드가 필수인지"를 바로 못 알아봄 |
| 도구 학습 곡선 | Foam/위키링크·PlantUML 같은 새 표기법을 기획자가 익혀야 함 |

### 4-2. 실제로 이미 드러난 문제 (컨벤션 점검 결과에서 발췌)

> `설계산출물_컨벤션_점검결과_2026-08-23.md`에서 확인된 것 중 기획자 실무와 직접 관련된 항목:

- **C8 UX Writing**: DN의 mobile 화면 다수가 admin식 문어체("~습니다")로 통일돼 있어, 규정된 mobile
  구어체("~해요/~됐어요")와 어긋남. 동일 상황(결제 실패) 문구도 DL·DN·C8이 각각 다르게 표현됨.
- **C7 디자인시스템**: partner 반송(RETURN) 상태 배경색이 DN에는 있는데 C7-partner 문서에는
  이 구분 자체가 없음 — 디자인 시스템이 실제 화면보다 낡아 있는 상태.

이 두 가지는 "문서가 여러 개로 쪼개져서 생긴 불일치"의 실제 사례다. PPT 한 장에 다 있었다면 발견이
더 쉬웠을 수도 있지만, 반대로 PPT는 이런 불일치를 기계적으로 점검할 방법이 없었다는 점도 함께 짚는다.

> **질문 4**: 위 예상 문제 중 실제로 가장 크게 느껴지는 것은 무엇인가? 목록에 없는 다른 불편함이 있는가?
> (특히: 화면 하나 작업할 때 몇 개 문서를 열어두고 작업하는지, 그게 감당 가능한 수준인지)

## Step 5. "지금까지 보완한 것"

Step 4의 문제를 완전히 해결한 것은 아니지만, 아래는 이미 반영된 보완 조치다.

| 보완 | 내용 |
|---|---|
| DN 화면정의서 메타블록 신설 | 각 화면 섹션 상단에 화면ID·앱·접근권한·관련UC·호출API·화면전환·검증규칙 링크를 5줄로 요약 — PPT의 "화면 식별 정보" 항목을 DN 안으로 되돌림 |
| Foam 위키링크 도입 제안 | `[[DK-세부유스케이스\|UC-1]]` 형태로 텍스트 ID를 클릭 가능한 링크로 전환 — 단, 별도 확장 설치 필요 (`Foam-위키링크-활용가이드.md`) |
| 방법론 표준양식/샘플 동기화 | DN 표준양식과 샘플 문서(`17-화면레이아웃.md`)에 동일한 메타블록 템플릿을 반영해, 향후 신규 화면도 같은 형식으로 작성 |

> 단, 이 보완은 "문서 개수를 줄인 것"이 아니라 "문서 사이 이동을 쉽게 만든 것"이다. 근본적으로
> 여러 문서로 나뉘어 있다는 사실 자체는 바뀌지 않았다 — 이 트레이드오프가 기획자에게 수용 가능한지가
> Step 6에서 확인할 핵심 질문이다.

## Step 6. 기획자에게 묻고 싶은 것 — 개선점 유도 질문 리스트

아래 질문은 이 시나리오의 실질적 목적이다. 순서대로 던지고 답변을 기록한다.

1. 화면 하나를 작업할 때 DK(행위흐름)와 DN(레이아웃)을 오가는 지금 방식이 감당 가능한가,
   아니면 두 문서를 화면 단위로 병합한 "통합 뷰"가 따로 필요한가?
2. 유효성 검증 규칙(항목6)을 DN에 링크만 걸어두는 지금 방식이 괜찮은가, 아니면 화면 작업 시엔
   규칙 본문이 DN에 그대로 보이는 게 더 편한가? (본문 복제 시 유지보수 부담이 커진다는 트레이드오프 포함해서 판단)
3. Figma로 넘어가기 전에, 이 md 스펙(DK+DN)만으로 디자이너·개발자와 충분히 소통이 되는가?
   아니면 지금도 별도로 PPT나 손그림을 병행해서 쓰고 있는가?
4. PPT의 "한 슬라이드 = 한 화면" 구조가 그리운 지점은 구체적으로 어디인가?
   (예: 회의에서 화면 하나만 띄워놓고 논의하기, 인쇄해서 벽에 붙이기 등)
5. Foam/위키링크 같은 새 도구를 익히는 데 대한 부담은 어느 정도인가? 그 학습을 감당할 가치가
   있다고 느끼는가, 아니면 지금처럼 grep/Ctrl+F로 찾는 게 오히려 익숙한가?
6. DD(메뉴구조도)·DK(세부유스케이스)에서 기획자가 "주도"로 작성하는 게 실제로 맞는 역할 분배인가,
   아니면 이 중 일부는 개발자가 먼저 초안을 잡아주는 게 더 효율적이라고 느끼는가?

## Step 7. 다음 단계 제안

- 지금 논의한 문제/개선 요청을 이슈 목록으로 정리해, 우선순위가 높은 것부터 다음 스프린트에 반영
- 파일럿으로 신규 화면 1~2개를 지금 체계(DK→DN 메타블록)로 기획자가 직접 작성해보고, 실제 소요 시간과
  불편 지점을 재점검
- Step 6-1(통합 뷰 필요성)에 대한 답이 "필요"로 나오면, DK+DN을 화면 단위로 나란히 보여주는 뷰(문서 내
  상호 링크 강화 또는 별도 요약 문서) 검토
