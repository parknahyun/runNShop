## C1 — 보안 컨벤션

1. **PII 마스킹 표기 불일치**: DL-인터페이스명세 §5(주문서 생성)의 `orderer.name`·`addresses[].recipient`·`orderer.email`은 마스킹 없이 노출되는데, §30(내 주문 상세)의 동일 성격 데이터는 `"홍*동"`처럼 마스킹됨. 같은 문서 안에서 표기가 다릅니다.
2. **Rate Limiting 수치 불일치**: C1은 "일반 100회/분/사용자"인데 D8 NFR-SE-14는 "300req/분"으로 다름. C1의 "인증 5회/분" 항목에 대응하는 NFR도 D8에 없음.
3. **에러 메시지 커스터마이징 범위 모호**: C1 §3.5는 403 메시지를 "접근 권한이 없습니다"로 고정했는데, DL §7은 "본인 주문만 취소할 수 있습니다"로 커스텀 사용. 허용 범위가 C1에 없음.
4. **프로토타입 예외 미반영**: C1·D7은 프로토타입 단계 "인증/인가 미적용"을 규정하는데, DL·DP는 전 API에 정식 Bearer 인증·401/403 응답을 명시해 예외 관계가 불명확.

일치 확인: 카드번호 마스킹(뒤 4자리), PG 토큰화 원칙, 카드 3회 실패 제한은 C1·D8·DL·DP 전체에서 일관됩니다.

## C2 — 용어 컨벤션

1. **"판매자" vs "입점사" 혼용(가장 광범위)**: C2는 "입점사"를 표준어로, "판매자"를 금지어로 명시하지만, DE-EARS(Order)와 DG-상태머신(Order), DB-도메인정의서 여러 곳에서 "판매자"가 반복 사용됩니다.
2. **`ord_order.status` 상태 개수 불일치**: C2는 11개 상태(IN_DELIVERY 포함)로 정의하는데, 실제 DF/DG(v6)는 10개 상태(IN_DELIVERY를 배송 도메인으로 이관)로 갱신되어 있음 — C2가 최신 설계를 못 따라감.
3. **`ord_claim.status` 상태 개수 불일치**: C2는 14개, 실제 DF/DG는 11개(3개 상태 제거). 위와 동일한 원인.
4. **C2 근거표 자체가 구버전 수치 인용**: C2 본문의 "근거" 란도 낡은 11/14 상태 수를 그대로 인용하고 있어 이중으로 낡음.
5. **이벤트명 표기 스타일 불일치**: DB는 PascalCase(`PaymentApproved`), DE·DG는 SCREAMING_SNAKE_CASE(`PAYMENT_APPROVED`) 사용. `PaymentFailed`·`ClaimCompleted`는 DB 이벤트 목록에 아예 빠져 있음.
6. **테이블 접두사 정책 모호**: C2는 "ord" 같은 축약을 금지 예시로 들었는데 DF-ERD 전체가 `ord_`, `pay_` 접두사를 실제로 사용 — DB 스키마 접두사가 예외인지 C2에 명시되어 있지 않음.

일치 확인: `pay_payment.status` 5개 상태, 클레임/귀책/수거 등 복합 용어는 문서 전반에서 일관됩니다.

## C3 — 아키텍처 컨벤션

1. **DP 패키지 구조가 C3와 다름**: C3 §4.1은 도메인 아래 단일 평면(`controller/service/repository/dto/entity`) 구조인데, DP는 `cart/order/shipping/claim/...`로 한 번 더 쪼갠 2단 구조이고 `entity/` 대신 `domain/`을 씁니다.
2. **Controller 네이밍 불일치**: C3·DM은 `{App}{Domain}Controller`(예: `CustomerOrderController`)를 강제하는데, DP는 `OrderController`처럼 App 접두사를 빼고 정의. `CustomerClaimPaymentController`(DM 참여자)에 대응하는 클래스도 DP에 없음(누락).
3. **기술스택 버전·테마 불일치**: C3는 admin/partner FE를 "Next.js 14", partner 테마를 "orange"로 정의하는데, D9은 "Next.js 15 + React 19", "틸 테마"로 서술.
4. **모노레포 구조 미반영**: D9의 `runNshop-consumer`, `runNshop-batch` 모듈이 C3 §3.3의 모노레포 트리에 없음.

일치 확인: API Namespace, 포트 할당(3000/3001/3002/8080)은 C3·D9이 정확히 일치.

## C4 — 데이터 모델링 컨벤션

1. **PK 컬럼명 예외**: C4 §5.1은 PK를 `id`로 고정하는데, `pay_card_fail_counter`는 PK가 `card_hash`. 같은 ERD 내 다른 테이블과도 불일치.
2. **FK 표기 방식이 도메인마다 다름**: C4 §15는 `<<FK {Domain}>>`(도메인명) 표기인데, Payment ERD는 `<<FK ord_order>>`(테이블명)로 표기. Order ERD는 규칙대로 도메인명을 씁니다.
3. **`ord_cart` 공통 컬럼 누락**: C4 §7의 기본 컬럼(`created_at`/`updated_at`)이 예외 대상이 아닌데 `ord_cart`엔 `added_at`만 있고 `updated_at`이 없음.
4. **금액 필드 네이밍 스타일 차이**: Payment는 `point_amount`로 규칙(`{대상}_amount`)을 지켰는데, Order의 `point_used`·`coupon_discount`는 접미사 없이 명명.

일치 확인: 상태값 UPPER_SNAKE_CASE 표기, PK/FK ULID 표기 형식은 두 도메인 ERD에서 동일합니다.

## C5 — 이벤트 설계 컨벤션

1. **DM이 DI에 없는 이벤트를 발행**: DM §19가 발행하는 `SHIPMENT_DELIVERED`는 DI 카탈로그의 `DELIVERY_COMPLETED`와 이름·payload가 완전히 다름. `CLAIM_PAYMENT_EXPIRED`도 DI에 정의되어 있지 않음 — C5 §8("DI가 이벤트 카탈로그의 단일 진실 공급원")을 위반.
2. **Notification 소비 이벤트 누락**: DI가 정의한 배송완료→알림 이벤트가 DM 시퀀스에는 주석으로만 있고 실제 `EventPublisher.publish()` 호출이 없음.
3. **이벤트 접두사 규칙이 C5 자체에서도 일관되지 않음**: C5 §3 예시표가 Order가 발행하는 이벤트에 도메인 접두사를 안 붙인 사례가 있어, DI의 `STOCK_FAILED`가 규칙 위반인지 판단이 애매함(컨벤션 자체 정비 필요).
4. **DI 문서 내 마크다운 깨짐**: `CLAIM_COMPLETED` 이벤트 스키마 블록에 코드펜스 닫힘이 중복되어 있어 파싱 오류 소지.

일치 확인: 이벤트 Envelope 구조(eventId/eventType/payload 등)는 C5·DI가 정확히 일치. DG↔DI 트리거명도 일치.

## C6 — API 설계 컨벤션

1. **DL 자기모순**: 결제요청 API를 Response 200으로 명시했지만 본문에는 "비동기 처리"라 서술 — C6 §7의 202 Accepted 규정과 어긋남.
2. **DQ가 DL 최신 상태를 놓침**: DQ는 클레임 자진취소 API를 "DL 미반영"이라 적었지만 실제로는 이미 DL에 반영되어 있음.
3. **전수 도출 누락**: DL의 클레임 처리시작 API(#24)에 대응하는 프로그램이 DQ 목록에 없음 — DQ가 "48/49 매칭"이라 주장하지만 실제로는 그 이상의 누락.
4. **DM이 DL의 에러코드 정정을 반영 못함**: DL은 CART_FULL 등 에러를 422/409로 정정했는데, DM 시퀀스는 옛 400 코드를 그대로 사용.
5. **공용 API의 URL Prefix 처리 기준 없음**: 재배송 API(#44)가 partner/admin 공용인데 `/api/partner/v1` 단독 경로만 사용 — C6에 공용 API prefix 규칙이 없음.
6. **API 개수 표기가 문서마다 다름**: DL 50개, DQ 49개, DM은 "27개 중 15개 상세화"라 적었는데 실제 시퀀스는 19개 — 세 문서 수치가 전부 다릅니다.

일치 확인: URL Prefix 원칙(`/api/v1`, `/api/admin/v1`, `/api/partner/v1`) 자체와 Controller 네이밍은 대부분 잘 지켜짐.

## C7 — 디자인시스템

1. **C7이 DN보다 낡음**: partner 화면의 반송(RETURN) 상태 배경색이 DN에는 있는데(`#FFF3E0`), C7-partner.md에는 이 구분 자체가 없고 회수·재배송 색상값도 DN과 다름.
2. **대응 BEM 클래스 부재**: 위 반송 구분에 대응하는 `.table-row--return` 클래스가 C7에 없어 구현 시 네이밍 기준이 없음.

일치 확인: mobile/admin/partner 앱별 레이아웃 구조, Tailwind vs BEM 구분은 DN에서 스펙 수준으로 올바르게 분리되어 있고 C7과 부합합니다.

## C8 — UX Writing 컨벤션

1. **mobile 화면에 admin 톤 사용**: C8은 mobile에 "~해요/~됐어요" 반말체를 규정하는데, DN의 CartPage·OrderNewPage 등 다수 mobile 화면이 "~습니다"(admin식)로 통일되어 있음.
2. **시스템 오류 문구 패턴 불일치**: DN의 시스템 오류 메시지가 C8이 정한 mobile 패턴과 어미·구조가 다름.
3. **DL 문구가 띄어쓰기 규칙과 다름**: C8 예시는 "~해 주세요"(띄어쓰기)인데 DL 전역은 "~해주세요"(붙여쓰기)로 이질적.
4. **동일 상황(결제 실패) 문구가 3곳 제각각**: DL·DN·C8이 각각 다른 표현을 씁니다.

일치 확인: 금칙어("에러", "OK", "유저" 등) 사용은 발견되지 않음.

## C9 — 코딩 컨벤션

1. **DTO 폴더 구조 미준수**: C9 §4.1은 `dto/request/`, `dto/response/` 분리를 규정하는데 DP는 전 도메인이 `dto/` 아래 구분 없이 평면 배치.
2. **폴더명 불일치**: C9은 `entity/`를 쓰는데 DP는 `domain/`을 사용(C3 점검에서도 동일하게 지적됨 — 두 컨벤션이 서로 다른 이름을 요구하고 있을 가능성도 있음, C3·C9 간 조율 필요).
3. **DTO 네이밍 패턴 이탈**: `OrderSheetRequest`, `ClaimProcessRequest` 등이 C9의 `{Action}Request`/`{Entity}Response` 규칙과 어순이 다름.
4. **Boolean 네이밍 위반**: `Claim.tagIntact`가 `is/has/can/should` 접두사 없이 명명됨.

일치 확인: C9 §9 근거표의 컨벤션 번호 인용은 새 체계(C1,C3,C4,C5,C6)와 전부 정확히 일치 — 지난번 재부여 작업이 C9 안에서는 완전히 반영되어 있습니다. API 경로 파라미터 camelCase 규칙도 준수됨.

## 지침서 v2.3 구조 원칙 점검 (제가 직접 확인)

1. **버전/상태 태그 전무**: 지침서 7.5 "산출물 버전 관리 정책"은 Major.Minor 버전 채번과 `APPROVED`/`DRAFT-v{n}` 태깅을 규정하지만, 실제 D1~DQ 31개 파일 중 이 태그를 가진 파일은 없습니다(헤더에 "단계/문서범위/문서종류"만 있고 버전 표기 없음). 롤백·Diff 관리 정책을 적용하려면 이 태그부터 채워야 합니다.
2. **상세설계가 "Bolt 단위"가 아니라 통짜 문서**: 산출물_흐름.md는 상세설계(DJ~DQ)를 "Bolt(유스케이스 1개) 단위로 반복 작성"하도록 정의하지만, 실제로는 DJ~DQ 8개 파일이 전부 `(Order-Payment)` 하나의 파일로 합쳐져 있습니다(DN은 209KB, DL은 62KB). Bolt 분할 문서 자체도 아직 없어서, 지금 파일들이 몇 개의 Bolt를 묶은 것인지 검증할 기준도 없는 상태입니다.
3. **구조설계 단계의 Tasks 6종 미작성**: 산출물_흐름.md는 구조설계 단계에 RACI·DoD템플릿·의존성맵·WBS·리스크대응계획·DoD체크리스트·Bolt분할까지 포함하도록 정의하지만, S2-구조설계 폴더에는 DC~DI 12개 파일만 있고 이 6종은 아직 만들어지지 않았습니다. (누락이지 오류는 아니며, 프로토타입 단계에서는 건너뛸 수 있는 항목일 수 있습니다.)

## 우선순위 제안

가장 먼저 손보시면 좋을 것 같은 항목 3가지를 꼽으면: 첫째는 C2 용어컨벤션의 상태값 개수(ord_order/ord_claim)를 최신 DG 기준으로 재동기화하는 것 — 용어집이 낡으면 이후 모든 산출물이 이걸 근거로 계속 어긋나게 됩니다. 둘째는 C5/DI에 없는 이벤트(SHIPMENT_DELIVERED, CLAIM_PAYMENT_EXPIRED)를 카탈로그에 추가하거나 DM 쪽 이벤트명을 DI에 맞게 고치는 것 — 지금 상태로는 이벤트 계약이 실제로 지켜지지 않습니다. 셋째는 DL·DM·DQ 세 문서의 API 개수·에러코드를 한 번 맞추는 것 — API가 몇 개인지조차 문서마다 다르면 이후 코딩 단계에서 그대로 혼란이 이어집니다.
