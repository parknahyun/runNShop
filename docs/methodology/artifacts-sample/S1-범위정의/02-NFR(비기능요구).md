# 샘플: NFR (비기능요구사항)

> **단계**: 범위정의
> **문서범위**: Project
> **문서종류**: Spec
>
> **작성 목적**: 시스템이 달성해야 하는 품질 목표를 정량적으로 정의한다.
> "얼마나 빨라야 하는가, 얼마나 안정적이어야 하는가"를 측정 가능한 수치로 확정한다.
>
> **흐름 내 위치**:
> ```
> ① 제약사항 → ② NFR → ③ 컴포넌트 → ④ 시스템구성도 → ...
> ```
> 안정화 단계에서 실측치로 보정(자연 보완).
>
> **작성 주체**: 시니어 개발자 + AI 협업 (인프라·QA 검토)

---

## ID 규칙

```
NFR-{CATEGORY}-{SEQ}
```
- CATEGORY: PERF(성능), AVAIL(가용성), SEC(보안), SCALE(확장성), MAINT(유지보수)

## 샘플 (이커머스 플랫폼)

### 성능 (Performance)

| ID | 요구사항 | 기준치 | 측정 방법 | 근거 |
|---|---|---|---|---|
| NFR-PERF-001 | 상품 목록 API 응답 시간 | p95 ≤ 500ms | 부하테스트 (k6, 동시 1,000명) | 정책서 |
| NFR-PERF-002 | 주문·결제 API 응답 시간 | p95 ≤ 3,000ms | 부하테스트 | 정책서 |
| NFR-PERF-003 | 화면 초기 로딩 (FCP) | ≤ 2초 (mobile LTE 기준) | Lighthouse | UX 표준 |
| NFR-PERF-004 | DB 쿼리 실행 시간 | 단건 ≤ 100ms, 목록 ≤ 300ms | Slow query log | 운영 기준 |

### 가용성 (Availability)

| ID | 요구사항 | 기준치 | 측정 방법 | 근거 |
|---|---|---|---|---|

| ID | 요구사항 | 기준치 | 측정 방법 | 근거 |
|---|---|---|---|---|

## 작성 규칙

| 규칙 | 설명 |
|---|---|
| **정량 필수** | "빨라야 한다"는 NFR이 아님 — 수치 없으면 측정 불가 |
| **측정 방법 필수** | 기준치만 있고 측정 방법 없으면 검증 불가 |
| **제약사항과 구분** | 제약="못 하는 것", NFR="달성해야 하는 수준" |
| **안정화 시 보정** | 초기 기준치는 추정. 실측 후 조정(자연 보완) |

---

## 작성 팁

| 팁 | 설명 |
|---|---|
| **정책서에서 도출** | "응답 5초 이내" 같은 요구는 정책서에 있는 경우 많음 |
| **제약사항(①)에서 파생** | CONS-002(카드 미저장) → NFR-SEC-003(암호화) 연계 |
| **시스템구성도(④) 입력** | NFR이 인프라 설계(스케일링·가용성)를 결정 |
| **테스트 단계에서 실측** | Go/No-Go 판단 시 NFR 기준치 달성 여부 확인 |
