# 샘플: 제약사항

> **단계**: 범위정의
> **문서범위**: Project
> **문서종류**: Spec
>
> **작성 목적**: 프로젝트가 반드시 지켜야 하는 기술·법무·보안·벤더 제한 조건을 정의한다.
> "이것은 바꿀 수 없다"는 경계를 확정하여, 이후 설계·구현의 자유도 범위를 제한한다.
>
> **흐름 내 위치**:
> ```
> 착수(Proposal) → ① 제약사항 → ② NFR → ③ 컴포넌트 → ...
> ```
>
> **작성 주체**: 시니어 개발자 + AI 협업 (법무·보안·인프라 담당자 검토)

---

## ID 규칙

```
CONS-{SEQ}
```

---

## 카테고리

| 카테고리 | 설명 | 예시 |
|---|---|---|
| 법무 | 법률·규정·약관에 의한 제약 | 개인정보보호법, 전자상거래법 |
| 보안 | 보안 정책·표준에 의한 제약 | OWASP Top 10, 카드정보 미저장 |
| 기술 | 확정된 기술 선택에 의한 제약 | PG 단일(토스), DB PostgreSQL |
| 벤더 | 외부 서비스 계약 조건에 의한 제약 | 택배사 2곳 한정, API 호출 제한 |
| 조직 | 인력·일정·예산에 의한 제약 | 5개월 일정, 팀 규모 |

## 작성 팁

| 팁 | 설명 |
|---|---|
| **"바꿀 수 없는 것"만** | 바꿀 수 있으면 제약이 아니라 "설계 결정"(ADR 대상) |
| **근거 필수** | 법률·계약·의사결정 근거 없으면 제약으로 인정 안 함 |
| **예외 승인 절차** | 제약을 위반해야 하면 별도 승인 필요 — ADR에 기록 |
| **NFR과 구분** | 제약="못 하는 것", NFR="달성해야 하는 수준" |
| **Proposal 대안비교에서 도출** | 기술 제약 대부분은 대안비교 채택 결과 |
