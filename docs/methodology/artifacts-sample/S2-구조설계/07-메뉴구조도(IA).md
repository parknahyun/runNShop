# 샘플: 메뉴구조도 (IA)

> **단계**: 구조설계
> **문서범위**: Project (앱별)
> **문서종류**: Design

> **작성 목적**: 앱(액터 관점)과 메뉴(도메인/업무 관점)를 매핑하여,
> "어떤 액터가 어떤 앱에서 어떤 업무 메뉴로 접근하는가"를 확정한다.
> - **앱 분리 기준**: 액터 (고객→mobile, 판매자→partner, 관리자→admin)
> - **메뉴 분리 기준**: 도메인/업무 (주문관리, 상품관리, 프로모션...)
>
> **흐름 내 위치**:
> ```
> ⑤ 도메인 경계 → ⑥ 상위 유스케이스 → ⑦ 메뉴 정리(화면 대상 도출) → ⑧ EARS(기능 정의)
> ```
> 도메인 경계에서 업무를 나누고, 상위 유스케이스에서 액터별 행위를 나열한 뒤,
> 메뉴구조도에서 **화면 대상 전체 목록**을 확정한다.
> 이후 EARS에서 각 화면 대상에 대해 "시스템이 무엇을 해야 하는가"를 기능 단위로 기술한다.
>
> **작성 주체**: 기획자 + 개발자 협업

## 작성 기준

| 기준 | 설명 | 도출 근거 |
|---|---|---|
| 1depth | 업무 대분류 (상위 유스케이스의 업무그룹에 대응) | 상위 유스케이스(⑥) 업무그룹 |
| 2depth | 업무 소분류 (상위 유스케이스의 개별 유스케이스에 대응) | 상위 유스케이스(⑥) 개별 UC |
| 화면 | Bolt 대응 (실제 구현 단위) | 상위 유스케이스 → 화면 분해 |
| 셸 구조 | 앱별 네비게이션 골격 (NavBar/Sidebar/BottomNav) | 이 산출물에서 자체 정의 (앱 목록은 컴포넌트③, UI 골격은 기획자+개발자 협의) |
| 메뉴 배치 순서 | 사용 빈도·업무 중요도 기준 | 발주자 확인 (정책서 또는 인터뷰) |
| 메뉴 명칭 (라벨) | 정책서 용어 기준, 없으면 상위UC 명칭 사용 | 정책서 or 발주자 확인 |
| 앱별 노출 범위 | 액터·권한에 따라 메뉴 노출/비노출 결정 | 상위 유스케이스(⑥) ④ 권한 범위 |

## Platform Bolt vs Domain Bolt 구분

| 구분 | 범위 | 메뉴구조도에서의 위치 |
|---|---|---|
| **Platform Bolt** | 셸 구조 (NavBar·Sidebar·TabBar·BottomNav·로그인·공통 컴포넌트) | 위 표의 "셸 구조" 행 |
| **Domain Bolt** | 업무 화면 (1depth~2depth 메뉴의 각 화면) | 위 표의 나머지 전체 |
