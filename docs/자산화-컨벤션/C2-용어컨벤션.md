# C2 용어컨벤션
> 수립 데드라인: S1 시작 전 | 참고 대상: 도메인정의서, EARS
---

## 1. 목적
프로젝트 내에서 사용하는 업무 용어를 통일하여 커뮤니케이션 혼란을 방지하고, 코드·문서·UI 간 일관성을 확보한다.

## 2. 규칙

### 2.1 12개 업무도메인 용어

| 영문 | 한글 | 설명 |
|------|------|------|
| order | 주문 | 주문 생성·조회·취소·반품 |
| catalog | 상품 | 상품 등록·수정·카테고리 관리 |
| member | 회원 | 회원 가입·인증·프로필 관리 |
| payment | 결제 | 결제 처리·환불·빌링키 관리 |
| promotion | 프로모션 | 쿠폰·할인·이벤트 |
| settlement | 정산 | 매출 정산·수수료 계산 |
| vendor | 입점사 | 입점사 등록·계약·관리 |
| notification | 알림 | 푸시·SMS·이메일 발송 |
| community | 커뮤니티 | 리뷰·Q&A·게시판 |
| search | 검색 | 통합검색·자동완성·필터 |
| config | 설정 | 시스템 설정·코드 관리 |
| audit | 감사 | 이력 추적·로그 관리 |

### 2.2 용어 사용 원칙

1. **코드 내 네이밍**: 영문 도메인명을 기본으로 사용
2. **UI 텍스트**: 한글 용어를 사용
3. **문서**: 한글(영문) 병기 — 최초 1회 병기 후 한글만 사용
4. **약어 금지**: 도메인명을 임의로 축약하지 않음 (예: noti ✗ → notification ✓)

### 2.3 상태값 용어

| 도메인 | 상태값 (DB/API) | UI 표시 |
|--------|-----------------|---------|
| order | PENDING | 결제대기 |
| order | PAID | 결제완료 |
| order | SHIPPING | 배송중 |
| order | DELIVERED | 배송완료 |
| order | CANCELLED | 주문취소 |
| order | RETURN_REQUESTED | 반품요청 |
| catalog | DRAFT | 임시저장 |
| catalog | ON_SALE | 판매중 |
| catalog | SOLD_OUT | 품절 |
| catalog | HIDDEN | 숨김 |
| vendor | APPLIED | 입점신청 |
| vendor | APPROVED | 승인완료 |
| vendor | REJECTED | 반려 |

### 2.4 복합 용어

| 용어 | 정의 | 잘못된 사용 |
|------|------|-------------|
| 주문번호 | 고객에게 노출되는 주문 식별자 | 오더번호, 거래번호 |
| 상품번호 | 개별 상품 SKU 식별자 | 품번, 아이템번호 |
| 입점사 | 플랫폼에 입점한 판매자 | 셀러, 판매자, 파트너 |
| 정산금 | 입점사에 지급할 금액 | 수익금, 판매대금 |

## 3. 예시

### 코드에서의 용어 사용
```kotlin
// ✓ 올바른 사용
package com.runnshop.order.controller
class OrderController { ... }

// ✗ 잘못된 사용
package com.runnshop.ord.ctrl
class OrdCtrl { ... }
```

### API Path에서의 용어 사용
```
✓ /api/v1/orders
✓ /api/v1/products
✓ /api/admin/v1/settlements

✗ /api/v1/ord
✗ /api/v1/item
✗ /api/admin/v1/stlmt
```

### 문서에서의 용어 사용
```
첫 등장: "주문(order) 도메인은 ..."
이후: "주문 생성 시 ..."
```

## 근거
- 12개 도메인 용어는 Kotlin 패키지, API Path, Mock 파일명, 이벤트명 등 전체 시스템에서 일관되게 사용
- 용어 통일은 신규 참여자의 온보딩 시간을 단축하고 코드 검색성을 향상시킴
- 상태값의 영문/한글 매핑을 사전에 정의하여 UI 구현 시 일관성 확보
