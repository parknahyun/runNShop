# C1 보안컨벤션 (Security Convention)

> **수립 데드라인**: S0 착수 중 | **참고 대상**: D8 NFR
> **적용 범위**: 프로젝트 전체 (Backend + Frontend + Infrastructure)
> **프로토타입 예외**: §E 검증 항목 중 일부는 프로토타입 단계에서 미적용 (명시된 항목만)

---

## A. Security Principles (보안 원칙)

### A-1. Security by Design
- 보안은 기능 구현 후 추가하는 것이 아니라, **설계 단계에서 내장**한다.
- 모든 API endpoint, 데이터 모델, 화면 설계 시 보안 요구사항을 함께 검토한다.

### A-2. Least Privilege (최소 권한)
- 각 역할(고객/입점사/어드민)은 **필요한 최소한의 권한**만 부여받는다.
- API Path Prefix로 접근 경계를 분리: `/api/v1/` (고객), `/api/admin/v1/` (어드민), `/api/partner/v1/` (입점사)
- 프로토타입 예외: 권한 체크 미적용 (메뉴 전체 노출), 실 프로젝트 시 RBAC 적용

### A-3. Defense in Depth (심층 방어)
- 단일 보안 계층에 의존하지 않고, **다중 계층**으로 방어한다.
- 계층: Network(Firewall) → Gateway(Rate Limit) → Application(Auth/Authz) → Data(Encryption)

### A-4. Default Deny (기본 거부)
- 명시적으로 허용되지 않은 모든 접근은 **기본 거부**한다.
- Whitelist 방식: 허용할 endpoint/역할을 명시, 나머지는 403 Forbidden

### A-5. Server Trust (서버 신뢰)
- 클라이언트 데이터는 **항상 신뢰하지 않는다** (검증 필수).
- 모든 유효성 검증, 권한 판단, 금액 계산은 **서버 측에서** 수행한다.
- 클라이언트에서 전달된 가격·할인액·권한 정보는 서버에서 재검증한다.

## B. Security Requirements (보안 요구사항)

### B-1. Authentication (인증)

| 항목 | 규칙 |
|------|------|
| 인증 방식 | JWT (Access Token + Refresh Token) |
| Access Token 만료 | 30분 |
| Refresh Token 만료 | 14일 |
| 토큰 저장 | HttpOnly Secure Cookie (FE), Authorization Header (API) |
| 비밀번호 저장 | bcrypt (cost factor 12 이상) |
| 소셜 로그인 | OAuth 2.0 (카카오, 네이버, 구글) |
| 2FA | 어드민 계정 필수 (TOTP 기반) |
| 프로토타입 예외 | 로그인 API 항상 성공 응답, 세션 만료 미적용 |

### B-2. Authorization (인가)

| 항목 | 규칙 |
|------|------|
| 모델 | RBAC (Role-Based Access Control) |
| 역할 | CUSTOMER, VENDOR, ADMIN, SUPER_ADMIN |
| 리소스 소유권 | 본인 데이터만 접근 (memberId 일치 검증) |
| 어드민 권한 | 기능별 Permission 그룹 (주문관리, 클레임처리, 정산, 시스템설정) |
| Path 기반 분리 | `/api/v1/` = CUSTOMER, `/api/admin/v1/` = ADMIN, `/api/partner/v1/` = VENDOR |
| 프로토타입 예외 | 권한 체크 미적용, 메뉴 전체 노출 |

### B-3. Data Protection (데이터 보호)

| 항목 | 규칙 |
|------|------|
| 전송 암호화 | TLS 1.3 (HTTPS 필수) |
| 저장 암호화 | 민감 데이터 AES-256-GCM |
| PII 마스킹 | 이름: 홍*동, 전화: 010-\*\*\*\*-5678, 이메일: h\*\*@example.com |
| 카드번호 | 원본 미저장, PG 빌링키(토큰)만 보관 (PCI DSS) |
| 비밀번호 | 평문 저장 금지, 로그 출력 금지 |
| 개인정보 보관 | 전자상거래법 5년 보관 후 파기 (배치 처리) |
| Mock 데이터 | 반드시 마스킹 적용 (실 데이터 사용 금지) |

### B-4. API Security (API 보안)

| 항목 | 규칙 |
|------|------|
| Rate Limiting | 인증 API: 5회/분, 일반 API: 100회/분/사용자 |
| 요청 크기 제한 | Body max 10MB, 파일 업로드 max 5MB/건 |
| CORS | 허용 Origin 명시 (와일드카드 금지) |
| 금액 위변조 방지 | 클라이언트 전달 금액 무시, 서버 재계산 (REQ-PAY-007) |
| 멱등성 | POST 요청에 Idempotency-Key 헤더 권장 |
| 프로토타입 예외 | Rate Limiting 미적용, CORS AllowAll |

### B-5. Web Security (웹 보안)

| 항목 | 규칙 |
|------|------|
| XSS | 출력 시 HTML 이스케이프 (React 기본 적용) |
| CSRF | SameSite=Strict Cookie + CSRF Token (폼 전송 시) |
| Clickjacking | X-Frame-Options: DENY |
| Content-Type | X-Content-Type-Options: nosniff |
| CSP | Content-Security-Policy 헤더 설정 (인라인 스크립트 제한) |

### B-6. Business Logic Security (비즈니스 로직 보안)

| 항목 | 규칙 |
|------|------|
| 결제 금액 검증 | 서버에서 재계산, 클라이언트 값과 불일치 시 거부 |
| 재고 선점 | 동시성 제어 (낙관적 잠금 또는 Redis 분산락) |
| 카드 결제 제한 | 동일 카드 3회 연속 실패 시 당일 차단 (REQ-PAY-018) |
| 쿠폰 중복 사용 | 서버 측 사용 여부 검증, 동시 요청 방지 |
| 환불 한도 | 환불 금액 합계 ≤ 원결제 금액 (서버 검증) |
| 클레임 기한 | 배송완료 후 10일 초과 시 서버에서 거부 |

## C. Security Design Rules (보안 설계 규칙)

### C-1. Architecture (아키텍처)

```
┌─ Client ─┐    ┌─ Gateway ─┐    ┌─ Application ─┐    ┌─ Data ─┐
│ Browser  │───→│ Nginx/ALB │───→│ Spring Boot   │───→│ DB     │
│ Mobile   │    │ WAF       │    │ Auth Filter   │    │ Redis  │
└──────────┘    │ Rate Limit│    │ RBAC Check    │    │ S3     │
                └───────────┘    └───────────────┘    └────────┘
```

- Gateway: TLS 종단, Rate Limiting, WAF (SQL Injection/XSS 패턴 차단)
- Application: Spring Security Filter Chain (JWT 검증 → 역할 확인 → 리소스 소유권)
- Data: 암호화 저장, 접근 로그 기록

### C-2. Access Control (접근 제어)

| 계층 | 처리 |
|------|------|
| URL Path | Path Prefix로 1차 분리 (/v1/, /admin/v1/, /partner/v1/) |
| Filter | JWT 검증 → 역할 추출 → Path와 역할 매칭 |
| Method | @PreAuthorize("hasRole('ADMIN')") 또는 커스텀 어노테이션 |
| Data | WHERE member_id = :currentUserId (본인 데이터 필터) |

### C-3. Data Flow (데이터 흐름)

| 구간 | 보호 방법 |
|------|-----------|
| Client → Server | HTTPS (TLS 1.3) |
| Server → DB | 커넥션 풀 암호화 (SSL) |
| Server → PG | HTTPS + PG사 인증키 |
| Server → 택배사 | HTTPS + API Key |
| 로그 | PII 마스킹 후 기록, 카드번호/비밀번호 절대 로깅 금지 |

### C-4. Data Protection (데이터 보호 설계)

| 데이터 | 분류 | 저장 방식 | 마스킹 |
|--------|------|-----------|--------|
| 이름 | PII | 평문 (검색 필요) | 표시 시 홍*동 |
| 전화번호 | PII | 평문 (검색 필요) | 표시 시 010-\*\*\*\*-5678 |
| 이메일 | PII | 평문 | 표시 시 h\*\*@example.com |
| 주소 | PII | 평문 | 표시 시 전체 노출 (배송 목적) |
| 비밀번호 | Secret | bcrypt 해시 | 절대 노출 안 함 |
| 카드번호 | PCI | 미저장 (PG 토큰만) | \*\*\*\*-1234 |
| PG 빌링키 | Secret | AES-256 암호화 저장 | 노출 안 함 |

### C-5. External Integration (외부 연동)

| 연동처 | 인증 방식 | 보안 수칙 |
|--------|-----------|-----------|
| PG (토스페이먼츠) | Secret Key + API Key | 키 환경변수 관리, 코드 하드코딩 금지, 원본 응답 PII 마스킹 후 로깅 |
| 택배사 API | API Key | 키 로테이션 주기 90일 |
| 소셜 로그인 (OAuth) | Client ID + Secret | Redirect URI 화이트리스트 |
| 알림톡 (카카오) | API Key | 발신 번호 인증, 템플릿 사전 등록 |

## D. Secure Coding Rules (시큐어 코딩 규칙)

### D-1. Input / Output Validation (입출력 검증)

| 규칙 | 적용 |
|------|------|
| 모든 입력은 서버에서 검증 | @Valid + DTO 제약 어노테이션 (@NotBlank, @Size, @Min) |
| 출력 이스케이프 | React JSX 기본 이스케이프 활용, dangerouslySetInnerHTML 금지 |
| 파일 업로드 | 확장자 화이트리스트 (jpg, png, webp), MIME 타입 이중 검증 |
| 수량/금액 범위 | @Min(1) @Max(99) — 음수·0·초과값 서버 거부 |
| 열거형 | enum 타입 매핑, 미정의 값 → 400 에러 |

### D-2. Injection (인젝션 방지)

| 유형 | 대책 |
|------|------|
| SQL Injection | JPA/QueryDSL 파라미터 바인딩 (문자열 결합 SQL 금지) |
| NoSQL Injection | MongoDB 사용 시 $regex 등 연산자 입력 차단 |
| Command Injection | 외부 프로세스 호출 금지, 필요 시 화이트리스트 인자만 허용 |
| Log Injection | 로그 메시지에 사용자 입력 직접 삽입 금지 (포맷 파라미터 사용) |

### D-3. Secret Management (비밀 관리)

| 규칙 | 적용 |
|------|------|
| 코드 내 하드코딩 금지 | API Key, DB Password, PG Secret 등 절대 소스에 포함 안 함 |
| 환경변수 사용 | application.yml에 `${ENV_VAR}` 참조, .env 파일은 .gitignore |
| 시크릿 저장소 | 운영: AWS Secrets Manager 또는 Vault |
| 키 로테이션 | 90일 주기 (외부 API Key), 유출 의심 시 즉시 폐기 |
| Git 이력 | 실수로 커밋된 시크릿 → git filter-branch로 이력 제거 + 즉시 키 교체 |

### D-4. Error Handling (에러 처리)

| 규칙 | 적용 |
|------|------|
| 클라이언트 응답 | 사용자 친화적 메시지만 노출 (내부 스택트레이스 금지) |
| 에러 응답 구조 | `{ "code": "ERROR_CODE", "message": "사용자 메시지" }` — detail은 개발 환경에서만 |
| 인증 실패 | 401 + "로그인이 필요합니다" (원인 상세 미노출 — 계정 존재 여부 유추 방지) |
| 인가 실패 | 403 + "접근 권한이 없습니다" |
| 서버 에러 | 500 + "일시적인 오류가 발생했습니다" (로그에만 상세 기록) |

### D-5. Logging (로깅)

| 규칙 | 적용 |
|------|------|
| PII 마스킹 | 로그에 이름/전화/이메일/주소 기록 시 반드시 마스킹 |
| 금지 로깅 대상 | 비밀번호, 카드번호, PG Secret, JWT 토큰 원문 |
| 감사 로그 | 상태 변경(주문취소, 환불, 권한변경) 시 who/when/what 기록 |
| 로그 보관 | 90일 온라인, 1년 아카이브, 이후 파기 |
| 로그 포맷 | 구조화 JSON (timestamp, level, traceId, message, context) |

## E. Security Verification (보안 검증)

### E-1. Code (코드 레벨)

| 항목 | 방법 | 시점 |
|------|------|------|
| SAST | SonarQube / SpotBugs | CI/CD 파이프라인 (매 PR) |
| Dependency Check | OWASP Dependency-Check / npm audit | 주 1회 + PR 시 |
| Secret Scan | git-secrets / gitleaks | pre-commit hook |
| 프로토타입 예외 | SAST/Dependency 미적용 (로컬 개발 한정) |

### E-2. API (API 레벨)

| 항목 | 방법 | 시점 |
|------|------|------|
| 인증 우회 테스트 | 토큰 없이 호출, 만료 토큰 호출 | 통합테스트 |
| 인가 우회 테스트 | 타 사용자 리소스 접근, 역할 불일치 접근 | 통합테스트 |
| 금액 위변조 테스트 | 클라이언트 금액 조작 후 결제 요청 | GWT 시나리오 |
| Rate Limit 테스트 | 제한 초과 요청 → 429 확인 | 부하테스트 |

### E-3. Authorization (인가 레벨)

| 항목 | 방법 |
|------|------|
| 수직 권한 상승 | CUSTOMER 토큰으로 /admin/ 접근 → 403 |
| 수평 권한 침해 | 타 회원 주문번호로 조회 → 403 또는 빈 결과 |
| IDOR | Path Parameter 조작으로 타 리소스 접근 → 서버 소유권 검증 |

### E-4. Integration (통합 레벨)

| 항목 | 방법 |
|------|------|
| PG 연동 | 테스트 키로 결제/환불 시나리오 전수 검증 |
| 택배사 API | Mock → Sandbox → 실 환경 단계적 전환 |
| 알림톡 | 발신자 인증, 템플릿 승인 확인 |

### E-5. Production (운영 레벨)

| 항목 | 방법 | 주기 |
|------|------|------|
| 침투 테스트 | 외부 보안 업체 위탁 | 연 1회 |
| 취약점 스캔 | Nessus / Qualys | 분기 1회 |
| 접근 로그 모니터링 | 비정상 패턴 알림 (다회 401, 대량 조회) | 상시 |
| 인증서 갱신 | TLS 인증서 자동 갱신 (Let's Encrypt / ACM) | 자동 |
| 키 로테이션 | API Key, DB Password | 90일 |
