# C3 아키텍처컨벤션
> 수립 데드라인: S2 시작 전 | 참고 대상: 컴포넌트, ERD, 이벤트플로우, 시퀀스
---

## 1. 목적
시스템 전체 구조와 계층 간 책임 분리를 정의하여, 일관된 아키텍처 패턴으로 개발할 수 있도록 한다.

## 2. 규칙

### 2.1 기술 스택

| 계층 | 기술 |
|------|------|
| Backend | Kotlin + Spring Boot 3.3, JDK 21, Gradle Kotlin DSL |
| Frontend (고객웹) | Next.js (App Router), Tailwind CSS |
| Frontend (어드민) | Next.js, 순수 CSS (BEM, globals.css) |
| Frontend (입점사) | Next.js, 순수 CSS (BEM, 틸 테마, globals.css) |

### 2.2 앱 구성

| 앱 | Path Prefix | 화면 구조 |
|----|-------------|-----------|
| 플랫폼 고객웹 (mobile) | `/api/v1/**` | Header + Content + BottomNav |
| 플랫폼 어드민 (admin) | `/api/admin/v1/**` | NavBar + TabBar + TabContent (MDI) |
| 플랫폼 입점사 (partner) | `/api/partner/v1/**` | NavBar + TabBar + TabContent (MDI) |

### 2.3 Backend 계층 구조

```
com.runnshop.{domain}/
├── controller/     ← API 진입점, Request/Response 매핑
├── service/        ← 비즈니스 로직 (프로토타입: MockLoader 호출)
├── dto/            ← 요청/응답 데이터 클래스
└── mock/           ← MockLoader (JSON 파일 로딩)
```

### 2.4 Controller 분리 기준

| 조건 | 처리 방식 |
|------|-----------|
| 동일 로직, 3개 앱 사용 | 하나의 메서드에 다중 URL 매핑 |
| 앱별 응답/권한이 다름 | 별도 Controller 분리 |

```kotlin
// 공용: 다중 매핑
@GetMapping("/api/v1/products/{id}", "/api/admin/v1/products/{id}", "/api/partner/v1/products/{id}")
fun getProduct(@PathVariable id: String): ResponseEntity<*> { ... }

// 앱 전용: 별도 Controller
@RequestMapping("/api/v1/orders")         // 고객웹 전용
@RequestMapping("/api/admin/v1/orders")   // 어드민 전용
@RequestMapping("/api/partner/v1/orders") // 입점사 전용
```

### 2.5 모노레포 구조

```
runNshop/                        ← 모노레포 루트
├── apps/
│   ├── runNshop-mobile/         ← Next.js 고객웹 (독립 package.json)
│   ├── runNshop-admin/          ← Next.js 어드민 (독립 package.json)
│   └── runNshop-partner/        ← Next.js 입점사 (독립 package.json)
├── api/
│   └── runNshop-api/            ← Kotlin Spring Boot (독립 Gradle)
└── docs/                        ← 산출물·방법론·컨벤션
```

**원칙:**
- 각 앱은 **독립적으로 빌드·실행** 가능 (npm run dev, ./gradlew bootRun)
- 앱 간 코드 의존 없음 (공유 라이브러리는 향후 `packages/` 도입 시 처리)
- docs는 코드와 동일 레포에서 버전 관리

### 2.6 독립 실행 및 포트 할당

| 앱 | 실행 명령 | 포트 | 비고 |
|----|-----------|------|------|
| runNshop-mobile | `cd apps/runNshop-mobile && npm run dev` | 3000 | |
| runNshop-admin | `cd apps/runNshop-admin && npm run dev` | 3001 | |
| runNshop-partner | `cd apps/runNshop-partner && npm run dev` | 3002 | |
| runNshop-api | `cd api/runNshop-api && ./gradlew bootRun` | 8080 | |

- 모든 앱은 **독립 프로세스**로 실행 (의존 순서 없음)
- API 서버 미실행 시에도 FE 앱은 기동 가능 (API 호출 시 에러만 발생)

### 2.7 로컬 ↔ 개발계 리소스 참조

| 환경 | FE → API | API → DB/외부 |
|------|----------|---------------|
| **로컬 개발** | `next.config.js` rewrite로 `localhost:8080` 프록시 | Mock JSON 파일 (로컬 파일시스템) |
| **개발계** | 환경변수 `NEXT_PUBLIC_API_URL`로 개발계 API 지정 | 개발계 DB + 외부 연동 (향후) |
| **운영** | Nginx reverse proxy | 운영 DB + PG·택배사 연동 |

**FE 프록시 설정 (next.config.js):**
```javascript
async rewrites() {
  return [
    { source: '/api/:path*', destination: 'http://localhost:8080/api/:path*' }
  ]
}
```

**전환 원칙:**
- 로컬에서는 항상 `localhost:8080` Mock API를 기본으로 사용
- 개발계 리소스 참조 필요 시 `.env.local`에 API URL 오버라이드
- BE는 프로토타입(MockLoader) → 실 구현(Service+Repository) 전환 시 Controller 코드 변경 없음

### 2.8 프로토타입 데이터 흐름

```
Client → Controller → MockLoader → JSON 파일 → Response
```

- 실제 DB 연동 없음
- POST/PUT/DELETE 요청도 API를 호출하되, 저장 없이 성공 응답 반환
- Front-end는 API 응답 결과를 사용자에게 안내 (예: "저장되었습니다")

### 2.9 12개 도메인 패키지

order, catalog, member, payment, promotion, settlement, vendor, notification, community, search, config, audit

각 도메인은 독립된 패키지로 구성하며, 도메인 간 직접 참조를 최소화한다.

### 2.10 이벤트 기반 통신 (향후)

도메인 간 통신은 이벤트를 통해 느슨하게 결합한다.
- 이벤트 발행: 도메인 서비스에서 발행
- 이벤트 수신: eventId 기반 멱등 처리
- 재시도: 최대 3회 지수백오프, 실패 시 DLQ

## 근거
- 계층 분리(Controller/Service/DTO/Mock)로 프로토타입 → 실 프로젝트 전환 시 Service·Repository만 교체
- 도메인 단위 패키지로 MSA 전환 대비
- 프로토타입에서도 실제와 동일한 API 호출 패턴을 유지하여 Front-end 코드 재활용 극대화
