# C5 이벤트설계컨벤션

> **수립 데드라인**: S2 이벤트플로우 작성 전 | **참고 대상**: DI 이벤트플로우, DM 시퀀스

---

## 1. 목적

도메인 간 비동기 통신의 계약(Event Contract)·발행·소비·보장 규칙을 정의하여,
이벤트 기반 아키텍처의 일관성과 신뢰성을 확보한다.

---

## 2. 이벤트 설계 원칙

| 원칙 | 설명 |
|------|------|
| **Event = Fact** | 이벤트는 "발생한 사실"을 표현한다 (Command와 구분) |
| **Producer Ownership** | 상태를 변경한 도메인이 그 상태 변화의 사실을 이벤트로 발행한다 |
| **Loose Coupling** | Consumer는 Producer의 내부 구현에 의존하지 않는다 |
| **At-Least-Once** | 이벤트는 최소 1회 전달을 보장한다 (Consumer가 멱등 처리) |
| **Self-Contained** | Payload는 Consumer가 독립 처리할 수 있는 충분한 데이터를 포함한다 |

### Event vs Command

| | Event (사실) | Command (지시) |
|---|---|---|
| 표현 | "무엇이 발생했다" | "무엇을 해라" |
| 예시 | `ORDER_PAID` ✅ | `PAY_ORDER` ❌ |
| 예시 | `PAYMENT_COMPLETED` ✅ | `COMPLETE_PAYMENT` ❌ |
| 시제 | 과거형 (PAST_TENSE) | 명령형 |
| 발행자 | 상태 소유 도메인 | 요청자 |

## 3. 이벤트 명명 규칙

### 형식

```
{DOMAIN}_{PAST_TENSE_ACTION}
```

### 규칙

| 항목 | 규칙 | 예시 |
|------|------|------|
| 형식 | UPPER_SNAKE_CASE | `ORDER_PAID`, `CLAIM_COMPLETED` |
| 접두사 | 발행 도메인명 | ORDER_, PAYMENT_, CLAIM_ |
| 동사 | 과거 분사형 | PAID, COMPLETED, CANCELLED, FAILED |
| 도메인 구분 | 상태를 소유하는 도메인이 접두사 | Payment가 완료한 사실 = `PAYMENT_APPROVED` (Order가 아님) |

### 주요 이벤트명

| 이벤트 | 발행 도메인 | 의미 |
|--------|-------------|------|
| PAYMENT_APPROVED | Payment | PG 승인 성공 |
| PAYMENT_FAILED | Payment | PG 실패 (3회 재시도 소진) |
| ORDER_PAID | Order | 주문 결제 완료 상태 진입 |
| ORDER_CONFIRMED | Order | 구매확정 |
| ORDER_CANCELLED | Order | 주문 취소 |
| CLAIM_RECEIVED | Order | 클레임 접수 |
| CLAIM_COMPLETED | Order | 클레임 완료 |
| DELIVERY_COMPLETED | Order | 배송 완료 |
| SHIPPING_STARTED | Order | 출고 (배송 시작) |

## 4. 이벤트 계약 (Event Contract)

### 4.1 Envelope 구조

```json
{
  "eventId": "evt_01HXYZ...",
  "eventType": "ORDER_PAID",
  "eventVersion": 1,
  "occurredAt": "2026-08-21T10:30:00Z",
  "producer": "order-service",
  "correlationId": "cor_01HXYZ...",
  "payload": { ... }
}
```

| 필드 | 타입 | 필수 | 설명 |
|------|------|------|------|
| `eventId` | string (ULID) | ✅ | 이벤트 고유 식별자 (멱등키) |
| `eventType` | string | ✅ | 이벤트명 (UPPER_SNAKE_CASE) |
| `eventVersion` | int | ✅ | 스키마 버전 (1부터 시작) |
| `occurredAt` | ISO 8601 | ✅ | 비즈니스 이벤트 발생 시각 (UTC) |
| `producer` | string | ✅ | 발행 서비스 식별자 |
| `correlationId` | string (ULID) | ✅ | 업무 흐름 추적 ID (동일 주문의 이벤트 체인 공유) |
| `payload` | object | ✅ | 이벤트 데이터 |

### 4.2 Payload 원칙

| 원칙 | 설명 |
|------|------|
| 충분한 데이터 | Consumer가 Producer API 재호출 없이 처리 가능한 데이터 포함 |
| 민감 데이터 최소화 | PII(이름/전화/주소)는 ID로 참조, 직접 포함 지양 |
| 변경 가능 데이터 주의 | 금액·상태 등은 이벤트 발생 시점의 스냅샷임을 인식 |

### 4.3 Versioning (스키마 변경)

| 규칙 | 설명 |
|------|------|
| 필드 추가 | 하위 호환 — 동일 version 유지 (기존 Consumer 영향 없음) |
| 필드 제거/타입 변경 | **version 증가** (breaking change) |
| Consumer | 자신이 처리 가능한 version 목록을 명시 |
| 신규 version 배포 | Consumer 먼저 업데이트 → Producer 배포 (순서 중요) |

## 5. 이벤트 발행 규칙

### 5.1 Outbox 패턴 (기본 원칙)

> **비즈니스 데이터 변경과 Outbox 이벤트 저장을 동일 트랜잭션으로 처리한다.**

```
┌─ DB Transaction ─────────────────┐
│ 1. 비즈니스 데이터 변경           │
│    (예: order.status = PAID)     │
│ 2. Outbox 테이블에 이벤트 저장    │
│    (예: ORDER_PAID event row)    │
└──────────────────────────────────┘
         ↓ COMMIT
┌─ Outbox Publisher (비동기) ──────┐
│ Outbox 테이블 polling            │
│ → Message Broker 발행            │
│ → 발행 완료 시 outbox row 삭제   │
└──────────────────────────────────┘
         ↓
┌─ Consumer ───────────────────────┐
│ 이벤트 수신 → 처리               │
└──────────────────────────────────┘
```

**이점**: DB 커밋과 이벤트 발행의 원자성 보장 → 유실 없음

### 5.2 Publisher Retry

| 항목 | 규칙 |
|------|------|
| 대상 | Outbox Publisher → Broker 발행 실패 시 |
| 방식 | Outbox 테이블 재조회 (polling 주기 1초) |
| 한계 | 없음 (성공할 때까지 반복) |
| 모니터링 | Outbox 미발행 건수 > 임계치 시 알림 |

### 5.3 프로토타입 예외

| 규칙 | 프로토타입 | 실 프로젝트 |
|------|-----------|------------|
| Outbox 테이블 | 미사용 (in-process ApplicationEvent) | Outbox 테이블 + Publisher |
| Broker | Spring ApplicationEventPublisher | Kafka / RabbitMQ |
| 보장 수준 | Best-effort (프로세스 내) | At-Least-Once (Outbox) |

## 6. 이벤트 소비 규칙

### 6.1 멱등성 (Idempotency)

> **Consumer의 비즈니스 처리와 처리완료 기록을 동일 DB 트랜잭션으로 묶는다.**

```
┌─ Consumer Transaction ───────────┐
│ 1. processed_event INSERT 시도   │
│    (eventId = UNIQUE)            │
│    → 중복 시 DUPLICATE KEY 예외  │
│    → 즉시 SKIP (이미 처리됨)     │
│ 2. 비즈니스 로직 실행             │
│    (예: settlement 생성)         │
│ 3. COMMIT                        │
└──────────────────────────────────┘
```

| 규칙 | 설명 |
|------|------|
| 멱등키 | `eventId` (UNIQUE 제약) |
| 처리 기록 | `processed_event` 테이블 (eventId PK) |
| 동시성 방지 | INSERT UNIQUE → DUPLICATE 시 SKIP |
| 원자성 | 비즈니스 처리 + 처리기록 = 1 트랜잭션 |

### 6.2 Consumer Retry

| 항목 | 규칙 |
|------|------|
| 대상 | Consumer Handler 실행 실패 시 |
| 재시도 횟수 | 기본 3회 (이벤트 중요도에 따라 조정 가능) |
| 백오프 | 지수 백오프 (1초, 2초, 4초) |
| 재시도 대상 예외 | 일시적 오류 (네트워크, 타임아웃, DB 커넥션) |
| 즉시 실패 예외 | 비즈니스 예외 (데이터 무결성) → 재시도 없이 DLQ |

### 6.3 DLQ (Dead Letter Queue)

| 항목 | 규칙 |
|------|------|
| 진입 조건 | Consumer retry 모두 소진 |
| 저장 정보 | eventId, eventType, payload, failReason, failedAt, retryCount |
| 재처리 | 수동 재처리 도구 제공 (운영 대시보드) |
| 보관 기한 | 30일 (이후 아카이브) |
| 알림 | DLQ 진입 시 운영팀 알림 (Slack/알림톡) |

## 7. 이벤트 흐름 규칙

### 7.1 Ordering (순서 보장)

| 규칙 | 설명 |
|------|------|
| 기본 | 순서 보장 없음 (Consumer는 순서 무관하게 처리 가능해야 함) |
| 순서 필요 시 | `orderingKey` 지정 (동일 Key는 동일 파티션 → 순서 보장) |
| orderingKey 예시 | 주문 이벤트 = `orderId`, 결제 이벤트 = `paymentId` |

### 7.2 Fan-out

| 규칙 | 설명 |
|------|------|
| 하나의 이벤트 → 다수 Consumer | 각 Consumer는 독립적으로 처리 |
| Consumer 간 의존 | 금지 (A Consumer 완료를 B가 기다리지 않음) |
| 부분 실패 | 한 Consumer 실패가 다른 Consumer에 영향 주지 않음 |

### 7.3 이벤트 → 상태 관계

| 규칙 | 설명 |
|------|------|
| 이벤트 = 과거 사실 | "이 시점에 상태가 X였다"는 스냅샷 |
| 현재 상태 확인 | 필요 시 원본 도메인 API로 조회 (이벤트만으로 현재 상태 단정 금지) |
| 지연/재처리 | 이벤트 순서 역전 가능성 인식 → Consumer는 방어적으로 처리 |

## 8. 이벤트 목록

> 전체 이벤트 카탈로그는 이벤트플로우(DI) 문서가 Single Source of Truth.
> 아래는 컨벤션 적용 예시.

| 이벤트 | Producer | Consumer | 방식 | 멱등키 | orderingKey | Version |
|--------|----------|----------|------|--------|-------------|---------|
| PAYMENT_APPROVED | Payment | Order | async | eventId | paymentId | 1 |
| PAYMENT_FAILED | Payment | Order | async | eventId | paymentId | 1 |
| ORDER_PAID | Order | Settlement*, Notification* | async | eventId | orderId | 1 |
| ORDER_CONFIRMED | Order | Settlement*, Member* | async | eventId | orderId | 1 |
| ORDER_CANCELLED | Order | Payment, Catalog* | async | eventId | orderId | 1 |
| CLAIM_COMPLETED | Order | Payment, Catalog* | async | eventId | claimId | 1 |
| SHIPPING_STARTED | Order | Notification* | async | eventId | orderId | 1 |
| DELIVERY_COMPLETED | Order | Notification* | async | eventId | orderId | 1 |

> `*` 표시: 2차 파트 착수 시 Consumer 구현. 이벤트 발행은 1차에서 구현.

## 9. 예시

### 발행 (Producer)

```kotlin
// OrderService — 주문 결제 완료 처리
@Transactional
fun completePayment(orderId: String) {
    val order = orderRepository.findById(orderId)
    order.status = OrderStatus.PAYMENT_COMPLETED

    // 비즈니스 변경 + Outbox 저장 = 동일 트랜잭션
    orderRepository.save(order)
    outboxRepository.save(
        OutboxEvent(
            eventId = ULID.generate(),
            eventType = "ORDER_PAID",
            eventVersion = 1,
            occurredAt = Instant.now(),
            producer = "order-service",
            correlationId = order.correlationId,
            payload = mapOf("orderId" to orderId, "totalAmount" to order.totalAmount)
        )
    )
}
```

### 소비 (Consumer)

```kotlin
// SettlementEventListener — ORDER_PAID 수신
@Transactional
fun handleOrderPaid(event: DomainEvent) {
    // 1. 멱등성 확인 (UNIQUE 제약으로 중복 방지)
    try {
        processedEventRepository.save(ProcessedEvent(eventId = event.eventId))
    } catch (e: DuplicateKeyException) {
        return // 이미 처리됨 — SKIP
    }

    // 2. 비즈니스 처리
    settlementService.createSettlement(
        orderId = event.payload["orderId"],
        amount = event.payload["totalAmount"]
    )
    // 3. COMMIT (비즈니스 + processed_event 원자적)
}
```

## 10. 운영 및 모니터링

| 항목 | 규칙 | 프로토타입 적용 |
|------|------|----------------|
| 로그 필수 필드 | eventId, eventType, correlationId, producer, occurredAt | ✅ |
| Outbox 미발행 모니터링 | 미발행 건수 > N 시 알림 | ⏳ 실 프로젝트 |
| Consumer lag | 처리 지연 시간 모니터링 | ⏳ 실 프로젝트 |
| DLQ 알림 | DLQ 진입 시 즉시 알림 | ⏳ 실 프로젝트 |
| 이벤트 추적 | correlationId로 업무 흐름 전체 조회 | ⏳ 실 프로젝트 |

## 근거

| 항목 | 출처 |
|------|------|
| 이벤트 카탈로그 | DI 이벤트플로우 (15+ 이벤트 정의) |
| Outbox 패턴 | C3 아키텍처 §5.3 Domain 간 통신 — "상태 전파 = Event" |
| 멱등성 | DI 이벤트플로우 — "eventId로 중복 처리 방지" |
| 재시도 정책 | DI 이벤트플로우 — "최대 3회 지수백오프, DLQ" |
| ULID | C4 데이터모델링 — PK/eventId 생성 방식 |
| correlationId | 시퀀스(DM) — 동일 주문의 여러 이벤트 추적 필요 |
| Producer Ownership | C3 아키텍처 §5.2 Domain 의존 규칙 — Data 소유권 |
