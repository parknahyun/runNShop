# C5 이벤트설계컨벤션
> 수립 데드라인: S2 이벤트플로우 전 | 참고 대상: 이벤트플로우, 시퀀스
---

## 1. 목적
도메인 간 비동기 통신을 위한 이벤트 설계 표준을 정의하여, 느슨한 결합과 안정적인 메시지 처리를 보장한다.

## 2. 규칙

### 2.1 이벤트명 규칙

| 항목 | 규칙 | 예시 |
|------|------|------|
| 형식 | UPPER_SNAKE_CASE | ORDER_PAID |
| 구조 | {DOMAIN}_{PAST_TENSE_ACTION} | CLAIM_COMPLETED |
| 금지 | 동사 원형 사용 금지 | ORDER_PAY ✗ |

### 2.2 이벤트 Payload 표준 구조

```json
{
  "eventType": "ORDER_PAID",
  "eventId": "evt_01HXYZ...",
  "timestamp": "2024-01-15T10:30:00Z",
  "payload": {
    "orderId": "ord_01HXYZ...",
    "memberId": "mbr_01HXYZ...",
    "totalAmount": 35000
  }
}
```

| 필드 | 타입 | 설명 |
|------|------|------|
| eventType | string | UPPER_SNAKE_CASE 이벤트명 |
| eventId | string | 이벤트 고유 ID (멱등 판별 키) |
| timestamp | ISO 8601 | 이벤트 발생 시각 |
| payload | object | 이벤트별 데이터 |

### 2.3 멱등성 (Idempotency)

- 수신 측은 `eventId`로 중복 처리를 판별한다
- 동일 eventId의 이벤트를 2회 이상 수신해도 1회만 처리
- 처리 완료된 eventId는 별도 테이블에 기록

```sql
CREATE TABLE evt_processed_events (
    event_id    varchar(50)  PRIMARY KEY,
    event_type  varchar(50)  NOT NULL,
    processed_at timestamp   NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

### 2.4 재시도 정책

| 항목 | 규칙 |
|------|------|
| 최대 재시도 횟수 | 3회 |
| 백오프 전략 | 지수 백오프 (1초, 2초, 4초) |
| 최종 실패 시 | DLQ (Dead Letter Queue)로 이동 |
| DLQ 모니터링 | 어드민 알림 발송 |

### 2.5 이벤트 발행 원칙

1. 이벤트는 비즈니스 트랜잭션 커밋 후 발행한다
2. 발행 실패 시 Outbox 패턴으로 재발행을 보장한다 (향후)
3. 하나의 트랜잭션에서 여러 이벤트를 발행할 수 있다
4. 이벤트 payload에는 수신자가 필요한 최소 데이터만 포함한다

### 2.6 주요 이벤트 목록

| 이벤트명 | 발행 도메인 | 주요 수신 도메인 |
|----------|-------------|-----------------|
| ORDER_CREATED | order | notification, vendor |
| ORDER_PAID | order | payment, settlement, vendor |
| ORDER_CANCELLED | order | payment, promotion |
| PAYMENT_COMPLETED | payment | order |
| PAYMENT_REFUNDED | payment | order, settlement |
| CLAIM_REQUESTED | order | vendor, notification |
| CLAIM_COMPLETED | order | payment, settlement |
| PRODUCT_APPROVED | catalog | vendor, notification |
| MEMBER_REGISTERED | member | notification, promotion |
| SETTLEMENT_CONFIRMED | settlement | vendor, notification |

## 3. 예시

### 이벤트 발행 (Kotlin)
```kotlin
// OrderService.kt
fun completePayment(orderId: String) {
    // 비즈니스 로직 처리
    val order = orderRepository.findById(orderId)
    order.status = "PAID"
    orderRepository.save(order)

    // 이벤트 발행
    eventPublisher.publish(
        DomainEvent(
            eventType = "ORDER_PAID",
            eventId = "evt_${ULID.random()}",
            timestamp = Instant.now(),
            payload = mapOf(
                "orderId" to orderId,
                "memberId" to order.memberId,
                "totalAmount" to order.totalAmount
            )
        )
    )
}
```

### 이벤트 수신 (멱등 처리)
```kotlin
// SettlementEventListener.kt
@EventListener
fun handleOrderPaid(event: DomainEvent) {
    if (processedEventRepository.existsById(event.eventId)) {
        return // 이미 처리된 이벤트
    }

    // 정산 데이터 생성 로직
    settlementService.createSettlement(event.payload)

    // 처리 완료 기록
    processedEventRepository.save(ProcessedEvent(event.eventId, event.eventType))
}
```

## 근거
- 이벤트 기반 아키텍처로 도메인 간 결합도를 낮추어 독립 배포·확장 가능
- eventId 기반 멱등 처리로 네트워크 불안정 환경에서도 데이터 정합성 보장
- 지수 백오프 + DLQ로 일시적 장애와 영구 장애를 구분하여 대응
- UPPER_SNAKE_CASE 과거형 네이밍으로 "이미 발생한 사실"임을 명시
