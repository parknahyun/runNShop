# C9 코딩컨벤션

> **수립 데드라인**: S3 클래스설계 작성 전 | **참고 대상**: DP 클래스설계, 코드구현, 코드리뷰
> **위치**: C9는 다른 컨벤션(C2~C8)의 설계를 **코드로 구현하는 실행 규칙**을 담당한다.
> 아키텍처 구조는 C3, API 계약은 C6, 데이터 모델은 C4를 따르며, C9에서 재정의하지 않는다.

---

## 1. 목적

코드의 일관성·가독성·유지보수성을 확보하기 위한 코딩 규칙을 정의한다.
자동 검증 가능한 규칙은 Tool로 강제하고, 사람이 판단해야 하는 규칙만 문서로 관리한다.

---

## 2. 기본 원칙

| 원칙 | 설명 |
|------|------|
| 일관성 | 같은 것은 같은 방식으로 |
| 단순성 | 불필요한 추상화·코드 최소화 |
| 책임 분리 | 한 클래스/함수는 하나의 책임 |
| 자동화 우선 | Formatter/Linter로 강제할 수 있는 규칙은 Tool에 위임 |
| 다른 컨벤션 참조 | 구조(C3), API(C6), 데이터(C4), 이벤트(C5), 보안(C1) 규칙을 코드로 구현 |

## 3. Naming

### 3.1 Kotlin (Backend)

| 대상 | 규칙 | 예시 |
|------|------|------|
| 클래스 | PascalCase | `OrderService`, `CustomerOrderController` |
| 함수 | camelCase | `getOrderDetail()`, `cancelOrder()` |
| 변수 | camelCase | `orderId`, `totalAmount` |
| 상수 | UPPER_SNAKE_CASE | `MAX_CART_ITEMS`, `DEFAULT_PAGE_SIZE` |
| 패키지 | 소문자 | `com.runnshop.order` |
| Boolean | `is/has/can/should` 접두사 | `isDeleted`, `hasPermission`, `canCancel` |
| Enum 클래스 | PascalCase | `OrderStatus` |
| Enum 값 | UPPER_SNAKE_CASE | `PAYMENT_COMPLETED`, `IN_DELIVERY` |

### 3.2 TypeScript / React (Frontend)

| 대상 | 규칙 | 예시 |
|------|------|------|
| 컴포넌트 | PascalCase | `OrderCard.tsx`, `ProductCard.tsx` |
| 함수/변수 | camelCase | `fetchOrders()`, `orderId` |
| 훅 | `use` 접두사 + camelCase | `useOrders.ts`, `useCartItems.ts` |
| 상수 | UPPER_SNAKE_CASE | `MAX_CART_ITEMS` |
| Type/Interface | PascalCase | `OrderResponse`, `CartItem` |
| Boolean | `is/has/can/should` | `isLoading`, `hasError`, `canSubmit` |
| 파일명 (컴포넌트) | PascalCase | `OrderCard.tsx` |
| 파일명 (유틸/훅) | camelCase | `useOrders.ts`, `formatPrice.ts` |

### 3.3 CSS (BEM)

```
.{block}__{element}--{modifier}
```

| 대상 | 규칙 | 예시 |
|------|------|------|
| Block | kebab-case | `.order-card`, `.filter-bar` |
| Element | `__` + kebab-case | `.order-card__title`, `.filter-bar__input` |
| Modifier | `--` + kebab-case | `.order-card--active`, `.badge--red` |

> Modifier는 **상태/변형** 표현에만 사용한다 (Block Modifier와 Element Modifier 모두 허용).

### 3.4 Mock 파일

```
{domain}__{HTTP_METHOD}_{API_PATH}.json
```

| 규칙 | 설명 |
|------|------|
| Path 내 구분 | URL의 `/`를 `_`로 치환 |
| Path Parameter | `{camelCase}` 사용 (**통일**) |
| 도메인 구분자 | `__` (이중 언더스코어) |

**예시:**

```
order__GET_cart.json
order__GET_members_me_orders.json
order__GET_members_me_orders_{orderId}.json
catalog__GET_products_{productId}.json
order__POST_orders_{orderId}_cancel.json
```

> Mock 파일명은 C6 API설계컨벤션의 HTTP Method 및 Path 규칙을 따른다.

## 4. Backend Coding

### 4.1 패키지 구조

> C3 아키텍처 §4.1 계층 구조를 따른다.

```
com.runnshop.{domain}/
├── controller/     ← 앱별 Controller (C3 §4.2)
├── service/        ← 비즈니스 로직
├── repository/     ← 데이터 접근 추상화 (C3 §4.3)
├── dto/
│   ├── request/    ← Request DTO
│   └── response/   ← Response DTO
└── entity/         ← (향후) JPA Entity
```

### 4.2 DTO 규칙

| 규칙 | 설명 |
|------|------|
| Entity 직접 노출 금지 | Request/Response는 별도 DTO |
| Request DTO | `{Action}Request` (예: `CreateOrderRequest`) |
| Response DTO | `{Entity}Response` (예: `OrderResponse`) |
| Validation | Request DTO에 `@NotBlank`, `@Size`, `@Min` 등 어노테이션 |

### 4.3 Validation 책임 분리

| 계층 | 책임 | 예시 |
|------|------|------|
| Frontend | 형식/필수값/UX (즉각 피드백) | 빈 입력, 이메일 형식, 수량 범위 |
| Backend | 무결성/업무 규칙/보안 | 재고 확인, 권한 확인, 금액 재계산, 상태 전이 가능 여부 |

> FE validation을 통과해도 BE validation은 반드시 수행한다.

### 4.4 Error Handling

| 규칙 | 설명 |
|------|------|
| 공통 예외 처리 | `@ControllerAdvice`로 전역 에러 핸들링 |
| 응답 구조 | C6 API §6.3 Error Response 규격 준수 |
| 비즈니스 예외 | 도메인별 Exception 클래스 정의 (`OrderNotFoundException` 등) |
| 스택트레이스 | 클라이언트 미노출, 로그에만 기록 |
| HTTP Status 매핑 | C6 §7 Status Code 테이블 준수 |

## 5. Frontend Coding

### 5.1 컴포넌트 구조

```
src/{domain}/
├── components/     ← 도메인 전용 컴포넌트
├── hooks/          ← 도메인 전용 훅
└── ...

components/
├── layout/         ← 레이아웃 (Header, NavBar, BottomNav)
└── common/         ← 공용 (Toast, Skeleton, LayerPopup)

lib/
├── api.ts          ← API Client (공통 fetch 래퍼)
└── constants.ts    ← 공용 상수
```

### 5.2 API 호출 규칙

> 화면 컴포넌트는 API 호출 구현을 직접 포함하지 않으며, API Client 또는 Hook을 통해 데이터를 조회한다.

**사용자 행위 → API 처리 패턴:**

```
사용자 행위 (버튼 클릭)
    ↓
API 요청 (fetch/axios)
    ↓
API 응답 수신
    ↓
성공 → UI 상태 반영 + 사용자 안내 (Toast)
실패 → 에러 처리 + 사용자 안내
```

| 규칙 | 설명 |
|------|------|
| 하드코딩 금지 | FE에서 Mock 데이터 직접 생성 금지 — 반드시 API 호출 |
| POST/PUT/DELETE | 프로토타입에서도 실제 API 호출 (서버가 성공 응답 반환) |
| 응답 구조 | C6 API Response Schema를 임의 변환하지 않음 |
| 로딩 상태 | API 호출 중 Skeleton 또는 로딩 표시 |

### 5.3 Error Handling (Frontend)

| HTTP Status | 처리 |
|-------------|------|
| 400 | Inline 에러 메시지 (필드별) |
| 401 | 로그인 페이지 이동 (프로토타입: 미적용) |
| 403 | "접근 권한이 없습니다" Toast |
| 404 | NotFound 화면 표시 |
| 409/422 | `message` 필드를 Toast로 표시 |
| 500 | "일시적인 오류가 발생했습니다" Toast |

### 5.4 Navigation

| 규칙 | 설명 |
|------|------|
| 라우팅 동작 | 미구현 화면이라도 라우팅은 정상 동작 |
| 미구현 화면 | PlaceholderPage 표시 ("해당 기능은 준비 중입니다.") |
| 존재하지 않는 리소스 | 404 / NotFound 화면 제공 |
| 뒤로가기 | 브라우저 히스토리 기반 동작 |

## 6. CSS

### 6.1 앱별 스타일링

| 앱 | 방식 | 규칙 |
|----|------|------|
| mobile | Tailwind CSS | Design Token(C7) 우선 사용, 임의 값 최소화 |
| admin | 순수 CSS (globals.css) | BEM 네이밍, C7 디자인시스템(admin) 클래스 사용 |
| partner | 순수 CSS (globals.css) | BEM 네이밍, C7 디자인시스템(partner) 클래스 사용 |

### 6.2 Tailwind 규칙 (mobile)

| 규칙 | 설명 |
|------|------|
| Design Token 우선 | `text-primary`, `bg-secondary` 등 tailwind.config 토큰 우선 |
| 임의 값 최소화 | `text-[#FF4D00]` 대신 `text-primary` |
| 반복 패턴 | 동일 클래스 조합 반복 시 컴포넌트로 추출 |

### 6.3 BEM 규칙 (admin/partner)

| 규칙 | 설명 |
|------|------|
| 신규 클래스 | globals.css에 추가 (인라인 style 최소화) |
| Modifier 사용 | 상태/변형 표현에만 (`--active`, `--warn`, `--compact`) |
| 중복 회피 | 기존 C7에 정의된 클래스 우선 재사용 |

## 7. Import 정렬

### 7.1 TypeScript/React

```typescript
// 1. 외부 라이브러리
import { useEffect, useState } from 'react';
import Link from 'next/link';

// 2. 프로젝트 내부 모듈
import { api } from '@/lib/api';
import { formatPrice } from '@/lib/utils';

// 3. 컴포넌트
import { Toast } from '@/components/common/Toast';

// 4. 타입
import type { OrderResponse } from '@/types/order';
```

### 7.2 Kotlin

```kotlin
// 1. Java/Kotlin 표준
import java.time.Instant

// 2. Spring Framework
import org.springframework.web.bind.annotation.*

// 3. 프로젝트 내부
import com.runnshop.common.MockLoader
import com.runnshop.order.dto.OrderResponse
```

### 7.3 자동화

| 도구 | 대상 | 역할 |
|------|------|------|
| Prettier | TypeScript/React | 코드 포매팅 |
| ESLint | TypeScript/React | Lint + Import 정렬 |
| ktlint | Kotlin | 코드 포매팅 + Import 정렬 |

> Import 정렬은 도구로 자동 강제하며, 수동 정렬을 최소화한다.

## 8. 프로토타입 규칙

> 프로토타입 단계에서만 적용되는 예외 규칙. 실 프로젝트 전환 시 해제.

| 규칙 | 설명 |
|------|------|
| Mutation API | 실제 영속화 없이 성공 응답 반환 (C3 §4.4) |
| 인증/인가 | 미적용 (C1 보안 프로토타입 예외) |
| 미구현 화면 | PlaceholderPage 표시 (개발 환경 전용) |
| 구현 완료 표시 | 메뉴에 `implemented: true` → 초록 원(●) 표시 |
| Mock 데이터 | PII 마스킹 적용 (홍\*동, 010-\*\*\*\*-5678) |
