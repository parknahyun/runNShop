> 핵심 책임: 운영자 계정·롤·권한·공통코드·공지·약관·배너·FAQ·팝업·시스템 설정을 관리하고,
> 인증·인가·계정보호·접근통제·개인정보보호·이상행위탐지·API보안 등 플랫폼 공통 보안 기능을
> 포함한다(2026-07-30, 사업 오너 확인으로 옛 13-Security.md를 Config로 편입).

> **진행 상태 전제(2026-07-28)**: 고객화면(mobile)·배치·컨슈머(비동기 처리)는 아직 미착수,
> admin·partner도 초안 작업 상태 — 아래 N/A·스텁·dead code 발견은 결함이 아니라 진행 전 상태.
> 상세는 `README.md`의 "현재 진행 상태 안내" 절 참고.

**API 호출 개수 카운트 기준**: 화면/탭 로드 1개 = API 1개, 실제 제출 버튼 1개 = API 1개(취소·
편집토글처럼 API를 호출하지 않는 UI 전용 버튼은 제외). 아직 실제 백엔드 연동 전이라 미연결인
것도 많지만, 이 기준으로 API 표면 규모를 추정한다. 화면 자체가 없는 코드/구성 자산은 "N/A"로
표기(추정치를 억지로 만들지 않음).

## 코드 기반 보완 (2026-07-28, apps/ 실제 소스 조사)

- **"배치관리"가 완전히 새로운 대분류로 확인됨** — 도메인정의서엔 배치 개념이 도메인별 배치
  목록(Order/Catalog 등)으로만 흩어져 있었는데, admin엔 **배치잡을 등록·모니터링·수동실행하는
  전용 화면**(`system/batch-job`)이 따로 있음. 이건 Config가 관리하는 "배치 자체의 운영"이지,
  각 도메인 배치의 비즈니스 로직과는 다른 층위.
- **운영자 계정관리와 신청승인이 별도 화면**으로 확인됨(도메인정의서엔 뭉뚱그려져 있었음).
- **권한관리(Role)가 단순 "권한 부여"가 아니라 Role↔Program↔Operator 3자 매트릭스**임을 확인
  — 프로그램관리(화면/API/배치/이벤트 레지스트리) 자체도 새 대분류로 분리했다.
- 대분류가 5개로 늘었고 "운영자권한관리"가 소분류 4개로 임계값(6개)엔 여유 있음 — 중분류는
  아직 불필요.
