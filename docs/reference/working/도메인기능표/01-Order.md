# Order 도메인 기능표

> 핵심 책임: 고객 주문의 전체 생명주기를 오케스트레이션한다.

> **진행 상태 전제(2026-07-28)**: 고객화면(mobile)·배치·컨슈머(비동기 처리)는 아직 미착수,
> admin·partner도 초안 작업 상태 — 아래 N/A·스텁·dead code 발견은 결함이 아니라 진행 전 상태.
> 상세는 `README.md`의 "현재 진행 상태 안내" 절 참고.

**API 호출 개수 카운트 기준**: 화면/탭 로드 1개 = API 1개, 실제 제출 버튼 1개 = API 1개(취소·
편집토글, 그리고 `alert()`만 뜨는 스텁 버튼처럼 실제 API를 호출하지 않는 것은 제외). 화면 자체가
없는 기능은 "N/A"로 표기. 상세 모달이 탭 없이 단일 정보 섹션이면(list row 데이터를 그대로 보여줄
뿐 별도 fetch가 없으면) "목록(모달기반)=1"로 묶어 세고, 탭이 있는 상세는 목록(1)+탭(각 1)로
나눠 센다. **admin `OrderDetail`(주문상세)의 "CS·클레임" 탭 하나가 예외 취소·CS 대응 조치·
클레임 접수(admin) 3개 소분류의 버튼을 동시에 호스팅** — 화면 로드는 "클레임 접수(admin)" 행에만
귀속시키고 나머지 두 행은 0(공유)으로 처리했다. 반품(4개)·교환(3개) 각각도 상세 모달 하나(반품:
기본정보/처리이력 2탭, 교환: 기본정보/처리이력 2탭)를 공유하므로, 목록+탭 로드는 각 그룹의 첫
액션 행(수거 운송장 등록/재고 확인)에만 귀속시키고 나머지는 버튼만 개별 산정했다(행별 버튼 합이
실제 코드상 물리 버튼 수와 일치함을 상호 검증).

## 2계층 주문구조 반영 (`01-Spec/01-용어집.md` HR#3 해결, 2026-07-30)

> **확정 구조(사업 오너 확인)**
> - **`ord_platform_order`**(상위) — 고객이 실제로 보는 주문 단위. 여러 입점사 상품을 한 번에
>   담아 결제하면 이 하나의 주문으로 묶임
> - **`ord_order`**(하위) — 입점사별로 쪼개진 실제 처리 단위. **배송·정산·클레임은 전부 이
>   단위로 진행됨**

위 대분류별로 어느 레벨에서 동작하는지 정리하면:

| 대분류 | 적용 레벨 | 비고 |
|---|---|---|
| 장바구니 | 해당 없음(레코드 기준) | platform_order/order 레코드는 아직 생성 전이지만, **배송비는 상품 단위가 아닌 입점사 단위로 부과**(정책 §3.6, 묶음배송)돼 UI상 입점사별로 이미 분리 표시됨(`vendors[].shipping_fee`) — order 단위 개념이 레코드 생성 전부터 선반영되는 예외 케이스 |
| 주문서 | platform_order(레코드) + 입점사별 분리 표시 | 결제·약관동의·포인트사용은 주문 전체 1회 적용(platform_order)이지만, 상품·배송비 금액요약은 장바구니와 동일하게 입점사별로 분리 표시됨(`orders/new` `vendor_id`/`shipping_fee`). "배송지 선택(주문서)"의 최초 선택은 platform_order 레벨이지만, 결제 후 변경은 아래 배송관리(order 단위) 흐름을 따름 |
| 주문결제 — 생성/결제완료전환(주문 생성(TEMP), 결제 완료 전환) | platform_order → order 분할 | 고객은 PG 승인 1건으로 여러 입점사 상품을 함께 구매 — 생성 시점엔 platform_order 1건, 결제 완료 즉시 입점사별 order로 분할되는 구조로 추정(코드상 분할 시점 확인 필요 — Design 단계 과제) |
| 주문결제 — 취소·구매확정·조회 계열(단순 취소·예외 취소·구매확정·주문 조회(admin)·주문내역 조회(고객)·주문 취소 신청(고객)·구매확정(고객)) | order(입점사별) | A입점사 상품만 취소되고 B입점사 상품은 유지되는 부분 처리가 원칙 — 현재 소분류 설명엔 이 구분이 명시돼 있지 않음. EARS 작성 시 "주문내역 조회(고객)"는 platform_order 단위 목록 + order 단위 상세로 나눠 기술 필요 |
| 배송관리 전체 | order(입점사별) | 확정 구조의 "배송은 order 단위" 원칙과 이미 일치 — 현재 소분류 설명 그대로 유지 가능 |
| 클레임처리 전체 | order(Level2) 중심 | 용어집의 "클레임 Level 1/2/3"(Level1=주문 전체/platform_order, Level2=입점사 단위/order, Level3=상품 단위)과 맞물림 — 취소는 Level1 성격(플랫폼 자동 처리), 반품·교환은 Level2(입점사 단위) |
| 연동 | 이벤트별 상이 | 결제완료 이벤트 처리=platform_order 단위, 재고선점 요청·포인트쿠폰 금액 반영=order/상품 단위 |

**결론**: 기존 75개 소분류 자체를 지금 재작성하지는 않는다 — 위 레벨 구분을 `04-기능요구사항
(EARS)/01-Order.md` 현행화 시 각 요구사항 문장에 "platform_order 기준" / "order 기준"으로
명시하는 방식으로 반영한다. 특히 **"주문결제 — 취소·구매확정·조회 계열"이 실제로 입점사별
부분 처리를 지원하는지는 코드 검증이 안 된 추정**이라 EARS 작성 시 우선 확인이 필요하다.
