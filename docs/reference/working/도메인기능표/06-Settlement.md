# Settlement 도메인 기능표

> 핵심 책임: 구매확정 기준으로 입점사 정산을 계산·확정·지급·대사한다.

> **진행 상태 전제(2026-07-28)**: 고객화면(mobile)·배치·컨슈머(비동기 처리)는 아직 미착수,
> admin·partner도 초안 작업 상태 — 아래 N/A·스텁·dead code 발견은 결함이 아니라 진행 전 상태.
> 상세는 `README.md`의 "현재 진행 상태 안내" 절 참고.

**API 호출 개수 카운트 기준**: 화면/탭 로드 1개 = API 1개, 실제 제출 버튼 1개 = API 1개(취소·
편집토글, 그리고 `alert()`만 뜨는 스텁 버튼처럼 실제 API를 호출하지 않는 것은 제외). 화면 자체가
없는 기능은 "N/A"로 표기. **정산계산 3종은 `SettlementDetail` 모달 하나(목록+3탭)를 공유** —
목록 로드는 "정산 확정" 행에만 귀속시키고, 나머지 두 행은 각자 대응하는 탭(정산항목 탭/재정산내역
탭)만 카운트해 3중 계산을 피했다. 마찬가지로 "지급 보류·보류 해제"는 "정산금 지급"과 동일한
`SettlementPaymentDetail` 화면을 재사용하므로 화면/탭은 0으로 표기하고 버튼·API만 추가 산정한다.

## 코드 기반 보완 (2026-07-28, apps/ 실제 소스 조사)

- **벤더(입점사) 쪽은 정산이 완전 조회 전용** — partner 앱엔 정산 확정·이의제기 등 벤더가 트리거
  하는 액션이 전혀 없음. 실제 정책이 "정산은 플랫폼만 처리"가 맞는지, 아니면 미구현 갭인지 확인
  필요(Human Review).
- **지급 보류/해제**가 별도 상태 전이로 확인됨 — 도메인정의서엔 "지급"만 있고 보류 처리 흐름은
  없었음.
- **일괄 처리(일괄확정·일괄지급) 버튼은 있지만 스텁** — 실제 다중 선택 UI(체크박스)도 없어서,
  "버튼은 설계됐지만 아직 구현 안 됨" 상태.
- **API 호출 개수 산정(2026-07-28)** — Config와 동일 기준(화면/탭=1, 실제 제출 버튼=1)을 적용.
  "정산계산" 3개 소분류가 `SettlementDetail` 모달 하나(목록 + 기본정보/정산항목/재정산내역 3탭)를
  공유하는 구조라, 목록 로드는 "정산 확정" 행에만 귀속시키고 나머지는 각자의 탭만 카운트해 중복
  집계를 피했다. "정산 이의제기 처리"와 "세금계산서 발행"은 도메인정의서엔 소분류로 있으나 실제
  코드엔 대응 화면·로직이 전혀 없어 N/A 처리(전자는 `objectionCount`/`objectionDeadline` 표시
  필드만 존재, 후자는 관련 코드 자체가 없음) — 둘 다 미구현 갭인지 확인 필요(Human Review). 일괄
  확정/일괄 지급 스텁 버튼은 `alert()`만 호출하므로 API 0으로 산정. 벤더(입점사) 쪽은 위에서 확인한
  대로 조회·엑셀다운로드 버튼만 있어 API 표면에 추가되는 액션이 없다. 합계: 소분류 12개 중 7개
  산정, API 호출 약 15개(N/A 5건 제외).
- **신규 추가(대사관리, 2026-07-29)**: 운영자/입점사 일반 기능표 대조 검토 결과 반영 — 대사
  실행(배치)/대사 결과·오류 처리(운영자)/대사 결과 확인·이의제기(입점사) 3개 소분류로 대분류
  "대사관리" 신설. `apps/` 전체에서 reconcil/대사/차이금액 관련 키워드 코드 근거 0건, 12개
  도메인기능표 어디에도 등재되지 않은 순수 신규 공백으로 확인됨(04-Payment.md의 PG 연동,
  12-Audit.md의 장애처리/DLQ는 시스템 이벤트 재처리 개념이라 금액 대사와는 무관). 같은 대조
  검토에서 나온 정산서·지급명세서 생성/다운로드·정산 리포트(대시보드)·지급 실패 관리(신규
  공백), 수수료 정책 관리(BC 대상: Vendor)·배송비 부담 정책(BC 대상: Vendor+Order)·회원 측
  기능(BC 대상: Order+Payment)·입점사 판매분석 확장(BC 대상: Vendor)은 이번 반영 범위에서
  제외 — 별도 논의 예정.
