## 1. 개요

### 1.1 프로젝트명

- runNshop 플랫폼 구축 프로젝트(국문) — 러닝 전문 e커머스 플랫폼 신규 구축

### 1.2 예상 오픈 일정

- 본 프로젝트는 프로토타입(UI 흐름 검증) 단계와 본개발 단계로 나뉘어 진행되며, 정책서에 프로토타입→본개발 전환 기준(핵심 화면 프로토타입 리뷰 완료, 이해관계자 피드백 반영, 개발서버 인프라 준비 완료)이 정의되어 있다.
- 다만 구체적인 목표 오픈(Go-Live) 일자, Kick-off 일자, 전체 프로젝트 기간은 문서에 확정되어 있지 않으며 착수 단계에서 발주사와 협의하여 확정해야 한다.

### 1.3 프로젝트 추진 배경 및 목적

- 본 프로젝트는 기존 시스템을 대체하는 재구축이 아닌 신규 구축(Greenfield) 프로젝트다. 정책서 16장(이관·마이그레이션 정책)에 따라 기존 시스템으로부터의 데이터 이관 대상이 없으며, 모든 데이터는 런칭 이후 신규 등록으로만 적재한다.
- 러닝 전문 버티컬 e커머스 시장을 겨냥해 러닝화·러닝 의류·러닝 기어·보충제·웨어러블 등 5개 카테고리에 특화된 플랫폼을 구축하고, 플랫폼 직매입과 다수 입점사가 공존하는 하이브리드(직매입+입점형) 거래 구조를 통해 상품 다양성과 재고 안정성을 동시에 확보하는 것을 목적으로 한다.
- 아키텍처 측면에서는 향후 트래픽·조직 성장에 대응할 수 있도록 1단계 Modular Monolith에서 2단계 MSA로 무중단 전환 가능한 구조를 처음부터 설계에 반영하는 것을 목적으로 한다.
- 사업적 착수 배경(신규 시장 진입/기존 시스템 노후화/경쟁사 대응 등 구체적 동기), 정량적 목표(KPI, 예산, 목표 오픈일)는 문서에 명시되어 있지 않으므로 착수 단계에서 발주사 확인이 필요하다.

### 1.4 주요 구축 범위

① 애플리케이션 3종에 대한 요구사항 분석·설계·구축·테스트·안정화를 진행한다.

| 애플리케이션 | URL | 채널 | 인증 | 대상 |
|---|---|---|---|---|
| 고객 웹 | www.runNshop.com | 모바일 웹 (360px) | JWT + Redis | 일반 고객 |
| 플랫폼 어드민 | admin.runNshop.com | PC 웹 (1280px+) | JWT + 세션 8시간 + IP 접근 제한 | 플랫폼 운영자 |
| 입점사 BO | partners.runNshop.com | PC 웹 (1280px+) | JWT + 2단계 인증 + 세션 3시간 | 입점사 담당자 |

② 화면·API 규모는 화면정의서 v1.1 기준으로 아래와 같이 확정되어 있다.

| 애플리케이션 | 화면 수 | API 수 |
|---|---|---|
| 고객 웹 | 38개 | 101개 |
| 플랫폼 어드민 | 80개 | 238개 |
| 입점사 BO | 40개 | 131개 |
| **합계** | **158개** | **470개** |

③ 업무 도메인은 아래 12개 Bounded Context로 구성되며, 발주사가 별도로 제외를 지정하지 않는 한 12개 영역 전체를 구축 범위로 한다.

| 레이어 | 도메인 | 핵심 책임 |
|---|---|---|
| 거래 | Order | 주문·배송·클레임 생명주기 오케스트레이션 |
| 상품 | Catalog | 상품 정보·재고·전시 관리 |
| 고객 | Member | 회원·등급·포인트·쿠폰 관리 |
| 거래 | Payment | 결제 트랜잭션 처리 |
| 혜택 | Promotion | 쿠폰·행사가·수량할인·기획전 관리 |
| 정산 | Settlement | 정산 계산·확정·지급 |
| 파트너 | Vendor | 입점사 생명주기·계약·등급 관리 |
| 운영 | Notification | 알림 발송·이력 관리 |
| 커뮤니티 | Community | 리뷰·QnA·크루·챌린지 |
| 운영 | Search | 통합 검색·인덱스 |
| 운영 | Config | 운영자 권한·공통코드·공지·약관·배너 |
| 운영 | Audit | 로그·감사·Trace 수집·보존 |

④ DB는 12개 도메인 기준 107개 테이블과 5개 복제(동기화) 테이블로 설계되어 있으며, PostgreSQL + MyBatis 기반으로 구축한다.

⑤ 1단계는 Modular Monolith(단일 실행 모듈, 도메인별 패키지 분리) + Docker Compose로 구축하며, 2단계는 Hybrid MSA + Kubernetes로 무중단 전환하는 것을 전제로 아키텍처를 설계한다.

⑥ 신규 데이터 이관(마이그레이션) 대상은 없으며, 모든 데이터는 런칭 후 신규 등록으로 적재한다.

### 1.5 추가 요청사항

- 프로토타입(UI 흐름 검증) 단계와 본개발 단계를 구분하여 진행하되, 각 단계 전환 기준(정책서 20.8)을 준수해야 한다.
- 통합 테스트 시나리오·케이스·결과 문서를 필수로 작성하고, 정책서에 정의된 표준 에러 응답 형식(`SUCCESS`/`BAD_REQUEST`/`UNAUTHORIZED`/`FORBIDDEN`/`NOT_FOUND`/`INTERNAL_ERROR`)을 준수해야 한다.
- Outbox Pattern 기반 이벤트 처리, 소프트 삭제(물리적 DELETE 금지), 감사 로그(Trace ID 기반 전 구간 추적) 등 정책서에 명시된 운영 안정성 원칙을 설계·구현 전 구간에 일관되게 적용해야 한다.
- 런칭 후 운영 단계에서 필요한 수동 처리 항목(상품 심사, 재고·포인트·쿠폰 수동 복원, DLQ 처리, 정산 이의제기 처리 등)이 운영매뉴얼 백로그에 이미 도출되어 있으므로, 제안사는 이를 반영한 운영 인수인계 방안을 제시해야 한다.

### 2.2 기능 요구사항

기능 요구사항은 P1(런칭 필수)·P2(런칭 권장)·P3(2단계) 우선순위로 분류되어 있으며, 도메인별 핵심 요건은 다음과 같다.

| 도메인 | 핵심 기능 요건(P1 중심) |

| Member(회원) | 이메일·소셜(네이버·Apple) 가입, JWT 인증, 4단계 회원등급(New·Runner·Pacer·Elite), 포인트·쿠폰 관리, 배송지 5개 등록, 약관 동의 이력 관리 |

### 2.3 커머스 플랫폼(아키텍처) 요구사항

① **단계적 아키텍처 진화**: 1단계 Modular Monolith(Docker Compose, 수동 스케일 아웃) → 2단계 Hybrid MSA(Kubernetes, HPA 자동 스케일 아웃) → 3단계 Full MSA로 진화하는 구조를 전제로 설계해야 한다.

② **Event-driven 처리**: 1단계는 Outbox Pattern + Spring Event Consumer(인프로세스, Kafka 미사용)로 처리하며, 2단계에서는 Debezium CDC가 Outbox 테이블 변경을 감지하여 Kafka Topic으로 코드 변경 없이 자동 전환 가능해야 한다.

③ **API 접근 통제**: 하나의 Backend에서 3개 앱(고객·어드민·입점사)의 API를 URL Path Prefix(`/api/v1/`, `/api/admin/v1/`, `/api/partner/v1/`)로 구분하여 서비스하며, 외부 접속은 Nginx Reverse Proxy(Whitelist 방식)를 통해서만 허용하고 미등록 경로는 403으로 차단한다.

④ **대용량 처리 요소**: Redis 기반 재고 선점·행사 수량 관리, Elasticsearch 기반 통합 검색, 도메인별 독립 스케일링이 가능한 구조를 요구한다.

⑤ **데이터 정합성 요소**: 전 테이블 공통 컬럼(`is_deleted`/`deleted_at`/`deleted_by`) 기반 소프트 삭제, 물리적 DELETE 전면 금지 원칙을 준수해야 한다.

### 2.4 비기능 요구사항

| 구분 | 기준 |

### 2.5 보안 요구사항

① 제안사는 아래 관련 법령을 충분히 이해하고, 이를 준수하기 위한 자원과 일정 계획을 프로젝트 Scope에 반영해야 한다.

> 개인정보보호법, 정보통신망 이용촉진 및 정보보호 등에 관한 법률, 전자상거래 등에서의 소비자보호에 관한 법률, 전자금융거래법, 전자문서 및 전자거래 기본법, 전자서명법 등 (전자상거래·개인정보·결제 관련 법령, 발주사 확정 시점 최신 법령 기준)

② 카드 정보는 플랫폼에 저장하지 않고 PG사 토큰화로 처리하여 PCI-DSS 준수 범위를 최소화해야 한다.

③ 개인정보(휴대폰·SNS ID 등)는 암호화 저장해야 하며, 조회 화면에는 마스킹 기준을 적용해야 한다.

### 2.6 로그·모니터링 적용 가이드

① **Trace ID 체계**: `TRC-{YYYYMMDD}-{일련번호 8자리}` 형식으로 고객 요청 최초 진입 시 발급하며, HTTP Header `X-Trace-Id`로 전 서비스·외부 API 호출까지 전파해야 한다. 로그 출력 형식은 `[TraceID] [SpanID] [레벨] 메시지`를 따른다.

② **로그 레벨·보존 기간**

| 레벨 | 용도 | 운영 환경 수집 | 보존 기간 |
|---|---|---|---|
| ERROR | 시스템 오류·예외 | 수집 | 1년 |
| WARN | 재시도·임계치 근접 | 수집 | 1년 |
| INFO | 주요 비즈니스 이벤트 | 수집 | 1년 |
| DEBUG | 개발·디버깅 | 미수집(스테이징만) | 30일 |

③ **감사 로그**: 주문·결제·재고·가격·상품상태 변경은 변경 전/후 값·처리 주체·Trace ID와 함께 Append-only로 기록해야 하며, 개인정보 접근 이력은 AOP 기반으로 별도 자동 기록해야 한다.

④ **Outbox·DLQ 모니터링**: Outbox 이벤트는 PENDING/PROCESSING/PROCESSED/FAILED 상태로 관리하고, 최대 3회 재시도(즉시→30초→1분) 후 실패 시 DLQ 적재와 함께 운영팀에 즉시 알림해야 한다. Prometheus + Grafana로 Pod 리소스·Outbox 적체량을 모니터링하고 HPA 임계치(예: consumer Outbox PENDING 1,000건 초과)에 따라 자동 스케일 아웃해야 한다.

- 제안사가 제출하는 제안서와 모든 첨부 서류의 소유권과 사용권은 발주사에 귀속된다.

- 제안사가 제시한 하드웨어 및 시스템 소프트웨어에 대한 최종 검증·결정권은 발주사에 있다.
- 사업 일부 또는 전부가 변경·취소되는 경우 제안사는 이에 대해 이의를 제기할 수 없다.
- 제출기한까지 제안서를 제출하지 않을 경우 참여를 포기한 것으로 간주한다.

### 3.4 유의사항

- 본 사업은 발주사의 사정에 따라 연기되거나 취소될 수 있다.
- 프로젝트 관리자(PM)가 직접 제안 발표하는 것을 원칙으로 한다.
- 제공된 정보는 사전 승인 없이 외부로 유출하거나 본 제안 목적 이외로 사용할 수 없다.

- 제안 내용이 허위이거나 사실과 다르게 기재된 경우 평가 대상에서 제외되며, 계약 후에도 계약 파기 및 손해배상 청구의 대상이 될 수 있다.
- 본 제안 요청과 관련하여 발생하는 제반 비용은 제안사 부담으로 한다.

## 4. 제안서 작성 지침(작성 요령 상세)

### 4.1 제안의 개요

- 본 사업(러닝 전문 e커머스, 직매입+입점형 하이브리드 구조, 12개 도메인 Modular Monolith)에 대한 이해도가 충분히 드러나도록 기술한다.
- 제안사 판단 하에 의미 있는 버티컬 커머스·MSA 전환 관련 기술 동향을 제시할 수 있다.

### 4.2 제안사 소개

- 일반적인 회사 소개와 함께, 본 사업과 직접 관련되는 기술 인력(Spring Boot/Kotlin, Next.js, PostgreSQL, Elasticsearch, Kubernetes) 보유 현황을 제시한다.
- 커머스 플랫폼(특히 오픈마켓형·하이브리드형) 구축 실적을 상세히 기술한다.

### 4.3 제안 시스템 내용

**4.3.1 시스템 구축 전략**: 12개 도메인을 Modular Monolith로 우선 구현하고 2단계 MSA로 전환하는 단계적 전략과 수행 방법론을 제시한다.

**4.3.2 시스템 구축 범위**: 1.4장 구축 범위를 기준으로 구축 가능 범위와 제외 범위를 명확히 하고, 필요한 전제 사항(개발서버 인프라 제공 시점, 표준 산출물 템플릿 제공 등)을 제시한다.

**4.3.3 목표 시스템 아키텍처 구성 및 특징**: 2장에 기술된 아키텍처 원칙(Outbox Pattern, Event-driven, Nginx 접근 통제, K8s HPA)을 충분히 이해하고, 성능·확장성·보안을 고려한 아키텍처 구성도(애플리케이션·인터페이스·인프라)를 제시한다.

**4.3.4 시스템 구축 방안**: 2.2장 도메인별 기능 요건에 대한 업무 기능별 구현 방안을 상세히 제시한다.

**4.3.5 예상 Risk 및 해결/경감 방안**: Modular Monolith → MSA 전환, Outbox 기반 이벤트 정합성, 재고 선점·동시성 제어, 정산 재계산 로직 등 본 프로젝트 특유의 기술적·업무적 Risk를 유형별로 제시하고 대응 방안을 제시한다.

**4.3.6 제안 시스템 특성 및 기대효과**: 제안 시스템의 특장점과 기대효과(성능·운영 효율화 등)를 가능한 계량화하여 제시한다.

### 4.4 프로젝트 관리 부문

- 진척·변경·품질 관리를 위한 전략과 관리 도구를 제시한다.
- 제안하는 업무 범위에 대한 전체 추진 일정 및 프로토타입→본개발 단계별 세부 일정을 제시한다.
- 프로젝트 수행 조직 구성과 분야별(백엔드/프론트엔드/인프라/QA) 업무 분장을 상세히 제시한다.
- 2.7장 표준 산출물 목록을 기준으로 단계별 중간·최종 산출물의 종류, 제출 시기, 형태를 제시한다.
- 품질관리 절차와 프로젝트 보고·검토 계획을 제시한다.
- 보안 요구사항(2.5장)에 따른 보안 관리 계획을 제시한다.

### 4.5 지원 부문

- 개발환경(로컬/개발서버/스테이징/운영 프로파일) 구축에 있어 발주사·제안사의 역할을 구분하여 제시한다.
- 프로젝트 수행 이후 안정적 운영을 위한 기술 이전·운영팀 인수인계 계획을 제시한다(운영매뉴얼 백로그 반영).
- 무상·유상 유지보수 범위·기간·조건, 시스템 개발 소스의 소유권 및 사용 범위를 제시한다.

### 4.6 제안 가격(별도 제출)

- 제안 내용에 포함된 모든 서비스·솔루션에 대한 가격을 포함하여 제시한다.
- H/W·S/W·서비스 등 분야별, 프로토타입·본개발 단계별 제안 가격을 구분하여 제시한다.
- 가격 산출 근거(인력 투입 공수, 라이선스 비용 등)를 상세히 제시한다.
- 부가세 별도 금액으로 작성한다.
