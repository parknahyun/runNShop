## 1. 시스템 아키텍처 정책

### 1.0 설계 원칙

플랫폼 설계는 아래 6개 원칙을 기반으로 한다. 원래 MSA + Kafka 스펙에서 Modular Monolith + Outbox Pattern으로 변경하였으나 설계 원칙은 동일하게 유지한다.

| # | 원칙 | 구현 방식 |
|---|------|----------|
| 1 | **도메인 중심 아키텍처** | 12개 업무 도메인 기반 Bounded Context 설계 |
| 2 | **Runtime 선택 실행 가능 구조** | Frontend·Backend·Consumer·Batch 로컬·개발서버 선택 실행 |
| 3 | **운영 안정성 우선** | Outbox Pattern + 재시도 3회 + DLQ + 모니터링 |
| 4 | **Event-driven Architecture** | Outbox + Spring Event Consumer → 2단계 Kafka 전환 |
| 5 | **독립 배포 가능 구조** | 모듈 단위 설계 → 2단계 K8s 독립 배포 |
| 6 | **Spec 기반 개발 프로세스** | AI 9대 공정 기반 Spec → 코드 생성 흐름 |

#### Runtime 선택 실행 구조

DB·Redis·Elasticsearch는 개발서버 공용 인프라로만 제공한다. 로컬은 애플리케이션(Frontend·Backend·Consumer·Batch)만 실행하며, 개발 착수 전 프레임워크가 필수 인프라 접속 환경을 제공해야 한다.

| 컴포넌트 | 로컬 (Local) | 개발서버 (Dev) |
|---------|------------|--------------|
| Frontend | ✅ 로컬 실행 | ✅ 개발서버 실행 |
| Backend API | ✅ 로컬 실행 | ✅ 개발서버 실행 |
| Consumer | ✅ 로컬 실행 | ✅ 개발서버 실행 |
| Batch | ✅ 로컬 실행 | ✅ 개발서버 실행 |
| PostgreSQL | ❌ 로컬 미제공 | ✅ 개발서버 공용 |
| Redis | ❌ 로컬 미제공 | ✅ 개발서버 공용 |
| Elasticsearch | ❌ 로컬 미제공 | ✅ 개발서버 공용 |

#### 로컬 실행 구조

```
프로토타입 환경 (prototype 프로파일)
    ├─ Frontend    (localhost:3000~3002)  → Backend Mock API
    └─ Backend     (localhost:8080)       → Mock JSON 반환 (DB·Redis·ES 미사용)

본개발 환경 (local 프로파일)
    ├─ Frontend    (localhost:3000~3002)  ─┐
    ├─ Backend     (localhost:8080)       ─┤→ 개발서버 PostgreSQL
    ├─ Consumer    (로컬 프로세스)         ─┤→ 개발서버 Redis
    └─ Batch       (로컬 수동 실행)       ─┘→ 개발서버 ES
```

#### 프로파일 구성 기준

| 프로파일 | 용도 | 인프라 |
|---------|------|--------|
| `prototype` | 프로토타입 개발 | Mock JSON (DB·Redis·ES 미사용) |
| `local` | 로컬 개발·검증 | 개발서버 인프라 연결 |
| `dev` | 개발서버 전체 실행 | 개발서버 인프라 |
| `staging` | 스테이징 검증 | 스테이징 인프라 |
| `prod` | 운영 | 운영 인프라 |

> 프로토타입 단계에서는 `prototype` 프로파일로 실행하며, DB·Redis·ES 없이 Mock JSON만으로 동작한다.

#### 개발 착수 전 필수 제공 항목

프레임워크가 개발 착수 전 아래 항목을 완료 상태로 제공한다.

| 항목 | 제공 주체 |
|------|----------|
| 개발서버 PostgreSQL·Redis·ES 접속 정보 | 인프라팀 |
| `application-local.yml` 템플릿 | 프레임워크 |
| `.env.example` 파일 | 프레임워크 |
| 초기 DB DDL 스크립트 | 프레임워크 |
| 초기 ES 인덱스 매핑 스크립트 | 프레임워크 |
| VPN / 허용 IP 설정 | 인프라팀 |

#### 개발 착수 체크리스트

```
□ 개발서버 PostgreSQL 접속 확인
□ 개발서버 Redis 접속 확인
□ 개발서버 ES 접속 확인
□ application-local.yml 템플릿 제공
□ .env.example 파일 제공
□ 초기 DDL 스크립트 실행 완료
□ 초기 ES 인덱스 생성 완료
□ VPN / IP 허용 설정 완료
□ 로컬 Backend 기동 확인
□ 로컬 Consumer 기동 확인
```

### 1.2 이벤트 처리 정책

#### 이벤트 처리 방식

| 단계 | 방식 | 비고 |
|------|------|------|
| 1단계 (Monolith) | Outbox Pattern + Spring Event Consumer | Kafka 없음. 인프로세스 Consumer |
| 2단계 (Hybrid MSA) | Kafka + Debezium CDC | Outbox 테이블 → Kafka 자동 전환 |
| 3단계 (Full MSA) | Kafka | 전 도메인 브로커 기반 |

#### Outbox Pattern 기반 이벤트 처리 (1단계)

모듈 간 비동기 이벤트는 **Transactional Outbox Pattern + Spring Event Consumer**로 처리한다.

```
[저장] 비즈니스 로직 + Outbox 테이블 저장 → 단일 DB 트랜잭션
[감시] Outbox Consumer (상시 대기 스레드)가 PENDING 레코드 즉시 감지
[처리] Spring @EventListener + @Async → 수신 모듈 Consumer에 전달
[완료] 성공/실패 상태 업데이트
```

#### 배치 vs Consumer 처리 방식 비교

| 항목 | 배치 (Polling) | Consumer (채택) |
|------|--------------|----------------|
| 실행 방식 | 주기적 실행 (N초 간격) | 상시 대기·즉시 처리 |
| 처리 지연 | 폴링 주기만큼 지연 | 거의 즉시 |
| Kafka 필요 | 없음 | 없음 (인프로세스) |

#### Outbox 테이블 상태값

| 상태 | 설명 |
|------|------|
| `PENDING` | 처리 대기 중 |
| `PROCESSING` | Consumer 처리 중 |
| `PROCESSED` | 처리 완료 |
| `FAILED` | 최종 실패 (운영팀 이관) |

#### 재시도 및 실패 처리

| 항목 | 기준 |
|------|------|
| 재시도 횟수 | 최대 3회 |
| 재시도 간격 | 즉시 → 30초 → 1분 (점진적 백오프) |
| 최종 실패 시 | `FAILED` 상태 전환 + 운영팀 알림 + 수동 처리 |
| 프로세스 중단 복구 | 재기동 시 `PENDING`·`PROCESSING` 레코드 자동 재발행 |

#### 2단계 MSA 전환 시 연결

```
1단계: Outbox Consumer (인프로세스 상시 감시)
    ↓
2단계: Debezium CDC가 Outbox 테이블 변경 감지
       → Kafka Topic 자동 발행
       → Kafka Consumer로 전환
       → 코드 변경 없이 브로커 교체
```

### 1.3 시스템 진화 정책

| 단계 | 아키텍처 | 배포 | 조건 |
|------|----------|------|------|
| 1단계 (기본) | Modular Monolith + Event-Driven | Docker Compose | 런칭 시점 |
| 2단계 | Hybrid MSA | Kubernetes (Pod 설계 완성 시) | 트래픽·도메인 복잡도 증가 시 |
| 3단계 | Full MSA | Kubernetes 전면 운영 | 서비스 안정화 및 팀 규모 성장 후 |

#### 1단계 — Docker Compose 운영

```
컨테이너 구성 (4개)
    ├─ backend-api   (Spring Boot)
    ├─ consumer      (Spring Boot)
    ├─ batch         (Spring Boot)
    └─ frontend      (Next.js)

스케일 아웃: 수동 (docker-compose scale)
Load Balancing: 수동 설정
```

#### 2단계 — Kubernetes 도입 기준

Kubernetes 도입은 **컨테이너 수**가 아닌 **Pod 설계 완성** 시점에 결정한다.

```
Pod 설계 완성 기준
    ├─ 분리할 도메인 서비스 확정
    ├─ Pod별 스케일 정책 정의
    ├─ Pod 간 네트워크 통신 방식 확정
    └─ Pod별 리소스 할당 기준 정의
```

#### 자동 스케일 아웃 (K8s HPA)

Prometheus가 Pod 리소스 사용률을 수집하고 HPA가 자동으로 Pod를 증감한다.

```
Prometheus → Pod 사용률 수집
    ↓
HPA → 임계치 비교
    ↓
초과 시 → Pod 자동 추가 + Load Balancer 자동 연결
이하 시 → Pod 자동 감소
```

#### 도메인별 스케일 아웃 기준 (2단계 예시)

| Pod | 주요 지표 | 임계치 |
|-----|---------|--------|
| backend-api | CPU 사용률 | 70% 초과 |
| consumer | Outbox PENDING 건수 | 1,000건 초과 |
| payment | CPU + HTTP 요청 수 | CPU 60% or 초당 500건 |
| batch | 메모리 사용률 | 80% 초과 |
| frontend | CPU 사용률 | 70% 초과 |

#### Prometheus + Grafana 연동

| 도구 | 역할 |
|------|------|
| Prometheus | Pod 리소스 사용률 수집·HPA 메트릭 제공·알림 발송 |
| Grafana | Pod별 CPU·메모리·요청수 대시보드·스케일 아웃 이력 시각화 |

## 2. 플랫폼 운영 정책

### 2.1 운영 방식

플랫폼은 **직매입(DIRECT)**과 **입점형(VENDOR)**의 하이브리드 구조로 운영한다.

### 2.2 입점 유형 정의

| 구분 | 직매입 (DIRECT) | 입점형 (VENDOR) |
|------|----------------|----------------|
| 재고 소유 | 플랫폼 | 입점사 |
| 출고 주체 | 플랫폼 물류 | 입점사 직접 |
| 가격 결정 | 플랫폼 MD | 입점사 (최저가 유지 요구 정책 적용) |
| 정산 방식 | 매입가 기준 내부 정산 | 판매가 기준 수수료 차감 |
| CS 1차 대응 | 플랫폼 | 플랫폼 (이행은 입점사) |
| 주요 리스크 | 재고 부담 | 이행 품질 부담 |

### 2.2-1 직매입 기초 데이터 설정

- 플랫폼 직매입 전용 입점사 계정을 시스템 기초 데이터로 생성
- vendor_id = 1 예약 (시스템 고정값)
- vnd_vendor.is_platform_direct = TRUE
- 정산 계산 대상에서 제외 (내부 정산 처리)
- 상품 등록·심사·배송·클레임은 플랫폼 어드민에서 처리

### 2.3 단일 공급 원칙 (1 Product : 1 Supplier)

- 동일 상품(`product_id`)은 직매입·입점형 구분 없이 **단일 공급 주체만 허용**한다.
- 플랫폼 직매입과 입점사 공급이 동시에 존재할 수 없다.
- 공급 주체 변경 시 기존 계약 종료 후 신규 등록으로 처리한다.
- 상품 등록 시 `supplier_id` 기준 중복 체크로 중복 공급을 차단한다.

### 2.4 상품 등록 권한

| 항목 | 직매입 | 입점형 |
|------|--------|--------|
| 상품 등록 | 플랫폼 MD | 입점사 BO |
| 가격 수정 | 플랫폼 MD | 입점사 BO (최저가 유지 요구 정책 범위 내) |
| 재고 수정 | 플랫폼 WMS | 입점사 BO |
| 노출 관리 | 플랫폼 어드민 | 공동 (플랫폼 최종 승인) |

### 2.5 입점 자격 기준

- 입점 가능 사업자 유형: 법인·개인사업자·브랜드 직영
- 러닝 전문 카테고리 적합성 기준 충족 (러닝화·의류·기어·보충제·웨어러블 등)
- 브랜드 정품 인증 요건 충족
- 최소 상품 수 및 월 거래 가능 물량 기준 충족

### 2.6 입점 심사 프로세스

신청 → 서류 검토 → 상품 적합성 심사 → 계약 → 입점

- 심사 기간: 영업일 기준 7일 이내
- 결과 통보: 심사 완료 후 1영업일 이내
- 재심사 조건: 거절 사유 해소 후 30일 이후 재신청 가능

**입점사 상태 전이**

```
신청 → 서류검토 → 심사중 → 계약체결 → 운영중
                         ↓
                       거절 → (재신청)
```

### 2.7 입점 계약 조건

| 항목 | 기준 |
|------|------|
| 계약 기간 | 1년 (기본), 만료 30일 전 미해지 시 자동 갱신 |
| 계약 형태 | 전자계약 (공인전자서명 기반) |
| 독점 공급 | 기본 비독점, 브랜드 독점 계약 별도 협의 |
| 최저가 유지 요구 | 타 채널 대비 낮은 가격 인지 시 가격 인상 요구권 행사. 미수용 시 플랫폼 임의 행사 제외 가능. 고객 보상 없음 |

### 2.8 입점사 등급 체계

입점사 등급은 **고객 회원 등급과 동일한 4단계 명칭**을 사용한다.

#### 등급 구분

| 등급 | 명칭 | 진입 조건 |
|------|------|----------|
| 1 | 신규 (New) | 입점 후 3개월 미만 또는 기준 미달 |
| 2 | 일반 (Runner) | 60점 이상 + 월 거래액 100만원 이상 |
| 3 | 우수 (Pacer) | 75점 이상 + 월 거래액 500만원 이상 |
| 4 | 프리미엄 (Elite) | 90점 이상 + 월 거래액 2,000만원 이상 |

#### 등급 산정 기준 (월 1회 자동 산정)

| 지표 | 가중치 | 측정 기준 |
|------|--------|----------|
| 월 거래액 | 40% | 최근 3개월 평균 구매확정 거래액 |
| 주문 이행률 | 30% | 정상 출고 건수 / 전체 주문 건수 |
| 클레임율 | 20% | 클레임 건수 / 전체 주문 건수 (낮을수록 유리) |
| 리뷰 평점 | 10% | 최근 3개월 평균 별점 |

#### 등급별 혜택

| 혜택 항목 | 신규 | 일반 | 우수 | 프리미엄 |
|-----------|------|------|------|----------|
| 수수료 감면 | 0% | -1% | -2% | -3% |
| 정산 주기 | 익월 15일 | 익월 15일 | 익월 10일 | 익월 5일 |
| 노출 우선순위 | 기본 | 기본 | 우선 | 최우선 |
| 전담 MD 배정 | X | X | O | O |
| 광고 크레딧 | X | X | 월 10만원 | 월 30만원 |
| 챌린지 공식 스폰서 | X | X | X | O |

#### 등급 운영 기준

- **산정 주기**: 매월 1일 전월 데이터 기준 자동 갱신
- **하향 유예**: 등급 하향 시 1개월 유예 후 적용
- **신규 보호**: 입점 후 3개월간 등급 하향 없음
- **이의신청**: BO를 통해 7일 이내 신청, 14일 이내 결과 통보

### 2.9 입점 제한 및 퇴점 정책

- 판매 금지 상품: 모조품, 미인증 건강기능식품 등
- 운영 기준 미달 시: 경고 → 판매 중지 → 강제 퇴점 단계 적용
- 퇴점 시 진행 중인 주문·정산·재고는 별도 기준에 따라 처리

### 2.10 직매입 전환 프로세스

#### 전환 원칙

- 입점형 상품의 직매입 전환은 **입점 계약과 무관하게 상품 단위**로 처리한다.
- 입점사는 계약을 유지한 채 해당 상품만 판매 종료하며, 플랫폼은 직매입 신규 상품으로 등록한다.
- 직매입 전환 상품은 **신규 `product_id`를 발번**한다.

#### 전환 트리거 유형

| 유형 | 트리거 | 주도 주체 |
|------|--------|----------|
| 전략적 전환 | 플랫폼이 직매입 전환 대상으로 지정 | 플랫폼 MD |
| 계약 종료 전환 | 입점사 계약 만료·해지 후 직매입 유지 결정 | 플랫폼 MD |
| 강제 전환 | 입점사 운영 기준 미달·퇴점 후 상품 유지 필요 | 플랫폼 운영팀 |

#### 전환 단계별 프로세스

| 단계 | 내용 | 처리 주체 |
|------|------|----------|
| Step 1. 전환 협의 | 전환 대상 상품 지정 및 입점사 통보 (최소 14일 전), 매입가·재고 처리 방식 협의 | 플랫폼 MD |
| Step 2. 판매 종료 | 대상 상품 신규 주문 차단, 진행 중 주문은 입점사 계속 이행, 입점사 계약 유지 | 플랫폼 운영팀 |
| Step 3. 재고 처리 | [경로A] 재고 인수: 실사 → 매입가 협의 → 플랫폼 입고 / [경로B] 재고 소진: 입점사 자체 소진 후 직매입 발주 | 플랫폼 MD / 입점사 |
| Step 4. 신규 등록 | 직매입 신규 상품 등록 (product_id 신규 발번), 1 Product : 1 Supplier 원칙 적용 | 플랫폼 MD |

#### 데이터 승계 처리

| 데이터 항목 | 승계 여부 | 처리 방식 |
|------------|----------|----------|
| 리뷰·평점 | 미승계 (원칙) | 신규 상품이므로 미승계. 운영 정책으로 별도 허용 가능 |
| 판매 통계 | 미승계 | 입점형 이력은 별도 보존 |
| 상품 이미지·설명 | 협의 | 저작권 확인 후 재사용 또는 재제작 |
| 가격 | 미승계 | 플랫폼 직매입가로 신규 설정 |

#### 콘텐츠 저작권 처리 기준

| 콘텐츠 유형 | 저작권 귀속 | 처리 방식 |
|------------|-----------|----------|
| 입점사 자체 촬영 이미지 | 입점사 | 사용 시 입점사 서면 동의 필수. 미동의 시 플랫폼 재촬영 |
| 브랜드 공식 제공 이미지 | 브랜드사 | 브랜드사 직접 사용 허가 확인 후 재사용 가능 |
| 입점사 작성 상품 설명 | 입점사 | 사용 시 입점사 서면 동의 필수. 미동의 시 플랫폼 재작성 |
| 브랜드 공식 제공 설명 | 브랜드사 | 브랜드사 허가 확인 후 재사용 가능 |
| 고객 리뷰 이미지·텍스트 | 고객 | 직매입 신규 상품으로 미승계 (원칙) |

콘텐츠 사용 동의 여부는 전환 협의(Step 1) 시 동시에 협의하며, 미동의 시 플랫폼이 자체 재제작하고 비용은 플랫폼이 부담한다.

## 3. 상품 관리 정책

### 3.1 상품 상태 정의

#### 상태값

| 상태 | 코드 | 설명 |
|------|------|------|
| 임시저장 | `DRAFT` | 등록 중, 미제출 |
| 심사요청 | `REVIEW_REQUESTED` | 입점사 제출 완료 |
| 심사중 | `UNDER_REVIEW` | 플랫폼 검토 중 |
| 판매중 | `ON_SALE` | 정상 판매 |
| 품절 | `SOLD_OUT` | 재고 0 또는 수동 설정 |
| 판매종료 | `DISCONTINUED` | 영구 판매 중단 |
| 반려 | `REJECTED` | 심사 탈락 |

#### 상태 전이 규칙

```
DRAFT → REVIEW_REQUESTED → UNDER_REVIEW → ON_SALE
                                        ↓
                                    REJECTED → DRAFT (재심사 허용)

ON_SALE   ──→ SOLD_OUT   : 재고 0 시 자동 전환
SOLD_OUT  ──→ ON_SALE    : 주문취소로 재고 복구 시 자동 전환
SOLD_OUT  ──→ SOLD_OUT   : 반품·교환으로 재고 복구 시 상태 유지
SOLD_OUT  ──→ ON_SALE    : 담당자 수동 변경만 허용

ON_SALE / SOLD_OUT → DISCONTINUED : 수동 판매종료
```

#### 재고-상태 연동 규칙

| 이벤트 | 재고 변화 | 상태 변화 | 처리 주체 |
|--------|----------|----------|----------|
| 주문 발생 | -1 | 재고 = 0 이면 `SOLD_OUT` 자동 전환 | 시스템 |
| 주문 취소 | +1 | `SOLD_OUT` → `ON_SALE` 자동 전환 | 시스템 |
| 반품 확정 | +1 | 상태 변화 없음 (`SOLD_OUT` 유지) | 시스템 (재고만) |
| 교환 확정 | ±0 | 상태 변화 없음 | 시스템 |
| 담당자 수동 | 무관 | `SOLD_OUT` → `ON_SALE` 전환 가능 | 담당자 |
| 입점사 재고 등록 | +N | 상태 변화 없음 (담당자 확인 후 수동 전환) | 입점사 → 담당자 |

#### 반려 재심사 프로세스

- 반려 시 반려 사유를 입점사 BO에 명시한다.
- 재심사 횟수 제한 없음. 단, 동일 사유 반복 반려 3회 시 입점 심사팀 에스컬레이션한다.
- 재제출 가능 기간: 반려일로부터 30일 이내 (초과 시 `DRAFT` 자동 삭제)

### 3.2 카테고리 정책

#### 계층 구조

**단일 계층 (대분류만)** 운영. 중·소분류 없이 대분류 단위로 관리한다.

| 코드 | 대분류명 | 수수료율 | 비고 |
|------|---------|---------|------|
| `CAT_001` | 러닝화 | 8% | |
| `CAT_002` | 러닝 의류 | 12% | |
| `CAT_003` | 러닝 기어·액세서리 | 15% | |
| `CAT_004` | 보충제·영양식품 | 10% | 건강기능식품 별도 심사 |
| `CAT_005` | 웨어러블·디바이스 | 8% | |

#### 운영 기준

- 상품은 대분류 1개에만 귀속. 다중 카테고리 미허용
- 검색·필터 세분화는 카테고리 대신 태그·속성 기반으로 운영

#### 카테고리별 필수 입력 속성

| 대분류 | 필수 속성 |
|--------|----------|
| 러닝화 | 브랜드, 성별, 사이즈(mm), 드롭(mm), 용도(로드/트레일/트랙) |
| 러닝 의류 | 브랜드, 성별, 사이즈, 소재, 용도(상의/하의/이너/아우터) |
| 러닝 기어·액세서리 | 브랜드, 용도 분류 |
| 보충제·영양식품 | 브랜드, 제품 유형, 용량, 인증 여부(건강기능식품/일반식품) |
| 웨어러블·디바이스 | 브랜드, 호환 OS, 주요 기능 |

### 3.3 가격 정책

#### 가격 구조

```
정가 (소비자가) ≥ 판매가 (할인 적용) ≥ 입점사 공급가 (정산 기준)
```

| 가격 유형 | 코드 | 설명 | 결정 주체 |
|----------|------|------|----------|
| 정가 | `price_original` | 소비자 기준 공식 가격. 할인 전 표시 기준 | 입점사 / 플랫폼 MD |
| 판매가 | `price_sale` | 실제 결제 기준 가격. 할인 쿠폰·프로모션 적용 전 기준 | 입점사 / 플랫폼 MD |
| 입점사 공급가 | `price_supply` | 정산 계산 기준 가격. 고객에게 미노출 | 입점사 |

#### 가격 운영 기준

- 정가 표시는 의무. 판매가가 정가보다 낮은 경우 할인율을 표시한다.
- 판매가는 정가 이하로만 설정 가능하다.
- 입점사 공급가는 판매가 이하로만 설정 가능하다.
- 최저가 유지 요구 정책: 타 채널 대비 낮은 가격 인지 시 플랫폼이 입점사에 가격 인상 요구 가능. 미수용 시 해당 상품을 프로모션·기획전·노출 우선순위에서 임의 제외 가능. 고객 대상 보상 없음
- 가격 변경 이력은 시스템이 자동 보존한다.

### 3.4 SKU 정책

#### SKU 구조

```
상품(Product)
  └─ 옵션그룹1: 색상 (예: 블랙, 화이트, 레드)
       └─ 옵션그룹2: 사이즈 (예: 250, 255, 260)
            └─ SKU (재고·가격 관리 단위)
```

- 옵션은 최대 **2 depth** (색상 + 사이즈)
- 옵션그룹 순서: 1depth 색상, 2depth 사이즈 권장 (입점사 자율 설정 가능)
- SKU별 개별 가격 설정 **미허용**. 가격은 상품 단위로 통일
- SKU별 재고는 개별 관리

#### 옵션 미사용 상품

옵션이 없는 단일 상품(예: 보충제 단일 용량)은 옵션그룹 없이 상품 단위로 재고 관리한다.

### 3.5 상품 노출 정책

#### 운영 방식

| 단계 | 방식 | 조건 |
|------|------|------|
| 1단계 (기본) | MD 수동 노출 순서 설정 | 런칭 시점 |
| 2단계 | AI 스코어링 배치 추가 → 자동화 추천 전환 | 운영 안정화 후 |

#### 노출 우선순위 로직

```
exposure_priority = COALESCE(md_override, ai_score, default_order)
```

- **md_override**: MD가 수동으로 설정한 노출 순서. 항상 최우선 적용
- **ai_score**: AI 스코어링 배치가 산출한 추천 점수. 1단계에서는 NULL
- **default_order**: md_override·ai_score 모두 없을 경우 최신 등록순 적용

#### 설계 원칙

- 노출 로직은 처음부터 **플러그인 구조**로 설계하여 2단계 전환 시 기존 코드 수정 없이 배치만 추가
- MD 수동 설정값은 AI 점수보다 항상 우선 적용 (MD Override 원칙)
- 2단계 AI 스코어링 배치 산정 기준 (예정): 판매량·리뷰 평점·클릭률·재고 상태·회원 구매 이력

#### MD 수동 운영 항목 (1단계)

| 항목 | 설명 |
|------|------|
| 메인 기획전 | 메인 화면 배너·기획전 상품 수동 편집 |
| 카테고리 추천 상품 | 카테고리별 상단 노출 상품 MD 지정 |
| 신상품 노출 | 신규 등록 상품 상단 고정 기간 설정 |
| MD 추천 | MD 큐레이션 상품 수동 선정 |
| 광고 상품 | 입점사 광고 계약 기반 노출 위치 수동 설정 |

#### 행사 제외 처리 기준

최저가 유지 요구 미수용 시 플랫폼은 해당 상품을 아래 항목에서 임의 제외할 수 있다.

- 메인 기획전·특가 행사 노출
- 카테고리 추천 상품 노출
- 프로모션 대상 상품
- 노출 우선순위 우대 적용

> 행사 제외는 일반 판매 중단이 아니며, 상품 상태(`ON_SALE`)는 유지된다.

### 3.6 배송 정책 (Vendor Shipping Policy)

- 주문 배송비는 **상품 단위가 아닌 입점사 단위**로 부과한다.
- 동일 입점사의 상품은 배송 정책에 따라 **묶음배송**을 적용한다.
- 무료배송 기준은 입점사 자율 설정 (플랫폼 권고: 5만원 이상)
- 반품 배송비는 귀책 주체(고객 귀책 / 입점사 귀책)에 따라 부담 주체를 구분한다.

### 3.7 시즌·행사 가격 정책

#### 운영 방식

모든 행사 가격은 MD가 직접 설정·관리한다.

#### 행사 가격 유형

| 유형 | 설명 | 설정 주체 |
|------|------|----------|
| 기간 한정 할인 | 특정 기간 동안 판매가 일시 인하 | MD / 입점사 |
| 시즌 세일 | 봄·여름·가을·겨울 시즌 전환기 할인 | MD |
| 특가 기획전 | MD 기획 특가 묶음 행사 | MD |
| 입점사 자체 행사 | 입점사가 직접 신청·운영하는 할인 | 입점사 → MD 승인 |
| 플랫폼 공동 행사 | 플랫폼·입점사 공동 부담 할인 | MD 기획 + 입점사 동의 |

#### 가격 설정 기준

- 행사 판매가는 정가 이하로만 설정 가능
- 행사 판매가는 입점사 공급가 이상으로만 설정 가능
- 행사 기간 중 가격 변경은 MD 승인 필수
- 행사 종료 후 판매가는 행사 전 가격으로 자동 복원

#### 행사 기간 운영 기준

| 항목 | 기준 |
|------|------|
| 최소 행사 기간 | 1일 |
| 최대 행사 기간 | 90일 |
| 행사 등록 마감 | 행사 시작 1영업일 전까지 |
| 중복 행사 | 동일 상품에 복수 행사 중복 적용 불가 |
| 행사 조기 종료 | MD 수동 종료 가능, 즉시 가격 복원 |

#### 최저가 유지 요구 정책 연동

- 행사 가격 적용 중 타 채널에서 낮은 가격 인지 시 플랫폼은 입점사에 가격 인상 요구권 행사
- 미수용 시 해당 상품을 행사에서 임의 제외 가능
- 고객 대상 최저가 보상 없음

#### 사후 처리 정책

심사 시점에 판별 불가한 경우가 있으므로, 판매 중 발견 시에도 즉시 처리 가능한 사후 정책을 운영한다.

| 발견 경로 | 처리 기준 |
|----------|----------|
| 심사 단계 발견 | 즉시 반려 (`REJECTED`) |
| 판매 중 내부 발견 | 즉시 판매 중단 → 정산 보류 → 사실 확인 후 처리 |
| 고객 분쟁으로 확인 | 분쟁 종결 후 판매 중단 + 해당 거래 정산 처리 |

#### 고객 분쟁으로 판매불가 확인 시 프로세스

```
고객 분쟁 접수
    ↓
플랫폼 1차 검토 → 판매 금지 상품 해당 여부 판단
    ↓
[판매 금지 확인]
    ├─ 해당 상품 즉시 판매 중단 (DISCONTINUED)
    ├─ 분쟁 건 환불 처리 (플랫폼 선처리)
    ├─ 해당 거래 정산 보류
    ├─ 입점사에 사실 통보 및 소명 요청
    └─ 소명 결과에 따라 정산 처리
```

#### 정산 처리 기준

> **판매 금지 품목은 발견 경로·귀책 주체와 무관하게 정산 대상에서 제외한다.**

| 귀책 | 정산 처리 | 추가 조치 |
|------|----------|----------|
| 입점사 귀책 | 정산 미지급 + 환불 비용 입점사 부담 | 경고 또는 강제 퇴점 |
| 플랫폼 귀책 (심사 오류) | 정산 미지급 + 환불 비용 플랫폼 부담 | 내부 심사 프로세스 개선 |
| 귀책 불분명 | 정산 미지급. 환불 비용 귀책 협의 후 결정 | — |

#### 반복 발생 시 제재

- 동일 입점사 2회 이상 확인 시: 입점사 등급 하향 및 경고
- 동일 입점사 3회 이상 확인 시: 강제 퇴점 처리

### 3.10 화면별 할인가 노출 정책

| 그룹 | 해당 화면 |
|------|---------|
| A — 상품목록 | 상품목록·검색결과·관심상품·카테고리·기획전·메인추천 |

#### 그룹별 노출 기준

| 항목 | 그룹 A | 그룹 B (비로그인) | 그룹 B (로그인) | 그룹 C | 그룹 D |
|------|--------|----------------|--------------|--------|--------|
| 정가 | ✅ 취소선 | ✅ | ✅ | ✅ | ✅ |

| 장바구니 할인 | ❌ | ❌ | ❌ | ✅ | 항목 구분 |
| 포인트 사용 | ❌ | ❌ | ❌ | ❌ | 항목 구분 |

#### 주문서 할인 항목 구분 표시 예시

```
정가 합계            120,000원
- 행사가 할인         -10,000원
- 공개 쿠폰 할인       -5,000원
- 회원 등급 할인        -1,980원
- 보유 쿠폰 할인        -3,000원
- 장바구니 할인         -3,000원
- 포인트 사용           -2,000원
+ 배송비                3,000원
─────────────────────────────────
최종 결제가            98,020원
```

#### 가격 역전 안내 정책

수량 소진으로 행사가 종료 시 상품목록 가격 > 상품상세 가격 역전 발생.

| 케이스 | 안내 방식 |
|--------|---------|
| 상세 진입 시 행사가 소진 | 상세 화면 상단 안내 배너 |
| 상세 체류 중 행사가 소진 | 실시간 가격 변경 + 토스트 알림 |
| 장바구니 담은 후 소진 | 장바구니 가격 변경 안내 |
| 주문서 진입 후 소진 | 주문서 가격 재확인 요청 (고객 확인 필수) |

### 3.11 수량 할인 정책

#### 수량 할인 적용 조건 (3가지 모두 충족)

- MD가 수량 할인 행사로 설정한 상품
- 동일 입점사 (`vendor_id` 동일)
- 동일 판매가 (`price_sale` 동일)

#### 수량별 차등 할인 구조

```
QuantityDiscount
    ├─ event_id         행사 ID
    ├─ vendor_id        입점사
    ├─ product_ids      행사 설정 상품 목록 (MD 지정)
    ├─ min_quantity     최소 수량
    ├─ max_quantity     최대 수량 (null = 상한 없음)
    ├─ discount_rate    할인율
    ├─ start_at / end_at
    └─ status           ACTIVE / ENDED
```

#### 수량 변경 시 재계산 기준

- 장바구니에서 수량 변경 시 그룹 전체 재계산
- 그룹 내 다른 상품 할인율도 변경될 수 있음
- 예) 3개(30%) → 2개로 변경 → 그룹 수량 3→2 → 할인율 30%→13% 전체 재계산

### 3.12 전시 페이지 상태 정책

| 상태 | 설명 |
|------|------|
| DRAFT | 최초 작성 중 |
| DRAFT_EDIT | PUBLISHED 페이지 수정 중 (2세트 구조, 고객 화면 영향 없음) |
| PUBLISHED | 고객 화면 노출 중 |
| SCHEDULED | 예약 전환 대기 중 |
| RESERVED | 예약 전환으로 교체된 이전 버전 |
| CLOSED | 종료 |
| CANCELLED | 예약 취소 |

- PUBLISHED 수정 시 DRAFT_EDIT 행 별도 생성 (최대 2세트 유지)
- 예약 페이지(SCHEDULED) 수정 필요 시 예약 취소(CANCELLED) 후 재등록
- 페이지당 예약 1개만 허용 (조건부 유니크 인덱스)
- 미리보기: preview_token 발급 (Redis TTL 30분), 고객 화면 기준 렌더링

## 4. 회원 관리 정책

### 4.1 일반 회원

- **가입 방식**: 이메일 or SNS (네이버·Apple)
- **필수 수집 항목**: 이름·이메일
- **본인인증**: 가입 시 옵션널. 단, 주문 시 휴대폰 본인인증 필수 (세션 기준 1회). 동일 번호 중복 가입 불가
- **선택 수집 항목**: 러닝 경력·주 훈련 거리·착용 신발 사이즈·선호 브랜드
- **탈퇴 처리**: 즉시 탈퇴 처리, 거래 데이터는 관련 법령에 따라 보존

### 4.2 SNS 회원

- **지원 채널**: 네이버·Apple (1단계 런칭 기준)
- **최초 로그인 시**: 추가 정보(휴대폰·생년월일) 입력 필수
- **SNS 연동 해제 시**: 이메일 계정으로 자동 전환

### 4.3 회원 등급 체계

입점사 등급과 동일한 4단계 명칭을 사용한다.

#### 등급 구분

| 등급 | 명칭 | 진입 조건 |
|------|------|----------|
| 1 | New | 가입 후 기준 미달 |
| 2 | Runner | 누적 구매 100만원 이상 + 활동지수 10점 이상 |
| 3 | Pacer | 누적 구매 200만원 이상 + 활동지수 20점 이상 |
| 4 | Elite | 누적 구매 300만원 이상 + 활동지수 30점 이상 |

> 등급 기준: 누적 구매금액 100만원 단위 + 커뮤니티 활동지수 10단위 합산

#### 활동지수 산정 기준

| 활동 | 지수 |
|------|------|
| 구매 인증 리뷰 작성 | +2 |
| 러닝 기록 공유 | +1 |
| 크루 활동 참여 | +1 |
| 챌린지 완료 | +3 |
| QnA 답변 채택 | +2 |

#### 등급별 혜택

| 혜택 항목 | New | Runner | Pacer | Elite |
|-----------|-----|--------|-------|-------|
| 기본 할인율 | 없음 | 없음 | 없음 | 없음 |
| 무료배송 기준 | 5만원 이상 | 3만원 이상 | 2만원 이상 | 무조건 무료 |
| 등급 승급 쿠폰 | 0장 | 1장 | 2장 | 3장 |
| 연말 등급 쿠폰 (12/31) | 0장 | 1장 | 2장 | 3장 |

## 7. 주문·재고 관리 정책

### 7.1 주문 상태 정의

#### 주문 상태값

| 상태 | 코드 | 설명 |
|------|------|------|
| 임시주문 | `TEMP` | 주문 요청 접수, 재고확보·결제 처리 대기 |
| 처리중 | `PROCESSING` | 비동기 재고확보·결제 처리 진행 중 (3분 타임아웃 → CANCELLED) |
| 결제완료 | `PAYMENT_COMPLETED` | 재고확보 + 결제 승인 완료 |
| 상품준비중 | `PREPARING` | 입점사 출고 준비 중 |
| 배송중 | `IN_DELIVERY` | 운송장 등록 완료, 배송 진행 |
| 배송완료 | `DELIVERED` | 배송사 완료 확인 |
| 구매확정 | `CONFIRMED` | 고객 수동 확정 또는 7일 자동 확정 |
| 주문취소 | `CANCELLED` | 결제 전·후 취소 처리 완료 |
| 반품접수 | `RETURN_REQUESTED` | 고객 반품 신청 완료, 수거 대기 |
| 반품진행중 | `RETURNING` | 수거 완료, 검수·환불 처리 중 |
| 반품철회 | `RETURN_WITHDRAWN` | 반품 신청 철회 (수거 전 고객 요청) |
| 반품완료 | `RETURNED` | 반품 확정, 환불 완료 |
| 교환접수 | `EXCHANGE_REQUESTED` | 고객 교환 신청 완료, 수거 대기 |
| 교환진행중 | `EXCHANGING` | 수거 완료, 교환 출고 처리 중 |
| 교환철회 | `EXCHANGE_WITHDRAWN` | 교환 신청 철회 (수거 전 고객 요청) |
| 교환완료 | `EXCHANGED` | 교환 출고 완료 |

#### 주문 상태 전이 규칙

```
TEMP
    ├─ 동기: 재고확보 성공 + 결제 성공 → PAYMENT_COMPLETED
    ├─ 비동기: 처리 시작 → PROCESSING → PAYMENT_COMPLETED
    └─ 재고확보 실패 or 결제 실패 → CANCELLED

PROCESSING (비동기 전용)
    ├─ 재고확보 + 결제 성공 → PAYMENT_COMPLETED
    ├─ 3분 타임아웃 → CANCELLED + 보상 처리
    └─ 최종 실패 → CANCELLED + 보상 처리

PAYMENT_COMPLETED → PREPARING → IN_DELIVERY → DELIVERED
    ├─ 고객 확정 or 7일 경과 → CONFIRMED
    ├─ 반품 신청 (10일 이내)
    │   → RETURN_REQUESTED (반품접수)
    │       ├─ 수거 완료 → RETURNING (반품진행중) → RETURNED (반품완료)
    │       └─ 수거 전 철회 → RETURN_WITHDRAWN (반품철회) → DELIVERED 복귀
    └─ 교환 신청 (10일 이내)
        → EXCHANGE_REQUESTED (교환접수)
            ├─ 수거 완료 → EXCHANGING (교환진행중) → EXCHANGED (교환완료)
            └─ 수거 전 철회 → EXCHANGE_WITHDRAWN (교환철회) → DELIVERED 복귀
```

#### 재고·상태 연동 규칙

| 상태 전이 | 재고 변화 | 비고 |
|----------|----------|------|
| TEMP 생성 | -1 (선점) | 30분 선점 유지 |
| CANCELLED (미결제) | +1 복구 | 선점 해제 |
| CANCELLED (결제후) | +1 복구 | 즉시 복구 |
| RETURNED | +1 복구 | 상품 상태 SOLD_OUT 유지 |
| EXCHANGED | ±0 | 동일 상품 옵션 변경 |

#### 동기·비동기 처리 분기 기준

```
주문 내 MD 비동기 플래그 상품 포함 여부 확인
    ├─ 없음 → 동기 처리 (순차 블로킹)
    └─ 1개 이상 포함 → 비동기 처리 (이벤트 기반)
        → 주문 전체를 비동기 흐름으로 처리
```

> 재고확보 → 결제승인 처리 순서는 동기·비동기 공통 적용

### 7.2 주문 처리 기준

플랫폼은 고객 경험과 거래를 통합 관리하고, 판매 주체는 주문 이행을 책임하는 **역할 기반의 하이브리드 주문 운영 정책**을 적용한다.

- 고객은 플랫폼과 거래하며, 플랫폼이 주문 및 결제를 통합 관리한다.
- 직매입 상품은 플랫폼이 직접 출고 및 배송을 수행한다.
- 입점 상품은 Vendor Order 기반으로 입점사가 주문 이행을 수행한다.
- 고객 문의는 플랫폼이 1차 대응하며, 필요 시 입점사와 협업한다.
- 정산은 플랫폼이 통합 수행한다.

### 7.3 오류·보상 처리 정책

#### 동기 처리 오류 기준

| 항목 | 기준 |
|------|------|
| 결제 승인 오류 재시도 | **없음** (즉시 실패 처리) |
| 보상 처리 재시도 | **1회** (재고·포인트·쿠폰 복원) |
| 보상 실패 시 | 운영팀 수동 처리 이관 |

```
결제 승인 오류 (재시도 없음)
    ↓
보상 처리 1회 시도
    ├─ 재고 복원 1회 → 실패 시 운영팀 이관
    ├─ 포인트 복원 1회 → 실패 시 운영팀 이관
    └─ 쿠폰 복원 1회 → 실패 시 운영팀 이관
```

#### 비동기 처리 오류 기준

| 항목 | 기준 |
|------|------|
| 이벤트 처리 재시도 | **최대 3회** |
| 재시도 간격 | 즉시 → 30초 → 1분 (점진적 백오프) |
| 3회 실패 시 | DLQ 적재 → 운영팀 수동 처리 이관 |
| 적용 대상 | 결제 승인 / 재고·포인트·쿠폰 복원 |

```
이벤트 처리 실패
    ↓ 1차 재시도 (즉시)
    ↓ 2차 재시도 (30초 후)
    ↓ 3차 재시도 (1분 후)
    ↓ 최종 실패
DLQ 적재 → 운영팀 이관 + 모니터링 알림
```

#### 모니터링 기준

| 항목 | 알림 조건 | 알림 대상 |
|------|----------|----------|

| 재고·포인트·쿠폰 복원 실패 | 건별 즉시 | 운영팀 |
| DLQ 적재 | 건별 즉시 | 운영팀 |

#### 운영팀 수동 처리 기준

| 항목 | 기준 |
|------|------|
| 이관 방식 | 모니터링 대시보드 + 카카오 알림톡 |

### 7.4 장바구니 유효성 검사 정책

- 변경 케이스: 행사가 만료·가격 변경·수량 할인 조건 변경·쿠폰 만료·상품 가격 변경

### 7.6 재고 관리 기준

재고의 소유와 관리 책임은 판매 주체에 귀속하며, 초기에는 입점사 직접 관리 방식으로 운영한다.

- 직매입 상품 재고는 플랫폼이 관리한다.
- 입점 상품 재고는 입점사가 직접 관리한다.
- 입점사 전용 BO를 통해 재고 수량을 등록·수정한다.
- 재고 정확성 유지 책임은 재고 관리 주체에게 있다.

### 7.7 품절 관리 기준

품절 책임은 재고 관리 주체가 부담하며, 플랫폼은 고객 보호 및 운영 품질 관리를 수행한다.

- 직매입 상품 품절은 플랫폼이 책임진다.
- 입점 상품 품절은 입점사가 책임진다.
- 재고 연동 오류는 원인 분석 후 책임 주체를 결정한다.
- 고객 피해 최소화를 위한 취소·환불·보상 정책을 운영한다.
- 반복적인 품절 발생 시 입점사 평가 및 운영 정책에 반영할 수 있다.

## 8. 클레임·CS 관리 정책

### 8.1 클레임 접수 기준

- **취소**: 출고 전(PREPARING 이전) 언제든 신청 가능
- **반품·교환**: 배송완료일 기준 **10일 이내** 신청 가능
- 클레임 신청 채널: 플랫폼 내 주문 상세 페이지
- 플랫폼이 1차 접수 및 대응하며, 필요 시 입점사와 협업한다.

### 8.2 귀책 판단 기준

#### 판단 프로세스

```
클레임 신청 → 고객 사진 첨부 → 플랫폼 1차 판단
    ↓
[입점사 귀책]               [고객 귀책]
입점사에 통보               고객에 통보
입점사 비용 부담            고객 비용 부담
                              ↓
                          실물 수령 후 협의로 변경 가능
```

#### 귀책 판단 기준표

| 귀책 주체 | 사유 예시 |
|----------|----------|
| 입점사 귀책 | 상품 불량, 오배송, 상품 설명 상이, 파손 배송 |
| 고객 귀책 | 단순 변심, 사이즈 오선택, 사용 후 반품 |
| 협의 대상 | 사진으로 판별 불가한 경우, 실물 수령 후 재판단 |

#### 귀책 변경 프로세스

- 초기 판단은 고객이 첨부한 사진을 기준으로 한다.
- 실물을 수령한 후 고객 귀책으로 확인되는 경우, 입점사와 고객 간 협의를 통해 귀책을 변경할 수 있다.
- 귀책 변경 시 플랫폼이 중재하며, 최종 결정은 플랫폼이 내린다.

### 8.3 유형별 처리 기준

#### 취소

| 시점 | 처리 기준 |
|------|----------|
| 결제 후 출고 전 | 즉시 취소·환불 처리 |
| 출고 후 배송 중 | 반품 접수로 전환 |
| 배송완료 후 | 반품 절차 적용 |

#### 반품

- 반품 신청 → 반품 배송 → 상품 검수 → 환불 처리
- 검수 완료 후 영업일 기준 3일 이내 환불
- 반품 배송비: 귀책 주체 부담
- 반품 확정 후 재고 복구. 단, 상품 상태(`SOLD_OUT`)는 담당자 수동 확인 후 변경

#### 교환

- 교환 신청 → 회수 배송 → 상품 검수 → 교환 출고
- 교환 가능 조건: 동일 상품 내 옵션 변경 (색상·사이즈)
- 재고 없는 경우 교환 불가, 반품 후 재구매로 안내
- 교환 배송비: 귀책 주체 부담

- **비용 부담**: 플랫폼 쿠폰은 플랫폼 부담, 입점사 쿠폰은 입점사 부담, 공동 쿠폰은 계약 비율에 따라 분담

## 10. 정산 관리 정책

### 10.1 입점사 정산 기준

입점 정산은 **구매확정된 주문상품을 기준**으로 정산 대상을 확정하며, 구매확정 이후 발생한 취소·반품 등은 재정산 정책에 따라 조정한다.

#### 정산 대상

- 정산기간 내 구매확정된 주문상품을 기준으로 확정
- 구매확정 이전의 취소·반품 및 미완료 주문은 제외
- 구매확정 이후 발생한 취소·반품·교환 및 수기 조정 건은 재정산 정책에 따라 반영

#### 정산 주기

- 월 단위 구매확정 주문 기준으로 산정
- 익월 5일까지 정산 대상 확정
- 익월 15일 정산금 지급

#### 정산 금액 산정

- **수수료**: 부가가치세를 제외한 공급가액(과세표준)에 계약된 수수료율을 적용. 수수료 부가가치세는 별도 항목으로 정산
- **배송비**: 고객 부담 / 입점사 부담 / 플랫폼 부담으로 구분하여 각각 Revenue / Cost / Subsidy로 분리 정산
- **마케팅 비용**: 플랫폼과 입점사의 공동 부담 구조에 따라 산정. 부담 비율은 계약서에 따름
- **포인트**: 결제 시 사용된 포인트는 상품별 공급가 비중에 따라 배분. 플랫폼 70% / 입점사 30% 부담

#### 정산 차감 항목

- **패널티**: 운영 정책 또는 계약 위반에 따른 제재 금액
- **기타 계약상 공제**: 계약 또는 운영 정책에 따라 발생하는 추가 공제 항목

### 10.2 취소·반품 처리 기준

#### 정산 전 취소

구매확정 이전 취소된 주문상품은 정산 대상에서 제외하며, 이미 정산 대상으로 집계된 경우 해당 회차 정산에서 차감한다.

#### 정산 후 취소

구매확정 이후 발생한 취소는 재정산 정책에 따라 익월 정산금에서 차감 처리하며, 차감 금액이 정산금을 초과할 경우 입점사에 환수 청구한다.

#### 부분반품

반품 확정된 상품 단위로 정산 금액을 산정하며, 배송비·수수료·포인트 분담금은 반품 귀책 주체(고객/입점사/플랫폼)에 따라 조정한다.

#### 재정산 방식

취소·반품·교환·수기 조정 건은 익월 정산 시 차감 또는 가산 방식으로 반영하며, 누적 차감액이 정산금을 초과하는 경우 별도 환수 프로세스를 진행한다.

### 10.3 지급 정책

#### 지급일

익월 15일을 정산금 지급일로 하며, 지급일이 영업일이 아닌 경우 직전 영업일에 지급한다.

#### 지급 계좌 관리

- 입점사는 BO를 통해 정산 수령 계좌를 등록·변경한다.
- 계좌 변경 시 변경일 이후 도래하는 정산 회차부터 적용한다.
- 계좌 오류로 인한 미지급 책임은 입점사에 있다.

#### 지급 보류 조건

- 부정거래 의심 주문 포함 시
- 클레임·분쟁 미해결 건 포함 시
- 세금계산서 미발행 시
- 입점 계약 위반 사실 확인 시
- 법적 분쟁·가압류 등 외부 요인 발생 시

#### 최소 지급 금액 기준

정산금이 10,000원 미만인 경우 익월로 이월하며, 3회 연속 이월 시 강제 지급 처리한다.

### 10.4 세금 및 증빙

#### 세금계산서 발행 방식

- 플랫폼은 입점사에게 수수료에 대한 세금계산서를 발행한다.
- 입점사는 공급가액에 대한 세금계산서를 플랫폼에 발행한다.
- 발행 기준일은 정산 확정일로 한다.

#### 부가세 처리 기준

- 수수료 부가세는 플랫폼이 부담하며, 정산서에 공급가액과 부가세를 구분 표기한다.
- 면세 상품의 경우 별도 기준을 계약서에 명시한다.

#### 원천징수 여부

- 사업자 입점사: 원천징수 미적용
- 개인 셀러: 소득 유형에 따라 관련 법령에 준하여 처리

#### 정산서 제공 방식

- 정산 확정 후 입점사 BO를 통해 정산서 제공
- 항목별 상세 내역 포함 (매출·수수료·배송비·마케팅·포인트·차감·최종지급액)
- PDF 다운로드 및 엑셀 내보내기 지원

### 10.5 예외 처리 정책

#### 부정거래 의심 주문

FDS에 의해 부정거래로 의심되는 주문은 정산 보류 처리하며, 조사 완료 후 정상 거래 확인 시 익월 정산에 반영한다. 부정거래 확정 시 해당 정산금은 환수한다.

#### 클레임 분쟁 건

고객·입점사 간 분쟁이 미해결 상태인 주문상품은 분쟁 해결 시까지 정산 보류하며, 플랫폼 중재 결과에 따라 정산금을 조정한다.

#### 입점 종료 시 정산

- 입점 종료 시 종료일 기준 구매확정 주문에 대해 최종 정산 수행
- 미해결 클레임·환수금·패널티 등을 정산금에서 공제 후 지급
- 최종 정산 완료 후 30일 이내 지급 원칙

#### 지급 보류 및 해제 조건

- 보류 사유 해소 확인 후 익영업일 이내 지급 처리
- 보류 기간 60일 초과 시 플랫폼 내부 승인 절차를 거쳐 처리 방향 결정

### 10.6 외부 정산

#### PG사

PG 수수료는 결제 건별 발생하며, PG사 정산 주기(통상 D+2~3 영업일)에 따라 플랫폼 계좌로 입금된다.

#### 택배사/물류사

물류비는 월 단위로 청구·정산하며, 직매입 물류비는 플랫폼 부담, 입점사 물류비는 입점사 정산금에서 차감 또는 별도 청구한다.

#### 브랜드/광고주

광고 집행 비용은 집행 완료 기준으로 익월 정산하며, 성과형 광고(CPS)의 경우 구매확정 주문을 기준으로 산정한다.

#### 플랫폼 내부

직매입 매출·비용·마진은 내부 정산 기준에 따라 월 단위로 집계하며, 프로모션·포인트 비용은 마케팅 예산으로 처리한다.

### 12.2 결제 처리 기준

| 항목 | 기준 |
|------|------|
| 재고 선점 시점 | TEMP 생성 시 |
| 선점 유지 시간 | 30분 (결제 페이지 체류 기준) |
| 미결제 자동 취소 | 30분 경과 시 재고 해제 + 임시 주문 소멸 |
| 결제 실패 재시도 | 동기: 없음 / 비동기: 최대 3회 |

| PROCESSING 최대 시간 | 3분 (초과 시 자동 CANCELLED + 보상 처리) |

### 12.3 혼합 결제 (포인트 + 카드)

```
결제금액 = 포인트 사용금액 + 카드 결제금액

적용 순서:
1. 포인트 차감 (최소 1,000원, 최대 결제금액 100%)
2. 잔여 금액 카드 결제
```

### 15.9 외부 접속 제어 정책 (Nginx 라우터 기반)

#### 핵심 원칙

> 외부에서 Backend API 직접 접속 불가.  
> 모든 외부 요청은 Nginx Reverse Proxy를 통해서만 접근.  
> Nginx 라우터에 등록된 경로만 외부 접속 허용 (Whitelist 방식).  
> 라우터 미등록 경로는 기본 차단 (403).

#### 외부 접속 채널 구분

| 채널 | 경로 패턴 | 대상 | 접속 제어 |
|------|---------|------|---------|
| 고객 API | `/api/v1/{resource}` | 고객 | Nginx 라우터 등록 |
| 어드민 API | `/api/admin/v1/{resource}` | 운영자 | Nginx 라우터 등록 + VPN/IP 제한 |
| 입점사 API | `/api/partner/v1/{resource}` | 입점사 | Nginx 라우터 등록 |
| Webhook | `/webhook/v1/{provider}/{event}` | PG사·배송사 등 외부 시스템 | Nginx 라우터 등록 + IP 화이트리스트 |

#### 컴포넌트별 외부 접속 차단 기준

| 컴포넌트 | 외부 접속 | 이유 |
|---------|---------|------|
| backend-api | ❌ 차단 | Nginx 통해서만 접근 |
| consumer | ❌ 차단 | 내부 이벤트 처리 전용 |
| batch | ❌ 차단 | 내부 스케줄 실행 전용 |
| PostgreSQL | ❌ 차단 | 내부 네트워크만 |
| Redis | ❌ 차단 | 내부 네트워크만 |
| Elasticsearch | ❌ 차단 | 내부 네트워크만 |

#### API 네이밍 패턴

```
내부 API (단일 정의)
    /{domain}/{resource}/{action}
    예) /orders/create
        /payments/confirm
        /deliveries/complete

외부 채널 (Nginx 라우터로 노출 제어)
    /api/v1/{domain}/{resource}         → 고객용
    /webhook/v1/{provider}/{event}      → 외부 시스템용
    /admin/v1/{domain}/{resource}       → 운영자용
```

#### Nginx 라우터 등록 샘플

```nginx
# =============================================
# Case 1. /webhook 오픈 안 할 때
# /api 채널만 등록 → webhook 접속 차단
# =============================================

# 고객용 결제 확인 API (등록 O → 허용)
location /api/v1/payment/confirm {
    proxy_pass http://backend-api:8080/v1/payment/confirm;
    proxy_set_header X-Request-Source "api";
}

# webhook 경로 미등록 → 기본 차단 규칙에 의해 자동 차단


# =============================================
# Case 2. /webhook 오픈 할 때
# /api + /webhook 둘 다 등록
# =============================================

# 고객용 결제 확인 API (등록 O → 허용)
location /api/v1/payment/confirm {
    proxy_pass http://backend-api:8080/v1/payment/confirm;
    proxy_set_header X-Request-Source "api";
}

# PG사 Webhook 결제 확인 (등록 O → PG사 IP만 허용)
location /webhook/v1/payment/confirm {
    proxy_pass http://backend-api:8080/v1/payment/confirm;
    proxy_set_header X-Request-Source "webhook";

    allow 1.2.3.4;    # PG사 IP
    allow 1.2.3.5;    # PG사 IP (백업)
    deny all;         # 나머지 차단
}


# =============================================
# 공통 - 기본 차단 규칙 (모든 설정 하단)
# =============================================
location / {
    return 403;
}
```

#### X-Request-Source 헤더 활용

Nginx가 요청 출처를 헤더로 Backend에 전달하며, Backend는 출처별 처리를 분기할 수 있다.

| 채널 | 헤더값 | Backend 활용 예시 |
|------|--------|----------------|
| `/api` | `X-Request-Source: api` | 고객 인증 검증 |
| `/webhook` | `X-Request-Source: webhook` | PG사 서명 검증 |
| `/admin` | `X-Request-Source: admin` | 운영자 권한 검증 |

#### 라우터 등록 기준 예시

| 내부 API | /api 노출 | /webhook 노출 | /admin 노출 |
|---------|----------|--------------|------------|
| orders/create | ✅ 등록 | ❌ 미등록 | ❌ 미등록 |
| payments/confirm | ✅ 등록 | ✅ 등록 (PG사) | ❌ 미등록 |
| deliveries/complete | ❌ 미등록 | ✅ 등록 (배송사) | ❌ 미등록 |
| vendors/approve | ❌ 미등록 | ❌ 미등록 | ✅ 등록 |

#### 2단계 K8s 전환 시

```
Nginx 라우터 → K8s Ingress Controller로 동일 구조 유지
    Ingress 규칙에 등록된 경로만 외부 노출
    미등록 경로 자동 차단
    IP 화이트리스트 → K8s NetworkPolicy로 전환
```

### 17.1 로그 레벨 정의

|------|------|------|------|

| 환경 | 최소 로그 레벨 | 비고 |
|------|-------------|------|

### 17.2 트랜잭션 추적 (Trace) 정책

액션 하나에 대한 전체 흐름을 Trace ID 기반으로 추적한다.

#### 추적 ID 구조

```
Trace ID  : 액션 최초 진입 시 발급. 전체 흐름 추적 단위
Span ID   : Trace 내 각 처리 단계 단위
Parent ID : 상위 Span 참조 (계층 구조)
```

#### Trace ID 생성 규칙

```
TRC-{YYYYMMDD}-{일련번호 8자리}
예) TRC-20260617-00000001
```

#### 예시 — 주문 결제 흐름 추적

```
[Trace ID: TRC-20260617-00000001]
    │
    ├─ Span 1: 주문 요청 수신 (INFO)
    ├─ Span 2: 임시 주문 생성 (INFO)
    ├─ Span 3: 재고 확보 시도 (INFO)
    │       └─ Span 3-1: 재고 선점 (DEBUG)
    ├─ Span 4: 결제 승인 요청 (INFO)
    │       ├─ Span 4-1: PG API 호출 (DEBUG)
    │       └─ Span 4-2: PG 응답 수신 (DEBUG)
    └─ Span 5: 주문 상태 PAYMENT_COMPLETED 전환 (INFO)
```

#### 추적 ID 전파 기준

| 항목 | 기준 |
|------|------|
| 발급 시점 | 고객 요청 최초 진입 시 |
| 전파 방식 | HTTP Header `X-Trace-Id` 로 전 서비스 전달 |
| 외부 API 호출 시 | Trace ID 함께 전달 (PG사·배송사·알림) |
| 로그 출력 형식 | `[TraceID] [SpanID] [레벨] 메시지` |
| Trace 조회 | 운영 어드민에서 Trace ID 기반 전체 흐름 조회 가능 |

## 20. 프로토타입 개발 정책

### 20.1 프로토타입 목적 및 범위

프로토타입은 **UI 흐름 검증**을 목적으로 하며, 실제 데이터 처리·외부 연동·보안은 이후 단계에서 구현한다.

| 항목 | 기준 |
|------|------|
| 목적 | 화면 UI/UX 흐름 검증, 이해관계자 피드백 수집 |
| 데이터 소스 | Back-end API Mock JSON 반환 |
| 데이터 수정/등록 | **미수행** (Mock 읽기 전용) |
| 외부 연동 | 미구현 (PG, 배송사, SNS 등) |
| 인증/보안 | 항상 로그인된 상태로 간주 (JWT bypass) |

### 20.2 프로토타입 기술 스택

| 영역 | 기술 | 비고 |
|------|------|------|
| Front-end (고객웹) | Next.js 14+ (App Router) + TypeScript + Tailwind CSS | SSR + BFF 구조 |
| Front-end (어드민/입점사) | Next.js 15 + TypeScript + 순수 CSS 클래스 | CSR (SPA), MDI 탭 |
| Back-end API | Kotlin + Spring Boot 3.3 (단일 실행 모듈) | 12개 업무도메인 패키지 |
| 데이터 | Mock JSON 파일 (API resources 내 관리) | DB 미사용 |

### 20.2-1 고객웹 SSR + BFF 구조

고객웹은 SEO·보안을 위해 SSR + BFF(Backend For Frontend) 구조를 적용한다.

```
브라우저 ←→ Next.js Server (BFF) ←→ Back-end API (내부 네트워크)
           쿠키 기반 인증              서버 간 토큰 통신
           API 키·로직 은닉            외부 직접 접근 불가
```

| 구분 | 역할 |
|------|------|
| Server Component (SSR) | 초기 데이터 fetch + HTML 렌더링, API 키 서버에서만 사용 |
| Route Handler (`app/api/`) | BFF 프록시, 브라우저 → BFF → 백엔드 중계 |
| Client Component | 인터랙션(장바구니·옵션 선택 등), BFF 경유 `/api/*` 호출 |
| 쿠키 인증 | httpOnly + secure + sameSite=strict, 서버에서만 읽기 |

#### 보안 원칙

| 항목 | 기준 |
|------|------|
| API 키 은닉 | `SERVER_API_BASE` (서버 전용 환경변수), 브라우저에 미노출 |
| 백엔드 폐쇄 | 브라우저에서 직접 접근 불가, Next.js Server만 통신 |
| 쿠키 보안 | httpOnly + secure + sameSite=strict |
| CORS | Next.js BFF만 허용 |

#### 프로토타입 단계 처리

| 항목 | 프로토타입 | 본개발 |
|------|----------|--------|
| API 호출 주체 | Server Component (이미 적용) | Server Component + Route Handler |
| 인증 | bypass (항상 로그인) | httpOnly 쿠키 + JWT |
| 백엔드 접근 | localhost:8080 직접 | 내부 네트워크만 |

### 20.2-2 어드민/입점사 CSR (SPA) 구조

어드민·입점사는 내부 운영자 전용이므로 SSR/BFF 불필요. CSR(SPA)로 운영하며 네트워크 수준 접근 통제를 적용한다.

| 구분 | 기준 |
|------|------|
| 렌더링 | CSR (Client Side Rendering, MDI 탭 SPA) |
| API 호출 | Client Component에서 직접 호출 |
| 접근 통제 | VPN/IP 제한 (어드민), 2FA + 세션 (입점사) |
| SEO | 불필요 (로그인 후 화면) |

### 20.2-3 어드민/입점사 UI 구조

화면정의서의 `화면 구조 재사용 지침`에 따라 MDI(Multi Document Interface) 탭 기반으로 구성한다.

| 구성요소 | 역할 |
|---------|------|
| NavBar | 상단 드롭다운 메뉴 (화면 열기) |
| TabBar | 열린 화면 탭 표시 (최대 8개, 대시보드 고정) |
| TabContent | 활성 탭 화면 렌더링 |

#### 화면 유형별 CSS 클래스 패턴

| 유형 | 최외곽 | 핵심 구조 |
|------|--------|---------|
| 메인 (Dashboard) | `.dashboard` | `.dashboard__grid` + `.dash-card` |
| 현황 (Table) | `.page` | `.filter-bar` → `.summary-bar` → `.table-wrap` → `.pagination` |
| 상세 (Detail Modal) | `.detail-modal-overlay` | `.detail-modal__header` → `InnerTabs` → `.tab-panel-content` |

#### 상세 화면 운영 원칙

| 원칙 | 설명 |
|------|------|
| 모달 필수 | 모든 상세·등록·수정 화면은 모달(detail-modal)로 구현. 탭으로 열지 않음 |
| 기본 내부 구조 | InnerTabs (탭 방식). 명시적으로 단계별(step) UI를 요청한 경우에만 stepper 사용 |

### 20.5 데이터 수정/등록 처리 방침

프로토타입에서도 POST/PUT/DELETE 요청은 실제로 API를 호출한다.
API는 실제 저장 없이 성공 응답(Mock)을 반환하며, Front-end는 응답 결과를 사용자에게 표시한다.

| 원칙 | 설명 |
|------|------|
| API 호출 | 모든 저장/수정/삭제 요청은 실제 API를 호출한다 |
| API 응답 | 실제 DB 저장 없이 성공 Mock 응답을 반환한다 |
| 결과 표시 | Front-end는 API 응답을 받아 사용자에게 알린다 (예: "저장되었습니다") |
| 화면 이동 | 모든 네비게이션은 정상 동작한다 |
| 유효성 검증 | 프론트 유효성 검증은 실제와 동일하게 구현한다 |

### 20.7 에러 처리 표준

프로토타입 단계에서도 API 에러 응답 표준을 준수한다.

#### 정상 응답

```json
{
  "code": "SUCCESS",
  "data": { ... }
}
```

#### 에러 응답

```json
{
  "code": "ERROR_CODE",
  "message": "사용자에게 보여줄 메시지",
  "detail": "개발자용 디버그 정보 (운영 환경에서는 생략)"
}
```

#### 주요 에러 코드

| code | HTTP Status | 의미 |
|------|------------|------|
| `SUCCESS` | 200 | 정상 |
| `BAD_REQUEST` | 400 | 파라미터 오류 |
| `UNAUTHORIZED` | 401 | 인증 필요 |
| `FORBIDDEN` | 403 | 권한 없음 |
| `NOT_FOUND` | 404 | 리소스 없음 |
| `INTERNAL_ERROR` | 500 | 서버 오류 |
