## 작성 규칙

### 분류 체계 (조건부 3단)

- 기본: **대분류 → 소분류** 2단
- 한 대분류 안의 소분류가 **6개 초과** 시에만 중분류 추가 (3단)
- 그룹 기준은 도메인정의서의 책임 목록을 그대로 사용

### 소분류 분리 기준

> "CRUD가 다른가"가 아니라 **"워크플로우/상태전이가 다른가"**

- 조회·등록·수정·삭제는 소분류 1건에 포함 (별도 나열 안 함)
- 승인/반려·상태전이 등 별도 워크플로우가 있을 때만 분리

### 채널 표기

| 코드 | 의미 | 비고 |
|------|------|------|
| M | 모바일 (고객웹) | 프론트+백엔드 |
| A | 어드민 | 프론트+백엔드 |
| P | 파트너 (입점사) | 프론트+백엔드 |
| B | 배치 | 백엔드만 (화면 없음) |
| C | 컨슈머 (이벤트) | 백엔드만 (화면 없음) |

### 태그

| 태그 | 의미 |
|------|------|
| `[NFR]` | 비기능요건 (인프라·보안). 기능 수 카운트에서 제외 가능 |
| `N/A` | 화면/코드 자체가 없는 항목. 정책 근거만 존재 |

## 난이도·공수 산정 기준

### 난이도 5단계

| 등급 | 명칭 | 기준 | 대표 예시 |
|------|------|------|----------|
| 1 | 단순 | 단일 API + 조회 전용, 상태전이 없음 | 공지사항 조회, FAQ |
| 2 | 보통 | CRUD + 유효성 검증 + 단순 상태 (2~3상태) | 쿠폰 등록, 상품 수정 |
| 3 | 복잡 | 다중 도메인 연동 또는 복합 비즈니스 규칙 | 주문 생성, 정산 계산 |
| 4 | 고난도 | 상태머신 + 비동기 이벤트 + 보상 트랜잭션 | 클레임 처리, 비동기 주문 |
| 5 | 최고 | 외부 연동 + 동시성 제어 + 장애 대응 | PG 결제, FDS, Redis 선점 |

### 난이도별 시간 범위

| 난이도 | 프로토타입(h) | 본개발(h) |
|--------|-------------|-----------|
| 1 | 2~4 | 8~16 |
| 2 | 4~8 | 16~32 |
| 3 | 8~16 | 32~56 |

## 프로토타입 진행 상태 안내

N/A·스텁 발견을 "결함"으로 오해하지 않기 위한 전제:

- **고객 화면(M)**: 본격 작업 전. 대부분 스텁/미존재는 진행 순서상 당연한 상태
- **배치(B)·컨슈머(C)**: 미착수. 코드 없는 것은 누락이 아님
- **어드민·파트너(A/P)**: 초안 상태. dead code·스텁 다수는 미완성 초안의 자연스러운 특징
