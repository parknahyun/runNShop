## 코드 기반 보완 (2026-07-28, apps/ 실제 소스 조사)

admin `settings/notification`에서 템플릿 CRUD(수신자·채널·상태 필터)가 확인됨 — 기존 "템플릿관리"
소분류와 일치, 새로 발견된 기능은 없음. 발송 이력·취합배치 UI는 admin/partner 어디에도 화면으로
노출돼 있지 않음(백엔드 배치 개념으로만 존재) — partner `settings/notification`은 알림 "수신"
설정(벤더가 어떤 이벤트를 받을지)이라 이 도메인이 아니라 07-Vendor "계정·보안관리"로 분류함.

**API 호출 개수 산정(2026-07-28)**: `NotificationTemplatePage.tsx`는 Config의 공지/배너/약관/
금지어 관리와 동일한 "목록(모달기반)" 패턴 — 목록 조회 화면 1개, 모달 내 제출 버튼 등록·저장(수정)·
삭제 3개(취소 버튼 제외) = API 4개. 나머지 N/A 소분류(채널 fallback 발송·발송 정책 적용·이벤트
기반 알림 생성·예약 발송·발송 이력·취합배치 관리)는 admin/partner 어디에도 대응 화면이 없어
N/A 처리 — 백엔드 배치/로직·컨슈머로만 존재하는 기능이라 화면 기반 API 카운트 대상이 아님.
고객 알림 수신(알림 목록 조회·알림 설정 관리)은 mobile 미착수 상태이나 정의된 기능으로 산정했다.

## 코드 기반 보완 (2026-07-29, 회원/운영자/입점사 일반 기능표 대조 검토)

- **신규 추가 6건**: 대량·타겟 발송(운영자, 알림발송), 알림함 조회(운영자)·알림함 조회(입점사)
  (이상 알림수신), 실패 건 재발송(운영자)·재발송 요청(입점사)(이상 이력관리), 발송 통계
  조회(운영자)(신규 대분류 "발송통계"). 전부 코드·정책 근거 없는 신규 공백. 운영자 알림함은
  `apps/runNshop-admin/components/home/SystemAlerts.tsx`가 코드에 존재하지만 `Dashboard.tsx`
  어디서도 렌더링되지 않는 죽은 컴포넌트라 "이미 반영됨"으로 볼 수 없음을 확인. 입점사 알림함은
  `07-Vendor.md`의 "알림 수신 설정"(어떤 이벤트를 받을지 설정)과 짝을 이루는 실제 수신함 화면
  — 설정은 있지만 조회 화면이 없다는 비대칭을 확인.
- **이미 반영됨(신규 제외)**: 시스템 알림(서버장애·배치실패 등, admin 대상)은 `12-Audit.md`
  "장애처리연동 > 모니터링·알림"에 이미 N/A로 등재돼 있어 중복 추가하지 않음 — Audit이
  감지·트리거하고 Notification은 그 알림의 채널 발송(fallback·정책)만 담당하는 관계.
- **BC 대상(별도 논의)**: 공지사항의 회원(mobile)·입점사(partner) "조회" 화면 — admin 작성·게시는
  이미 `11-Config.md` "콘텐츠관리 > 공지사항 관리"에 등재돼 있으나, 고객·벤더가 공지를 조회하는
  화면은 Config 쪽에 M/P 채널로 확장돼야 할 잔여 공백(Notification 소관 아님). partner
  `components/home/Notices.tsx`는 코드는 있으나 어디서도 배선되지 않은 미연결 상태.
- **판단 보류**: 알림 읽음 처리·삭제(고객)는 mobile 마이페이지 전체가 미구현이라 코드·정책 근거가
  없어 이번엔 반영하지 않음 — mobile 착수 후 재확인 필요.
