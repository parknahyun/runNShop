# 샘플: 상위 유스케이스 — Order

> **단계**: 구조설계
> **문서범위**: Domain
> **문서종류**: Design

> **작성 목적**: 도메인 정의서(⑤)의 책임 목록을 "누가(액터) 무엇을(업무) 하는가" 단위로 분해한다.
> 이 산출물은 메뉴구조도(⑦)의 직접 입력이자 EARS(⑧)의 후보 목록이 된다.
>
> **흐름 내 위치**:
> ```
> ⑤ 도메인 정의서 → ⑥ 상위 유스케이스 → ⑦ 메뉴구조도 → ⑧ EARS
> ```
>
> **작성 주체**: 시니어 개발자 + AI 협업 (기획자·현업 검토·확인)

## ① 액터 정의

> **목적**: 이 도메인의 유스케이스를 "누가" 수행하는지 식별한다.
> **도출 방법**: 도메인 정의서 §4(도메인 간 관계)에서 호출 주체를 추출하고, 컴포넌트(③) 앱 구성에서 채널을 매핑한다.

| 액터 | 설명 | 채널 |
|---|---|---|
| 고객 | 로그인한 최종 구매자. 본인 주문에 대해서만 조회·조작 가능 | M(Mobile) |
| 판매자 | 입점사 운영자. 자기 매장으로 걸린 주문만 처리 | P(Partner) |
| CS 담당자 | 플랫폼 관리자. 예외 처리·클레임 중재 권한을 가짐 | A(Admin) |
| 시스템 | Payment·Catalog 도메인의 비동기 이벤트, 배치 스케줄러 | C(Consumer)/B(Batch) |

## ② 업무그룹별 유스케이스

> **업무그룹 도출**: 도메인 정의서 §2 Order "하는 것" 목록을 업무 성격별로 그룹핑
> **유스케이스 도출**: 도메인정의서 책임 + 정책서 업무 규칙 + 이해관계자 인터뷰

### 장바구니·주문서
| 유스케이스 | 액터 | 도출 근거 |
|---|---|---|
| 장바구니 담기 / 수량 변경 / 삭제 | 고객 | 도메인정의서 "주문 생성" 책임 |
| 바로구매(장바구니 미경유) | 고객 | 정책서: 상품상세에서 즉시구매 지원 |
| 배송지·포인트·결제수단 선택 후 주문서 제출 | 고객 | 도메인정의서 "주문 생성" + 정책서 결제 프로세스 |

### 주문결제·연동
| 유스케이스 | 액터 | 도출 근거 |
|---|---|---|
| 결제 요청(TEMP→PROCESSING) | 고객 | 도메인정의서 "주문 상태 관리" |
| 결제완료/결제실패 이벤트 수신 | 시스템(Payment 발행) | 도메인정의서 §4: Payment→Order 비동기 이벤트 |
| 재고선점 요청 | 시스템(Catalog 연동) | 도메인정의서 §4: Order→Catalog 동기 호출 |
| 구매확정(수동/자동) | 고객 / 시스템(배치) | 정책서: 배송완료 후 7일 자동확정 |
| 예외 취소 | CS 담당자 | 인터뷰: CS가 결제 후에도 취소할 수 있어야 함 |

### 배송관리
| 유스케이스 | 액터 | 도출 근거 |
|---|---|---|
| 출고 처리 / 운송장 등록 | 판매자 | 도메인정의서 "배송 처리" 책임 |
| 배송지 변경(출고 전) | 고객 / CS 담당자 | 정책서: 출고 전까지 변경 허용 |
| 배송상태 갱신 배치 | 시스템(배치) | 도메인정의서 §5: 택배사 API 연동 |

### 클레임처리
| 유스케이스 | 액터 | 도출 근거 |
|---|---|---|
| 반품/교환 신청 | 고객 | 도메인정의서 "클레임 접수" 책임 |
| 수거·재고복구 처리 | 판매자 | 정책서: 판매자 귀책 시 수거 의무 |
| 클레임 접수/처리시작/완료처리/반려확정 | CS 담당자 | 인터뷰: CS 중재·예외처리 워크플로우 |

## ③ 액터-유스케이스 관계도

```plantuml
@startuml
left to right direction
actor 고객 as Customer
actor 판매자 as Partner
actor "CS 담당자" as CS
actor 시스템 as System

package "장바구니·주문서" {
  usecase "장바구니 담기" as UC1
  usecase "바로구매" as UC2
  usecase "주문서 제출" as UC3
}
package "주문결제·연동" {
  usecase "결제 요청" as UC4
  usecase "구매확정" as UC5
  usecase "예외 취소" as UC6
}
package "배송관리" {
  usecase "출고 처리" as UC7
  usecase "배송지 변경" as UC8
}
package "클레임처리" {
  usecase "반품/교환 신청" as UC9
  usecase "클레임 처리" as UC10
}

Customer --> UC1
Customer --> UC2
Customer --> UC3
Customer --> UC4
Customer --> UC5
Customer --> UC8
Customer --> UC9
Partner --> UC7
Partner --> (수거·재고복구)
CS --> UC6
CS --> UC8
CS --> UC10
System --> UC4 : 결제완료/실패 이벤트
System --> UC7 : 배송상태 갱신 배치
@enduml
```

## ④ 권한 범위

| 규칙 | 도출 근거 |
|---|---|
| 고객은 본인 주문만 조회·결제·취소 가능(`order.memberId == 로그인 사용자`) | 정책서: 개인정보 보호 원칙 |
| 판매자는 자기 매장으로 걸린 주문만 출고·클레임 처리 가능 | 도메인정의서 §4: Vendor→Order 관계 |
| 고객의 단순 취소는 PAYMENT_COMPLETED 상태에서만 허용, 이후 상태는 CS 예외 취소만 가능 | 정책서: 취소 정책 |
| 반품·교환 신청은 배송완료 후 10일 이내로 제한 | 정책서: 반품 기한 규정 |
| 재고 수동 복구·귀책 이의제기는 반품 건당 1회로 제한(중복 방지) | 인터뷰: CS 운영 규칙 |

## Platform Bolt 예외 (참고)

이 문서는 Domain(Order) 스코프라 Platform Bolt(앱 셸) 유스케이스는 포함하지 않는다 — 로그인·메뉴
접근·탭 열기/닫기 같은 앱 공통 유스케이스는 컴포넌트 산출물의 "메뉴구조도·Platform Bolt 식별"
절로 갈음한다(`01-컴포넌트.md` 참고).
