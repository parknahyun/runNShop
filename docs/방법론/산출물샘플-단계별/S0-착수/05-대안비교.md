# 샘플: 대안 비교

> **단계**: 착수
> **문서범위**: Project
> **문서종류**: Proposal
>
> **작성 목적**: 주요 의사결정 항목에 대해 2개 이상 대안을 비교하고,
> 채택 근거를 명시하여 "왜 이 방향인가"를 기록한다.
> ADR(⑱)과 다른 점: 대안비교는 프로젝트 시작 전 전략 수준, ADR은 설계 중 기술 수준.
>
> **흐름 내 위치**:
> ```
> 범위(Scope) → 대안비교 → 리스크가정
> ```
>
> **작성 주체**: PM + 시니어 개발자 + AI 협업 (의사결정권자 승인)

## 필수 항목

| # | 항목 | 설명 |
|---|---|---|
| 1 | 의사결정 항목 | 무엇을 결정하는가 |

## 샘플 (이커머스 플랫폼)

### 의사결정 1: 아키텍처 패턴

| 대안 | 장점 | 단점 | 비용 | 채택 |
|---|---|---|---|---|
| A. MSA (도메인별 서비스) | 독립 배포, 스케일링 유연 | 인프라 복잡도 높음, 초기 비용 | 높음 | ❌ |
| B. 모놀리스 | 단순, 빠른 개발 | 스케일링 한계, 도메인 결합 | 낮음 | ❌ |
| **C. Modular Monolith** | 도메인 분리 + 단일 배포, MSA 전환 대비 | 경계 규칙 준수 필요 | 중간 | ✅ |

**채택 근거**: 초기 팀 규모(3~5명)에서 MSA는 과잉 설계. 모놀리스는 확장 한계. Modular Monolith는 도메인 경계를 유지하면서 단일 배포의 단순성을 확보하고, 트래픽 증가 시 MSA로 점진 전환 가능.

### 의사결정 2: 비즈니스 모델

| 대안 | 장점 | 단점 | 채택 |
|---|---|---|---|
| A. 자사몰 (단일 브랜드) | 단순, 빠른 구축 | 자산 재사용 범위 좁음 | ❌ |
| **B. 오픈마켓형 (자사+입점)** | 커머스 시장 대표 모델, 자산 재사용 넓음 | 복잡도 높음 (입점사·정산·클레임) | ✅ |
| C. 구독형 | 반복 결제 모델 | 시장 범위 좁음 | ❌ |

**채택 근거**: 방법론 자산화 목적상 가장 복잡한 모델(정산·입점사·클레임 등)을 경험해야 재사용 범위가 넓어짐.

### 의사결정 3: 기술 스택

| 항목 | 채택 | 대안 | 채택 근거 |
|---|---|---|---|
| BE 언어 | Kotlin + Spring Boot 3 | Java, Node.js | 코루틴 지원, null-safety, AI 코드 생성 호환성 |
| FE 프레임워크 | Next.js 14 (App Router) | React SPA, Vue | SSR(SEO) + CSR 혼합, 서버 컴포넌트(BFF) |
| DB | PostgreSQL | MySQL | JSON 지원, 복잡 쿼리 성능, 무료 |
| PG | 토스페이먼츠 | 아임포트, 나이스 | 개발자 친화 API, 테스트 환경 우수 |

## 작성 팁

| 팁 | 설명 |
|---|---|
| **대안 없는 결정은 기록 불필요** | 선택지가 1개면 결정이 아님 |
| **비교 기준을 먼저** | 기준 없이 비교하면 편향됨 |
| **탈락 사유 = 핵심** | "왜 안 했는가"가 미래의 재검토를 빠르게 해줌 |
| **기술스택 문서(자산)로 확장** | 채택된 기술 결정은 입력 자산 "기술스택 문서"로 정리 |
