# 샘플: ADR (Architecture Decision Record)

> **단계**: 상세설계 (또는 어느 단계든 발생 시)
> **문서범위**: 발생 시
> **문서종류**: Design
>
> **작성 목적**: 설계 중 발생한 기술 결정을 "왜 이렇게 결정했는가"와 함께 기록한다.
> 대안 비교·트레이드오프를 명시하여, 나중에 "왜 이렇게 되어 있는가" 질문에 답한다.
>
> **흐름 내 위치**: 어느 단계에서든 발생 가능. 특정 선행 없음.
>
> **작성 주체**: 시니어 개발자 (결정 참여자 전원 검토)

---

## ADR 템플릿

```markdown
# ADR-{SEQ}: {결정 제목}

## 상태
- [ ] 제안 (Proposed)
- [x] 승인 (Accepted)
- [ ] 폐기 (Deprecated)
- [ ] 대체 (Superseded by ADR-xxx)

## 맥락 (Context)
{어떤 상황에서 이 결정이 필요했는가}

## 결정 (Decision)
{무엇을 결정했는가 — 한 문장}

## 대안 비교

| 대안 | 장점 | 단점 | 탈락 사유 |
|---|---|---|---|
| A. ... | ... | ... | ... |
| B. ... | ... | ... | ... |
| **C. (채택)** | ... | ... | — |

## 결과 (Consequences)
- 긍정: ...
- 부정: ...
- 주의: ...

## 참여자
- {이름/역할}
- {이름/역할}
```

## 샘플: ADR-001 재고 선점 방식

### 상태: 승인 (Accepted)

### 맥락
주문 결제 시 재고를 선점해야 하는데, 일반 상품과 행사 상품의 트래픽 패턴이 다르다.
일반 상품은 동시 주문이 적지만, 행사 상품은 특정 시간에 트래픽이 폭증한다.

### 결정
일반 상품은 DB `SELECT FOR UPDATE`, 행사 상품은 Redis `DECR`로 선점한다.
복원은 양쪽 모두 비동기(Outbox 이벤트)로 처리한다.

### 대안 비교

| 대안 | 장점 | 단점 | 탈락 사유 |
|---|---|---|---|
| A. DB FOR UPDATE 단일 | 구현 단순, 트랜잭션 보장 | 행사 상품 동시성 병목 | 초당 1000+ 요청 처리 불가 |
| B. Redis DECR 단일 | 높은 동시성 처리 | 장애 시 데이터 유실 위험, 복잡도 증가 | 일반 상품에 과잉 설계 |
| **C. 혼합 (채택)** | 상황별 최적, 일반은 단순·행사는 고성능 | 분기 로직 필요 | — |

### 결과
- 긍정: 일반 상품 단순성 유지 + 행사 상품 고성능 확보
- 부정: 재고 선점 로직에 분기 존재 (상품 유형 판별 필요)
- 주의: Redis 장애 시 DB fallback 전략 필요 (REQ-CAT-015 연계)

## 작성 팁

| 팁 | 설명 |
|---|---|
| **결정 = 한 문장** | 길면 여러 ADR로 분리 |
| **대안 최소 2개** | 대안 없는 결정은 ADR 대상 아님 (당연한 것) |
| **탈락 사유가 핵심** | "왜 안 했는가"가 "왜 했는가"보다 중요 |
| **상태 관리** | 나중에 뒤집힐 수 있으므로 Deprecated/Superseded 추적 |
