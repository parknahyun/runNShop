# 샘플: GWT 수용기준

> **단계**: 상세설계
> **문서범위**: Bolt
> **문서종류**: Spec
>
> **작성 목적**: EARS(⑧)의 기능요구를 Given-When-Then 시나리오로 변환하여,
> "이 요구가 올바르게 구현되었는지 어떻게 검증하는가"를 정의한다.
> QA가 그대로 테스트 케이스로 사용할 수 있는 수준으로 작성한다.
>
> **흐름 내 위치**:
> ```
> Bolt 분할 → ⑬ GWT → ⑭ 세부UC → ⑮ 인터페이스 명세
> ```
>
> **작성 주체**: 시니어 개발자 + AI 협업 (QA·기획자 검토)

---

## ID 규칙

```
AC-{DOMAIN}-{SEQ}
```
- AC: Acceptance Criteria
- DOMAIN: 3글자 약어
- SEQ: 3자리 순번

---

## 카테고리

| 카테고리 | 설명 |
|---|---|
| 정상 | Happy path — 기대 동작 확인 |
| 경계값 | 최소/최대/정확한 경계 (예: 정확히 50개, 정확히 D+10) |
| 예외 | 실패·오류·비정상 상황 |

---

## 샘플: Order-Cart Bolt (장바구니 담기)

| ID | 카테고리 | 대응 EARS | Given | When | Then |
|---|---|---|---|---|---|
| AC-ORD-001 | 정상 | REQ-ORD-059 | 고객이 로그인 상태이고, 상품A(SKU-001)가 판매중이다 | 고객이 상품A를 장바구니에 담는다 | 장바구니에 상품A·SKU-001·수량1이 저장된다 |
| AC-ORD-002 | 정상 | REQ-ORD-060 | 장바구니에 상품A·수량2가 있다 | 고객이 수량을 5로 변경한다 | 수량이 5로 갱신되고 소계가 재계산된다 |
| AC-ORD-003 | 경계값 | REQ-ORD-061 | 장바구니에 상품이 49개 있다 | 고객이 50번째 상품을 담는다 | 정상 추가된다 (최대 50개 허용) |
| AC-ORD-004 | 예외 | REQ-ORD-061 | 장바구니에 상품이 50개 있다 | 고객이 51번째 상품을 담는다 | "장바구니가 가득 찼습니다" 메시지 반환, 추가 거부 |
| AC-ORD-005 | 정상 | REQ-ORD-066 | 비회원 장바구니에 상품A·수량3이 있고, 회원 장바구니에 상품A·수량5가 있다 | 비회원이 로그인한다 | 상품A 수량이 8로 합산 병합된다 |

## 작성 규칙

| 규칙 | 설명 |
|---|---|
| 1 EARS → 1~N GWT | 정상 최소 1개 + 경계값/예외 필요 시 추가 |
| Given = 사전 상태 | 테스트 fixture 설정 조건 |
| When = 단일 트리거 | 외부에서 관찰 가능한 이벤트 1개 |
| Then = 검증 가능 결과 | 상태 변화·응답·부수효과 |
| 수치는 정책서 근거 | "50개", "10일" 같은 값에 근거 명시 |

---

## 작성 팁

| 팁 | 설명 |
|---|---|
| **When절은 트리거만** | "시스템이 판단한다"는 When이 아님 — 외부 이벤트여야 함 |
| **경계값은 3단계** | min-1(거부), min(허용), max(허용), max+1(거부) |
| **EARS 커버리지 100%** | 모든 EARS에 최소 1개 GWT 존재해야 함 |
| **QA가 바로 실행 가능** | Given이 모호하면 테스트 불가 — 구체적 데이터 예시 포함 |

---

## 근거

| 항목 | 출처 |
|---|---|
| 시나리오 도출 | EARS(⑧) 1개 → GWT N개 변환 |
| 경계값 수치 | 정책서 (50개, 10일, 3분 등) |
| 예외 시나리오 | EARS Unwanted 패턴 |
