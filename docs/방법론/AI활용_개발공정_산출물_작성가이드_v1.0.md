# AI 활용 개발 공정 — 산출물 작성 가이드 (전 공정 40종)

**버전: 1.0 (초안)**
**관련 문서**: `AI활용_개발공정_산출물_표준양식_v1.0.md`(산출물별 **무엇을** 담을지 — 필수 항목·파일 형식),
`AI활용_개발공정_프롬프트_라이브러리_v2.0.md`(**어떤 프롬프트**로 AI 초안을 뽑을지)
**목적**: 위 두 문서가 다루지 않는 마지막 한 켜 — 산출물을 **어떤 순서로, 어떤 기준으로 판단하며**
작성해야 하는지(작성 절차·판단 기준·주의사항·선행 의존성)를 정의한다. 구조(표준양식)나 프롬프트
문구를 반복하지 않고, 여기서는 **작성자가 실제로 손을 움직이는 순서와 그 과정에서 흔히 틀리는
지점**만 다룬다.

## 0. 공통 작성 절차 (전 산출물 공통)

모든 산출물은 아래 7단계를 따른다 — 개별 산출물 절만 보지 말고 항상 이 공통 절차를 기본으로 깔고,
아래 각 산출물 절은 그 위에 얹히는 **산출물 특유의 판단 포인트**만 추가로 다룬다.

1. **입력자료 확인** — 가이드 6장의 "입력자료" 열 + 표준양식 문서의 Scope를 먼저 확인해 이 산출물이
   참조해야 할 원본(정책서·ERD·이전 공정 산출물 등)을 특정한다.
2. **AI 초안 생성** — 프롬프트 라이브러리의 해당 절 프롬프트를 그대로 쓰거나 현재 맥락에 맞게
   변형해 초안을 뽑는다.
3. **Gap 판별** — 초안 중 원본 근거가 없는 항목을 걸러낸다. **추정으로 채우지 않고 "확인 필요"로
   명시**한다(00-proposal 6종에서 확립된 원칙).
4. **Human Review 요청** — Gap·휴먼결정포인트(가이드 6장)를 표로 정리해 결정권자에게 넘긴다.
5. **근거 자료 출처 매핑 작성** — 모든 서술을 원본 문서·확인 발언·타 산출물로 역추적 가능하게 표로
   남긴다(추적성 기준).
6. **선후행 산출물 정합성 확인** — 아래 각 절의 "선행 산출물"을 실제로 참조했는지, 그 산출물과
   모순되는 서술이 없는지 대조한다.
7. **5.1 자가평가** — 완전성·일관성·추적성·실행가능성·정책준수 5개 기준으로 자가평가를 남기고,
   미충족 항목은 감추지 않고 정직하게 표기한다(Reject 가능성을 감수).

**작업 흐름 다이어그램**:

```
  ① 입력자료 확인          ② AI 초안 생성          ③ Gap 판별
  ┌──────────────┐        ┌──────────────┐        ┌──────────────┐
  │ 가이드 6장의  │        │ 프롬프트      │        │ 원본 근거 없는│
  │ "입력자료" 열 │───────▶│ 라이브러리    │───────▶│ 항목 식별    │
  │ + Scope 확인  │        │ 해당 절 활용  │        │ → "확인 필요" │
  └──────────────┘        └──────────────┘        └──────┬───────┘
                                                         │
                                                         ▼
  ⑥ 선후행 정합성 확인     ⑤ 출처 매핑 작성         ④ Human Review 요청
  ┌──────────────┐        ┌──────────────┐        ┌──────────────┐
  │ 선행 산출물과  │◀───────│ 모든 서술을   │◀───────│ Gap + 휴먼    │
  │ 모순 없는지   │        │ 원본으로      │        │ 결정포인트를  │
  │ 대조          │        │ 역추적 가능   │        │ 결정권자에게  │
  └──────┬───────┘        └──────────────┘        └──────────────┘
         │
         ▼
  ┌──────────────┐
  │ ⑦ 5.1 자가평가│
  │ 완전성·일관성 │
  │ 추적성·실행성 │
  │ 정책준수      │
  └──────────────┘
```

## 1. Proposal (Initiative 단위, 6종)

### 문제정의서
- **작성 순서**: ① 배경 자료 수집(정책서·decision log·주간보고) → ② Background 서술(이 사업이
  왜 시작됐는가, 인과관계 순서로) → ③ Problem 도출(핵심 문제를 1~3개로 압축, 우선순위 순) →
  ④ Impact 작성(방치했을 때의 결과) → ⑤ Opportunity 작성(대응했을 때의 기대효과) → ⑥ 근거매핑·
  Human Review
- **판단 기준/주의사항**: BPIO 순서를 지킬 것 — Impact(방치 시 문제)와 Opportunity(대응 시 효과)를
  한 문장에 섞지 않는다(이 프로젝트에서 실제로 섞여 있던 걸 분리한 사례 있음). Impact/Opportunity를
  정량화할 근거가 없으면 "확인 필요"로 남기고 지어내지 않는다.
- **선행 산출물**: 없음(Proposal의 최초 산출물)

### 목표·KPI
- **작성 순서**: ① 문제정의서의 Problem·Impact에서 대응 목표(Objective) 도출 → ② Objective별
  KR(정량 목표) 정의, KR마다 출처 명시 → ③ baseline 대비 target 수치 확정 → ④ 조건부 목표(예:
  상위 스코프 승인 전제)는 그렇게 표기 → ⑤ 근거매핑·Human Review
- **판단 기준/주의사항**: KR의 "출처" 열은 반드시 원본 문서 또는 "없음(신규 제안)"으로 채운다 —
  출처를 얼버무리지 않는다. Objective가 여러 개면 서로 우선순위가 충돌하지 않는지 반드시 확인한다
  (독립 목표처럼 보이지만 실제로는 하나가 다른 하나의 전제조건인 경우가 있다 — 이 프로젝트의
  O1/O2/O3 재구조화 사례 참고).
- **선행 산출물**: 문제정의서

### 이해관계자맵
- **작성 순서**: ① 조직도·프로젝트 참여자 목록 확인 → ② 방법론 역할 체계(PM/TL/DE/QA/AI CoE/
  AM/Dev)에 실제 인물 매핑 → ③ 미확정 역할은 Gap으로 표기 → ④ 외부 이해관계자(고객사 등) 존재
  여부 확인
- **판단 기준/주의사항**: 소규모 팀이면 겸임 구조(5인 이하 팀 가이드)가 적용되는지 확인한다.
  담당자가 미정인 역할을 임의로 채워 넣지 않는다 — 특히 O3(자산화) 등 실행 책임이 걸린 역할(Asset
  Manager 등)이 비어 있으면 그 자체로 리스크다.
- **선행 산출물**: 문제정의서와 병행 작성 가능(엄격한 선행관계 없음)

### 범위(Scope)
- **작성 순서**: ① 스코프 변경 이력 정리(있다면 시점별로) → ② In-Scope(확정/검토중) vs
  Out-of-Scope 분류 → ③ 제외 항목별 **리스크 수용 여부** 확인(이 산출물의 핵심 의사결정 포인트) →
  ④ 근거매핑
- **판단 기준/주의사항**: 제외 항목의 리스크 수용 여부를 공란으로 두지 말고 최소 "확인 필요"로
  명시한다 — 이 열이 이 산출물 전체에서 가장 중요한 필드다.
- **선행 산출물**: 문제정의서(Background의 스코프 서사)

### 대안비교
- **작성 순서**: ① 대안 축 식별(플랫폼 모델·아이템 등 결정이 필요했던 지점) → ② 후보 목록화 →
  ③ 채택 여부 + 채택 이유 기록 → ④ 실제 비교 기록이 없는 후보는 "미기록"으로 구분
- **판단 기준/주의사항**: 비교 근거가 없는데 그럴듯한 장단점을 만들어 채우지 않는다 — 없으면
  Human Review로 넘기고 "미기록"이라고 정직하게 표시한다.
- **선행 산출물**: 문제정의서

### 리스크·가정
- **작성 순서**: ① 앞선 5개 산출물(문제정의서~대안비교)의 Human Review 항목·실측 이력에서 리스크
  수집 → ② "실제 발생함" vs "가능성 있음"으로 구분 → ③ 대응(완화/수용) 기록 → ④ 가정은 baseline·
  구조에 이미 내재된 전제를 명문화하고 검증 상태를 표기
- **판단 기준/주의사항**: 실제로 발생한 리스크는 더 높은 근거 수준을 부여한다. 가정을 이 문서에서
  처음 지어내지 말고, 다른 산출물의 수치·구조에 암묵적으로 깔려 있던 전제를 드러내는 것임을
  명시한다.
- **선행 산출물**: 앞선 5개 Proposal 산출물 전체(마지막에 작성)

## 2. Spec (Project/Bolt 단위, 6종)

**산출물 의존관계 다이어그램**:

```
  ┌──────────┐     ┌──────────┐     ┌──────────┐
  │ 용어집    │     │ 제약사항  │     │  NFR     │
  │ (Project) │     │ (Project) │     │ (Project)│
  └─────┬────┘     └──────────┘     └──────────┘
        │                                  │
        │ 용어 일관성 확보                   │ 목표 수치 참조
        ▼                                  │
  ┌──────────────┐                         │
  │ 기능요구(EARS)│◀────────────────────────┘
  │ (Bolt)       │
  └──────┬───────┘
         │ EARS 1개당 ≥1 GWT
         ▼
  ┌──────────────┐
  │ 수용기준(GWT) │
  │ (Bolt)       │
  └──────┬───────┘
         │ GWT 예외 → error_catalog 매핑
         ▼
  ┌──────────────────┐
  │ 인터페이스 명세    │
  │ (Bolt)           │
  └──────────────────┘
```

### 용어집
- **작성 순서**: ① 정책서·도메인정의서에서 용어 추출 → ② 정의·동의어 정리 → ③ 충돌 용어 발견
  시 표기 → ④ 신규 발견 용어는 버전 이력에 기록
- **판단 기준/주의사항**: 같은 용어가 다른 도메인에서 다르게 쓰이면 "충돌 여부" 열에 반드시 남긴다
  — 조용히 하나로 통일하지 않는다.
- **선행 산출물**: 없음(Spec의 최초 산출물)

### 제약사항
- **작성 순서**: ① 정책서·법무/보안 요구에서 제약 후보 추출 → ② 카테고리 분류(법무/보안/기술/
  벤더계약) → ③ 예외 승인 여부 확인
- **판단 기준/주의사항**: 출처 없는 제약을 "관행적으로 다들 그렇게 하니까"로 추정해 넣지 않는다 —
  제약은 반드시 근거 문서가 있어야 한다.
- **선행 산출물**: 없음

### 비기능요구(NFR)
- **작성 순서**: ① 품질특성별(성능/가용성/보안 등) 목표 수치 확인 → ② 측정 방법 정의 → ③ 근거
  문서 연결
- **판단 기준/주의사항**: 목표 수치의 근거가 없으면 임의로 만들지 않고 "확인 필요"로 표기한다.
- **선행 산출물**: 없음

### 기능요구(EARS)
- **작성 순서**: ① 화면·정책서에서 요구사항 후보 추출 → ② EARS 5패턴 중 적합한 패턴 선택 → ③
  ID 부여(`REQ-{DOM}-{SEQ}`) → ④ 우선순위 지정 → ⑤ 이후 GWT 매핑을 염두에 두고 트리거를 명확히
  서술
- **판단 기준/주의사항**: 패턴 선택을 틀리면(예: 트리거가 있는데 Ubiquitous로 분류) 이후 GWT
  작성이 꼬인다 — "트리거가 있는가"를 먼저 확인해 Event-driven/State-driven인지부터 가른다.
- **선행 산출물**: 용어집(용어 일관성 확보를 위해 먼저 확인 권장)

### 수용기준(GWT)
- **작성 순서**: ① EARS 요구사항 1개당 최소 1개 시나리오 도출 → ② 정상/경계값/예외로 카테고리
  분류 → ③ 대응 EARS ID 명시 → ④ 요구사항 커버리지 100% 확인
- **판단 기준/주의사항**: 대응 EARS ID 없는 GWT를 만들지 않는다(추적성 훼손). 경계값 케이스(예:
  재고 정확히 1개 남았을 때의 동시 요청)를 빠뜨리기 쉬우니 EARS 각각에 대해 "이 요구사항이 깨지는
  최소 조건이 뭔가"를 항상 자문한다.
- **선행 산출물**: 기능요구(EARS)

### 인터페이스 명세
- **작성 순서**: ① GWT 시나리오 기반으로 endpoint 도출 → ② request/response 필드 정의 → ③
  공통 응답구조 적용 → ④ error_catalog 작성(GWT의 예외 시나리오와 매핑) → ⑤ cross_field_rules 정의
- **판단 기준/주의사항**: error_catalog의 각 에러 코드가 GWT의 예외 카테고리 시나리오와 1:1
  대응하는지 반드시 대조한다 — GWT에 있는 예외인데 에러코드가 없거나, 에러코드는 있는데 GWT에
  대응 시나리오가 없는 상태를 남기지 않는다.
- **선행 산출물**: 기능요구(EARS), 수용기준(GWT)

## 3. Design (Project/Domain/Bolt 단위, 11종)

### 컴포넌트
- **작성 순서**: ① 요구사항의 도메인 경계 확인 → ② 모듈/서비스 분리 → ③ 책임 정의 → ④
  의존관계 다이어그램(plantuml component) 작성 → ⑤ **앱별 메뉴구조 작성** — 각 앱(admin/partner/
  mobile)의 전체 네비게이션 트리(1depth→2depth→화면)를 정의하고, 셸 구조(NavBar/Sidebar/BottomNav
  등)를 확정한다. 이 메뉴구조는 이후 상위 유스케이스에서 업무그룹·Bolt 매핑의 선행자료가 된다.
- **판단 기준/주의사항**: 도메인 간 직접 접근을 허용하지 않는 경계 규칙(PublicApi 경유 등)을
  반드시 명시한다 — 나중에 코드 구현에서 이 규칙이 지켜지는지 검증할 기준이 된다.
  **메뉴구조 주의사항**: 앱별로 별도 작성한다(admin·partner·mobile은 메뉴 체계가 완전히 다르다).
  메뉴 계층이 상위 유스케이스의 업무그룹·Bolt 목록과 대응하는지 대조한다 — 유스케이스에는 있는데
  메뉴에 없는 항목은 미구현(PlaceholderPage)으로 명시, 메뉴에는 있는데 유스케이스에 없는 항목은
  누락된 요구사항 후보로 검토한다.
- **선행 산출물**: 인터페이스 명세
- **Platform Bolt 식별 규칙**: 컴포넌트 작성 시 앱별 메뉴구조를 정의하면서, **앱 셸(프레임)에
  해당하는 작업을 Platform Bolt로 분리**한다.

  **Bolt 유형 분류**:
  ```
  Bolt 유형
  ├── Platform Bolt  ← 앱 셸/프레임 (도메인 무관, Project 직속, 앱별 1~2개)
  └── Domain Bolt    ← 업무화면 (기존과 동일, 도메인 소속)
  ```

  | 항목 | Platform Bolt | Domain Bolt |
  |---|---|---|
  | 소속 | **Project 직속** (도메인 없음) | Domain 소속 |
  | 범위 | 앱 셸(레이아웃·네비게이션·MDI 탭관리·인증 셸·공통 UI 컴포넌트) | 업무화면 (주문목록, 상품상세 등) |
  | 선후행 | **모든 Domain Bolt의 선행 조건** | Platform Bolt 완료 후 진입 |
  | 수량 | 앱당 1~2개 | 도메인별 다수 |

  **앱별 Platform Bolt 예시**:

  | 앱 | Platform Bolt ID | 포함 범위 |
  |---|---|---|
  | admin | BOLT-ADMIN-SHELL | NavBar + Sidebar + TabBar + MDI 탭관리 + 로그인 셸 + 공통 모달/토스트/테이블/폼 |
  | partner | BOLT-PARTNER-SHELL | NavBar + Sidebar + TabBar + MDI 탭관리 + 로그인 셸 + 공통 컴포넌트 |
  | mobile | BOLT-MOBILE-SHELL | Header + BottomNav + App Router 셸 + 로그인/인증 + 공통 컴포넌트 |

  메뉴구조도에 정의된 셸 구조가 그대로 Platform Bolt의 구현 범위가 된다.

### 상위 유스케이스
- **작성 순서**: ① 액터 식별 → ② 액터별 유스케이스 나열 → ③ 권한 범위 정의 → ④ 유스케이스가
  여러 업무 갈래로 나뉘면 **업무그룹**(대분류)으로 소제목을 나눠 정리
- **판단 기준/주의사항**: 권한 범위(예: "본인 주문만 조회 가능")를 빠뜨리면 보안 결함으로 직결될
  수 있어 반드시 명시한다. **업무그룹 규칙(조건부 3단)**: 공식 Scope 단위가 아니라 이 문서 안의
  구조화용 표기일 뿐이다 — Bolt 분할·산정·RACI·자산분류에는 영향을 주지 않는다. 그룹 기준은 새로
  만들지 않고 도메인정의서의 "OO가 하는 것" 책임 목록을 그대로 묶는다(예: Order → 주문결제/
  배송관리/클레임처리). 기본은 **업무그룹 → Bolt** 2단이며, 한 그룹 안의 Bolt 후보가 **6개를
  넘으면** 그 그룹만 중분류를 추가해 **업무그룹 → 중분류 → Bolt** 3단으로 쪼갠다 — 모든 도메인에
  강제로 3단을 채우지 않는다.
  **Platform Bolt 예외**: Platform Bolt(앱 셸)는 Domain에 소속되지 않으므로 이 문서에서 업무그룹에
  포함시키지 않는다. Platform Bolt의 유스케이스(로그인·메뉴 접근·탭 열기/닫기 등)는 별도로
  "앱 공통 유스케이스" 섹션을 만들어 기술하거나, 컴포넌트 산출물의 메뉴구조도로 갈음한다.
- **선행 산출물**: 컴포넌트

### 도메인·ERD
- **작성 순서**: ① 유스케이스에서 필요한 엔티티 도출 → ② 컬럼 정의(타입/nullable/default) → ③
  PK/FK 설정 → ④ 불변식(invariants) 명시 → ⑤ soft delete 정책·감사컬럼 적용 → ⑥ 유스케이스/화면
  대응 주석
- **판단 기준/주의사항**: 불변식(예: "결제 금액 == 주문 총액")을 빠뜨리면 코드 구현에서 검증
  로직이 누락될 위험이 크다 — ERD 작성 시점에 이미 "이 값들이 항상 만족해야 하는 관계가 뭔가"를
  자문해 명시한다.
- **선행 산출물**: 상위 유스케이스

### 상태머신
- **작성 순서**: ① ERD의 status 필드 확인 → ② 상태 목록 도출 → ③ 허용 전이표 작성 → ④
  forbidden_transitions와 사유 명시 → ⑤ 전이 트리거 조건 연결
- **판단 기준/주의사항**: 금지 전이를 빠뜨리면 잘못된 상태 전이가 코드에 그대로 구현될 위험이
  있다 — "이 상태에서 되돌아갈 수 없는 지점이 어디인가"를 항상 점검한다.
- **선행 산출물**: 도메인·ERD

### 비즈니스 프로세스
- **작성 순서**: ① 상태머신의 전이 트리거를 액티비티로 확장 → ② 액터별 스윔레인 분리(plantuml
  activity) → ③ 시작/종료조건 정의 → ④ 예외 흐름 도출
- **판단 기준/주의사항**: 정상 흐름만 그리고 예외 흐름(품절·타임아웃 등)을 누락하면, 시퀀스
  설계 단계에서 재작업이 발생한다 — 상태머신의 각 forbidden_transition에 대응하는 예외 흐름이
  있는지 대조한다.
- **선행 산출물**: 상태머신

### 이벤트 플로우
- **작성 순서**: ① 비즈니스 프로세스의 상태전이 시점에서 이벤트 후보 도출 → ② 발행/구독 도메인
  확인 → ③ 스키마 정의 → ④ 동기/비동기 결정
- **판단 기준/주의사항**: 구독 도메인이 아직 구현되지 않았으면 "구독 예정"으로 표기한다 — 실제로
  구독하지 않는데 구독한다고 쓰지 않는다(이 세션의 통합테스트 샘플에서 실제로 발견된 gap 유형).
- **선행 산출물**: 비즈니스 프로세스

### 세부 유스케이스
- **작성 순서**: ① 상위 유스케이스를 버튼/화면 요소 단위로 분해 → ② 액터 행위별 기대 결과 정의
- **판단 기준/주의사항**: 상위 유스케이스와의 연결(어느 상위 유스케이스의 하위인지)을 명시해
  추적성을 확보한다.
- **선행 산출물**: 상위 유스케이스

### 시퀀스
- **작성 순서**: ① 세부 유스케이스 + 인터페이스 명세를 결합 → ② 참여 컴포넌트 나열 → ③ 트랜잭션
  경계 표시(rect 블록) → ④ 이벤트 발행 타이밍 결정(AFTER_COMMIT 우선) → ⑤ 실패 분기(alt) 작성 →
  ⑥ wrong_patterns 기록
- **판단 기준/주의사항**: 외부 API(PG 등) 호출을 트랜잭션 안에 넣어 동기 블로킹시키지 않는다.
  이벤트를 BEFORE_COMMIT에 발행하지 않는다(커밋 실패 시 이벤트만 발행되는 정합성 문제). 이 두
  규칙은 wrong_patterns에도 명시적으로 남긴다.
- **선행 산출물**: 세부 유스케이스, 이벤트 플로우

  구현 후 비주얼 재작업 리스크가 크다 — 고객 접점 화면은 반드시 Figma 확정을 거친다.
- **선행 산출물**: 시퀀스

### ADR
- **작성 순서**: ① 설계 중 발생한 주요 의사결정 포인트 식별 → ② Context 서술 → ③ Decision 확정
  → ④ Alternatives 비교(실제 검토했던 대안만) → ⑤ Consequences 명시
- **판단 기준/주의사항**: 이미 내려진 결정을 사후에 정당화하는 문장만 채우지 않는다 — 그 시점에
  실제로 검토했던 대안과 트레이드오프를 남겨야 나중에 재검토할 때 의미가 있다(대안비교 문서와
  같은 원칙).
- **선행 산출물**: 그 결정이 발생한 시점의 산출물(ERD·시퀀스 등)

### 클래스 설계
- **작성 순서**: ① 시퀀스의 참여 객체를 클래스로 전환 → ② 책임 분배(상태전이 검증/외부통신/조회
  등을 분리) → ③ 상속·합성 구조 결정
- **판단 기준/주의사항**: 서로 다른 책임(예: 결제 로직과 재고 로직)을 한 클래스에 몰아넣지 않는다
  — 시퀀스에서 참여자가 분리되어 있었다면 클래스도 그 경계를 그대로 따른다.
- **선행 산출물**: 시퀀스

## 4. Tasks (Initiative/Project/Domain/Bolt 단위, 6종)

### RACI
- **작성 순서**: ① 이해관계자맵의 역할 체계 확인 → ② 산출물별 R/A/C/I 배정 → ③ 실제 담당자
  매핑(미배정 시 Gap 표기)
- **판단 기준/주의사항**: A(Accountable)는 반드시 산출물당 1인만 지정한다 — 복수 지정은 책임
  소재를 흐린다.
- **선행 산출물**: 이해관계자맵

### DoD 템플릿
- **작성 순서**: ① 정책서·코딩표준에서 품질기준 추출 → ② 카테고리별(코드품질/테스트/보안/문서화)
  체크항목 정의
- **판단 기준/주의사항**: 측정 불가능한 항목("품질이 좋아야 한다" 같은)은 넣지 않는다 — 체크
  가능한 항목만 포함한다.
- **선행 산출물**: 없음(Project 최초 1회 작성 후 재사용)

### 리스크 대응계획
- **작성 순서**: ① 리스크·가정(Proposal)에서 이 Bolt/Initiative에 해당하는 리스크 발췌 → ②
  트리거 조건 구체화 → ③ 대응 액션 정의 → ④ 우선순위·담당자 배정
- **판단 기준/주의사항**: 트리거 조건이 "문제가 생기면" 처럼 모호하면 실행 불가능하다 — 측정
  가능한 조건("PG 응답 5초 초과")으로 구체화한다.
- **선행 산출물**: 리스크·가정(Proposal)

### 의존성 맵
- **작성 순서**: ① WBS 초안(또는 설계 산출물 순서)에서 작업 단위 확인 → ② 작업 간 선후관계
  도출(plantuml DAG) → ③ 크리티컬 패스 식별
- **판단 기준/주의사항**: 병렬로 가능한 작업(예: Mock 완료 후 FE/BE 동시 진행)을 억지로 순차로
  그리지 않는다 — FE가 BE를 기다리며 블로킹되지 않는 구조인지 확인한다.
  **Platform Bolt 의존 규칙**: Platform Bolt(앱 셸)는 모든 Domain Bolt의 선행 노드로 배치한다.
  의존성 맵에서 아래와 같이 표현한다:
  ```
  [Phase 0] Platform Bolt (BOLT-XXX-SHELL)
      │
      │  앱 셸 완성 = 업무화면을 담을 공간 확보
      ▼
  [Phase 1] Domain Bolt (P1 핵심 업무화면) ← 병렬 진행 가능
      │
      ▼
  [Phase 2] Domain Bolt (P2/P3 나머지 업무화면)
  ```
- **선행 산출물**: 없음(WBS와 상호 보완하며 함께 작성)

### WBS(하위)·산정
- **작성 순서**: ① 클래스 설계·시퀀스에서 구현 단위 도출 → ② Epic > Story > Task 분해 → ③
  Task별 예상시간 산정(반나절 이내로 쪼개기) → ④ 선행 Task ID 연결 → ⑤ DoD 체크 항목 매핑 →
  ⑥ FE/BE 배분
- **판단 기준/주의사항**: Task가 반나절을 넘으면 더 쪼갠다(Time-box 원칙). Mock 우선 원칙에 따라
  FE 작업이 BE 완료를 기다리지 않도록 Mock JSON 작성을 앞단에 배치한다.
  **Platform Bolt WBS 배치**: Platform Bolt(앱 셸)의 Task를 WBS 최상단(Phase 0)에 배치한다.
  Domain Bolt의 모든 Task는 Platform Bolt 완료를 선행 조건으로 갖는다. 이렇게 하면 크리티컬 패스의
  첫 노드가 Platform Bolt가 되어, 셸 지연 = 전체 프로젝트 지연임이 명확해진다.
- **선행 산출물**: 클래스 설계, 의존성 맵

### DoD 체크리스트(Bolt 적용본)
- **작성 순서**: ① DoD 템플릿에서 이 Bolt에 해당하는 카테고리만 선택 → ② 체크리스트로 전환
- **판단 기준/주의사항**: 해당 없는 카테고리(예: FE가 없는 Bolt의 UI 항목)는 제외한다 — 템플릿
  전체를 기계적으로 복사하지 않는다.
- **선행 산출물**: DoD 템플릿, WBS

## 5. Code (Bolt 단위, 5종)

**작업 흐름 다이어그램**:

```
                    ┌──────────────────┐
                    │ WBS Task 순서     │
                    │ (Tasks 공정 산출물)│
                    └────────┬─────────┘
                             │
                             ▼
                    ┌──────────────────┐
                    │ Mock JSON 작성    │  ◀── API 계약(인터페이스 명세) 기준
                    │ (BE 선행)         │
                    └────────┬─────────┘
                             │
              ┌──────────────┼──────────────┐
              │              │              │
              ▼              ▼              ▼
  ┌────────────────┐  ┌──────────┐  ┌────────────────┐
  │ BE 코드 구현    │  │ FE 코드   │  │ 클래스 설계     │
  │ Controller →   │  │ 구현      │  │ (현행화)        │
  │ MockLoader →   │  │ (Mock 기반│  │ 설계 diff 기록  │
  │ JSON 반환      │  │  병렬 가능)│  └────────────────┘
  └───────┬────────┘  └─────┬────┘
          │                  │
          └────────┬─────────┘
                   │
                   ▼
          ┌──────────────────┐
          │ 자동 검증(활동)    │
          │ 컴파일 → Lint →  │
          │ SAST             │
          └────────┬─────────┘
                   │
                   ▼
          ┌──────────────────┐
          │ 단위 테스트        │
          │ GWT 경계값 기반   │
          │ Pass/Fail 기록    │
          └────────┬─────────┘
                   │
                   ▼
          ┌──────────────────┐
          │ 도메인·ERD/상태머신│

          │ 변경분 diff 기록  │
          └──────────────────┘
```

### 코드 구현
- **작성 순서**: ① WBS의 Task 순서대로 구현 → ② 클래스 설계의 책임 분배를 그대로 반영 → ③
  네이밍·컨벤션 준수 확인 → ④ Mock 데이터를 인터페이스 명세의 response 필드와 1:1 대응하도록 작성
- **판단 기준/주의사항**: 설계와 다르게 구현해야 할 사정이 생기면(프로토타입 단순화 등) 조용히
  다르게 만들지 않고 반드시 "클래스 설계(현행화)"에 diff로 남긴다.
- **선행 산출물**: WBS, 클래스 설계, 인터페이스 명세

### 자동 검증(활동)
- **작성 순서**: ① 컴파일 → ② Lint → ③ SAST 순서로 실행 → ④ 실패 시 원인 기록 후 재시도 → ⑤
  결과 요약
- **판단 기준/주의사항**: 재시도 이력을 남기지 않으면 같은 실패가 반복되는지 추적할 수 없다 —
  실패했던 시도도 기록에 남긴다.
- **선행 산출물**: 코드 구현

### 단위 테스트 실행·결과
- **작성 순서**: ① GWT 시나리오를 테스트케이스로 전환(경계값 포함) → ② 실행 → ③ 커버리지 측정
  → ④ Pass/Fail 기록
- **판단 기준/주의사항**: GWT에는 있는데 테스트가 없는 시나리오가 있으면(동시성 등 프로토타입
  단계에서 구현하지 못한 경우) 커버리지 수치와 별개로 SKIP/FAIL로 정직하게 표기한다 — 조용히
  누락시키지 않는다.
- **선행 산출물**: 수용기준(GWT), 코드 구현

### 클래스 설계(현행화)
- **작성 순서**: ① 구현 중 설계와 달라진 부분만 diff로 기록 → ② 사유 명시
- **판단 기준/주의사항**: 전체를 다시 쓰지 않는다 — 변경분만 diff로, 원본 설계 문서는 그대로
  유지한다.
- **선행 산출물**: 코드 구현

### 도메인·ERD/상태머신(현행화)
- **작성 순서**: ① 실제 DB 반영 여부 확인(프로토타입 단계는 보통 변경 없음) → ② 변경 있으면
  diff 기록
- **판단 기준/주의사항**: 실제 DB에 반영되지 않은 경우(Mock 단계) "변경 없음"이라고 정직하게
  기록한다 — 있지도 않은 변경을 지어내지 않는다.
- **선행 산출물**: 코드 구현

- **판단 기준/주의사항**: 계획과 실측이 어긋나면 오차 원인을 기록한다 — 이 기록이 다음 산정

  ("검토중" → "실제 발생함")
- **판단 기준/주의사항**: 실제로 발생하지 않았는데 발생했다고 쓰지 않는다 — 발생 여부를 정직하게

- **판단 기준/주의사항**: 통합테스트에서 이미 발견된 결함을 E2E에서 빠뜨리지 않고 동일하게 반영한다.
- **선행 산출물**: 통합테스트 결과보고서

### NFR(현행화)

- **판단 기준/주의사항**: 미충족 항목이 있으면 Go/No-Go 판단근거에 그대로 반영한다 — 임의로
  통과 처리하지 않는다.
- **선행 산출물**: DoD 체크리스트(Bolt 적용본)

### Go/No-Go 판단근거
- **작성 순서**: ① 결함 등급별 건수 집계 → ② 5.2 Go/No-Go 판단 매트릭스 적용 → ③ 최종 판정
- **판단 기준/주의사항**: Critical 결함이 남아 있는데 Go로 판정하지 않는다 — 매트릭스 기준을
  엄수한다. 판정이 곤란하면 조건부(Hold)로 정직하게 남긴다.
- **선행 산출물**: 통합테스트 결과보고서, DoD 체크리스트(최종)

## 7. 안정화 (Project/Initiative 단위, 9종)

### 운영매뉴얼/Runbook
- **작성 순서**: ① 예상 장애 유형 나열(NFR·리스크 대응계획 참고) → ② 대응 절차 작성 → ③
  에스컬레이션 경로·담당자 연결
- **판단 기준/주의사항**: 이론적으로 있을 수 있는 모든 장애가 아니라, 이번 Bolt/Initiative에서
  실제로 있을 법한 장애부터 우선 작성한다.
- **선행 산출물**: NFR(현행화), 리스크 대응계획(현행화)

### Go-Live 승인기록
- **작성 순서**: ① Go/No-Go 판단근거 확인 → ② 승인자·승인일시 기록 → ③ 조건부 승인이면 조건 명시
- **판단 기준/주의사항**: No-Go 상태인데 승인기록을 만들지 않는다 — Hold 상태면 Hold로 정직하게
  표기한다(이 세션의 안정화 샘플 사례 참고).
- **선행 산출물**: Go/No-Go 판단근거(통합테스트)

### 목표·KPI(베이스라인)
- **작성 순서**: ① 오픈 시점 실측값을 최초로 기록(이후 지속 갱신의 기준점)
- **판단 기준/주의사항**: 목표(KR) 수치와 혼동하지 않는다 — 베이스라인은 어디까지나 "시작 시점의
  실측값"이다.
- **선행 산출물**: 목표·KPI(Proposal)

### 장애/이슈 로그
- **작성 순서**: ① 발생 즉시 발생일시·등급·원인 기록 → ② 조치 완료 후 재발방지책 추가 → ③
  지속 누적
- **판단 기준/주의사항**: 사후에 몰아서 기록하지 않는다 — 발생 시점에 즉시 기록해야 추적성이
  훼손되지 않는다.
- **선행 산출물**: 운영매뉴얼/Runbook

### 리스크 대응계획(현행화)
- **작성 순서**: ① Tasks의 리스크 대응계획 대비 실제 발생 이슈로 갱신
- **판단 기준/주의사항**: 실제로 발생하지 않은 리스크는 그대로 두고, 발생한 것만 갱신한다.
- **선행 산출물**: 리스크 대응계획(Tasks), 장애/이슈 로그

### NFR(현행화)
- **작성 순서**: ① 운영 실측 데이터로 NFR 기준 재조정
- **판단 기준/주의사항**: 목표치를 실측에 맞춰 사후적으로 낮추는 것이 아니라, 실측이 목표에
  못 미치면 "미달"로 기록한다.
- **선행 산출물**: NFR(통합테스트 현행화)

### 용어집(현행화)
- **작성 순서**: ① 운영 중 발생한 신조어·CS 용어 반영 → ② 최종 확정
- **판단 기준/주의사항**: 확정 이후 변경은 버전 이력으로 관리한다 — 조용히 덮어쓰지 않는다.
- **선행 산출물**: 용어집(Spec)

### 목표·KPI(최종)
- **작성 순서**: ① 목표(KR) 대비 실적 비교 → ② 달성/미달 판정
- **판단 기준/주의사항**: 미달 항목을 누락시키지 않는다 — 성공 사례만 남기고 미달은 빼는 식으로
  편집하지 않는다.
- **선행 산출물**: 목표·KPI(베이스라인)

### 안정화 결과보고서
- **작성 순서**: ① 전체 과정 종합 → ② KPI 달성 평가 → ③ 자산화(다음 프로젝트 재사용) 권고사항
  작성
- **판단 기준/주의사항**: 이 산출물이 O3(자산화)와 직접 연결되는 지점이다 — 권고사항을 "어떤
  산출물을 어떤 프로젝트에 어떻게 재사용할지" 구체적으로 쓴다("전반적으로 잘 됐다" 같은 뭉뚱그린
  서술 금지).
- **선행 산출물**: 목표·KPI(최종), 장애/이슈 로그

## 변경 이력

v1.0 (2026-07-28): 초판 작성 — 표준양식 문서(무엇을)·프롬프트 라이브러리(어떤 프롬프트로)에
이어, 40종 전체에 대해 작성 순서·판단 기준/주의사항·선행 산출물을 정의. 대부분의 "주의사항"은
이 세션에서 `docs_method/산출물-샘플/`을 실제로 작성하며 발견한 gap 유형(구독 미구현을 구독한 것처럼
기재, 실패를 SKIP/FAIL로 숨기지 않고 정직하게 표기, 프로토타입 단순화를 diff 없이 조용히 반영
등)을 근거로 삼았다.

v1.0 개정 (2026-07-28): "상위 유스케이스" 작성 순서·판단 기준에 **업무그룹(조건부 3단 분류)**
규칙 추가 — 페페 확인. runNshop의 실제 12개 도메인 중 Order를 검토하다가, 도메인정의서에는
배송(`Delivery`)·클레임(`Claim`)이 별도 도메인이 아니라 Order의 소유 데이터·책임으로 이미
포함돼 있다는 게 확인됐다 — 즉 "누락된 도메인"이 아니라 "Order 안에 숨어서 안 보이던 업무"였다.
새 Scope 계층을 만드는 대신, 도메인정의서의 책임 목록을 그대로 업무그룹 기준으로 삼고(예: Order
→ 주문결제/배송관리/클레임처리), 그룹당 Bolt 후보가 6개를 넘을 때만 중분류를 추가하는 조건부
규칙으로 확정했다 — 모든 도메인에 3단을 강제하지 않는다.
