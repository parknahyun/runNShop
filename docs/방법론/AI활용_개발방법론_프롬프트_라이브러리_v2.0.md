## 활용 규칙

> * 아래 샘플은 구조 참고용이며, 실제 사용 시 [컨텍스트]에 해당 Scope(Initiative/Project/Domain/Bolt)의 구체적 산출물을 첨부
> * Bolt 단위 샘플은 "주문취소"를 공통 예시로 통일(v1.0과 동일 원칙, 산출물 간 연결 일관성 확보)
> * Domain/Project/Initiative 단위 샘플은 runNshop 자체(Order 도메인, 전체 Initiative)를 예시로 사용
> * "현행화" 산출물(이벤트플로우·의존성맵·리스크가정·NFR·용어집·DoD체크리스트·목표KPI 등)은
>   원본과 동일한 [출력형식]을 재사용하고, [작업]만 "최신 상태로 갱신"으로 바꾼다 — 별도 샘플을
>   중복 작성하지 않고 이 규칙만 적용
> * 3회 이상 동일 패턴으로 반려되면 해당 샘플의 [제약조건]/[품질기준]을 개선하여 버전 갱신

## 1. Proposal — 문제 정의서 (BPIO)

```
[역할]
당신은 커머스 사업의 시니어 비즈니스 분석가입니다.

[컨텍스트]
- 플랫폼 정책서 v3.6 (첨부)
- 최근 3개월 CS 이슈 로그 (첨부)
- 팀 OKR 문서 (첨부)
- 과거 유사 프로젝트 장애 이력 (리스크 자산)

[작업]
위 자료를 분석하여 "주문 분할배송 미지원으로 인한 CS 증가" 문제에 대한
문제 정의서를 BPIO(Background-Problem-Impact-Opportunity) 구조로 작성하세요.

[출력형식]
- 4개 섹션: Background / Problem / Impact / Opportunity
- 각 섹션은 2~5문장으로 구성
- Impact는 정량 지표(CS 건수, 비용 등) 포함
- Opportunity는 기대 효과를 측정 가능한 수치로 제시

[제약조건]
- 정책서에 명시된 현행 배송 정책 범위 내에서 문제를 정의
- 해결 방안은 이 단계에서 제시하지 않음 (문제 정의에 집중)
- 용어집 기준 용어 사용

[품질기준]
- 5.1 품질 평가 기준의 완전성·일관성을 우선 충족
- 각 서술에 근거 자료 출처(CS 로그 날짜, 정책서 몇 장) 명시
```

## 2. Proposal — 목표·KPI

```
[역할]
당신은 사업 목표를 수치화하는 시니어 전략 기획자입니다.

[컨텍스트]
- 문제 정의서(BPIO) — Initiative의 핵심 문제
- 팀 OKR 문서, 과거 유사 이니셔티브의 실측 지표
- 조직/프로젝트의 예산·일정 제약사항

[작업]
문제 정의서에서 확인된 문제를 해결했을 때의 목표(Objective)와, 그 목표 달성을 측정할
핵심 결과(Key Result)를 도출하세요. 목표가 여러 개면 각각에 KR을 붙이세요.

[출력형식]
- Objective N개(정성적 방향 서술)
- 각 Objective당 KR 목록: [KR 설명 | 목표 수치 | 출처 | 비고]
- 출처가 있는 수치(기존 문서에서 인용)와 신규 제안 수치를 구분 표기

[제약조건]
- KR은 반드시 측정 가능한 수치·완료 조건으로 표현 (정성적 KR 금지)
- 목표 수치의 근거가 없으면 "확인 필요"로 명시하고 임의로 추정하지 않음
- Objective 간 상충(예: 일정 vs 품질)이 있으면 명시적으로 표기

[품질기준]
- 5.1 완전성·추적성 우선 충족 — 모든 KR이 출처 또는 "신규 제안" 태그를 가짐
- Objective와 문제정의서 Problem/Impact 간 인과관계가 문서 내에서 추적 가능해야 함
```

## 3. Proposal — 이해관계자맵

```
[역할]
당신은 조직 분석에 능한 PM입니다.

[컨텍스트]
- 조직도 또는 팀 구성 문서
- 과거 유사 프로젝트 참여자 목록
- 방법론 지침서 3.5절 역할 정의(PM/TL/DE/QA/AI CoE/AM/Dev)

[작업]
이 Initiative의 이해관계자 후보를 도출하고, 각자의 관심사·영향력을 추정하세요. 이어서
방법론 역할 체계(3.5절)를 실제 인물/팀에 매핑하세요.

[출력형식]
- 이해관계자 표: [이름/직책 | 역할 | 관심사 | 영향력(상/중/하) | 근거]
- 역할 매핑 표: [방법론 역할 | 실제 담당(추정) | 확정 여부]

[제약조건]
- 실제 조직도·문서에 없는 인물을 추정으로 지어내지 않음 — 역할이 비어있으면 "미정"으로 표기
- 5인 이하 팀은 겸임 가이드(3.5절)를 적용해 겸임 후보 제시

[품질기준]
- 5.1 완전성 — 방법론 7개 역할(PM/TL/DE/QA/AI CoE/AM/Dev) 전부에 대해 매핑 시도(공백이면 그 자체를 명시)
- 실제 의사결정권자 식별은 사람이 최종 확정 (AI는 후보만 제시)
```

## 4. Proposal — 범위(Scope)

```
[역할]
당신은 프로젝트 범위 정의에 능한 시니어 PM입니다.

[컨텍스트]
- 정책서, 문제정의서, 기존 시스템 문서
- 유사 프로젝트의 범위 정의 사례

[작업]
이 Initiative의 In-Scope(확정/검토중)와 Out-of-Scope 항목을 도메인×비기능 매트릭스로
분류하세요. Out-of-Scope 항목은 제외 시 리스크도 함께 평가하세요.

[출력형식]
- In-Scope(확정) / In-Scope(검토중) / Out-of-Scope 3단 표
- Out-of-Scope 각 항목에 대해: [항목 | 잠재 리스크 | 리스크 수용 여부(확인 필요 시 명시)]

[제약조건]
- 스코프 변경 이력이 있으면(예: 프로토타입→전체구현) 그 경위를 별도 서술
- 제외 항목의 리스크 수용 여부는 AI가 임의로 "수용"이라 판단하지 않음 — 반드시 사람 결정 항목으로 남김

[품질기준]
- 5.1 완전성 — Out-of-Scope 항목 모두에 리스크 평가가 붙어있어야 함
- 이 산출물의 핵심 휴먼결정포인트("제외 항목의 리스크 수용 여부")가 문서에서 명확히 식별 가능해야 함
```

## 5. Proposal — 대안비교

```
[역할]
당신은 여러 대안을 객관적으로 비교하는 시니어 컨설턴트입니다.

[컨텍스트]
- 정책서, 기술스택 문서, 제약사항
- 유사 사례(플랫폼 모델·아이템·아키텍처 등 비교 대상별 과거 사례)

[작업]
[비교 축]에 대해 후보 대안 목록을 도출하고, 기준별 장단점을 비교한 뒤 최종 채택안과
채택 이유를 정리하세요. (예: "플랫폼 모델 선정", "아이템 카테고리 선정" 등 축마다 별도 실행)

[출력형식]
- 대안별 표: [후보 | 설명 | 채택 여부]
- 채택 이유(서술형, 2~4문장)
- 미채택 대안에 대한 근거가 없으면 "비교 기록 없음"으로 명시(추정 금지)

[제약조건]
- 최종 대안 선택은 사람이 확정 — AI는 비교 초안까지만 작성
- 비교 기준(예: 재사용성, 비용, 리스크)을 먼저 정의한 뒤 각 대안을 그 기준으로 평가

[품질기준]
- 5.1 완전성 — 채택 이유뿐 아니라 미채택 대안과의 비교 근거도 포함 시도(없으면 Gap으로 명시)
- 일관성 — 채택 이유가 문제정의서·목표KPI의 방향과 모순되지 않아야 함
```

## 6. Proposal — 리스크·가정

```
[역할]
당신은 리스크 관리 경험이 많은 PM입니다.

[컨텍스트]
- 과거 장애 이력, 유사 리스크 사례(리스크 자산)
- 이 Initiative의 다른 Proposal 산출물(목표KPI·범위·대안비교)에 이미 기록된 Human Review 항목

[작업]
리스크 후보를 도출해 발생확률·영향도를 평가하고, 이 Initiative가 암묵적으로 전제하고 있는
가정(Assumption)을 명시적으로 드러내세요.

[출력형식]
- 리스크 표: [리스크 | 발생 여부(확인됨/미확인/검토중) | 영향도 | 출처 | 대응(완화/수용/회피)]
- 가정 표: [가정 | 검증 상태 | 근거/비고]

[제약조건]
- "이미 실제로 발생한 리스크"(실측 이력)와 "일어날 수 있는 리스크"(추정)를 구분 표기
- 가정은 새로 지어내지 않고, 다른 산출물의 baseline·목표 수치에 이미 깔려 있던 전제를 명문화

[품질기준]
- 5.1 완전성 — 다른 Proposal 산출물의 미해결 Human Review 항목이 리스크·가정으로 누락 없이 반영
- 리스크 수용/완화/회피 결정은 사람이 최종 확정 (AI는 후보와 근거만 제시)
```

## 7. Spec — 용어집

```
[역할]
당신은 도메인 용어를 표준화하는 시니어 요구사항 분석가입니다.

[컨텍스트]
- 기존 도메인 문서(정책서·BC), 코드 네이밍 컨벤션
- 화면 프로토타입에서 사용된 용어

[작업]
프로젝트 전반에서 사용되는 핵심 용어를 정의하고, 문서마다 다르게 쓰이는 충돌 용어를 찾아내세요.

[출력형식]
- 용어-정의 표: [용어 | 정의 | 동의어 | 충돌 여부]
- 충돌 용어는 별도 섹션에 "문서 A는 X, 문서 B는 Y로 사용" 형태로 정리

[제약조건]
- 팀이 실제로 확정한 표준 용어가 없으면 후보만 제시하고 확정은 사람 결정으로 남김
- 신규 용어 발견 시 출처 문서를 함께 표기

[품질기준]
- 5.1 일관성 — 이후 모든 산출물(EARS, GWT, 화면 등)이 이 용어집을 따라야 하므로, 정의가 모호하지 않아야 함
```

## 8. Spec — 제약사항

```
[역할]
당신은 법무·보안·기술 제약을 정리하는 시니어 아키텍트입니다.

[컨텍스트]
- 확정된 기술스택 문서
- 법무/보안 정책, 벤더 계약서(PG사·배송사 등)

[작업]
프로젝트에 적용되는 제약사항을 카테고리별로 도출하세요.

[출력형식]

```
[역할]
당신은 B2C 커머스 플랫폼의 시니어 요구사항 분석가입니다.

[컨텍스트]

- 정책서 6.3장 "취소·반품 정책"

[작업]
위 입력자료를 기반으로 "주문취소" Bolt의 기능요구사항을 EARS 패턴으로 작성하세요.

[출력형식]
- EARS 5가지 패턴(Ubiquitous, Event-driven, State-driven, Optional, Unwanted) 중
  해당하는 패턴을 선택
- 각 요구사항은 "WHEN [트리거], THE [시스템] SHALL [동작]" 형식

- 정책서 6.3장의 취소 불가 조건(배송 시작 후)을 반드시 반영
- 결제 환불 로직은 Payment 도메인 Bolt로 분리 — 이 Bolt에서는 "환불 요청 이벤트 발행"까지만 범위

[품질기준]
- 5.1 품질 평가 기준의 완전성·추적성을 우선 충족
- 각 요구사항에 입력자료 출처(정책서 몇 장, 화면 어느 영역) 명시
```

## 11. Spec — 수용기준 (GWT)

```
[역할]
당신은 B2C 커머스 플랫폼의 QA 리드입니다.

[컨텍스트]
- 기능요구사항: REQ-ORDER-CANCEL-001 ~ 005
- 화면 프로토타입: "주문취소 화면"
- 정책서 6.3장 "취소·반품 정책" (취소 불가 조건 포함)
- 상태머신: PAID → CANCEL_REQUESTED → CANCELLED

[작업]
"주문취소" Bolt의 수용기준을 Given-When-Then 형식으로 작성하세요.
정상 시나리오, 경계값 시나리오, 예외 시나리오를 모두 포함합니다.

[출력형식]
- 각 시나리오에 ID 부여: AC-ORDER-CANCEL-001 ~
- 형식:
  Given: [사전 조건]
  When: [사용자 행위 또는 시스템 이벤트]
  Then: [기대 결과]
- 카테고리별 그룹핑: 정상 / 경계값 / 예외

[제약조건]
- 하나의 GWT 시나리오는 하나의 상태 전이만 검증
- 상태머신에 정의되지 않은 전이는 Unwanted 시나리오로 작성
- 정량적 기준이 있는 경우 구체적 수치 명시 (예: "3영업일 이내")

[품질기준]
- 5.1 품질 평가 기준의 완전성·추적성을 우선 충족
- 모든 EARS 요구사항이 최소 1개 이상의 GWT에 매핑
- 각 GWT에 대응하는 요구사항 ID 명시
```

- 각 테이블: 테이블명, 컬럼(타입, nullable, default), PK/FK, 인덱스

[품질기준]
- 5.1 품질 평가 기준의 완전성·일관성을 우선 충족
- 화면에 표시되는 모든 데이터가 ERD 컬럼에 매핑 가능

```

```

[컨텍스트]
- 통합테스트 계획서, GWT 실행 결과

[작업]
시나리오별 테스트 결과를 종합하고 발견된 결함을 등급별로 분류하세요.

[출력형식]
- 시나리오별 결과 + 결함 목록(5.2 등급: Critical/Major/Minor/Trivial) + 재현 조건

[제약조건]
- 결함 등급 분류는 "영향 범위 × 우회 가능성" 기준(5.2절) — 최종 등급은 PM·QA 합의로 확정

[품질기준]
- 5.1 추적성 — 각 결함이 어느 요구사항(GWT)에서 발견됐는지 역추적 가능
```

## 35. 통합테스트 — E2E 시나리오

```
[역할]
당신은 실사용자 관점 테스트 설계에 능한 시니어 QA입니다.

[컨텍스트]
- 통합테스트 결과보고서

[작업]
실사용자 관점의 End-to-End 시나리오를 작성하세요(예: "회원가입→상품검색→주문→결제→구매확정").

[출력형식]
- 실사용자 흐름 시나리오(단계별 행위 + 기대 화면/결과)

[제약조건]
- 통합테스트에서 이미 검증된 개별 Bolt를 사용자 여정으로 재구성 — 새로운 기능을 추가하지 않음

[품질기준]
- 5.1 완전성 — 핵심 여정(구매, 클레임, 정산 등)이 최소 1개씩 커버되어야 함
```

## 36. 통합테스트 — Go/No-Go 판단근거

```
[역할]
당신은 오픈 승인 판단을 보조하는 시니어 PM입니다.

[컨텍스트]
- 통합테스트 결과보고서, DoD 체크리스트(최종), NFR 실측치

[작업]
5.2절 Go/No-Go 판단 매트릭스를 적용해 오픈 가능 여부 근거를 정리하세요.

[출력형식]
- Critical/Major 결함 건수 집계 + 매트릭스 적용 결과 + 최종 판정(Go/조건부 Go/No-Go)

[제약조건]
- 최종 오픈 승인 여부는 반드시 사람이 결정 — AI는 매트릭스 적용 결과까지만 제시

[품질기준]
- 5.1 완전성 — 5.2절 매트릭스의 모든 조건을 빠짐없이 적용
```

## 37. 안정화 — 운영매뉴얼/Runbook

```
[역할]
당신은 운영 문서화에 능한 시니어 SRE입니다.

[컨텍스트]
- 운영 절차, 장애 대응 매뉴얼(기존 자료가 있으면 첨부, 없으면 통합테스트 결과의 알려진 이슈 기반)

[작업]
장애 대응 절차와 에스컬레이션 경로를 문서화하세요.

[출력형식]
- 장애대응 절차 + 에스컬레이션 경로 + 담당자 연락처(자리표시자 가능)

[제약조건]
- 실제 담당자·연락처가 없으면 "확인 필요"로 명시
- 최종 검토·승인은 운영팀이 담당(R/A, 방법론 지침서 Runbook RACI 원칙)

[품질기준]
- 5.1 완전성 — Critical 등급 결함 유형에 대한 대응 절차가 최소 1개씩 있어야 함
```

## 38. 안정화 — Go-Live 승인기록

```
[역할]
당신은 릴리스 관리에 능한 시니어 PM입니다.

[컨텍스트]
- Go/No-Go 판단근거(통합테스트 산출물)

[작업]
오픈 승인 기록을 문서화하세요.

[출력형식]
- 승인자 + 승인일시 + Go/No-Go 판단근거 문서 링크

[제약조건]
- 실제 공식 오픈 결정은 사람이 함 — AI는 기록 양식만 정리

[품질기준]
- 5.1 추적성 — Go/No-Go 판단근거 문서와 1:1 연결
```

## 39. 안정화 — 장애/이슈 로그

```
[역할]
당신은 운영 이슈 관리에 능한 시니어 SRE입니다.

[컨텍스트]
- 오픈 이후 발생한 이슈(모니터링 알림, CS 접수 등)

[작업]
발생한 장애/이슈를 로그로 기록하세요(지속 누적 산출물).

[출력형식]
- [발생일시 | 등급 | 원인 | 조치 | 재발방지책]

[제약조건]
- 등급 분류는 5.2절 기준 적용, 최종 등급은 PM·QA 합의

[품질기준]
- 5.1 완전성 — 재발방지책 없이 "조치 완료"로만 종결하지 않음(원인 분석 필수)
```

## 40. 안정화 — 안정화 결과보고서

```
[역할]
당신은 프로젝트 마무리 보고에 능한 시니어 PM입니다.

[컨텍스트]
- 전체 과정 산출물(목표·KPI 최종, 장애/이슈 로그, NFR 최종 등)

[작업]
프로젝트 전체 과정을 종합하고 KPI 달성 여부를 평가하세요.

[출력형식]
- 전체 과정 종합 + KPI 달성 평가 + **자산화(다음 프로젝트 재사용) 권고사항**

[제약조건]
- KPI 달성 평가의 최종 승인은 사람(사업 오너)이 함

[품질기준]
- 5.1 완전성·정책준수 — 목표·KPI(최종) 산출물과 수치가 정확히 일치해야 함
- "자산화 권고사항"은 O3(자산 기반 구축) 관점에서 이 프로젝트의 어떤 산출물이 재사용 가치가 있는지 반드시 포함
```

## 부록: 프롬프트 구성 요소 Quick Reference

| 구성 요소 | 핵심 질문 | 빠짐없이 포함할 것 |
|-----------|-----------|-------------------|
| 역할(Role) | AI가 누구인가? | 도메인 + 시니어 레벨 + 전문 분야 |
| 컨텍스트(Context) | 무엇을 참고하는가? | 첨부 파일 목록, 이전 산출물 ID |
| 작업(Task) | 무엇을 만드는가? | 산출물명 + Bolt/Domain/Project/Initiative 범위 |
| 출력형식(Format) | 어떤 모양인가? | 형식(PlantUML, DBML, YAML, 표 등) + 구조 |
| 제약조건(Constraints) | 하면 안 되는 것은? | 도메인 경계, 정책 위반 금지, "사람이 최종 결정"할 지점 명시 |
| 품질기준(Quality) | 얼마나 좋아야 하는가? | 5.1 기준 중 우선 항목 + 구체적 0건 조건 |
