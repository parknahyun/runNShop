## ADR-011: 재고 선점 시점을 "PG 결제 요청 시"로 확정

| 항목 | 내용 |
|---|---|
| **제목** | 재고 선점 시점 결정 |
| **상태** | 승인 (2026-07-28) |
| **Context** | 재고 선점을 언제 할지 결정 필요. 선점 시점에 따라 재고 낭비율과 사용자 경험이 상충. 주문서 진입~결제 완료까지 평균 3분 소요(이커머스 표준) — 이 시간 동안 재고를 묶으면 다른 고객 구매 기회가 차단됨. |
| **Decision** | **결제 요청 시점**에 재고 선점한다. 고객이 "결제하기" 버튼을 눌러 실구매 의도를 확인한 후에만 재고를 잡는다. |
| **Alternatives** | |

| 대안 | 장점 | 단점 | 채택 여부 |
|---|---|---|---|
| (a) 주문서 진입 시 선점 | 결제 시 품절 확률 낮음 | 이탈률(60~70%) 감안 시 재고 낭비 심각, TTL 관리 복잡 | ❌ |
| (b) 결제 요청 시 선점 | 실구매 의도 확인 후 선점, 재고 효율 극대화 | 결제 요청 폭주 시 선점 API 부하 집중 | ✅ 채택 |
| (c) 결제 완료 후 차감 | 가장 단순 | 동시 주문 시 초과 판매 발생 가능 (치명적) | ❌ |

| **Consequences** | - 결제 요청 폭주 시 재고선점 API 부하 집중 → Redis 기반 TTL 락으로 대응 (프로토타입에서는 미적용, 본개발 시 구현)<br>- 재고선점 실패 시 주문 즉시 CANCELLED + 품절 안내 (REQ-ORD-058)<br>- 선점 후 3분 내 PG 응답 미수신 시 타임아웃으로 선점 해제 (REQ-ORD-078) |

## ADR-012: Outbox 패턴으로 이벤트 발행 (AFTER_COMMIT)

| 항목 | 내용 |
|---|---|
| **제목** | 도메인 이벤트 발행 방식 결정 |
| **상태** | 승인 (2026-07-28) |
| **Context** | Order→Payment, Order→Catalog 등 도메인 간 이벤트 통신에서 "DB 커밋과 이벤트 발행의 정합성"을 보장해야 한다. BEFORE_COMMIT에 이벤트를 발행하면 커밋 실패 시 이벤트만 소비되는 유령 이벤트 문제가 발생한다. |
| **Decision** | **Outbox 패턴**을 채택한다. 트랜잭션 안에서 Outbox 테이블에 이벤트를 INSERT하고, AFTER_COMMIT 시점에 비동기로 발행한다. |
| **Alternatives** | |

| 대안 | 장점 | 단점 | 채택 여부 |
|---|---|---|---|
| (a) BEFORE_COMMIT 발행 | 구현 단순 | 커밋 실패 시 유령 이벤트 — 정합성 치명적 | ❌ |
| (b) AFTER_COMMIT 직접 발행 (Outbox 없음) | DB 부하 없음 | 발행 실패 시 이벤트 유실 — 복구 불가 | ❌ |
| (c) Outbox 테이블 + Polling Publisher | 정합성 보장 + 유실 없음 | 약간의 지연(polling 주기), Outbox 테이블 관리 | ✅ 채택 |
| (d) CDC(Change Data Capture) | Outbox보다 지연 짧음 | 인프라 복잡도 높음 (Debezium 등), 프로토타입에 과도 | ❌ |

| **Consequences** | - 모든 도메인 이벤트는 Outbox 테이블 경유 → `08-시퀀스.md` wrong_patterns에 "BEFORE_COMMIT 발행 금지" 명시<br>- Outbox Polling 주기: 1초 (프로토타입), 본개발 시 CDC 전환 검토 가능<br>- 멱등 처리 필수: 구독자는 동일 이벤트 중복 수신 가능 (REQ-PAY-035 콜백 멱등) |

## ADR-013: 부분취소 미지원 — 전체취소 후 재주문 방식 채택

| 항목 | 내용 |
|---|---|
| **제목** | 주문 부분취소 지원 여부 |
| **상태** | 승인 (2026-07-30) |
| **Context** | 고객이 3개 상품 주문 중 1개만 취소하고 싶을 때, (a) 부분취소로 해당 상품만 빼거나 (b) 전체취소 후 나머지 2개로 재주문하는 방식이 있다. 부분취소는 상품별 할인 안분·부분 PG 취소·배송비 재계산 등 복잡도가 극도로 높다. |
| **Decision** | **1단계에서는 부분취소 미지원** — 전체취소 후 재주문 방식으로 운영한다. |
| **Alternatives** | |

| 대안 | 장점 | 단점 | 채택 여부 |
|---|---|---|---|
| (a) 부분취소 지원 | UX 우수 | 할인 안분·PG 부분취소·배송비 재계산 복잡도 극고, 정산 로직 복잡 | ❌ (2단계 검토) |
| (b) 전체취소 후 재주문 | 구현 단순, 정산 명확 | 고객 1~2분 추가 소요 | ✅ 채택 |

| **Consequences** | - REQ-ORD-006에 "부분취소 불가 — 전체취소 후 재주문" 명시<br>- 반품(배송완료 후)은 상품 단위 부분반품 가능 — 이때는 결제 시점 스냅샷 기준 안분 환불 (REQ-ORD-092)<br>- 2단계 UX 개선 시 부분취소 도입 재검토 |
