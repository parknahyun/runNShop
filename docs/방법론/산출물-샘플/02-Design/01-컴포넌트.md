# 샘플: 컴포넌트 (Design, Project 단위)

> 아래 두 다이어그램은 Scope가 다르다 — ①은 "주문결제" Bolt 하나를 구현할 때 필요한 서비스
> 클래스 수준의 상세도이고, ②는 Initiative 전체(12개 도메인)의 의존관계를 도메인 단위로 조망한
> 것이다. 컴포넌트 산출물은 실제로는 ②(Project 전체 조감)를 먼저 그리고, ①처럼 Bolt를 진행할
> 때마다 해당 슬라이스만 클래스 수준으로 확대해 나가는 방식으로 함께 쓰인다.

## ① 클래스 수준 상세 (주문결제 Bolt 슬라이스)

```
Order Module            Payment Module           Inventory(Catalog) Module
┌──────────────┐        ┌──────────────┐         ┌──────────────┐
│ OrderController│──────▶│PaymentController│      │ StockService  │
│ OrderService   │◀────▶│PaymentService   │──────▶│ (재고 선점 API)│
│ OrderRepository│       │PaymentGateway   │       └──────────────┘
└──────────────┘        │ (PG 어댑터)      │
                         └──────────────┘
```
- **책임**: Order=주문 오케스트레이션(상태 관리), Payment=PG 연동·결제 상태 관리, Inventory=재고 선점/복원
- **경계 규칙**: Order는 Inventory 테이블 직접 접근 금지 → StockService의 PublicApi만 호출
- **배포 단위**: 현재 Modular Monolith 내 패키지 분리(`com.runnshop.order`, `com.runnshop.payment`)

## ② 도메인 수준 전체 조감 (Initiative 전체, 12개 도메인)

> 舊 Security 도메인은 2026-07-30 사업오너 확인으로 Config에 편입되어 별도 박스로 두지 않는다
> (인증·접근통제는 Config가 Member/Vendor와 함께 담당).

```
┌─────────────────── 1차 거래 ───────────────────┐
│   Order ◀──── 결제요청/취소, 추가배송비결제 ────▶ Payment │
└──────┬──────────────────────────────────┬──────┘
       │ 재고선점/복구, 상품가격조회             │ (분담금·귀책조회는 Settlement가 Order 호출)
       ▼                                  │
┌─────────────────── 2차 상품 ─────────────┼──────┐
│  Catalog ──── 상품승인/품절/가격변경 ───▶ Search  │
│     ▲                                   │      │
│     │ 평점업데이트(Community)              │      │
│     │ 입점사정지→상품노출중지(Vendor)         │      │
│  Promotion ──── 쿠폰조건유효성/행사가(Order조회) │      │
└──────┬───────────────────────────────────┼──────┘
       │ 쿠폰발급(Member)                     │
       ▼                                  │
┌─────────────────── 3차 고객 ─────────────┼──────┐
│  Member ◀──── 활동완료 ────▶ Community      │      │
│     ▲ 쿠폰/포인트 사용·복원(Order 호출)         │      │
│     ▼ 등급변경·포인트소멸임박                  │      │
│  Notification ◀── 주문확인/클레임접수(Order), 정산지급알림(Settlement) │
└───────────────────────────────────────────┼──────┘
       ▲ 구매확정·반품·취소완료 이벤트(Order)        │
┌──────┴──────────── 4차 파트너·운영 ──────────┼──────┐
│  Vendor ◀── 정산계좌·지급정보조회 ──▶ Settlement   │
│     ▲ MD롤 권한확인(Catalog)                  │      │
│  Config ◀────────── 전 도메인 권한확인 ──────────┘      │
│  Audit  ◀────────── 전 도메인 CUD 로그(부수효과) ───────  │
└──────────────────────────────────────────────────┘
```

**연관 강도별 분류** (강결합=동기 API 호출/오케스트레이션, 약결합=비동기 이벤트):

| 강결합 (호출자→피호출자) | 연관 기능 |
|---|---|
| Order → Catalog | 재고선점/복구, 재고존재여부 확인 |
| Order → Member | 쿠폰보유확인, 포인트잔액확인, 쿠폰/포인트 사용·복원 |
| Order → Payment | 결제승인, 결제취소, 추가배송비결제 |
| Order → Promotion | 쿠폰조건유효성 확인, 행사가조회 |
| Settlement → Order | 분담금조회, 배송비·귀책조회 |
| Settlement → Vendor | 정산계좌조회, 지급정보조회 |
| Catalog → Vendor | 입점사 계약·상태 확인 |
| Catalog → Config | MD롤 권한 확인 |

| 약결합 (발행자→수신자) | 이벤트 |
|---|---|
| Order → Settlement | 구매확정·반품완료·취소완료·교환완료 |
| Order → Vendor | 주문지표(거래액·이행률·클레임율) |
| Order → Notification | 주문확인·클레임접수·배송기한초과 |
| Catalog → Search | 상품승인·품절·가격변경·상태변경 |
| Community → Catalog | 평점업데이트(RatingUpdated) |
| Community → Member | 활동완료(ActivityCompleted) |
| Promotion → Member | 쿠폰발급(CouponIssued) |
| Vendor → Catalog | 입점사정지(VendorSuspended) → 상품노출중지 |
| Member → Notification | 등급변경·포인트소멸임박 |

**경계 규칙 예시** (①의 Order↔Catalog 규칙과 같은 원칙을 전 도메인에 적용):
- 영수증 조회는 Payment에 통합 소유, Order는 Payment API 호출로 위임(중복 정의 해소)
- PII 접근이력은 Audit이 수집·보관 전담, Member는 조회 UI만 제공
- 쿠폰 생명주기는 역할 분리 — Promotion=정의, Member=보유, Order=사용 트리거

**배포 단위**: Modular Monolith 내 12개 패키지 분리(`com.runnshop.{order,payment,catalog,promotion,
member,vendor,settlement,community,notification,search,config,audit}`), 도메인 간 호출은 전부
PublicApi 경유(직접 테이블 접근 금지 — ①의 원칙을 전 도메인으로 확장 적용)

## 앱별 메뉴구조

> Project Scope로 앱 전체 네비게이션 트리를 정의한다. 상위 유스케이스(Domain)의 선행자료로 활용.

| NavBar | 로고 + 검색 + 알림 + 프로필 |

### Platform Bolt 식별

메뉴구조 작성 과정에서 앱 셸(프레임)에 해당하는 부분을 Platform Bolt로 분리한다 — 위 표의
"셸 구조" 행들이 각 앱의 Platform Bolt 범위이며, 나머지 1depth~2depth 업무화면들은 각 도메인의
Domain Bolt로 분류된다.

| 앱 | Platform Bolt ID | 포함 범위 |
|---|---|---|
| admin | BOLT-ADMIN-SHELL | NavBar + Sidebar + TabBar + TabContent |
| partner | BOLT-PARTNER-SHELL | NavBar + Sidebar + TabBar + TabContent |
| mobile | BOLT-MOBILE-SHELL | Header + Content + BottomNav |
