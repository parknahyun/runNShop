# **AI 활용 개발 공정 가이드**

**버전: 2.2**  
**적용 범위: B2C 커머스 플랫폼 신규 구축 (기준: runNshop)**  
**전제: 업무 도메인 초기 분류 완료 (12개), 공정 진행에 따라 도메인 경계 보완 가능**

## **1\. 산업 현황 (Problem)**

기존 개발 방법론은 오랫동안 프로젝트 수행의 기준으로 활용되어 왔지만, 최근 AI 기반 개발 환경에서는 다음과 같은 변화와 한계가 나타나고 있습니다.

> * 요구사항 변경이 빈번하여 산출물 유지 비용이 증가  
> * 산출물이 많아질수록 관리 부담 증가  
> * 핵심 인력 의존도가 높아 생산성 편차 발생  
> * 테스트와 검증에 많은 시간과 비용 소요  
> * 개발 방식이 사람이 도구를 사용하는 형태에서 AI Agent와 협업하는 형태로 빠르게 변화

이러한 변화로 인해 기존 개발 방법론만으로는 AI를 개발 공정에 효과적으로 활용하기 어려워졌습니다. 특히 AI가 공정별 산출물을 생성하고 재활용하기 위해서는 입력자료와 산출물의 관계가 명확하게 정의된 체계가 필요합니다.  
따라서 **AI가 개발 공정을 이해하고 자산을 활용하여 산출물을 생성할 수 있는 새로운 AI 활용 방법론이 필요하게 되었습니다.**

## **2\. AI 활용 방법론 (Solution)**

본 방법론은 AI(Kiro, Claude 등)를 개발 공정에 실질적으로 활용하기 위해 정의한 **AI 기반 개발 활용 방법론**입니다.  
기존 개발 방법론이 사람이 요구사항을 분석하고 산출물을 작성·관리하는 방식이었다면, 본 방법론은 **AI가 조직의 자산(Asset)과 이전 산출물을 활용하여 각 공정의 산출물 초안을 생성하고, 사람이 검토·의사결정하는 협업 방식**을 목표로 합니다.  
이를 위해 각 공정을 AI가 이해할 수 있는 형태로 표준화하고, 공정별 입력자료·자산·산출물 간의 관계를 명확하게 정의합니다. 이 관계가 구체적으로 어떻게 작동하는지는 3장(구조)에서 다룹니다.  
본 방법론은 Proposal부터 Code까지는 의사결정과 구현을 위한 **Artifact 생성 중심 공정**으로 구성하고, 이후 통합 테스트와 안정화 단계는 실행 결과와 운영 경험을 **Artifact 및 Asset으로 축적하는 실행 중심 공정**으로 확장합니다.

## **3\. AI 활용 방법론 구조 (Framework)**

본 방법론은 **공정(Process), 산출물(Artifact), 자산활용(Asset Utilization)**의 세 가지 핵심 요소와 이를 뒷받침하는 기반 정의(Scope 단위, 역할)로 구성됩니다. 이들은 각각 독립적인 개념이 아니라 하나의 실행 체계를 구성하며, 프로젝트 수행 과정에서 유기적으로 연결되어 산출물 생성과 자산 축적을 반복하는 선순환 구조를 형성합니다.

```
        Asset
          │
          ▼
AI + 자산활용 ──▶ 공정(Process) ──▶ 산출물(Artifact) ──▶ 다음 공정
  ▲                                                        │
  └────────────── 프로젝트 수행을 통해 자산 축적 ───────────┘
```

프로젝트가 반복될수록 자산이 증가하고, 자산을 활용한 AI 초안의 품질과 생산성이 함께 향상되는 선순환 구조를 지향합니다. 아래에서 세 가지 핵심 요소(3.1~3.3)와 기반 정의(3.4~3.5)를 정의합니다.

### **3.1 공정 (Process)**

공정(Process)은 **AI가 개발 공정을 이해하고 수행하는 흐름**을 정의합니다. 본 방법론은 Proposal부터 Code까지는 의사결정과 구현을 위한 Artifact 생성 중심 공정으로 구성하고, 이후 통합 테스트와 안정화 단계는 실행 결과와 운영 경험을 Artifact로 축적하는 실행 중심 공정으로 확장하였습니다.  
이를 통해 AI는 각 공정에서 이전 산출물과 자산을 입력으로 활용하여 **다음 공정의 산출물 초안**을 생성하며, 구현 이후에도 검증과 운영 단계까지 일관된 AI 활용 체계를 제공합니다.

| 공정 | 핵심 개념 | 한 줄 설명 |
| :---: | ----- | ----- |
| **Proposal** | (Why) 왜 만드는가 | 해결할 문제와 목표, 추진 범위를 정의합니다. |
| **Spec** | (What) 무엇을 만들 것인가 | 기능·비기능 요구사항과 인터페이스를 정의합니다. |
| **Design** | (How) 어떻게 만들 것인가 | 요구사항을 만족하는 구조와 설계를 구체화합니다. |
| **Tasks** | (Plan) 무엇부터 구현할 것인가 | 설계를 구현 가능한 작업 단위로 분해하고 수행 계획을 수립합니다. |
| **Code** | (Build) 구현 | 설계와 작업 계획을 기반으로 실제 동작하는 코드를 구현합니다. |
| **통합 테스트** | (Verify) 검증 | 구현 결과가 요구사항대로 동작하는지 통합 환경에서 검증합니다. |
| **안정화** | (Operate) 운영 및 개선 | 운영 중 발생하는 문제를 해결하고 시스템을 안정화합니다. |

본 방법론은 산출물 중심 방법론을 기반으로 구현 이후의 검증과 운영 공정을 포함하여, AI 활용 범위를 개발부터 운영까지 확장합니다.

### **3.2 산출물 (Artifact)**

산출물은 각 공정의 수행 결과로 생성되는 공식 결과물이며, **AI가 다음 공정을 수행하는 입력자료로 활용할 수 있도록 표준화된 형태로 작성합니다.**  
산출물은 단순한 문서가 아니라 공정의 의사결정과 구현 결과를 기록하는 기준이며, **현재 공정의 출력(Output)이자 다음 공정의 입력(Input)** 역할을 합니다. 또한 재사용 가치가 있는 산출물은 자산(Asset)으로 관리되어 이후 프로젝트와 후속 공정에서 AI의 입력자료로 활용됩니다.  
**원칙**

> * **Output → Input**: 공정의 출력은 다음 공정의 입력으로 활용합니다.  
> * **Artifact → Asset**: 재사용 가능한 산출물은 자산으로 관리하여 AI가 활용할 수 있도록 합니다.

### **3.3 자산활용 (Asset Utilization)**

자산활용은 **AI 활용 방법론에 맞게 재구성된 자산을 AI의 입력자료로 활용하여 새로운 산출물을 생성하는 활동**입니다.  
AI는 각 공정의 목적에 따라 필요한 자산과 이전 공정의 산출물을 함께 활용하여 다음 공정의 산출물 초안을 생성합니다. 이를 통해 조직의 표준과 축적된 지식을 반영한 일관성 있는 산출물을 생성할 수 있으며, 사용자는 초안 작성보다 검토와 의사결정에 집중할 수 있습니다.  
공정별 자산활용 예시는 다음과 같습니다.

| 공정 | AI 입력 | AI 출력 |
| :---: | ----- | ----- |
| Proposal | 정책서, 장애 사례, 리스크 자산 | Proposal 문서(문제정의서, 목표·KPI, 범위, 리스크) |
| Spec | 정책서, 용어집, 화면 프로토타입 | SRS |
| Design | 화면정의서, 정책서, SRS | SDD |
| Tasks | SDD, 표준 템플릿 | WBS |
| Code | SDD, API 명세, 코딩 컨벤션 | Source Code |
| 통합 테스트 | Source Code, 테스트 시나리오 | 테스트 결과 |
| 안정화 | 운영 로그, 장애 이력, 운영 매뉴얼 | 운영 자산 |

프로젝트 수행 과정에서 생성된 산출물은 다음 공정의 입력자료로 활용되며, 재사용 가치가 있는 산출물은 **동일한 산출물 체계에 따라 자산으로 축적·현행화**됩니다. 축적된 자산은 이후 프로젝트와 후속 공정에서 다시 AI의 입력자료로 활용됩니다.  
정리하면, **자산(Asset)**은 재사용 가능한 조직의 지식 그 자체이고, **자산활용(Asset Utilization)**은 그 지식을 AI의 입력자료로 활용해 산출물을 생성하고, 생성된 산출물을 다시 자산으로 축적하는 선순환 과정입니다. 프로젝트를 수행할수록 AI 활용 기반은 강화되고, 산출물의 품질과 개발 생산성은 지속적으로 향상됩니다.

### **3.4 Scope 단위 정의 (초안)**

본 방법론에서 산출물의 적용 범위를 구분하는 Scope 단위는 다음과 같이 정의합니다.

| Scope 단위 | 정의 | 예시 |
| :---: | ----- | ----- |
| **Initiative** | 사업(프로젝트) 전체를 아우르는 최상위 단위. 1회 작성 후 전체 하위 공정의 출발점이 됨 | 문제정의서, 목표·KPI, 이해관계자 맵 |
| **Project** | Initiative 내에서 기술적·조직적으로 하나의 프로젝트로 관리되는 단위 | 용어집, NFR, 컴포넌트, DoD 템플릿 |
| **Domain** | 업무 도메인(주문, 상품, 회원 등) 단위. 여러 Bolt를 포괄하는 중간 계층 | ERD, 상태머신, 이벤트 플로우, 비즈니스 프로세스 |
| **Bolt** | 유스케이스 1개 단위. 설계·구현·테스트의 최소 반복 단위 | EARS, GWT, 시퀀스, WBS, 코드 |

Scope 계층 관계: Initiative ⊃ Project ⊃ Domain ⊃ Bolt

> * 하나의 Initiative는 하나 이상의 Project를 포함할 수 있다 (예: "플랫폼 리뉴얼" Initiative 아래 "고객웹 Project", "어드민 Project" 등).
> * 소규모 Initiative는 Project와 1:1로 대응될 수 있다.

### **3.5 역할 정의 (초안)**

본 방법론에서 사용하는 역할(Role)과 책임 범위는 다음과 같습니다.

| 역할 | 약어 | 책임 범위 |
| :---: | :---: | ----- |
| **PM (Project Manager)** | PM | 공정 전이 판단, Input/Output 관리, 일정·리소스 조율 |
| **Tech Lead** | TL | 기술 의사결정, 설계 승인, AI 활용 기준 공동 관리 |
| **도메인 전문가** | DE | 업무 적합성 검토, 요구사항·정책 준수 판단 |
| **QA** | QA | 산출물 품질 기준 관리, 테스트 계획·실행·판정 |
| **AI CoE (Center of Excellence)** | CoE | 프롬프트 표준 관리, AI 도구 선정·평가, 활용 기준 고도화 |
| **Asset Manager** | AM | 자산 등록·분류·현행화, Asset Registry 운영 |
| **개발자** | Dev | 코드 구현, 단위 테스트, AI 초안 검토·보완 |

**소규모 팀 역할 겸임 가이드**

> * 5인 이하 팀의 경우, 다음과 같이 역할을 겸임할 수 있다:
>   - Tech Lead가 AI CoE를 겸임 (기술 의사결정 + 프롬프트 표준 관리)
>   - PM이 Asset Manager를 겸임 (일정 관리 + 자산 등록·현행화)
>   - 도메인 전문가가 QA를 겸임 (업무 적합성 + 품질 검토)
> * 겸임 시에도 각 역할의 책임 범위는 유지하며, 의사결정 충돌 시 상위 역할(PM 또는 TL)이 최종 판단

## **4\. AI 활용 공정 실행 (Execution)**

AI 활용 공정은 프로젝트 수행 과정에서 **AI Agent가 각 공정을 효과적으로 수행하기 위한 실행 절차와 협업 방식을 정의**합니다.  
3장이 방법론의 구성 요소(What)를 정의했다면, 4장은 **각 공정에서 구체적으로 어떤 순서로, 누가, 무엇을 하는가(How)**를 정의하는 실행 체계입니다.  
본 공정은 단순히 개발 단계를 나열하는 것이 아니라, 각 공정에서 필요한 **자산(Asset)과 입력자료(Input)를 활용하는 방법, AI 수행 영역, 사람이 검토·판단해야 하는 의사결정 영역, 그리고 피드백에 의한 반복 조건**을 정의합니다.  
이를 통해 AI는 조직의 축적된 지식과 표준 자산을 기반으로 산출물 초안을 생성하고, 사람은 업무 판단, 설계 결정, 품질 검토와 같은 핵심 의사결정에 집중하는 협업 구조를 구현합니다.

### **4.1 AI 공정 실행 방식**

각 공정은 다음의 실행 Cycle로 수행됩니다. Human Review에서 반려(Reject)가 발생하면 AI Generation으로 복귀하여 피드백을 반영한 재생성을 수행합니다.

```
Asset Selection → AI Generation → Human Review ──(Pass)──→ Artifact Finalization → Asset Management
                       ▲                    │
                       └───(Reject/보완)────┘
```

| 단계 | 수행 내용 | 주체 | 진입 조건 | 종료 조건 |
| :---: | ----- | ----- | ----- | ----- |
| Asset Selection | 공정 목적에 적합한 기존 Asset과 이전 Artifact를 탐색하고 활용 범위를 결정 | AI \+ 사람 | 이전 공정 Artifact 확정 완료 | 활용 Asset 목록 합의 |
| AI Generation | 선정된 Asset과 입력자료를 기반으로 산출물 초안 생성 | AI | Asset 목록 확정 또는 Review 피드백 수신 | 초안 생성 완료 |
| Human Review | 업무 적합성, 설계 타당성, 정책 준수 검토 | 사람 | AI 초안 생성 완료 | Pass(승인) 또는 Reject(반려 사유 명시) |
| Artifact Finalization | 검토 결과 반영 후 공식 산출물 확정 | 사람 | Review Pass | 산출물 버전 태깅 및 저장 |
| Asset Management | 재사용 가능한 결과물을 자산으로 등록 및 현행화 | 사람 | Artifact 확정 | Asset Registry 등록 완료 |

**피드백 루프 규칙**

> * Review에서 Reject 시, 반려 사유를 AI의 다음 Generation 입력에 포함하여 재생성
> * 동일 산출물에 대해 3회 이상 반려가 반복되면 사람이 직접 수정 후 Finalization으로 진행
> * 반려 사유는 Asset으로 축적하여 향후 AI Generation 품질 개선에 활용

**Code 공정 실행 Cycle 예외**

Code 공정은 AI 자율도가 가장 높고(4.2 참조, High) 할루시네이션(존재하지 않는 API 호출)·보안 취약점 리스크가 다른 공정보다 크므로, Human Review 이전에 자동 검증 단계를 추가합니다.

```
Asset Selection → AI Generation → Automated Verification ──(Pass)──→ Human Review ──(Pass)──→ Artifact Finalization → Asset Management
                       ▲                       │                            │
                       │                       └──(Fail: 자동 반송)─────────┘
                       └─────────────────────(Reject/보완)──────────────────┘
```

> * **Automated Verification 항목**: 컴파일/빌드 성공, 정적 분석(Lint) 통과, 보안 스캔(SAST) 통과, 존재하지 않는 API·라이브러리 호출 여부 검증
> * Automated Verification 실패 시 사람 개입 없이 AI Generation으로 즉시 반송하여 재생성 (Human Review 단계로 넘어가지 않음)
> * Automated Verification 통과 후에만 Human Review로 진입 — 사람은 로직·설계 적합성 등 자동화가 어려운 판단에 집중
> * 6.5 Code 실행표의 "자동 검증" 행 참조

### **4.2 공정별 AI 활용 패턴**

AI 활용 방식은 공정 목적에 따라 달라지며, 각 공정에서는 기존 Asset 활용을 우선하여 산출물 생성을 지원합니다.

*아래 표는 공정 단위의 개괄적인 패턴입니다. 산출물 단위의 세부 내용(순서·입력자료·AI초안·휴먼결정포인트)은 6장 "공정별 산출물 상세"를 참고하세요.*

| 공정 | AI 활용 패턴 | 주요 활용 Asset | AI 자율도 | 핵심 리스크 |
| :---: | ----- | ----- | :---: | ----- |
| Proposal | 기존 사업 자료 분석, 문제 정의, 목표 및 추진 방향 초안 생성 | 정책서, Business Case, 장애 사례 | Low | 비즈니스 맥락 오해, 우선순위 오판 |
| Spec | 요구사항 구조화, 정책 반영, 인터페이스 정의 지원 | 용어집, 정책 Asset, 화면 Prototype | Mid | 요구사항 누락, 도메인 용어 오용 |
| Design | 설계 대안 생성, 구조 검토, 설계 문서 작성 지원 | Architecture Pattern, SDD Template | Mid | 과도한 추상화, 현실 제약 미반영 |
| Tasks | 설계 기반 작업 분해, 구현 순서 및 영향도 분석 | WBS Template, 개발 표준 | Mid-High | 공수 산정 부정확, 의존성 누락 |
| Code | 설계 기반 코드 생성, 기존 코드 패턴 활용 | Coding Convention, Source Asset | High | 할루시네이션(존재하지 않는 API 호출), 보안 취약점 |
| 통합 테스트 | 요구사항 기반 테스트 케이스 생성, 결과 분석 지원 | Test Scenario, 품질 기준 | Mid | 경계값 누락, 환경 차이 미반영 |
| 안정화 | 운영 데이터 분석, 장애 원인 분석, 개선안 도출 | Log, 장애 이력, 운영 Manual | Low | 운영 컨텍스트 부족, 긴급도 오판 |

**AI 자율도 기준**

> * **Low**: AI는 정보 수집·구조화까지, 판단과 의사결정은 전적으로 사람
> * **Mid**: AI가 초안을 완성 수준으로 생성, 사람은 검증·수정에 집중
> * **Mid-High**: AI가 높은 완성도의 결과물을 생성하나, 의존성·일정 등 외부 변수는 사람이 보정
> * **High**: AI가 실행 가능한 결과물(코드 등)을 생성, 사람은 품질 확인 중심

*Code 공정은 High 자율도와 핵심 리스크(할루시네이션, 보안 취약점) 특성상 Human Review 이전에 자동 검증 단계를 추가로 거칩니다 — 4.1 "Code 공정 실행 Cycle 예외" 참고.*

### **4.3 AI 활용 공정의 관리 기준**

AI 활용 공정은 공정별 Input, AI 작업, Human Decision, Output Artifact를 기준으로 관리합니다. 각 관리 항목의 구체적인 판단 기준과 품질 표준은 5장 "AI 활용 공정 기준"을 참조합니다.

| 관리 항목 | 관리 기준 | 관리 주체 | 관리 주기/트리거 |
| :---: | ----- | ----- | ----- |
| Input 관리 | AI 활용에 필요한 Artifact와 Asset의 범위 및 최신 상태 관리 | PM / Tech Lead | 공정 시작 시, Asset 변경 시 |
| AI 활용 기준 관리 | 공정별 AI 요청 방식, Context 구성, 프롬프트 템플릿 표준화 | AI CoE / Tech Lead | 분기 1회 정기 점검, AI 도구 변경 시 |
| Output 관리 | 생성 산출물의 형식, 품질 기준 및 검토 기준 관리 | QA / PM | Artifact 확정 시마다 |
| Review 관리 | 사람이 수행해야 하는 업무 판단 및 승인 영역 관리 | PM / 도메인 전문가 | Review 단계 진입 시 |
| Asset 관리 | 재사용 가능한 Artifact의 등록, 분류, 현행화 관리 | Asset Manager | Artifact 확정 후, 분기 1회 현행화 점검 |

### **4.4 공정 간 전이 조건**

각 공정의 완료와 다음 공정으로의 전이는 아래 기준을 충족해야 합니다. 아래 표의 "확정(Finalized)", "검토 완료", "Review 통과", "승인", "합의" 등의 표현은 해당 공정의 개별 산출물이 4.1 실행 Cycle의 Human Review에서 5.1 산출물 품질 평가 기준(Pass)을 이미 통과했음을 전제로 합니다. 즉 전이 조건은 개별 산출물 단위 품질 게이트(5.1)가 아니라, 그 산출물들이 모두 Pass된 뒤 공정 전체 단위로 추가 확인하는 상위 게이트입니다.

| 전이 | 전이 조건 (Exit Criteria) | 검증 방법 |
| :---: | ----- | ----- |
| Proposal → Spec | 문제정의·목표·범위 확정, 리스크 수용 여부 결정 완료 | Proposal 산출물 전체 Finalized 상태 확인 |
| Spec → Design | 기능요구(EARS)·수용기준(GWT)·인터페이스 명세 확정 | Spec 산출물 검토 완료, 미결 이슈 0건 |
| Design → Tasks | 설계 산출물(ERD·시퀀스·상태머신) 확정, ADR 기록 완료 | Design Review 통과, 아키텍처 승인 |
| Tasks → Code | WBS 확정, DoD 체크리스트 합의, 의존성 맵 승인 | Sprint Planning 완료 |
| Code → 통합 테스트 | Bolt 단위 구현 완료, 자동 검증(컴파일·정적분석·보안스캔) 통과, 단위 테스트 통과 | DoD 체크리스트 항목 전수 충족 |
| 통합 테스트 → 안정화 | Go/No-Go 판단 통과 | GWT 전체 Pass, NFR 기준치 충족, 5.2 Go/No-Go 판단 매트릭스 충족 |

**예외 조건**

> * **공정 생략**: 경미한 변경(버그 수정, UI 미세 조정)은 Proposal·Spec을 생략하고 Design 또는 Tasks부터 시작 가능. 단, 생략 사유를 ADR에 기록
> * **공정 병행**: Spec의 인터페이스 명세와 Design의 시퀀스는 상호 참조 관계이므로, 동일 Bolt 내에서 병행 작성 가능
> * **산출물 현행화**: 결함 발견 시점의 공정이 아니라, 결함의 근본 원인이 있는 산출물을 현행화하고 5.4 변경 영향 분석 절차에 따라 관련 산출물을 함께 재검토한다.
>   - **Code 중** 설계 결함 발견 시 → 관련 Design 산출물(클래스 설계, 시퀀스, ERD 등)을 현행화하고, 영향받는 하위 산출물 재검토
>   - **통합테스트 중** 결함 발견 시 → 단순 구현 버그는 Code 산출물만 현행화, 구조적·인터페이스 결함은 Design 산출물까지 현행화 (6.6 "이벤트 플로우/의존성 맵/리스크·가정 현행화" 행으로 반영)
>   - **안정화 중** 결함 발견 시 → 운영 영향이 있으면 우선 Hotfix로 Code 산출물을 즉시 현행화하고, 근본 원인이 설계에 있으면 Design 산출물도 별도로 현행화(차기 반영). Go-Live 이후이므로 즉시 대응과 정식 현행화를 분리한다
>   - 현행화 시 5.4 영향 전파 매트릭스로 관련 산출물을 식별해 의존성 맵에 반영하고, 영향 범위가 여러 Bolt/Domain에 걸치면 5.4 절차 전체를 따른다

AI 활용 공정의 품질과 일관성을 확보하기 위한 구체적인 기준과 표준을 정의합니다. 4장의 실행 절차가 "어떻게 진행하는가"라면, 5장은 "어떤 기준으로 판단하는가"를 정의합니다.

**"초안" 섹션 확정 우선순위**

> 아래 섹션들은 (초안) 상태이며, 프로젝트 진행 시점에 맞춰 순차 확정합니다.
>
> | 우선순위 | 섹션 | 확정 시한 | 사유 |
> | :---: | ----- | ----- | ----- |
> | 1 | 5.2 결함 분류 체계 | 통합테스트 시작 전 | Go/No-Go 판단 기준으로 즉시 필요 |
> | 2 | 3.5 역할 정의 + 부록 C RACI | Tasks 공정 시작 전 | 담당자 배정의 근거 |
> | 3 | 5.5 버전 관리 정책 | 첫 Artifact Finalization 전 | 버전 채번·태깅 기준 필요 |
> | 4 | 5.3 프롬프트 표준, 5.4 변경영향, 7.2~7.4 | 프로젝트 진행 중 점진 확정 | 운영하면서 보완 가능 |
> | 5 | 3.4 Scope 단위, 부록 A·B | 도메인 확정 단계에서 확정 | 초기 분류 후 실제 적용하며 검증 |

### **5.1 산출물 품질 평가 기준 (초안)**

Human Review 단계에서 AI 생성 산출물의 Pass/Reject를 판단하는 기준입니다. 개별 산출물이 이 기준을 Pass해야 Finalization으로 진행되며(4.1), 한 공정에 속한 산출물이 모두 Pass·Finalized된 상태가 4.4 공정 간 전이 조건의 전제가 됩니다.

| 평가 항목 | 정의 | Pass 기준 |
| :---: | ----- | ----- |
| **완전성(Completeness)** | 요구된 항목이 빠짐없이 포함되어 있는가 | 필수 항목 100% 포함, 선택 항목 80% 이상 |
| **일관성(Consistency)** | 용어·형식·논리가 문서 내/문서 간에 모순 없는가 | 용어집 준수, 이전 산출물과 모순 0건 |
| **추적성(Traceability)** | 이전 공정 산출물과의 연결(출처)이 명확한가 | 각 항목에 입력 Artifact 참조 명시 |
| **실행가능성(Actionability)** | 다음 공정에서 즉시 활용 가능한 수준인가 | 모호한 표현 0건, 구체적 수치/기준 포함 |
| **정책 준수(Compliance)** | 조직 정책·표준·제약사항을 위반하지 않는가 | 정책서 대비 위반 사항 0건 |

**공정별 평가 가중치**

| 공정 | 최우선 평가 항목 | 사유 |
| :---: | ----- | ----- |
| Proposal | 완전성, 일관성 | 후속 모든 공정의 출발점이므로 누락·모순이 치명적 |
| Spec | 완전성, 추적성 | 요구사항 누락이 설계·구현 전체에 파급 |
| Design | 일관성, 실행가능성 | 설계 간 모순은 구현 시 혼란 초래, 추상적 설계는 활용 불가 |
| Tasks | 실행가능성, 추적성 | 작업 분해가 모호하면 구현 착수 불가 |
| Code | 정책 준수, 실행가능성 | 보안·컨벤션 위반은 즉시 영향, 코드는 실행 가능해야 의미 |
| 통합 테스트 | 추적성, 완전성 | 요구사항 대비 누락 없는 검증 필요 |
| 안정화 | 완전성, 정책 준수 | 운영 매뉴얼 누락은 장애 대응 실패로 직결 |

### **5.2 결함 분류 체계 (초안)**

통합 테스트 및 안정화 공정에서 발견된 결함의 심각도를 분류하는 기준입니다. 4.4 "통합 테스트 → 안정화" 전이 조건의 "결함 0-Critical"은 아래 정의를 따릅니다.

| 등급 | 정의 | 예시 | Go/No-Go 영향 |
| :---: | ----- | ----- | ----- |
| **Critical** | 핵심 업무가 완전히 중단되며 우회 방법이 없음 | 결제 불가, 주문 데이터 유실, 시스템 전면 장애 | 0건이어야 Go |
| **Major** | 주요 기능이 정상 동작하지 않으나 우회 방법 존재 | 특정 조건에서 취소 실패(수동 처리 가능), 성능 NFR 미달 | 잔존 시 우회 방안·일정 합의 필요 |
| **Minor** | 사용에 지장은 없으나 불편하거나 표준에 어긋남 | UI 오정렬, 오탈자, 비필수 필드 누락 | Go 가능 (차기 수정 계획 수립) |
| **Trivial** | 외관·문서상의 경미한 결함 | 로그 메시지 오타, 주석 누락 | Go 가능 (백로그 등록) |

**Go/No-Go 판단 매트릭스**

| 조건 | 판정 |
| :---: | ----- |
| Critical 0건 + Major 0건 | Go |
| Critical 0건 + Major ≤ 3건 (전체 우회 방안 확보) | 조건부 Go (합의 필요) |
| Critical ≥ 1건 | No-Go |
| Major > 3건 또는 우회 불가 Major 존재 | No-Go |

**결함 분류 원칙**

> * 결함 등급은 "영향 범위 × 우회 가능성"으로 판단
> * 동일 결함이라도 운영 환경의 트래픽·사용자 규모에 따라 등급이 달라질 수 있음 — 최종 등급은 PM·QA 합의
> * 분류 시점: 결함 발견 즉시 초기 분류 → Human Review에서 최종 확정
> * Critical/Major 결함은 발견 즉시 의존성 맵에 영향 표기, 5.4 변경 영향 분석 절차 적용

### **5.3 프롬프트 엔지니어링 표준 (초안)**

AI Generation 단계에서 일관된 품질의 산출물을 생성하기 위한 프롬프트 구성 표준입니다.

**프롬프트 구성 요소**

| 구성 요소 | 설명 | 예시 |
| :---: | ----- | ----- |
| **역할(Role)** | AI가 수행할 전문가 역할 지정 | "당신은 이커머스 도메인의 시니어 시스템 설계자입니다" |
| **컨텍스트(Context)** | 참조할 Asset과 이전 Artifact 명시 | "첨부된 ERD, 인터페이스 명세, 정책서 3.2장을 참고하세요" |
| **작업(Task)** | 생성할 산출물과 범위 명확히 지정 | "주문 취소 Bolt의 시퀀스 다이어그램을 작성하세요" |
| **출력형식(Format)** | 산출물의 구조·형식·표기법 지정 | "PlantUML 형식, 액터-시스템 간 메시지 번호 포함" |
| **제약조건(Constraints)** | 지켜야 할 규칙, 제외할 사항 | "비동기 이벤트는 점선 화살표로 표기, 에러 시나리오 포함" |
| **품질기준(Quality)** | 기대하는 완성도 수준 | "5.1 품질 평가 기준의 5개 항목을 충족하도록 작성" |

**프롬프트 관리 규칙**

> * 공정별 표준 프롬프트 템플릿을 Asset으로 관리
> * 템플릿 변경 시 버전 관리 적용 (변경 사유·일자·담당자 기록)
> * 반려 사유가 3회 이상 동일 패턴이면 프롬프트 템플릿 개선 트리거
> * 각 공정별 구체적 프롬프트 예시는 별도 Asset(프롬프트 라이브러리)으로 관리하며, 위 구성 요소 6가지를 공정 특성에 맞게 조합하여 작성 — 참고: `docs_method/archive/AI활용_개발공정_프롬프트_라이브러리_v1.0.md`

### **5.4 변경 영향 분석 (초안)**

산출물 현행화 또는 수정 시 영향받는 범위를 판단하는 기준입니다.

**영향 전파 매트릭스**

| 변경 발생 산출물 | 영향받는 산출물 | 조치 |
| :---: | ----- | ----- |
| 기능요구(EARS) | GWT, 인터페이스 명세, 시퀀스, WBS, 코드 | 하위 전체 현행화 검토 |
| ERD | 상태머신, 시퀀스, 클래스, 테스트 케이스 | 관련 Bolt 재검토 |
| 인터페이스 명세 | 시퀀스, 클래스, 통합테스트 | API 계약 변경 공지 후 현행화 |
| WBS | 의존성 맵, DoD 체크리스트, 일정 | 리소스 재배정 검토 |
| 도메인 분리/통합 | ERD, 상태머신, 이벤트 플로우, 상위 유스케이스, 의존성 맵, 해당 Bolt 전체 | 영향 Domain의 Design 산출물 전면 재검토, Bolt 백로그 재구성 |

**변경 영향 분석 절차**

> 1. 변경 요청 접수 → 변경 대상 산출물 식별
> 2. 영향 전파 매트릭스에 따라 영향받는 산출물 목록 도출
> 3. 영향 범위를 의존성 맵에 표기
> 4. 변경 비용(재작업 공수) 산정 → 변경 승인/거부 결정
> 5. 승인 시 영향받는 산출물을 역순으로 현행화

*위 매트릭스는 대표 예시이며, 전체 산출물 간 영향 관계(상태머신, ADR, NFR, 비즈니스 프로세스 등 포함)는 프로젝트 착수 시 의존성 맵과 함께 전체 매트릭스로 확장·관리합니다.*

### **5.5 AI 산출물 버전 관리 정책 (초안)**

AI가 생성·재생성하는 산출물의 이력을 관리하는 정책입니다.

| 항목 | 정책 |
| :---: | ----- |
| **버전 관리 단위** | 버전은 산출물 "유형" 전체가 아니라, 3.4 Scope 단위의 개별 인스턴스마다 독립적으로 관리한다. 예: "시퀀스"는 Bolt마다 별도 인스턴스이므로 "주문취소 Bolt의 시퀀스 v1.2"와 "결제 Bolt의 시퀀스 v2.0"은 서로 무관한 버전. Initiative/Project 범위 산출물(목표·KPI, NFR 등)은 인스턴스가 하나이므로 그 하나가 계속 현행화되며 버전이 누적된다. 식별자 표기: `{산출물명}-{Scope 인스턴스명}-v{버전}` |
| **버전 채번** | Major.Minor (예: 1.0 → 1.1 → 2.0). AI 재생성은 Minor 증가, Human 확정은 Major 증가 |
| **이력 보존** | 모든 버전을 보존. 최소 직전 3개 버전은 즉시 접근 가능 상태 유지 |
| **Diff 관리** | 버전 간 변경 사항을 자동 추적. 변경 행/섹션 단위로 하이라이트 |
| **롤백 기준** | 현재 버전에서 품질 저하 발견 시, 직전 Finalized 버전으로 롤백 가능 |
| **태깅** | Finalized 산출물에 "APPROVED" 태그 부여, Draft 상태는 "DRAFT-v{n}" |
| **보관 주기** | 프로젝트 완료 후 최소 2년 보관, 자산 등록 산출물은 영구 보관 |

## **7\. 자산활용 전략 (Strategy)**

1~2장에서 정의한 방법론의 방향성(AI와 사람의 협업, 자산 기반 선순환)을 구체적인 실행 전략으로 전환합니다.  
본 방법론은 프로젝트 수행 과정에서 생성된 산출물을 AI가 활용 가능한 자산으로 관리하여 반복 작업을 최소화하고 개발 생산성을 향상시키는 것을 목표로 합니다.  
이를 위해 다음의 자산활용 전략을 적용합니다.

> 1. **표준 산출물을 재사용 가능한 자산으로 관리한다.**  
>    정책서, 화면정의서, API 명세, 설계서, 코드 등을 표준 형식으로 관리하여 AI의 입력자료로 활용한다.  
> 2. **공정별 산출물을 다음 공정의 입력자료로 활용한다.**  
>    이전 단계의 결과를 다음 단계에서 재사용하여 중복 작성과 정보 손실을 최소화한다.  
> 3. **프로젝트 자산을 조직의 공통 자산으로 재사용한다.**  
>    축적된 자산을 신규 프로젝트와 신규 Bolt의 입력자료로 활용하여 초안 작성 시간을 단축하고 산출물의 일관성을 높인다.  
> 4. **AI는 자산을 우선 활용하여 초안을 생성한다.**  
>    신규 작성보다 기존 자산의 재사용을 우선 적용하여 초안을 생성하고, 사용자는 이를 검토·보완하여 최종 산출물을 완성한다.

이 전략을 통해 프로젝트를 반복할수록 자산 활용률이 높아지고, AI 산출물의 품질과 개발 생산성이 지속적으로 향상됩니다.

### **7.1 기존 개발 방식과 차이**

| 구분 | 기존 방식 | AI 활용 공정 | 기대 효과 |
| :---: | ----- | ----- | ----- |
| 문서 작성 | 사람이 직접 작성 | AI 초안 생성 \+ 사람 검토 | 초안 작성 시간 50~70% 단축 |
| 지식 활용 | 개인 경험 중심 | Asset 기반 재사용 | 인력 교체 시 지식 손실 최소화 |
| 설계 방식 | 경험 기반 결정 | Pattern \+ Asset 기반 제안 | 설계 대안 탐색 범위 확대 |
| 품질 검증 | 수동 검토 중심 | AI 자동 검증 \+ 사람 판단 | 반복 검증 비용 절감 |
| 개선 방식 | 프로젝트 종료 후 소멸 | Asset으로 축적·재활용 | 프로젝트 반복 시 생산성 점진 향상 |

### **7.2 자산 분류 체계 (초안)**

조직의 자산을 효과적으로 관리·검색·재사용하기 위한 분류 체계입니다.

| 분류 기준 | 분류 값 | 설명 |

> * 4등급 데이터(PII, 인증키, 결제정보 등)는 AI 입력 전 마스킹·익명화 또는 완전 제외

**도구별 데이터 처리 원칙**

> * 외부 SaaS형 AI 도구: 3등급 이하만 입력, 4등급은 금지
> * 온프레미스/사내 배포형 AI 도구: 접근 통제·감사 로그를 전제로 3~4등급까지 입력 가능

**책임 주체**

> * 등급 분류 및 메타데이터 등록: Asset Manager
> * 입력 전 마스킹/제외 확인: 실제 입력을 수행하는 담당자 본인

### **부록 A. Bolt 분할 기준 (초안)**

Bolt(유스케이스 1개) 단위를 실무적으로 어떻게 나눌지에 대한 7가지 기준입니다. 아래 "도메인"은 3.4에서 정의한 Domain Scope(=Bounded Context)를 가리킵니다.

| 기준 | 내용 | 위반 시 문제 |
| :---: | ----- | ----- |
| 1. 액터 목표 단위 | 유스케이스가 액터가 하나의 목표를 완수하는 수준이어야 함 (예: "주문한다", "정산을 확인한다") | 목표보다 작으면 Bolt 오버헤드가 가치보다 커짐 |
| 2. 하나의 Bounded Context 안에서 완결 | Bolt는 반드시 도메인 1개 안에서 끝나야 함. 여러 도메인에 걸치면 이벤트 플로우로 연결하고 각 도메인은 별도 Bolt로 분리 | 도메인을 걸치면 여러 팀/여러 ERD에 걸쳐 완결 불가능해짐 |
| 3. 하나의 상태 전이(트리거→액션) | 상태머신에서 트리거 1개 → 액션 1개 단위 (예: "결제확인→CONFIRMED"와 "취소→CANCELLED"는 별도 Bolt) | 여러 전이를 한 Bolt에 넣으면 GWT 시나리오가 기하급수적으로 늘어남 |
| 4. API 1~3개 이내 | 인터페이스 명세가 한 Bolt당 API 1~3개 정도로 좁혀져야 함 | API가 5개 이상이면 시퀀스가 복잡해지고 리뷰가 어려워짐 |
| 5. Time-box: 반나절~1일 | Inception·Construction(본 문서의 Design~Tasks 논의와 Code 구현에 해당)이 이 시간 안에 끝나야 함 | 너무 크면 Bolt의 존재 의미(빠른 순환)를 상실 |
| 6. 독립적 배포/테스트 가능한 Vertical Slice | 화면+API+로직+DB를 전부 관통해서 이 Bolt 하나만으로 실제 동작 확인 가능해야 함 | 로직만 있고 화면이 없으면 다른 Bolt를 기다려야 함 |
| 7. 화면 1개 또는 화면의 핵심 상태 1개 | 자산(화면 프로토타입) 활용 관점에서 화면 하나 또는 주요 상태(목록/상세/작성 등) 하나에 대응 | 화면 여러 개를 한 Bolt에 넣으면 프로토타입 자산과 1:1 매칭이 깨짐 |

**runNshop 예시**

> * [X] 너무 큼: "주문 프로세스 전체"(Bolt 1개) → 장바구니, 결제, 재고예약, 주문분할까지 다 포함 = 여러 도메인 + 여러 상태전이 위반
> * [O] 적절함: "결제 전 재고 선점"(ADR-002) 하나만 Bolt 1개 → Inventory 도메인 안에서 완결, 상태전이 1개(AVAILABLE→RESERVED), API 1~2개, 화면 1개
> * [X] 너무 작음: "재고 선점 버튼의 로딩 스피너 표시"(Bolt 1개) → 액터 목표 수준이 아님, 별도 Bolt로 쪼갤 가치 없음

**판단이 애매할 때의 우선순위**

> 1. Bounded Context 경계 (절대 넘으면 안 됨)
> 2. 상태 전이 단위 (도메인 안에서 논리적 완결 단위)
> 3. Time-box (반나절~1일 초과 시 상태전이 기준으로도 쪼갤 방법 찾기)
> 4. API 개수(4번 기준)·화면 개수(7번 기준)는 경고 신호일 뿐 절대 기준이 아니다 — 액터 목표 완결성(1번)·Vertical Slice 완결성(6번)을 해치면서까지 API/화면 수를 맞추려고 쪼개지 않는다. 초과 시 먼저 "숨어 있는 상태전이가 있는지"(2번 기준 재적용) 확인하고, 없다면 쪼개지 않고 리뷰 시간을 늘리는 것으로 대응한다

### **부록 A.2 Bolt 분할 시점 가이드 (초안)**

Bolt 분할(매크로 레벨)은 Design 공정 안에서, Domain 단위 산출물이 끝나고 Bolt 단위 산출물이 시작되기 직전, 정확히 그 경계 지점에서 일어납니다.

```
Design 공정
  ├─ Domain 단위 (1회 작성)
  │    상위 유스케이스 → 도메인·ERD → 상태머신 → 비즈니스 프로세스 → 이벤트플로우
  │
  │    ▼ 여기서 Bolt 분할 (매크로 레벨)
  │
  └─ Bolt 단위 (반복 작성)
       세부 유스케이스 → 시퀀스 → 화면 레이아웃
            ↓
       Spec 공정 (Bolt 단위): EARS, GWT, 인터페이스명세
            ↓
       Tasks 공정 (Bolt 단위): WBS·산정, DoD 체크리스트  ← 마이크로 레벨
```

> Design과 Spec의 Bolt 단위 작업(세부 유스케이스·시퀀스 ↔ EARS·GWT·인터페이스명세)은 4.4 "공정 병행" 예외에 따라 실제로는 동시에 진행될 수 있습니다. 위 다이어그램은 Bolt 분할 이후 각 공정에서 무엇이 만들어지는지를 나열한 것이며, Design이 전부 끝난 뒤에만 Spec이 시작된다는 뜻은 아닙니다.

**왜 이 지점인가**: Bolt 분할기준 2번(Bounded Context 완결)과 3번(상태전이 단위)을 판단하려면 도메인·ERD와 상태머신이 이미 확정되어 있어야 합니다. 이 두 산출물이 없으면 "이 Bolt가 도메인 경계를 넘는지", "상태전이 1개 단위가 맞는지"를 판단할 근거 자체가 없습니다.

**두 가지 레벨**

| 레벨 | 시점 | 하는 일 |
| :---: | ----- | ----- |
| 매크로 (Bolt 백로그 구성) | Design 공정의 Domain 단위 완료 직후, Bolt 단위 반복 시작 직전 — 1회 | 도메인 전체를 몇 개의 Bolt로 쪼갤지 결정하고, 실행 순서를 배치 |
| 마이크로 (개별 Bolt 산정) | 각 Bolt의 Tasks 공정(WBS·산정) 시점 — Bolt마다 반복 | 그 Bolt 하나가 반나절/1일짜리인지 실제 작업량 추정 |

**매크로 상세: Domain 단위 산출물별 필요성**

| Domain 단위 산출물 (6.3) | Bolt 백로그 구성에 필요한 이유 |
| :---: | ----- |
| 상위 유스케이스 (item 2) | 이걸 쪼개야 Bolt 후보 목록이 나옴 |
| 도메인·ERD (item 3) | Bolt 분할기준 2번(Bounded Context 완결) 확인 가능 |
| 상태머신 (item 4) | Bolt 분할기준 3번(상태전이 단위) 확인 가능 |
| 이벤트 플로우 (item 6) + 의존성 맵 (6.4 item 4) | Bolt 순서(어떤 Bolt를 먼저 할지) 결정 가능 |

### **부록 B. 프로젝트 마일스톤 가이드 (초안, runNshop 예시)**

전체 프로젝트를 몇 주 단위로 배치할지에 대한 예시입니다. 아래 주차·기간은 runNshop 예시(12개 도메인, 7.2 참고)를 기준으로 한 추정치이며, 실제로는 팀 규모·도메인 복잡도(특히 정산·결제)·PG사 연동 등 외부 의존성에 따라 조정됩니다. 통합테스트·내부오픈의 정의는 6.6을 참고하세요.

**리소스 전제 조건**

| 항목 | 가정 |
| :---: | ----- |
| 팀 규모 | PM(PMO 겸임) 1명, 테크리드 1명, 개발 파트 4개(주문 4명, 상품 4명, 나머지 2개 파트 3명씩) — 총 16명, 개발자 14명 |
| 승인 구조 | 파트장(시니어) 위임 없이 Design·Code 산출물은 PM&테크리드 공동 승인 |
| AI 도구 활용도 | Code 공정 기준 60~70% (초안 생성 + 자동 검증), Spec/Design 공정 40~50% |
| 도메인 수 | 12개 (order, catalog, member, payment, promotion, settlement, vendor, notification, community, search, config, audit) — 파트당 3개 |
| Bolt 규모 (추정) | 도메인당 평균 5~8개 Bolt, 전체 약 60~90개 Bolt |
| 1 Bolt 소요 | 최소 2일 (부록 A Time-box의 Inception·Construction 반나절~1일에 산출물 확인·구현 검토·테스트 결과 보정 등 리뷰·수정 사이클을 더한 총 소요) |
| 병렬도 | 4개 파트 병렬 진행, 주당 8~10 Bolt 처리 가능 (Bolt당 최소 2일 기준으로 재추정, PM&테크 리뷰 병목 감안) |
| 외부 의존성 | PG사 연동 테스트 2주, 외부 API 연동 없음 (Mock 기반 프로토타입) |

> * 위 전제가 달라지면 마일스톤 주차는 비례하여 조정 필요
> * AI 도구 활용도가 30% 이하로 떨어지면 Bolt 반복 기간이 1.5~2배 증가 예상
> * 목표: 26주. 공정간 중첩 없이(순차 진행) 26주에 맞춰 배분하며, 공정별 최소 일정은 1주로 고정한다

### **약어 정리**

> * **BPIO**: Background-Problem-Impact-Opportunity (배경-문제-영향-기회 구조로 문제정의서를 서술하는 프레임워크)
> * **EARS**: Easy Approach to Requirements Syntax (패턴 기반 기능요구사항 서술 방식)
> * **GWT**: Given-When-Then (수용기준 시나리오 서술 방식)
> * **SRS**: Software Requirements Specification (소프트웨어 요구사항 명세서)
> * **SDD**: Software Design Document (소프트웨어 설계 문서)
> * **WBS**: Work Breakdown Structure (작업 분해 구조)
> * **DoD**: Definition of Done (완료 정의)
> * **ADR**: Architecture Decision Record (아키텍처 결정 기록)
> * **NFR**: Non-Functional Requirement (비기능 요구사항)
> * **RACI**: Responsible-Accountable-Consulted-Informed (역할별 책임 구분 매트릭스)
> * **DPA**: Data Processing Agreement (데이터처리 계약, AI 도구에 민감 자산 입력 시 체결 필요)
