# Vendor 도메인 기능표

> 핵심 책임: 입점사의 전체 생명주기와 계약·등급·배송사·계정 권한을 관리하고, 고객에게 노출되는
> 판매자 정보를 제공한다.

> **진행 상태 전제(2026-07-28)**: 고객화면(mobile)·배치·컨슈머(비동기 처리)는 아직 미착수,
> admin·partner도 초안 작업 상태 — 아래 N/A·스텁·dead code 발견은 결함이 아니라 진행 전 상태.
> 상세는 `README.md`의 "현재 진행 상태 안내" 절 참고.

**API 호출 개수 카운트 기준**: 화면/탭 로드 1개 = API 1개, 실제 제출 버튼 1개 = API 1개(취소·
편집토글처럼 API를 호출하지 않는 UI 전용 버튼은 제외). 같은 상세 컴포넌트를 여러 소분류가 공유할
때는 최초 진입 화면(목록 등)은 대표 소분류 1곳에만 산정하고 나머지는 자신의 탭/섹션분만 추가
산정한다(Config `11-Config.md`와 동일 원칙). 화면 자체가 없거나 코드에 해당 로직이 없는 소분류는
"N/A"로 표기.

## 코드 기반 보완 (2026-07-28, apps/ 실제 소스 조사)

- **"계정·보안관리"가 통째로 새 대분류로 확인됨** — 도메인정의서엔 없던, 벤더가 스스로 관리하는
  계정 설정 영역(담당자정보/비밀번호/2FA/세션/알림설정 5종)이 partner 앱에 전부 구현돼 있음.
  소분류가 5개라 아직 6개 임계값은 안 넘었지만 근접 — 항목이 더 늘면 중분류 검토.
  6번째로 "정산계좌 등록·인증"까지 이 대분류에 넣을지, 정산연동에 남길지는 판단이 필요해
  일단 정산연동에 남겨둠(Human Review).
- **배송사관리가 admin(마스터 관리)과 벤더(선택+배송비 설정) 2개 레이어**로 나뉨 — 도메인정의서엔
  "배송사 선택"만 있었음.
- **입점사 상태 변경은 admin에서 전용 버튼 없이 편집 폼 패턴** — Member 도메인과 동일한 UI 관행.
- **API 호출 개수를 Vendor 전체 16개 소분류로 산정(2026-07-28)** — Config에서 검증된 카운트 기준
  (화면/탭=1, 버튼=1, 취소·편집토글 제외)을 그대로 적용. admin `VendorDetail`은 기본정보/수수료율/
  패널티/정산계좌 4개 탭을 가진 하나의 상세 컴포넌트를 "입점사 상태 관리"·"수수료율 관리"·
  "정산 계좌 관리(admin 조회)"·"패널티 관리" 4개 소분류가 나눠 쓰므로, 목록 화면 로드는 "입점사
  상태 관리"에만 산정하고 나머지 3개 소분류는 각자의 탭분만 추가 산정했다(Config의 프로그램관리
  "프로그램 호출 로그 조회"와 동일 원칙).
- **partner `settings/account`의 `AccountSettingsPage`는 탭이 아니라 한 페이지에 5개 섹션이
  순차 배치된 구조**로 확인됨(담당자정보/비밀번호/2단계인증/세션관리/정산계좌, `InnerTabs` 미사용).
  실제 렌더링은 페이지 로드 1회로 통합돼 있지만, 5개 섹션이 각각 독립된 데이터 영역(담당자·인증·
  세션·정산계좌)이라 프로덕션에서는 별도 API 리소스가 될 가능성이 높아 소분류별로 화면 로드를
  각 1개씩 산정했다 — 문자 그대로의 네트워크 호출 수가 아니라 "API 표면 규모 추정"이라는 Config
  문서의 카운트 취지를 따른 것.
- **"유형별 원천징수 처리"·"계약 관리"·"등급 산정" 3개 소분류는 코드에 대응 화면/로직이 없어
  N/A 처리** — `businessType` 구분 표시, 계약기간·독점여부 필드 부재, `gradeCode`의 배치 산정·
  배지 표시만 확인됨(전용 관리 화면 없음).
- **"성과통계(벤더 자기관리)" 대분류 신규 추가(2026-07-28, 엄밀 재점검)**: `partner/src/stats/`
