# 화면정의서 작성 표준안

**작성일**: 2026-08-25
**적용 대상**: DN 화면레이아웃 산출물 (S3 상세설계) — 신규 도메인 작성 시 이 표준을 따른다
**연계 문서**: C1 보안컨벤션, C3 아키텍처컨벤션, C6 API설계컨벤션, C7 디자인시스템, C8 UX Writing컨벤션, DD 메뉴구조도(IA), DL 인터페이스명세, DM 시퀀스, 지침서 v2.3 §7.5(산출물 버전관리 정책)
**기존 DN과의 관계**: 이 표준안은 기존 `DN-화면레이아웃(Order-Payment).md`(와이어프레임 + "화면 구성"/"상태별 UI" 2분할 표) 방식을 **메타정보 + 영역·속성·기능·UI상태 4요소로 세분화**한 개정안이다. 기존 문서를 당장 이 형식으로 마이그레이션할지는 별도로 결정한다 — 이 문서는 표준(기준)만 정의한다.

---

## 1. 왜 나누는가

기존 방식은 와이어프레임(그림) 하나에 "화면 구성" 표 하나가 붙는 2단 구조였다. 화면이 복잡해질수록(예: DN의 클레임 관련 화면들) 이 표 하나에 데이터소스·검증규칙·상태분기가 뒤섞여 들어가면서 어떤 조건에서 무엇이 어떻게 보이는지 추적하기 어려워졌다. 또한 화면이 몇 개인지, 누가 담당하는지, 어느 상태(초안/승인)인지를 파악할 공통 자리도 없었다.

이 표준안은 **"이 화면은 무엇인가(메타정보)"** → **"무엇이 있는가(와이어프레임)"** → **"그것이 어떻게 동작·제약되는가(상세디스크립션)"** 순서로 분리한다. 메타정보는 화면을 목록·검색·추적 가능한 단위로 만들고, 와이어프레임은 화면을 구성하는 요소에 코드를 붙여 시각적으로 표기하는 역할만 하며, 그 코드 하나하나의 규칙·제약·데이터소스는 상세디스크립션에서 텍스트로 기술한다. 와이어프레임과 상세디스크립션은 코드로 1:1 대응하므로, 와이어프레임만 보고도 "이 요소가 궁금하면 상세디스크립션의 어느 항목을 보면 되는지" 바로 찾을 수 있어야 한다.

## 2. 화면 메타정보

모든 화면 섹션(`## {번호}. {채널} — {화면명}`)은 와이어프레임보다 먼저, 아래 7개 필드를 담은 메타정보 블록으록 시작한다. 화면 하나하나를 독립된 관리 단위로 만들어, 나중에 화면 수를 세거나 담당자를 찾거나 승인 여부를 확인할 때 이 블록만 모아서 보면 되게 하는 것이 목적이다.

| 필드 | 설명 | 형식/예시 |
|---|---|---|
| 화면 ID | 화면을 유일하게 식별하는 코드 | `{App}-{Domain}-{순번}` 예: `MOB-ORDER-01`, `ADM-CLAIM-11` |
| 화면명 | 한글 명칭 + 영문 컴포넌트명 | 장바구니 (CartPage) |
| 유형 | 7장의 화면유형 6종 중 하나 | 목록형 / 상세형 / 입력형 / 처리결과형 / 알림외부채널형 / 대시보드형 |
| 메뉴 경로 | 앱 내 접근 경로 (DD 메뉴구조도·IA 기준) 또는 라우팅 경로 | 홈 > 장바구니 (`/cart`) |
| 권한 | 접근 가능한 역할/채널 (C1 보안컨벤션 접근통제 연계) | mobile: 로그인 회원 / admin: `OPS_MANAGER` 이상 |
| 담당자 | 기획·FE·BE 담당자 또는 역할 (RACI 있으면 역할명으로 대체) | 기획: 홍길동 / FE: — / BE: — |
| 문서상태 | 이 화면정의서 항목의 버전·승인 상태 (지침서 §7.5 준용) | `DRAFT-v1.0` / `APPROVED-v1.1` |

```
> **화면 ID**: MOB-ORDER-01 · **유형**: 목록형 · **메뉴 경로**: 홈 > 장바구니 (`/cart`)
> **권한**: 로그인 회원 · **담당자**: 기획 홍길동 / FE — / BE — · **문서상태**: DRAFT-v1.0
```

> 화면 ID의 `{App}`은 `MOB`/`ADM`/`PTN`(partner)/`COM`(공용) 중 하나를, `{Domain}`은 D-시리즈 도메인명(ORDER, PAYMENT, CLAIM 등)을 쓴다. 문서상태 값(`DRAFT-v{n}`/`APPROVED`)은 지침서 v2.3 §7.5 "산출물 버전 관리 정책"의 태깅 규칙을 화면 단위로 그대로 적용한 것이다 — 이 필드를 채우기 시작하면 그 정책의 실제 적용 사례가 된다.

## 3. 작성 단위 4가지

| 단위 | 정의 | 예시 |
|---|---|---|
| **영역 (Region)** | 화면을 구성하는 시각적 블록. 하나의 컴포넌트 또는 컴포넌트 그룹 | Header, CartItemList, PriceSummary, BottomBar |
| **속성 (Property)** | 영역 안에서 표시되는 데이터 항목 | 상품명, 판매가, 재고수량, 배지 텍스트 |
| **기능 (Function)** | 영역 안에서 사용자가 수행할 수 있는 동작 | 수량 변경, 옵션 변경, 삭제, 결제하기 |
| **UI상태 (State)** | 영역·속성·기능이 조건에 따라 달라지는 표현 | 로딩중, 품절, 비어있음, 에러, 확인 대기 |

같은 요소라도 성격에 따라 분류가 달라질 수 있다. 예를 들어 "품절 배지"는 화면에 보이는 텍스트라는 점에서는 속성이지만, 특정 조건(재고=0)에서만 나타난다는 점에서는 UI상태의 표현이기도 하다 — 이런 경우 **속성(데이터가 어디서 오는가)은 속성표에, 조건부 표현(언제 나타나는가)은 상태표에** 나누어 적고, 서로 참조 코드로 연결한다(4장 표기 코드 체계 참고).

## 4. 표기 코드 체계

와이어프레임과 상세디스크립션을 연결하는 코드는 아래 형식을 쓴다. 화면 하나 안에서 유일하면 되고, 화면 간에는 중복되어도 된다(화면 ID로 이미 구분되므로).

| 코드 | 대상 | 형식 | 예시 |
|---|---|---|---|
| 영역 | Region | `R{n}` (화면 내 등장 순서, 위→아래·좌→우) | `R1`, `R2` |
| 속성 | Property | `R{n}-P{m}` | `R2-P1` (CartItemList의 첫 번째 속성: 상품명) |
| 기능 | Function | `R{n}-F{m}` | `R2-F1` (CartItemList의 첫 번째 기능: 수량 변경) |
| UI상태 | State | `R{n}-S{m}` | `R2-S1` (CartItemList의 첫 번째 상태: 품절) |
| 화면 전역 상태 | Global State | `R0-S{m}` | `R0-S1` (화면 전체 로딩 실패) |

번호는 영역 내에서 속성/기능/상태별로 각각 1부터 순서대로 매긴다(P와 F와 S는 서로 다른 채번 축). 팝업/레이어도 하나의 영역(R)으로 취급하며, 팝업 안의 요소는 그 팝업 영역 번호를 부모로 채번한다(예: 옵션변경 팝업이 R7이면 팝업 안 사이즈 선택 버튼은 `R7-F1`).

**화면 내부 탭(In-page Tab)도 같은 방식으로 처리한다.** 탭 전환 버튼(탭바) 자체를 하나의 영역으로 채번하고, 그 안에 "탭 전환" 기능(F)과 "현재 활성 탭" UI상태(S)를 둔다. 탭 콘텐츠(패널)는 탭 개수만큼 별도 영역으로 나누어 채번하며, 각 패널 영역의 "진입/노출 조건"(6.1 영역 개요)에 탭바의 활성 상태 코드를 조건으로 명시한다 — 예: "R3-S1(활성 탭)이 '배송정보'일 때만 노출". 이렇게 하면 탭마다 속성·기능이 완전히 달라도 조건 분기를 표마다 반복하지 않고 진입조건 한 줄로 모을 수 있다. 7.2절에 구체적 예시가 있다.

## 5. 와이어프레임 작성 규칙

- **작성 도구**: 와이어프레임은 **Figma 또는 PPT로 작성하고, 최종 산출물은 PDF로 내보낸다.** 둘 중 편한 도구로 그리되(신규 화면은 Figma, 간단한 수정·조합은 PPT가 편할 수 있음), 화면정의서에 첨부·공유하는 형태는 항상 PDF로 통일한다 — 뷰어 없이도 누구나 열람 가능하고, 페이지가 고정되어 버전 간 비교가 쉽기 때문이다.
- 화면정의서(.md) 본문에는 와이어프레임 그림 자체를 넣지 않고, md와 PDF는 서로 다른 파일로 두고 파일명·페이지 번호로만 연결한다 — Figma·PPT 둘 다 .md 파일을 그대로 불러와 렌더링(라이브 include)하는 기능이 없으므로, 파일을 합치려 하지 말고 참조만 남긴다. 아래 형식으로 위치를 참조한다:

  ```
  > **와이어프레임**: {화면 ID}.pdf — {페이지 번호}페이지 (원본: {Figma 파일/프레임 링크} 또는 {PPT 파일명})
  ```

- 각 영역은 원본(Figma 프레임 또는 PPT 슬라이드) 위에 `R{n} 영역명` 라벨(텍스트 박스 또는 주석)로 표시한다 (기존 DN의 ASCII 주석 `← R{n} 영역명` 관례를 시각적 라벨로 그대로 옮긴 것). PDF로 내보내도 이 라벨이 그대로 보여야 한다.
- 영역 안의 개별 속성·기능·상태 중 **상세디스크립션에서 따로 다룰 만큼 중요한 것**은 원본 위에 콜아웃/마커로 코드를 표시한다. 예: 상품명 옆에 `[P1]` 말풍선, `−`/`+` 버튼 옆에 `[F1]` 원형 마커, 품절 배지 옆에 `[S1]` 마커. PDF로 내보낼 때도 이 마커가 그대로 유지되어야 한다.
- **구성요소 인덱스**(그 화면에서 쓰인 모든 코드 목록)는 PDF가 아니라 화면정의서(.md) 쪽에 표로 남긴다 — 검색·유지보수가 쉬운 텍스트 쪽에 두는 것이 원칙이다(아래 7장 예시 참고). 상세디스크립션을 다 안 읽어도 이 인덱스만으로 "이 화면에 어떤 속성·기능·상태가 있는지" 파악 가능해야 한다.
- 팝업/레이어는 원본에서 별도 프레임/슬라이드로 분리하고, 어떤 기능(F)에 의해 열리는지 화살표/텍스트로 표시한다. PDF로 내보내면 별도 페이지가 된다.

> 이 표준안 문서 자체는 텍스트 문서라 Figma/PPT/PDF 파일을 담을 수 없으므로, 7장의 화면유형별 예시는 편의상 ASCII 스케치로 대체 표기했다. 실제 프로젝트 산출물을 작성할 때는 위 규칙대로 Figma 또는 PPT로 그리고 PDF로 내보내며, 화면정의서에는 참조 링크와 구성요소 인덱스만 남긴다.

## 6. 상세디스크립션 작성 규칙

영역별로 아래 4개 표를 순서대로 작성한다. 해당 사항이 없는 표(예: 상태가 없는 단순 영역)는 생략 가능하다.

### 6.1 영역 개요

| 항목 | 내용 |
|---|---|
| 코드 | `R{n}` |
| 역할 | 이 영역이 화면에서 하는 일 한 줄 요약 |
| 데이터 소스 | 관련 API (DL 인터페이스명세 참조 형식: `GET /api/v1/cart`) 또는 "—"(정적) |
| 컴포넌트 스타일 | 앱별 C7 디자인시스템 클래스/템플릿 참조 (예: admin이면 C7 `.table-wrap`, `T-LIST`) |
| 진입/노출 조건 | 이 영역이 나타나는 조건 (예: "장바구니에 1개 이상 있을 때만") |

### 6.2 속성 (Property) 표

| 코드 | 속성명 | 데이터 소스 | 표시 규칙 | 제약사항 |
|---|---|---|---|---|
| R{n}-P{m} | 화면에 보이는 이름 | 응답 필드 경로 (`vendors[].items[].name`) | 표기 형식(C8 §8 표기규칙 준용: 금액/날짜/수량 등) | 길이 제한, null 처리, 마스킹 여부(C1 보안 연계) |

> 이 속성 하나만 노출/비노출되는 단순 조건("재고 0일 때만 노출" 등)은 별도 상태(S) 코드를 만들지 않고 이 "제약사항" 칸에 조건문으로 바로 적는다. S코드는 6.4의 기준에 해당할 때만 만든다.

### 6.3 기능 (Function) 표

| 코드 | 기능명 | 트리거 | 동작 | 검증/제약사항 |
|---|---|---|---|---|
| R{n}-F{m} | 기능 이름 | 사용자 행위(클릭/입력 등) | 호출 API(DL 참조) + 결과 반영 방식 | 입력 검증 규칙(C6 API §, 프론트/백엔드 분담은 C9 §4.3 기준), 실패 시 분기(어떤 S코드로 가는지) |

> 이 버튼 하나만 활성화/비활성화되는 단순 조건("필수 약관 미동의 시 비활성화" 등)도 마찬가지로 별도 상태(S) 코드 없이 이 "검증/제약사항" 칸에 바로 적는다.

### 6.4 UI상태 (State) 표

| 코드 | 상태명 | 발생 조건 | 화면 표현 | 문구(있는 경우) |
|---|---|---|---|---|
| R{n}-S{m} | 상태 이름 | 이 상태가 되는 조건(데이터/API 응답 기준) | 어떤 요소가 어떻게 바뀌는지 | C8 UX Writing컨벤션 유형(Empty/Error/Loading 등) 및 앱별 문구 |

> UI상태 표의 "문구" 칸은 C8 §5(메시지 작성 규칙)·§7(상태별 콘텐츠)의 유형명을 직접 적고, 실제 문구는 C8 예시 패턴을 그대로 따른다. 문구를 새로 짓지 않고 C8을 인용하는 것이 원칙이다.

**S코드를 별도로 만드는 기준 — 아래 세 가지 중 하나에 해당할 때만 UI상태 표에 올린다.** 그 외(속성 하나·기능 하나만 단순히 노출/비노출·활성/비활성되는 경우)는 6.2·6.3의 "제약사항" 칸에 조건문으로 적고 끝낸다. 모든 노출/비노출·활성/비활성 조건을 전부 상태로 승격시키면 표만 늘어나고 오히려 추적이 불편해진다.

| 기준 | 설명 | 예 |
|---|---|---|
| ① 다중 영향 | 하나의 조건이 여러 요소(속성+기능+표현)에 동시에 영향을 줄 때 | "품절"(R3-S1) — 배지 표시 + 수량버튼 비활성화 + 주문 시 제외가 한 조건에서 동시에 발생 |
| ② 타 영역 참조 | 다른 영역이 이 상태값을 "진입/노출 조건"으로 참조할 때 | 탭바의 "활성 탭"(R3-S1) — R4·R5·R6 패널이 이 값을 조건으로 참조 |
| ③ 전용 문구 필요 | C8 §7 "상태별 콘텐츠"(Empty/Error/Loading/Maintenance 등) 문구가 별도로 대응될 때 | "비어있음"(R0-S1), "로딩 실패"(R0-S2) |

## 7. 화면유형별 표준 템플릿

C7 디자인시스템의 "Template → Page 매핑"(T-LIST, T-DETAIL-MDI, T-FORM-MODAL, T-DASHBOARD, T-TREE)과 DN에 실제 존재하는 화면 성격을 종합하면, 화면은 아래 6개 유형으로 수렴한다. 유형마다 전형적인 영역 구성과 축약 예시를 아래에 제시한다. 실제 작성 시 이 골격에서 시작해 영역을 가감한다.

> **축약 예시 표기법**: 아래 축약 예시는 raw HTML(인라인 `style`)로 표기한다. Markdown Preview Enhanced처럼 Chromium 기반 웹뷰로 렌더링하는 도구에서는 실제 박스 레이아웃 그대로 보인다. 다만 GitHub·GitLab 등 웹 마크다운 뷰어는 보안상 HTML을 새니타이즈(sanitize)하므로 그런 환경에서 열면 레이아웃이 깨질 수 있다 — 이 문서는 MPE(또는 동급 로컬 프리뷰) 기준으로 작성한다. 코드 안의 `[Rn]`/`[Pn]`/`[Fn]`/`[Sn]` 표기는 6장 상세디스크립션의 코드와 1:1 대응한다. 이 축약 예시는 표기 규칙을 보여주기 위한 것이며, **실제 화면의 정식 와이어프레임**은 5장 규칙에 따라 Figma 또는 PPT로 작성해 PDF로 산출한다(둘은 별개 산출물).

### 7.2 상세형 (Detail / Detail-MDI) — 예: 주문 상세, admin 클레임상세(MDI 탭)

admin/partner은 C7의 `T-DETAIL-MDI`(PageTitle + InnerTabs) 구조를 따르므로, 탭 각각을 별도 영역(R)으로 채번한다(탭1=R3, 탭2=R4 식).

### 7.3 입력형 (Form / Form-Modal) — 예: 주문서 작성, 옵션변경 팝업, 배송지 선택 팝업

**전형적 영역**: `R1` Header → `R2`~`Rn` 입력 필드 그룹(주소/쿠폰/포인트/결제수단 등, 각각 별도 R) → `R{n+1}` 약관동의 → `R{n+2}` CTA(BottomBar)

**상세디스크립션에서 특히 챙길 것**: 입력형은 기능(F)마다 "검증/제약사항" 칸이 핵심이다. 프론트 즉시검증과 백엔드 최종검증을 C9 §4.3(Validation 책임 분리)에 따라 구분해 적는다 — 예: "F1 포인트 입력: 프론트에서 1,000P 미만 입력 차단(즉시), 백엔드에서 보유포인트 초과 여부 재검증".

팝업(레이어)은 입력형의 축소판으로 취급하며, 여는 기능(F)과 닫는 기능(F)을 명시한다: "R2-F1(쿠폰 [>] 클릭) → R6(쿠폰팝업) 오픈, R6-F2(적용하기) → R6 닫힘 + R2 갱신". 팝업은 별도 화면 ID를 새로 만들지 않고 부모 화면 ID에 `-P{n}` 접미사를 붙인다(예: `MOB-ORDER-02-P1` 쿠폰팝업).

### 7.4 처리결과형 (Result) — 예: 주문 접수 완료/실패

**전형적 영역**: `R1` Header → `R2` 결과 아이콘/메시지 → `R3` 요약정보 → `R4` 진행상태 안내(비동기 처리 중인 경우) → `R5` 다음 행동 버튼(CTA 2개 이상인 경우 많음)

**상세디스크립션에서 특히 챙길 것**: 결과형은 "성공/실패/진행중" UI상태(S)가 화면의 핵심이므로, 상태표를 가장 먼저·상세히 쓴다. 각 상태가 어떤 이벤트(C5, DI 이벤트플로우)로 전환되는지 "발생 조건" 칸에 이벤트명을 직접 인용한다(예: "PAYMENT_APPROVED 수신 시 R2-S1(성공)로 전환").

### 7.5 알림/외부채널형 (Notification) — 예: 알림톡, 이메일

일반 화면과 달리 "영역"이 시각적 블록이 아니라 **메시지 블록**이므로 표기를 다음처럼 바꾼다. 메타정보의 "메뉴 경로"는 해당 없음(`—`)으로 두고, "권한" 자리에는 수신 채널 우선순위를 적는다.

**전형적 영역**: `R1` 메시지 본문(템플릿) → `R2` 버튼/딥링크 → `R0` 발송 조건

| 코드 | 속성명 | 데이터 소스 | 표시 규칙 | 제약사항 |
|---|---|---|---|---|
| R1-P1 | 템플릿 변수 | 이벤트 payload 필드 | 변수 치환 규칙 | 누락 시 기본값, PII 마스킹 여부(C1 §3.1) |

| 코드 | 기능명 | 트리거 | 동작 | 검증/제약사항 |
|---|---|---|---|---|
| R2-F1 | 딥링크 이동 | 버튼 클릭 | 앱/웹 라우팅 | 딥링크 보안 규칙(로그인 필요 여부, 만료시간) |

발송 조건(R0)은 상태표 대신 별도 표로: "트리거 이벤트(C5/DI 참조) | 수신자 결정 규칙 | 채널(카카오/이메일/SMS) 우선순위".

### 7.6 대시보드형 (Dashboard) — 예: admin 홈

**전형적 영역**: `R1` SummaryCards → `R2` TrendChart → `R3` PendingItems → `R4` SystemAlerts

각 SummaryCard는 속성(수치)+기능(클릭 시 해당 목록으로 이동)을 함께 가지므로, 카드 1장당 `P`(표시 수치)와 `F`(클릭 이동)를 한 쌍으로 채번한다.

## 8. 다른 산출물·컨벤션과의 연계 규칙

상세디스크립션의 각 칸은 새로 규칙을 만들지 않고 기존 컨벤션·산출물을 인용하는 것이 원칙이다.

| 항목 | 인용해야 할 산출물/컨벤션 |
|---|---|

## 9. 작성 완료 체크리스트

- [ ] 메타정보 7개 필드가 모두 채워져 있다(해당 없음은 "—"로 명시, 공란 아님).
- [ ] 화면 ID가 다른 화면과 중복되지 않는다.
- [ ] 와이어프레임의 모든 영역에 `R{n}` 코드가 붙어 있다.
- [ ] 상세디스크립션에서 다루는 모든 코드가 와이어프레임(또는 구성요소 인덱스)에도 나타난다 — 반대로 와이어프레임에만 있고 상세디스크립션에 없는 코드가 없다(1:1 대응).
- [ ] 속성표의 "표시 규칙"이 C8 §8을 벗어나지 않는다.
- [ ] 기능표의 "동작"이 DL의 실제 엔드포인트와 경로·메서드가 일치한다.
- [ ] UI상태표의 "문구"가 새로 지어지지 않고 C8 §5/§7 패턴에서 인용되었다.
- [ ] 화면유형(7장)에 맞는 전형적 영역 구성에서 벗어난 경우, 벗어난 이유가 영역 개요에 한 줄 설명되어 있다.
