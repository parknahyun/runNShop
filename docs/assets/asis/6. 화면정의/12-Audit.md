## 두 화면의 경계

두 화면은 성격이 비슷해 보이지만 **대상 범위가 다르다**.

| 구분 | ADM-090-010 (고객정보 접근 이력) | ADM-100-003 (감사 로그) |
|---|---|---|
| 대상 | **회원(고객) 개인정보를 조회한 행위**만 | 클레임·상품·정산·운영자 승인 등 **여러 도메인의 엔티티 생성/수정/삭제/상태변경 전체** |
| 기록 시점 | 운영자가 회원 목록·상세를 조회할 때 | 도메인 이벤트가 발생해 상태가 변할 때(엔티티 값이 바뀔 때) |
| 목적 | 개인정보 오남용 방지(누가 언제 어떤 회원을 왜 조회했는지) | 데이터 변경의 책임 소재 추적(무엇이 언제 왜 바뀌었는지, before/after) |
| 저장 테이블(추정) | `adt_member_access_log` | `adt_audit_log` |
| 값 변화(before/after) 기록 | 없음(조회 행위 자체만 기록, 조회 결과 값은 남기지 않음) | 있음(변경 전/후 값을 JSON으로 나란히 비교) |

`MemberAccessLogPage.spec.md`의 비고에도 "회원 목록 화면에는 상태변경·포인트지급·쿠폰발급 등 `ACTION` 유형까지 포함한 더 넓은 로깅 범위가 기술되어 있으나, 본 화면은 그중 조회(목록·상세) 이력만 다룬다"고 명시되어 있어, 회원에 대한 "조회"와 "변경" 두 로그가 향후 통합될 가능성도 열려 있다(현재는 조회 이력만 이 화면, 변경 이력은 ADM-100-003 감사 로그 쪽에 `MEMBER`/`MEMBER_POINT`/`MEMBER_COUPON` 등 `aggregateType`으로 흡수되는 구조로 추정).

### 다른 도메인 문서와의 관계

이 화면이 조회하는 로그는 [회원 목록](../../member/list/MemberPage.spec.md) 화면(`03-Member.md`의 ADM-050-001)에서 발생하는 검색·상세조회 행위다. `03-Member.md`에서 ADM-050-001을 다룰 때 이 접근 로그 자체는 언급하지 않았으므로, 두 문서를 함께 볼 때 "회원 조회 행위 → 이 화면에 로그로 남음"이라는 흐름으로 이해하면 된다.

> **Human Review**: 엑셀 다운로드가 버튼은 있으나 실제로는 `alert` 스텁이다. 개인정보 접근 이력을 감사 목적으로 외부(예: 개인정보보호위원회 제출용)로 추출해야 하는 실 서비스 요구사항을 고려하면, 이 기능의 실제 구현 우선순위가 낮지 않을 수 있다.

| R6-P1 | beforeValue/afterValue diff 뷰 | 각각 `JSON.stringify(value, null, 2)`로 좌우 2단 `<pre>` 블록 표시 | **별도 diff 라이브러리 없이 좌/우 값을 그대로 나열**하는 방식(줄 단위 강조 없음). 값이 없으면 `(없음)` 표시 |

### 비고 (spec.md 원본 인용)

- 실 서비스에서는 `adt_trace_log`(요청 단위 분산 추적 로그)를 함께 조회해 감사 로그의 `traceId`로 API 호출 체인을 역추적할 수 있으나, 본 화면은 감사 로그 조회에 집중하며 트레이스 로그 조회는 범위에서 제외한다(`11-Platform.md`의 원본 API 목록 #237~238에 `GET /api/admin/v1/audit/traces`, `GET /api/admin/v1/audit/traces/{trace_id}`가 정의돼 있으나 화면 자체는 없음).
- 감사 로그는 법적·내부통제 목적의 불변 기록이므로 실 서비스에서는 수정·삭제 API 자체가 존재하지 않는다.

### 08-Notification.md와의 연결 (발송 이력 조회 화면 부재 이슈에 대한 답)

`08-Notification.md`의 Human Review에서 "알림 발송 이력을 조회하는 admin 화면이 없다"는 이슈를 제기하며 "Audit 도메인이 이 역할을 겸하는지 확인이 필요하다"고 남겨두었다. 이 문서에서 감사 로그의 데이터 모델을 확인한 결과:

- 감사 로그(`adt_audit_log`)는 `domain`/`eventType`/`aggregateType` 필드를 갖고 있어 이론적으로는 `domain='Notification'`, `eventType='ORDER_CONFIRMED_KAKAO'` 같은 알림 발송 이벤트도 이 로그에 함께 적재될 수 있는 구조다.
- 다만 mockData.ts의 예시 데이터는 Claim 등 다른 도메인 사례만 확인되며, Notification 도메인 이벤트가 실제로 여기 적재되는지는 이 화면의 spec.md·mockData 어디에도 명시적으로 언급되지 않는다.
- **결론(Human Review로 이관)**: 감사 로그가 "발송 성공/실패" 같은 알림 특유의 상태(예: 카카오톡 발송 실패 사유)까지 포착할 수 있는 구조인지는 불확실하다. `beforeValue`/`afterValue`가 "엔티티 값의 변경"을 표현하는 모델이라 "발송 시도했으나 외부 API가 실패했다"는 이벤트를 자연스럽게 표현하기 어려워 보인다 — 알림 발송 이력은 감사 로그와는 별도의 전용 화면(또는 `adt_trace_log` 확장)이 필요할 가능성이 있다.
