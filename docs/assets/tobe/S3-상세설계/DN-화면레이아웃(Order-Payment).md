# 화면 레이아웃 — 주문·결제 도메인

> **단계**: 상세설계 (S3)  
> **문서범위**: Bolt (Order + Payment)  
> **문서종류**: Design  
> **도메인**: order, payment  
>
> **작성 목적**: 시퀀스(DM)에서 확정된 API 호출 시점과 응답 데이터를 화면에 매핑한다.  
> "어떤 화면에서 어떤 데이터를 어떤 API로부터 가져와 표시하는가"를 확정한다.
>
> **흐름 내 위치**:
> ```
> DM 시퀀스 → DN 화면 레이아웃
> ```
>
> **근거 소스**: `apps/runNshop-admin/src/order/`, `apps/runNshop-partner/src/order/`, `apps/runNshop-partner/src/claim/`, `apps/runNshop-mobile/app/cart/`, `apps/runNshop-mobile/app/orders/`, `api/runNshop-api/src/main/resources/mock/`

## 0. 문서 사용법 — 화면 섹션 표준 구조

> 모든 화면 섹션(`## N. ...`)은 아래 6개 하위섹션을 이 순서로 둔다.
> 이는 일반 웹 개발의 "화면정의서" 8항목(화면ID·접근권한·화면전환·유효성검증 등)을
> DN(화면레이아웃) 내부 구조로 흡수시켜, DK(세부UC)·DL(인터페이스명세)·DJ(GWT)를 오가지 않고도
> 화면 단위로 필요한 정보를 한 곳에서 찾을 수 있게 하기 위함이다.

```markdown
## N. {앱} — {화면명} ({컴포넌트명})

### 메타블록

| 항목 | 내용 |
|---|---|
| 화면 ID | SCR-M-001 |
| 앱 | mobile |
| 접근 권한 | 로그인 회원 |
| 관련 세부UC | [[DK-세부유스케이스(Order-Payment)|UC-1, UC-2, UC-23]] |
| 호출 API | [[DL-인터페이스명세(Order-Payment)|API-001~005]] |

### 와이어프레임
(ASCII 목업)

### 화면 구성
| 영역 | 데이터 소스 (API) | 표시 내용 |
|---|---|---|
...

### 화면 전환
| 트리거 | 이동 화면 (SCR-ID) |
|---|---|
| [선택상품 주문하기] 클릭 | SCR-M-002 (주문서) |
| [옵션변경] 클릭 | 레이어 팝업 (화면 전환 아님) |

### 유효성 검증
> [[DJ-GWT수용기준(Order-Payment)|GWT §1 장바구니 Bolt]] · 에러코드는 DL 참조

### 상태별 UI
| 상태 | 화면 표현 |
|---|---|
...
```

- **메타블록**: 화면 식별 정보(화면ID·앱·접근권한)와 상위 산출물 참조(관련 세부UC·호출 API)를 표로 묶는다.
  화면 ID는 프로그램목록(DQ) `SCR-*` ID를 그대로 표기. 외부 채널(알림톡/이메일)처럼 DQ에 화면(SCR)으로
  등록되지 않은 섹션은 `없음 (외부 채널)`로 표기. 관련 세부UC·호출 API는
  [[Foam-위키링크-활용가이드]] §3.2(별칭 링크) 방식을 사용한다 — 파일 단위 링크이며, 클릭하면 DK/DL
  파일이 열리고 본문에서 해당 번호를 검색(Ctrl+F)해 세부 내용을 확인한다(표 행 단위 정밀 앵커의 한계는
  [[Foam-위키링크-활용가이드]] §5 참조).
- **화면 전환**: 이 화면에서 발생하는 모든 화면 이동/레이어를 표로 나열한다. 다른 화면(SCR-ID)으로
  이동하는 트리거뿐 아니라, 레이어 팝업·모달처럼 **같은 화면 내에서 열리는 트리거도 함께 표기**한다 —
  다만 이동 화면 칸에 `레이어 팝업 (화면 전환 아님)`처럼 명시해 실제 SCR-ID 이동과 구분한다.
  외부(택배사 등) 이동이나 같은 화면 내 탭 전환(MDI)도 이 표에서 함께 표기한다.
- **유효성 검증**: 규칙 본문을 DN에 복제하지 않고 DJ(GWT)·DL(에러코드)로 링크만 건다 — 검증 규칙이
  바뀌어도 DN을 다시 손댈 필요가 없도록 하기 위함(방법론 "현행화는 자연 발생" 원칙 유지). 조회 전용 화면
  등 검증 대상이 없으면 `해당 없음`으로 표기.

### 0-1. 기획자·개발자 병행 작업 규칙 — "화면 구성" 표의 API 매핑

> admin/partner를 먼저 확정하고 mobile이 참조하는 순서(작성가이드 "화면 레이아웃" 절)가 원칙이지만,
> 실제로는 **화면 설계와 API 설계가 거의 동시에 진행**되는 경우가 많다. 이때는 완성된 문서를 넘기는
> 방식이 아니라, 미완성 칸을 서로 알아볼 수 있게 표시하고 각자 채워나가는 방식으로 협업한다.

- **데이터 소스(API) 칸에 확정된 API가 없을 때** — 기획자는 이 영역이 무엇을 보여줘야 하는지
  ("표시 내용" 칸)만 먼저 채우고, 데이터 소스 칸에는 `[TBD-API]`를 표기한다.
  ```markdown
  | 영역 | 데이터 소스 (API) | 표시 내용 |
  |---|---|---|
  | 클레임 가능 수량 뱃지 | [TBD-API] | 반품/교환 가능한 남은 수량을 뱃지로 표시 |
  ```
- **개발자가 API를 확정하면** — DL(인터페이스명세)에 endpoint를 추가한 뒤, DN의 `[TBD-API]`를
  실제 경로·필드명으로 교체한다. 이 교체는 화면 의미를 바꾸지 않는 단순 치환이라 기획자 재확인 없이
  진행 가능하다.
- **반대로 개발자가 먼저 API를 설계했는데 화면 표시 방식이 미정일 때** — "표시 내용" 칸에
  `[TBD-UX]`를 표기하고 기획자가 채우도록 남긴다.
- **`[TBD-*]` 태그는 Foam 미연결 언급(Unlinked mentions)처럼 grep으로 전수 검색 가능** —
  `grep -rn "TBD-" docs/assets/tobe/` 로 채널·Bolt 전체에서 미확정 항목을 한 번에 추적한다.
  Bolt 상세설계 완료(DoD) 시점에는 `[TBD-*]`가 0건이어야 한다.
- 이 규칙은 admin/partner ↔ mobile 사이뿐 아니라, 같은 화면 안에서 기획자·개발자가 동시에
  작업하는 모든 경우에 적용한다.

### 화면 구성

| 영역 | 데이터 소스 (API) | 표시 내용 |
|---|---|---|
| Header | — | "장바구니" 타이틀 + 전체 수량 `total_count` |
| 입점사별 상품 그룹 | GET /api/v1/cart → `vendors[]` | 입점사명, 배송비/무료배송 기준, 상품 목록 |
| 상품 카드 | GET /api/v1/cart → `vendors[].items[]` | 상품이미지, 상품명, 옵션(color/size), 정상가(취소선), 판매가, 수량(+/- 버튼), 삭제 |
| 혜택 안내 | GET /api/v1/cart → `summary` | 사용 가능 쿠폰 수(`coupon_benefit_text`), 포인트 잔액(`point_balance`) |
| 장바구니 할인행사 | GET /api/v1/cart → `cart_promotions[]` | 적용된 행사명, 할인 조건(N개 이상/세트 등), 할인 금액, 적용 여부 |
| 금액 요약 (CartSummary) | GET /api/v1/cart → `summary` | 상품금액, 상품할인, 장바구니할인, 배송비, 총 결제 예상금액 |
| 수량 변경 | PATCH /api/v1/cart/items/{cart_item_id}/quantity | +/- 버튼 클릭 시 재계산 |
| 옵션 변경 | PUT /api/v1/cart/items/{cart_item_id}/option | [옵션변경] 클릭 → 레이어 팝업(색상/사이즈 선택) → 변경 완료 시 재계산. 품절 판정 = 실재고 − 장바구니 선점수량 ≤ 0 (본인+타 고객 장바구니 포함), 품절 옵션 선택 불가 |
| 삭제 | DELETE /api/v1/cart/items/{cart_item_id} | 삭제 버튼 |
| CTA (CartBottomBar) | — | "선택상품 주문하기 · {total_payment}원" → 주문서(/orders/new) 이동 |

### 클레임 상태 흐름 (배송비 결제 포함)

> **v6 갱신**: 배송 실행 구간(수거중/반송 배송중)은 더 이상 `claim.status` 값이 아니다. 공용 배송실행 엔티티 `ord_shipment`(shipment_type=PICKUP/RETURN)로 분리되었고, `claim.status`는 "고객·입점사·CS가 판단·결정하는 지점"만 표현한다. 아래 흐름에서 "수거 진행 중"·"반송 배송중"으로 화면에 보이는 문구는 `claim.status` + `shipment.status` 조인으로 계산되는 파생 표시이며, 실제 claim.status 값은 아니다(예: 화면 표시 "수거중" = claim.status(PAYMENT_PENDING 결제완료 후 또는 INSPECTING 진입 전) + shipment(PICKUP).status=IN_TRANSIT).

```
[정상 흐름]
접수(RECEIVED)
  → 배송비 결제 대기(PAYMENT_PENDING) ... [고객 귀책 시, 결제완료 후 shipment(PICKUP) 자동생성·진행]
  → 품질점검(INSPECTING) ................ [shipment(PICKUP) 배송완료 시 자동 진입(고객 귀책) 또는 입점사 귀책 시 즉시 진입, 입점사: 합격/거부 판정]
  → 수거완료(PICKED_UP) ................. [입점사: 합격 확인]
  → 환불완료(REFUNDED) .................. [어드민: 환불 처리]
  → 클레임완료(COMPLETED) ............... [배치: 자동 전환]

[품질점검 거부 (수거거부)]
  → 품질점검(INSPECTING)
  → 수거거부(PICKUP_REJECTED) ........... [입점사: 불합격 + 사유 등록]
  → 어드민 판정:
     ├─ 폐기(DISPOSED) → 클레임완료(COMPLETED)
     └─ 추가결제요청 → 반송 배송비 결제 대기(RETURN_PAYMENT_PENDING) ... [고객 결제 후 shipment(RETURN) 진행] → shipment(RETURN) 배송완료 → 클레임완료(COMPLETED)

[반려 (접수 단계)]
접수(RECEIVED) → 반려(REJECTED) ......... [어드민]

[결제 미완료]
접수(RECEIVED) → 배송비 결제 대기(PAYMENT_PENDING) → 1일 초과 → 자동취소(PAYMENT_EXPIRED)
```

### 클레임 상태별 정리

> claim.status 11상태 (v6 — PICKUP/RETURN_SHIPPING/RETURN_DELIVERED는 `ord_shipment`로 이관되어 제외). 근거: `S2-구조설계/DG-상태머신(Order).md` §2.

| 상태 | 설명 | 수행 주체 |
|---|---|---|
| RECEIVED | 접수됨 | 고객 신청 |
| PAYMENT_PENDING | 수거 배송비 결제 대기 ~ 수거 진행 중 (고객 귀책, shipment(PICKUP) 병행) | 고객 → 입점사 (수거정보 입력) |
| PAYMENT_EXPIRED | 결제 1일 초과 → 자동 취소 | 배치 |
| INSPECTING | 품질점검 진행 중 (입점사 귀책 즉시 또는 shipment(PICKUP) 배송완료 후 진입) | 입점사 (합격/거부 판정) |
| PICKED_UP | 수거완료 (품질점검 합격) | 입점사 |
| PICKUP_REJECTED | 수거거부 (품질점검 불합격) | 입점사 (사유 등록) |
| REFUNDED | 환불 완료 | 어드민 |
| RETURN_PAYMENT_PENDING | 반송 배송비 결제 대기 ~ 반송 진행 중 (불합격 반송, shipment(RETURN) 병행) | 고객 → 입점사 (운송장 등록) |
| DISPOSED | 폐기 처리 | 어드민 |
| COMPLETED | 클레임 전체 완료 | 배치 (자동) |
| REJECTED | 접수 단계 반려 | 어드민 |

> 수거중/반송배송중 진행 상태의 상세(운송장·이동중·배송완료 등)는 `ord_shipment.status`(PENDING/IN_TRANSIT/DELIVERED/FAILED/CANCELLED)를 참조한다.

## 14. partner — 배송 관리 (ShippingPage)

> 출고 배송 + **회수(수거)** + **재배송(교환)** 통합 관리.
> 구분은 **행 배경색상**으로 시각적으로 구분한다.

### 메타블록

| 항목 | 내용 |
|---|---|
| 화면 ID | SCR-P-004 |
| 앱 | partner |
| 접근 권한 | 입점사 담당자 (권한 체크 미적용 — 프로토타입) |
| 관련 세부UC | [[DK-세부유스케이스(Order-Payment)\|UC-7 (출고), UC-25 (재발송)]] |
| 호출 API | [[DL-인터페이스명세(Order-Payment)\|API-035, API-048]] |

### 배경색상 규칙

| 구분 | 배경색 | 설명 |
|---|---|---|
| 출고 | 흰색 (기본) | 정상 주문 배송 |
| 회수 (수거) | 연노랑 (#FFFDE7) | 클레임 수거 건 |
| 재배송 (교환) | 연파랑 (#E3F2FD) | 교환 재발송 건 — PICKUP 진입(귀책판정 완료 직후) 시 회수 행과 동시에 생성되어 즉시 선출고 대상이 됨 |
| 반송 (RETURN) | 연주황 (#FFF3E0) | 반품 품질점검 불합격 건의 반송 배송 — RETURN_PAYMENT_PENDING(반송배송비) 결제완료 후 shipment(RETURN)로 생성 |
