## 1차 결과 (2026-07-24)

- 방법론적 문제(Problem #1: 기존 개발 방법론의 AI 협업 한계)는 `AI활용_개발공정_가이드_v2.2` 1장에서

  다루지 않는다.
- Impact 항목도 마찬가지로 gap이었다 — runNshop은 오픈 전 신규 구축이라 CS 로그·매출 등 실측
  지표가 원천적으로 없다. 프롬프트 라이브러리의 BPIO 샘플(주문취소 Bolt 예시)은 "기존 서비스의

  확인됐다.
- 목표·KPI는 반대로 대부분 원본에서 상속 가능했다 — 프로젝트관리방법론(14주 타임라인, 오픈
  체크리스트 성능기준), 방법론가이드(Go/No-Go 매트릭스)에 이미 구체적 수치가 있었기 때문. O1(사업
  오픈)과 O2(방법론 검증)이 이 Initiative에 원래 이원적으로 섞여 있다는 구조도 이 과정에서 명시적으로
  드러났다(기존엔 암묵적이었음).

**시사점**: Proposal 공정의 표준양식(방법론가이드 6.1)은 "기존 서비스의 신규 기능"을 만들 때는
자산 재사용이 잘 되지만, "완전 신규 서비스 자체"의 Proposal에는 Problem/Impact 항목에서 구조적으로
빈 곳이 생긴다 — 이 부분은 AI가 채우면 안 되고(근거 없는 서술이 됨) Human Review에서 사업 오너가
직접 공급해야 하는 영역이라는 게 이번 파일럿의 결론이다. 두 문서의 "Human Review 필요 항목" 표에
정리해뒀다.

**2차 업데이트 (2026-07-24, 같은 날)**: 위에서 Gap으로 남겨뒀던 "사업적 Problem" 근거를 페페가
직접 확인해줬다 — 핵심 문제는 "3TOP이 커머스 구축 노하우를 축적해왔으나 체계적으로 관리·적용하지
못했고, 짧은 개발기간·빠른 기술 변화 속에서 비체계적 자산으로는 대응이 어렵다"는 것. AI 활용
방법론 수립과 B2C(대표 플랫폼 유형) 실증이 그 대응 방향이며, runNshop은 그 실증 사례다. 이걸로
Problem 섹션의 완전성 공백은 대부분 해소됐고, 남은 잔여 항목은 (1) Impact 정량화(신규 구축 특성상
원천적 한계, 별도 표준양식 보완 필요)와 (2) "왜 러닝 버티컬인가"(B2C 대표성과 별개의 세부 사안)
2건으로 축소됐다. `01-문제정의서.md`에 반영 완료.

**3차 업데이트 (2026-07-24, 같은 날)**: 남았던 잔여 Gap 2건도 페페가 확인해줬다 —

**4차 업데이트 (2026-07-24, 같은 날)**: 페페가 Impact/Opportunity의 마지막 정량화 공백까지

  Initiative가 만들어내야 할 산출물(산정 모델)" 자체라는 점을 명시해뒀다
- 새로 발견된 미확정 사항 2건을 Human Review에 추가: (1) 30% 절감이 비용에만 적용되는지 기간·

표준양식 자체의 이슈로 분리해뒀다.

**중요 발견 — 방법론 검증 관점에서 의미 있는 결과**: 이번에 기간 목표가 숫자(5개월 ≈ 21.7주)로

**6차 업데이트 (2026-07-24, 같은 날)**: 페페가 "5개월이 맞음"으로 확정. `02-목표KPI.md`의
KR1-1을 5개월 기준으로 정정해 KR2-0과 정합시켰다. 5.1 자가평가도 일관성 "충족"으로 갱신 —

남은 건 **원본 문서 쪽 후속 조치**다: `docs/z. 작업여정/runNshop_project_management_v1_0.md`
4장은 여전히 "14주 기준"으로 되어 있어 이번 확정치(5개월)와 어긋난다. `docs/`는 백업 원칙이라

검증하는 역할을 한다"는 방법론 가이드 5.4(변경 영향 분석) 취지가 실제로 작동한 사례로 기록해둔다.

**7차 업데이트 (2026-07-24, 같은 날) — 불일치 원인 규명**: 14주 vs 5개월 불일치는 수치 오류가
아니라 **자산 범위(Scope) 변경**이 원인이었다. 착수 초기 스코프는 "설계 + 일부 구현"(9대 공정
설계 산출물 + Mock 기반 프로토타입)이었는데, 이후 **"전체구현"으로 확장**됐다. `project_management_v1_0.md`의
14주는 확장 이전 스코프(프로토타입) 기준 계획이고, 이번 KR2-0의 5개월/16억은 확장된 스코프(전체구현)
기준 baseline이라 — 애초에 같은 대상을 가리키는 두 숫자가 아니었다. 둘 다 각자 스코프에서는 틀리지
않았다.

이건 방법론 검증 관점에서 의미가 큰 발견이다: **Scope가 바뀌면 그 이전에 확정된 기간·비용·인력
목표가 통째로 무효화된다**는 걸 실증으로 확인한 것 — 방법론가이드 5.4(변경 영향 분석)의 "영향
전파 매트릭스"에 "도메인 분리/통합" 행은 있지만 "Initiative 전체 스코프 변경"(설계+부분구현→전체구현
같은 상위 레벨 변경)에 대한 영향 전파는 아직 명시되어 있지 않다 — 이번 사례를 근거로 5.4에
행을 추가하는 게 맞아 보인다(백로그로 남김). 이 스코프 변경 이력 자체는 아직 작성 전인
"04-범위(Scope)" Proposal 산출물에 정식으로 기록되어야 한다.

**8차 업데이트 (2026-07-24, 같은 날) — 두 번째 원인 추가**: 페페가 원인을 하나 더 짚어줬다 —
개발 방법론 자체가 **워터폴(Track·Phase 순차 진행)에서 Bolt 단위 반복으로 전환**됐다는 것.
`project_management_v1_0.md`의 "Track 1~6 병렬 진행" 구조는 워터폴 전제라, 스코프 변경(7차
업데이트)과 별개로 이 방법론 전환 자체가 기존 14주 계획을 무효화하는 두 번째 원인이었다. 결과적으로
14주 vs 5개월 불일치는 **(1) 스코프 확장(설계+일부구현→전체구현) + (2) 방법론 전환(워터폴→Bolt
반복)**, 두 가지가 겹친 결과다. `02-목표KPI.md`의 KR2-0에 "산정 모델은 Track/Phase가 아니라
Bolt 단위로 설계해야 한다"는 원칙을 반영해뒀다.

이 발견은 `project_management_v1_0.md`를 단순히 "숫자만 갱신"해서는 안 되고, **Track/Phase
구조 자체를 Bolt 단위 반복 구조로 다시 설계**해야 함을 뜻한다 — 이는 예상보다 큰 작업이라 별도
착수 시점 결정이 필요하다.

**9차 업데이트 (2026-07-24, 같은 날) — 실제 인력 램프업 계획 확보**: "방법론 정의와 검증(runNshop)"
워크스트림 기준으로 8/1 시니어 +1, 9/1 시니어 +1, 9월 중순 개발자 +2(총 +4명)가 확정됐다.
`02-목표KPI.md` KR2-0에 반영했는데, 이 실제 램프업 규모(+4명)가 baseline 역산치인 "평균 동시
투입인력 약 22.4명"과 크게 차이 난다는 게 눈에 띈다 — 두 가지로 해석 가능: ① AI 협업으로 인당
생산성이 크게 올라 실제 필요 인력이 baseline보다 훨씬 적다(이 Initiative의 핵심 가설을 증명하는
신호일 수 있음), ② 이 4명은 전체구현 전체가 아니라 일부(방법론 워크스트림 등)만 커버한다. 기존
투입 인력 규모를 모르니 지금은 판단 불가 — Human Review #7로 남겨뒀다. 이 데이터는 나중에
"06-리스크가정"(인력 온보딩 지연 리스크 등) 작성 시에도 입력 자산으로 재사용 가능하다.

**10차 업데이트 (2026-07-24, 같은 날) — 인력 램프업 해석 확정**: +4명은 "**하나의 파트를 구성하는
정도의 인력**"이며 1차로 **주문(Order) 파트**에 투입되고, 이후 진행하면서 다른 도메인으로 순차
증원 계획을 세운다는 것이 확인됐다. Human Review #7의 해석 (b)가 맞았다 — baseline 역산치
"22.4명"은 프로젝트 전체 기간의 누적/평균 수치일 뿐, 특정 시점의 실제 팀 규모와는 다른 개념이다.
실제 팀은 **Bolt/Domain 단위로 순차 증원**되는 구조이고, 이는 앞서 확인한 방법론 전환(워터폴→
Bolt 반복)과 정확히 맞물린다 — 스코프 변경·방법론 전환·인력 램프업 세 가지 발견이 전부 같은
전환(워터폴 전체 계획 → Bolt/Domain 단위 점진적 확장)을 가리키고 있다는 게 이번 라운드에서
드러난 일관된 패턴이다.

**11차 업데이트 (2026-07-24, 같은 날) — 구조적 누락 발견: O3(자산 목표) 신설**: 페페가 "자산의
목표도 중요한데 빠진듯해"라고 지적. 확인해보니 O2(방법론 검증)에 자산 관련 KR(舊 KR2-5, 타
프로젝트 이식)이 하나 섞여 있을 뿐, **"자산화 자체"를 목표로 하는 항목이 없었다** — 01-문제정의서의
핵심 문제(#1 자산화 부재)가 정작 목표·KPI에는 제대로 반영이 안 된 구조적 공백이었다. O2("방법론이
작동하는가")와 O3("무엇이 자산으로 남는가")를 분리해 O3을 신설하고, 舊 KR2-5를 KR3-4로 옮겼다.
KR3-1(Asset Registry 개시)~KR3-4(타 프로젝트 이식) 4개를 추가했으나 **전부 구체적 목표 수치가
없는 신규 제안 상태**다 — 이건 다른 항목처럼 "원천적 한계"가 아니라 아직 확정을 안 한 것이라
5.1 완전성 평가에서 "부분 충족"으로 낮춰 정직하게 표기했다.

**12차 업데이트 (2026-07-24, 같은 날) — O3의 진짜 목표는 "개수"가 아니라 "탄탄함"**: 페페가
"자산의 목표라면 자산의 내용이 탄탄해야 실 프로젝트에 도움이 되니까"라고 정정. O3를 Asset
Registry·등록 건수 같은 프로세스 지표 중심에서, **"자기완결성 검증을 통과한 것만 자산으로 인정"**
하는 품질 게이트 중심으로 다시 짰다. 이 원칙은 사실 새로 만든 게 아니라 `docs_ai/09-task-spec`에서
이미 실행 중이던 것과 동일하다 — Display 도메인 3개 화면을 "그 문서 하나만 보고 원본 없이 재구성
가능한가"로 검증해온 방식 그대로다. KR3-2(자산 목록 확정)에 이 검증 통과를 필수 조건으로 넣었고,
KR3-4(타 프로젝트 이식)를 "탄탄함의 최종 증명"으로 재정의했다. 정량 목표(건수·통과율·시점)는
여전히 비어있지만, 최소한 **"무엇을 기준으로 자산이라 부를지"는 이제 명확**하다.

**13차 업데이트 (2026-07-24, 같은 날) — O3 범위 확정**: "자산 후보 몇 건"이 무슨 뜻인지 되물어와서
설명하다가, 페페가 "방법론에 정의한 산출물 전체를 대상으로 해야 하고 업무의 깊이는 정의해 나가야
겠지"로 정리해줬다. 즉 KR3-2의 범위는 임의로 후보를 추리는 게 아니라 **방법론가이드 6장에 정의된
전체 산출물 유형(현행화 중복 제외 시 고유 기준 약 40종)**이고, 각 유형을 얼마나 엄밀하게 검증할지
(라운드 수·gap 판정 기준)는 지금 고정하지 않고 유형별로 진행하며 정해간다. 현재 커버리지를 세어보니
40종 중 Task Spec(⑨) 1종만 완전 검증 완료(Display 도메인 3화면), 화면정의서(⑤)는 부분 보완,
나머지 38종은 미착수 — 갈 길이 멀다는 게 숫자로 드러났다.

**14차 업데이트 (2026-07-24, 같은 날) — 방법론은 살아있는 문서**: 페페가 "추가산출물이나 양식변경,

**19차 업데이트 (2026-07-27) — Impact 3가지로 구조화**: 페페가 세 번째 Impact 축("AI 협업 경험

Impact를 다시 짰다 — ①AI 협업 경험 부재→산정(비용·기간) 실패(기존 baseline 리스크 + 신규인력

**21차 업데이트 (2026-07-27) — "방법론"의 3요소 정의**: Impact #3에서 "표준양식 없음"과 "방법론
없음"이 같은 말인지 질문이 나와서 확인한 결과, 페페가 방법론을 세 요소로 정의해줬다 — (1) 산출물

있을 것 같다 — 예: 자산 후보 검증 시 "이 산출물 정의는 명확한가/선후행관계는 정의됐는가/표준양식은
있는가" 3항목 체크리스트로.

**25차 업데이트 (2026-07-27) — 목표 구조 재정립: 삼원(O1/O2/O3 병렬) → 이원(O2·O3)+수단(O1)**:
페페가 "O1은 재사용 가능한 산출물의 품질을 높이는 것"이라고 짚어줘서 목표 구조를 다시 봤다.
지금까지 O1(플랫폼 구축·오픈)·O2(방법론 검증)·O3(자산화)를 동등한 3개 병렬 목표로 다뤄왔는데,
실제로는 **O1이 독립 목표가 아니라 O2를 실증하기 위한 수단**이었다 — 프로토타입이 아니라 진짜
완결된 시스템을 끝까지 만들어봐야 방법론이 Proposal부터 안정화까지 실제로 작동하는지 검증할 수
있기 때문. 그리고 O2를 수행하며 나오는 산출물이 O3의 자산이 되는데, 자산으로 인정되려면 **①
방법론 준수(산출물 정의·선후행관계·표준양식) + ② 고품질(탄탄함=자기완결성)** 두 조건을
충족해야 한다는 것도 이번에 명확해졌다 — 기존엔 "탄탄함" 하나만 O3의 기준이었는데 "방법론 준수"가
빠져 있었다. `02-목표KPI.md`의 인트로·O1 제목·O3 핵심원칙을 전부 이 구조로 다시 썼고, Human
Review #2(O1/O2/O3 우선순위 충돌)는 애초에 우선순위 경합이 성립하지 않는 구조임이 밝혀져 해결로
표기했다.

**45차 업데이트 (2026-07-28) — "도메인 기능표" 참고자료 12개 도메인 전체 작성**: 2차 이후 도메인
순서를 논의하다가(가이드 부록B "파트 구성" 참고 — 사용자참여→회원, 플랫폼운영→운영으로 명칭도
변경) 페페가 "배송 도메인이 누락되었는데... 클레임도"를 지적. 확인해보니 배송(`Delivery`)·클레임
(`Claim`)은 별도 도메인이 아니라 **Order 도메인의 소유 데이터·책임으로 이미 포함**돼 있었다 —
Order가 가이드 부록B에서 9 Bolt(파트 내 최다)로 잡힌 이유가 이것이었다.

이걸 계기로 "도메인 하위 업무를 어떻게 분류해 관리할지"를 논의 — 새 Scope 계층(Feature 등)을
만드는 대신, 이미 확정된 "상위 유스케이스" 업무그룹 규칙(조건부 3단: 대분류→소분류, 6개 초과
시만 중분류)을 12개 도메인 전체에 선제 적용한 **참고자료**를 만들기로 했다. 성격은 정책서·
도메인정의서와 같은 "여러 정식 산출물(범위·EARS·인터페이스명세)의 입력자료"이지 40종 방법론
산출물이 아니므로, RACI·Human Review 절차 없이 `docs/자산화/참고자료/도메인기능표/`에 12개
파일(도메인당 1개) + README로 작성했다 — 전량 도메인정의서(`runNshop_bounded_context_v1_0.md`)
원문에서 발췌, 새로 지어낸 항목 없음. 결과적으로 12개 도메인 전부 대분류당 소분류 6개를 안
넘어서 중분류 없이 2단으로 충분했다 — "조건부" 규칙이 실제로 과잉 구조화를 막아준 사례.

**46차 업데이트 (2026-07-28) — apps/ 실제 소스로 도메인 기능표 전면 보완**: 페페가 "apps 폴더의
소스도 참고해서 도메인 기능표 보완해줘 — 진행중이던 프로토타입이라 화면·버튼·기능이 정의되어
있어"라고 요청. Explore 에이전트 3개를 병렬 실행해 `runNshop-admin`·`runNshop-partner`·
`runNshop-mobile` 전체를 조사했다.

핵심 발견:
- **Order의 클레임처리가 실제로 중분류가 필요한 첫 사례로 확인됨** — 취소(벤더 액션 없음)·
  반품(수거→재고복구→이의제기)·교환(재고확인→수거→출고)이 완전히 다른 상태머신이라, 소분류가
  9개까지 늘어 조건부 규칙(6개 초과 시 중분류)이 실제로 발동했다.
- **12개 도메인 중 6개**(Order·Catalog·Vendor·Settlement·Config·Community)에서 도메인정의서엔
  없던 실제 기능이 발견돼 소분류를 추가했다 — 특히 Config는 "배치관리"·"프로그램관리"가 통째로
  새 대분류로 추가됐고, Vendor는 "계정·보안관리"(담당자정보·비밀번호·2FA·세션관리) 5종이 새로
  드러났다.
- **13번째 도메인 후보 "전시(Display)" 발견** — admin에 Page/Section/Template CMS가 실제
  구현돼 있는데 기존 12개 도메인 어디에도 안 속함(README에 Human Review로 기록).
- **Payment·Search는 코드 구현 0건**으로 확인 — 도메인정의서 기반 소분류는 유지하되 "실제 코드로
  검증된 것 없음"을 명시.
- **고객 앱(mobile)의 구현 격차를 정량 확인**: 주문서(결제 전)·PDP·홈·기획전만 실존, 주문내역·
  배송조회·클레임신청·마이페이지·검색·카테고리·리뷰작성·QnA작성은 스텁이거나 코드 자체가 없음.

각 도메인 파일에 "코드 기반 보완" 절을 별도로 추가해 도메인정의서 원본과 섞이지 않게 했고,
README에 13번째 후보(Display)·공통 패턴(엑셀/일괄처리 전부 스텁, 승인워크플로우 단계 수 상이,
상태변경 UI 관행 2종)·Human Review 6건을 정리했다.

**48차 업데이트 (2026-07-28) — 메인프레임·화면구조·메뉴를 Config로 편입**: 페페가 "메인프레임,

**49차 업데이트 (2026-07-28) — 소분류 분리 기준 명문화: "CRUD가 아니라 워크플로우"**: 페페가
"운영자 계정관리 화면에서 조회,추가,상세화면이동...등 버튼들은 기능이 아닌가?"라고 질문 —
소분류를 조회/등록/수정/삭제 단위까지 쪼개야 하는지에 대한 근본 질문이었다. 그렇게 하면 12개
도메인 × 소분류 약 80개 × CRUD 4~5개로 표가 폭발해 "한눈에 조망" 목적에 안 맞는다고 판단,
**소분류 분리 기준은 CRUD 차이가 아니라 워크플로우/상태전이 차이**라는 원칙으로 정리해 페페
확인을 받았다 — "운영자 신청 승인"을 "운영자 계정 관리"와 별도로 뽑은 것도 이 기준(승인/반려
워크플로우가 다름) 때문이었다는 걸 소급 확인. README "작성 규칙"에 명문화해 앞으로 이 표를
보완할 때 판단 기준으로 삼는다.

**50차 업데이트 (2026-07-28) — 소분류별 API 호출 개수 추정 (운영자권한관리 시범 적용)**: 페페가
"소분류(기능)별로 api 호출 갯수(횟수 말고), 운영자 권한 관리 하나만 확인해줘"라고 요청. 처음엔
실제 코드에 fetch/api 호출이 전혀 없어(전부 mockData+useState) 0건으로 보고했으나, 페페가
"작업중이라 연결 안 된 것도 많아, 그러나 화면(탭기준)·버튼이 하나의 api를 호출한다고 보면 됨"
이라고 카운트 기준을 정정 — **화면/탭 로드 1개=API 1개, 실제 제출 버튼 1개=API 1개**(취소·
편집토글 등 UI전용 버튼 제외) 기준으로 재산정했다.

결과: 운영자 계정 관리 4, 운영자 신청 승인 4, 권한(Role) 관리 8, 화면·API 접근 이력 조회 3 —
소계 API 약 19개. 이 과정에서 **지난번 미해결이었던 "프로그램 접근 권한(OperatorDetail)" 탭의
소분류 분리 여부도 해결됨** — 코드 확인 결과 버튼이 하나도 없는 조회 전용 화면이라, 워크플로우
분리 기준(49차)에 따라 별도 소분류가 아니라 "화면·API 접근 이력 조회"의 3번째 탭으로 합쳤다.
`11-Config.md`에 "API 호출 개수 추정" 절을 신설 — 다른 4개 대분류는 아직 이 방식으로 안 셈,
필요시 이어서 진행.

**51차 업데이트 (2026-07-28) — Config 전체 17개 소분류로 API 호출 개수 확장, 표 구조 통합**:
페페가 나머지 4개 대분류(프로그램관리·배치관리·공통설정관리·콘텐츠관리)도 같은 기준으로
작성해달라고 요청 — `system/{program-status,batch-job,common-code}`, `settings/{terms,
banned-word,notice,banner}` 실제 코드를 마저 확인했다. 결과를 별도 절이 아니라 **메인 표
자체에 화면/탭·버튼·API 호출개수 3개 열을 추가**하는 구조로 통합(기존 "API 호출 개수 추정"
절은 제거, 중복 방지).

소분류 17개 중 15개 산정(합계 API 약 57개), **2건("메뉴·화면구조 관리"·"공통 UI 셸 관리")은
화면 자체가 없는 코드/구성 자산이라 억지로 숫자를 만들지 않고 N/A로 정직하게 표기** — 이 문서
세트 전체가 지켜온 "근거 없으면 확인 필요/N/A로 남긴다" 원칙을 API 카운트에도 그대로 적용한
것. 약관·금지어·공지·배너 4종 관리 화면이 전부 API 4개로 균일하게 나온 것도 확인 — 동일
컴포넌트 패턴(목록+등록/수정모달)이 재사용된 결과라는 걸 코드로 실증했다.

**52차 업데이트 (2026-07-28) — 12개 도메인 전체로 API 호출 개수 확장 (병렬 에이전트 9개)**:
페페가 "모든 도메인에 대해서 작업해줘"로 Config에서 검증한 카운트 기준을 전 도메인에 적용하도록
요청. Payment·Search는 코드가 아예 없다는 걸 이미 알고 있어 직접 N/A 처리했고, 나머지 9개
도메인(Order·Catalog·Member·Promotion·Settlement·Vendor·Community·Notification·Audit)은
일반 에이전트 9개를 병렬로 띄워 각자 실제 코드를 읽고 표를 갱신하게 했다 — Order를 맡은 에이전트는

**병렬 작업에서 나온 주요 발견**(각 파일의 "코드 기반 보완" 절에 상세 기록):
- **Catalog**: 상품 등록(6단계 위저드)의 실제 구현이 admin이 아니라 **partner 앱**에 있음 — admin엔
  별도 단순 1단계 등록 모달이 따로 있어 등록 경로가 이중화됨. Display의 게시스케줄링·데이터매핑
  탭 2개는 코드는 완성돼 있지만 `PageDetail.tsx`에 import되지 않아 **실제로는 진입할 수 없는
  dead code**임을 발견 — 스텁 버튼과는 다른 새로운 유형의 갭.
- **Promotion**: "쿠폰 승인/반려(MD)"가 상태값·필터만 있고 실행 버튼 자체가 코드에 없어 N/A로 정정.
- **Community**: "주문 QnA 관리"가 별도 화면이 아니라 상품 QnA와 같은 화면(유형 필터로만 구분)임을
  코드로 확인, 기존 "OrderQnA" 표기를 정정.
- **Order**: 클레임처리 11개 소분류가 반품/교환 각각 상세 모달 하나(2탭)를 4개·3개 소분류가
  나눠 쓰는 구조라 화면 로드 귀속을 정교하게 나눴고, 표 밖의 기능(admin 주문상세의 비클레임
  4개 탭, partner "출고 처리" 버튼)도 추가로 발견해 Human Review로 남겼다.
- 여러 도메인에 걸쳐 **동일한 "탭 공유" 카운팅 원칙**(화면 로드는 대표 행에만 귀속, 나머지는
  버튼만 산정)이 일관되게 적용됨 — Config에서 확립한 방법론이 다른 도메인에도 무리 없이
  일반화된다는 걸 실증.

이 작업으로 "도메인 기능표"는 대분류·중분류·소분류 목록에 더해, 각 소분류가 실제로 몇 개의
