# C3 아키텍처컨벤션

> **수립 데드라인**: S2 시작 전 | **참고 대상**: 컴포넌트, ERD, 이벤트플로우, 시퀀스

---

## 1. 목적

시스템 전체 구조와 계층 간 책임·의존 규칙을 정의하여,
일관된 아키텍처 패턴으로 개발하고 향후 서비스 분리 가능성을 확보한다.

---

| App | 용도 | UI 구조 |
|-----|------|---------|
| mobile | 고객웹 | C7 디자인시스템(mobile) 참조 |
| admin | 관리자 | C7 디자인시스템(admin) 참조 |

### 3.2 API Namespace

| App | API Prefix | 인증 역할 |
|-----|-----------|-----------|
| mobile | `/api/v1/**` | CUSTOMER |
| admin | `/api/admin/v1/**` | ADMIN |
| partner | `/api/partner/v1/**` | VENDOR |

### 3.3 모노레포 구조

```
runNshop/                        ← 모노레포 루트
├── apps/
│   ├── runNshop-mobile/         ← 독립 package.json
│   ├── runNshop-admin/          ← 독립 package.json
│   └── runNshop-partner/        ← 독립 package.json
├── api/
│   └── runNshop-api/            ← 독립 Gradle
├── packages/                    ← (향후) 공유 모듈 (types, utils)
└── docs/                        ← 산출물·방법론·컨벤션
```

**원칙:**
- 각 앱은 **독립적으로 빌드·실행** 가능
- 앱 간 직접 코드 의존 금지. 공유 코드 필요 시 `packages/`를 통해 명시적으로 관리
- 모든 앱은 독립 프로세스로 기동 가능. FE는 API 서버 미실행 시에도 개발 서버 자체는 기동됨 (API 호출 시 에러만 발생)

## 4. Backend Architecture

### 4.1 계층 구조

```
com.runnshop.{domain}/
├── controller/     ← API 진입점 (앱별 분리)
├── service/        ← 비즈니스 로직
├── repository/     ← 데이터 접근 추상화
├── dto/            ← 요청/응답 데이터 클래스
└── entity/         ← (향후) JPA Entity
```

### 4.2 Controller 분리 원칙

> **Controller는 앱별로 분리하고, Service를 공유한다.**

```
CustomerOrderController ─┐
AdminOrderController     ─┼→ OrderService → OrderRepository
PartnerOrderController  ─┘
```

| 규칙 | 설명 |
|------|------|
| 앱별 Controller 분리 | 각 앱의 API 계약(요청/응답/권한)이 다르므로 분리 |
| Service 공유 | 동일 비즈니스 로직은 하나의 Service에서 처리 |
| 다중 URL 매핑 금지 | 프로토타입 편의였으나 실 프로젝트에서 복잡도 증가 → 금지 |

**Controller 네이밍:**

```kotlin
// 고객웹
@RestController
@RequestMapping("/api/v1/orders")
class CustomerOrderController(private val orderService: OrderService) { ... }

// 어드민
@RestController
@RequestMapping("/api/admin/v1/orders")
class AdminOrderController(private val orderService: OrderService) { ... }

// 입점사
@RestController
@RequestMapping("/api/partner/v1/orders")
class PartnerOrderController(private val orderService: OrderService) { ... }
```

### 4.3 Repository 추상화 (프로토타입 → 실 전환)

> Service는 Repository interface에 의존하고, 구현체를 교체하여 프로토타입 → 실 구현으로 전환한다.

```
┌─ Prototype ─────────────────┐    ┌─ Production ────────────────┐
│ Controller                  │    │ Controller                  │
│     ↓                       │    │     ↓                       │
│ Service                     │    │ Service                     │
│     ↓                       │    │     ↓                       │
│ Repository (interface)      │    │ Repository (interface)      │
│     ↓                       │    │     ↓                       │
│ MockRepository → JSON 파일  │    │ JpaRepository → Database    │
└─────────────────────────────┘    └─────────────────────────────┘
```

**전환 원칙:**
- Controller 코드 변경 없음
- Service 코드 변경 없음 (Repository interface 계약 유지)
- MockRepository → JpaRepository 교체만으로 전환

**프로토타입 MockRepository 예시:**

```kotlin
interface OrderRepository {
    fun findById(orderId: String): OrderEntity?
    fun findByMemberId(memberId: String): List<OrderEntity>
}

@Repository
@Profile("prototype")
class MockOrderRepository(private val mockLoader: MockLoader) : OrderRepository {
    override fun findById(orderId: String) = mockLoader.loadAs("v1", "order__GET_orders_$orderId.json")
    override fun findByMemberId(memberId: String) = mockLoader.loadList("v1", "order__GET_members_me_orders.json")
}
```

### 4.4 프로토타입 규칙

| 규칙 | 설명 |
|------|------|
| Mutation API | 실제 영속화하지 않으며, 성공 응답만 반환 |
| 조회 API | Mock JSON 파일에서 로딩 |
| 상태 비유지 | 서버 재시작 시 초기 상태 (in-memory 상태 없음) |
| FE 처리 | API 성공 응답을 받아 사용자에게 안내 (예: "저장되었습니다") |

## 5. Domain Architecture

### 5.1 12개 도메인

order, catalog, member, payment, promotion, settlement, vendor, notification, community, search, config, audit

### 5.2 Domain 의존 규칙

| 규칙 | 설명 |
|------|------|
| **내부 구현 직접 참조 금지** | 다른 Domain의 Service/Repository/Entity 직접 import 금지 |
| **Public Interface 사용** | 다른 Domain 호출 시 `{Domain}PublicApi` interface 통해서만 |
| **순환 의존 금지** | A → B → A 형태의 의존 불허 |
| **공유 모듈 최소화** | `common/` 패키지는 순수 유틸(MockLoader, CorsConfig 등)만 |
| **Data 소유권** | 각 Domain은 자기 테이블만 직접 접근. 타 Domain 데이터는 API/Event로 |

```
Order Domain                    Payment Domain
┌─────────────────┐            ┌─────────────────┐
│ OrderService    │            │ PaymentService  │
│     ↓           │            │     ↓           │
│ OrderRepository │            │ PaymentRepository│
│     ↓           │   Event    │     ↓           │
│ ord_* tables    │───────────→│ pay_* tables    │
└─────────────────┘            └─────────────────┘
         ↑                              ↑
    PublicApi                       PublicApi
  (동기 호출 시)                  (동기 호출 시)
```

### 5.3 Domain 간 통신

| 상황 | 방식 | 예시 |
|------|------|------|
| 즉시 결과가 필요 | **동기** (PublicApi 호출) | 재고 선점 요청, 금액 재계산 |
| 상태 변화 전파 | **비동기** (Event 발행) | ORDER_CANCELLED → Payment 환불 |
| 결합도 감소 필요 | **비동기** (Event) | ORDER_PAID → Settlement 정산 등록 |
| 장시간 작업 | **비동기** + 콜백 | PG 결제 요청 → 콜백 승인 |

**이벤트 규칙 상세는 C5 이벤트설계컨벤션 참조.**

## 6. Frontend Architecture

### 6.1 디렉토리 구조

```
apps/runNshop-{app}/
├── app/                ← Next.js App Router (라우팅)
├── components/
│   ├── layout/         ← 레이아웃 컴포넌트 (Header, NavBar 등)
│   └── common/         ← 공용 컴포넌트 (Toast, Skeleton 등)
├── src/
│   └── {domain}/       ← 도메인별 Feature 폴더
│       ├── {feature}/  ← 기능 단위 (order-list, order-detail 등)
│       └── components/ ← 도메인 전용 컴포넌트
├── lib/                ← API 호출, 유틸, 상수
└── styles/             ← globals.css (admin/partner)
```

### 6.2 FE → API 통신

| 규칙 | 설명 |
|------|------|
| 모든 데이터는 API 통해 조회 | 하드코딩 금지 |
| fetch/axios 사용 | lib/api.ts에 공통 래퍼 |
| 에러 처리 | API 에러 → 사용자 친화적 메시지 표시 |
| 로딩 상태 | Skeleton 또는 로딩 인디케이터 표시 |

## 7. 근거

| 항목 | 출처 |
|------|------|
| 계층 분리 | Repository 추상화로 프로토타입 → 실 전환 시 교체 범위 최소화 |
| Controller 앱별 분리 | 앱별 API 계약(권한/응답/검증)이 다르므로 분리가 유지보수에 유리 |
| Domain 경계 | 도메인정의서(DB) 12개 도메인 독립성 → 향후 서비스 분리 가능성 확보 |
| 동기/비동기 구분 | 이벤트플로우(DI) — 즉시 결과 vs 상태 전파 판단 기준 |
| 모노레포 | 앱 독립 빌드·배포 + 공유 코드 명시적 관리 |
| 포트 할당 | 기존 실행 환경 (mobile:3000, admin:3001, partner:3002, api:8080) |
| 환경 구성 | `next.config.js` rewrite 프록시 패턴 (실 소스 기반) |
