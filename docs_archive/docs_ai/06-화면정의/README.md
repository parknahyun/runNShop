# ⑤ 화면정의서 작성 기준

> 이 폴더(`docs_ai/06-화면정의/`) 전체에 적용되는 공통 규칙. 도메인별 상세 배경·이력은 각
> `<app>/<domain>/<Domain>-readme.md`에 있다 — 예: [admin/Display/Display-readme.md](admin/Display/Display-readme.md),
> [admin/Shell/Shell-readme.md](admin/Shell/Shell-readme.md).

## 폴더 구조

`docs_ai/06-화면정의/<app>/<domain>/<feature>.md` 단위로 분리한다. 화면 여러 개(예: 목록/상세/
등록)를 한 파일에 몰아넣지 않고 기능(feature) 단위 파일로 쪼갠다. 파일명 앞 번호는 실제 메뉴
노출 순서와 동일하게 맞춘다(목록에서 정렬했을 때 메뉴 순서 그대로 보이도록).

각 도메인 폴더에는 `<Domain>-readme.md` 인덱스 파일을 둔다. 포함할 내용:
- 도메인 개요와 원본 문서(`docs/6. 화면정의/...`) 상 위치(있다면 §번호까지)
- "이 도메인의 화면 (feature)" 표 — feature 파일 / 화면 ID / 화면명
- 도메인 공통 사항 — 관련 정책서·도메인정의서·엔티티정의 링크, 도메인 전체에 걸친 공통 패턴
  (예: 상태 배지 재사용 방식)

## 작성 방향 — 화면정의서가 기준(spec)이다, 소스의 사본이 아니다

이 문서는 **소스 코드를 있는 그대로 옮겨 적는 문서가 아니다.** 원본 SDLC 산출물
(`docs/6. 화면정의`, 정책서·도메인정의서 등)을 기준으로 "이 화면은 이렇게 동작해야 한다"를
먼저 정의하고, 그 다음에 현재 소스 코드가 그 기준과 얼마나 일치하는지 대조한다.

소스가 기준과 다를 때:
- **의도된 설계 변경**(예: Mock 단계라 상태값을 단순화)이면 — 그 사실을 명시하고 이 문서가 새
  기준이 된다. 예: [admin/Display/01-Page.md](admin/Display/01-Page.md) "알려진 이슈" 절.
- **의도되지 않은 누락/버그**이면 — "소스 수정 필요" 항목으로 명시한다. **화면정의서를 소스에
  맞춰 낮추지 않는다** — 본개발(실제 구현) 전환 시 이 문서가 곧 구현해야 할 목록이 된다.

`docs_ai/09-task-spec/`의 Task Spec은 이 문서를 참조해 작성되며, 반대로 이 문서가 Task Spec이나
현재 소스 상태에 맞춰 다시 쓰이지 않는다 — `docs_ai/README.md`의 "설계가 바뀌면 원천 문서를
고친다" 원칙과 동일하다.
