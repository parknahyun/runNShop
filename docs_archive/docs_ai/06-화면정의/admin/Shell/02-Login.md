## 보강 설명

### 개요
세션이 없거나 무효할 때 `app/page.tsx`가 셸 대신 보여주는 로그인 폼. 로그인 성공 시
`app/page.tsx`가 세션을 받아 [00-AppShell.md](00-AppShell.md)로 전환한다.

### 화면 구성

| 화면 | 화면유형 | 소스 |
|------|---------|------|
| 로그인 | `layer`(전체 화면) | `apps/runNshop-admin/src/shell/LoginScreen.tsx` |
| Mock 인증 | API 대체 함수 | `apps/runNshop-admin/src/shell/mockAuth.ts` |

### Mock 인증 동작

`mockAuth.login(email, password)`가 실제 인증 서버 대신 동작한다(`LoginGuide.tsx` 규칙: "프로토타입:
API 항상 성공 응답"):
- 이메일·비밀번호가 **둘 다 채워져 있으면 무조건 성공** — 실제 자격 증명 검증 없음.
- 성공 시 role은 항상 `'SUPER'`(최상위 권한)로 고정한다. "권한은 로그인 정보로 가져올 예정"이라는
  본개발 방향에 따라, 실제 로그인 API 연동 시 이 부분을 서버가 반환하는 실제 role로 교체한다.
- 성공한 세션은 `localStorage`에 저장한다(`LoginGuide.tsx` 규칙: "세션 만료 없이 항상 로그인
  유지" — 새로고침해도 로그인 상태가 풀리지 않는다. 로그아웃을 눌러야만 세션이 사라진다).

원본 §3.5 API 매핑표의 API #1(로그인)·#3(로그아웃)과 대응(위 [AI-H12] 참고). 토큰 갱신(API #2,
`/auth/refresh`)은 세션을 영구 유지하는 현재 Mock 방식에선 필요 없어 아직 다루지 않았다 — 실제
로그인 연동 시 토큰 만료 정책과 함께 재검토 필요.

### 알려진 제약 (Mock 단계, 의도된 단순화)

- 비밀번호 형식(8자 이상, 영문+숫자 포함)은 힌트 텍스트만 있고 실제로 검증하지 않는다.
- 로그인 실패 5회 잠금은 안내 문구만 있고 실제로 세지 않는다.
- "운영자 신청"·"비밀번호 찾기" 링크는 비활성 표시만 한다 — 대상 화면(`ADM-000-002/003`)이 없다.

### 이번 범위 밖

원본 메뉴 트리(§3.3)의 나머지 인증 화면 2종은 이번에 구현하지 않았다:
- `ADM-000-002` 운영자 신청
- `ADM-000-003` 비밀번호 변경 (최초)

두 화면 모두 아직 화면정의서·소스 어느 쪽에도 없다 — 별도 작업 필요.
