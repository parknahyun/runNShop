# AI 코딩을 위한 요구사항 정의서 표준양식 및 Harness 매핑 기준

- **문서버전**: v1.0
- **작성자**: 페페
- **작성일**: 2026-07-03
- **목적**: 일반 개발방법론의 요구사항 정의서 표준양식을 유지하면서, AI 코딩을 위한 Harness 보강 항목을 정의
- **적용범위**: 12개 비즈니스 도메인

---

## 0. 설계 원칙

### 기존 요구사항 정의서와의 관계

```
┌─────────────────────────────────────────────────────┐
│  일반 방법론 요구사항 정의서 (기본 섹션)              │
│  ─────────────────────────────────────────           │
│  ① 요구사항 ID·분류                                  │
│  ② 요구사항명·설명                                    │
│  ③ 우선순위·상태                                      │
│  ④ 관련 화면·업무흐름                                 │
│  ⑤ 수용 기준 (Acceptance Criteria)                   │
│  ⑥ 비기능 요구사항                                    │
├─────────────────────────────────────────────────────┤
│  AI 코딩 보강 섹션 (Harness 매핑)  ← 추가 부분       │
│  ─────────────────────────────────────────           │
│  ⑦ HARD Constraint + wrong_pattern                   │
│  ⑧ 검증 시나리오 (Given-When-Then)                   │
│  ⑨ 의존 도메인·이벤트 (Context)                      │
│  ⑩ 데이터 불변식 (Data Contract 요약)                │
├─────────────────────────────────────────────────────┤
│  참조 링크                                            │
│  → API 정의서 (상세 HOW)                             │
│  → 정책서·ERD·화면정의서                             │
└─────────────────────────────────────────────────────┘
```

**원칙**:
- ①~⑥은 **기존 방법론 그대로** (PMO·현업·QA가 읽는 문서)
- ⑦~⑩은 **AI 코딩 보강** (AI가 구현 시 참조하는 제약)
- ⑦~⑩이 없어도 요구사항 정의서로서 성립해야 함 (하위 호환)
- 상세 구현(HOW)은 API 정의서에 위임 → 중복 제거

|------|------|------|

| 승인자 | | 현업 확인 필수 |

### 1-2. 요구사항 단위 양식

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

요구사항 ID   : FR-{도메인}-{SEQ}         (예: FR-ORD-001)
요구사항명    : 장바구니
분류          : 기능(FR) / 비기능(NFR) / 제약(CR)
우선순위      : P1(Must) / P2(Should) / P3(Nice)
도메인        : Order
상태          : CONFIRMED
요청 부서     : 
관련 화면     : CUS-040
관련 업무흐름  : BPM-ORD-001

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 1-3. 요구사항 설명

```
[설명]
장바구니에 상품을 담고, 수량 변경·삭제할 수 있으며,
주문서 진입 시 장바구니 데이터를 기반으로 주문을 생성한다.

[상세 규칙]
• 입점사별 그룹핑 표시
• 할인 혜택 안내 (쿠폰·포인트·장바구니할인)
• 비로그인 장바구니 지원 (로그인 시 머지)
• 수량 변경·삭제·전체 삭제
• 최대 50개 (SKU 기준)
```

### 1-4. 수용 기준 (Acceptance Criteria)

```
AC-1: 상품을 장바구니에 담으면 입점사별로 그룹핑되어 표시된다
AC-2: 동일 SKU 재담기 시 수량이 합산된다 (새 행 추가 아님)
AC-3: 비로그인 상태에서 담은 상품은 로그인 시 기존 장바구니와 머지된다
AC-4: 장바구니 상품이 50개 초과 시 담기가 거부되고 안내 메시지가 노출된다
AC-5: 품절 상품은 장바구니에 유지되되 비활성(선택 불가) 상태로 표시된다
```

### 1-5. 비기능 요구사항 (해당 시)

```
성능: 장바구니 조회 응답 1초 이내
보안: 타 회원 장바구니 접근 불가
데이터: 주문 완료 후 90일 보관, 이후 아카이빙
```

## 2. 표준 양식 — AI 코딩 보강 섹션

> 아래 ⑦~⑩ 은 기존 요구사항 정의서 뒤에 **부록**처럼 붙이거나,
> 별도 탭(시트)으로 관리해도 무방하다.

### ⑦ HARD Constraint + wrong_pattern

AI가 **절대 다르게 구현하면 안 되는** 비즈니스 불변식.

| ID | 규칙 | 이유 | AI 오류 패턴 (wrong_pattern) |
|----|------|------|------------------------------|
| HC-ORD-CART-001 | 장바구니 최대 50개 (SKU 기준) | 주문서 처리 성능 + UX 한계 | 제한 없이 무한 추가 허용 |
| HC-ORD-CART-002 | 로그인 시 비로그인 장바구니 머지 (교체 아님) | 고객 담아둔 상품 유실 방지 | 로그인 시 비로그인 장바구니를 덮어씀 |
| HC-ORD-CART-003 | 동일 SKU 재담기 시 수량 합산 | 중복 행 방지 | 별도 행으로 추가 |

**작성 기준**:
- AC(수용 기준) 중 **위반 시 시스템 오류**가 되는 것만 HARD로 승격
- `wrong_pattern`은 AI(LLM)가 학습 데이터 편향으로 흔히 저지르는 구현 실수를 기술
- HARD가 없으면 AI 코딩 보강 불필요 (단순 CRUD 등)

### ⑧ 검증 시나리오 (Given-When-Then)

AI가 테스트 코드를 생성하는 기준. AC보다 **구체적·실행 가능**하게 작성.

| # | 시나리오명 | Given | When | Then |
|---|-----------|-------|------|------|
| 1 | 정상 담기 | ON_SALE 상품, 재고 10개 | 수량 3개 담기 | 장바구니에 추가, 수량=3 |
| 2 | 중복 담기 | 이미 SKU-A 2개 담김 | SKU-A 3개 추가 | 수량=5 (합산), 새 행 없음 |
| 3 | 품절 담기 | SKU 재고=0 | 담기 시도 | 에러 "품절", 장바구니 변경 없음 |
| 4 | 50개 초과 | 장바구니 50개 | 1개 추가 시도 | 에러 "최대 수량 초과" |
| 5 | 비로그인→로그인 머지 | 비로그인: SKU-A 2개, 회원: SKU-B 1개 | 로그인 | 장바구니: A+B, 재고·행사 재검사 |

**작성 기준**:
- AC 1건당 최소 1개 시나리오
- **엣지 케이스** 반드시 포함 (초과, 머지 충돌, 동시성 등)
- 실패 케이스가 성공 케이스보다 중요 (AI는 happy path는 잘 만듦)

### ⑨ 의존 도메인·이벤트

AI가 구현 시 **어떤 도메인 API를 호출해야 하는지** 판단하는 근거.

```
의존 (Upstream):
  • Catalog — 상품 정보·재고 확인
  • Promotion — 행사가·쿠폰 적용 가능 여부 확인

영향 (Downstream):
  • Order — 주문서 생성 시 장바구니 데이터 사용

발행 이벤트: 없음 (장바구니는 이벤트 미발행)
수신 이벤트: 없음
```

**작성 기준**:
- 도메인 간 호출이 없는 단독 기능이면 생략 가능
- 이벤트 발행/수신이 있으면 반드시 명시 (Outbox 적용 여부 판단)

### ⑩ 데이터 불변식 (요약)

AI가 구현 시 **항상 유지해야 할** 데이터 조건. (상세는 ERD·정책서 참조)

```
• cart.quantity >= 1 (0이면 삭제 처리)
• member_id + sku_id 조합 UNIQUE (중복 행 금지)
• soft_delete 적용 (is_deleted=TRUE, 물리 삭제 금지)
• 상태전이: 없음 (장바구니는 상태 머신 없음)
```

**작성 기준**:
- 상태 전이가 있는 엔티티(주문, 클레임 등)는 허용 전이만 나열
- ERD에 이미 있더라도 AI가 놓치기 쉬운 것은 중복 기재 허용

## 3. Harness 매핑 기준 — 보강 섹션과 6개 Harness의 관계

| 보강 섹션 | 매핑 Harness | 역할 | API 정의서 전파 |
|-----------|-------------|------|----------------|
| ⑦ HARD Constraint | Domain Constraint Harness | AI 오류 방지 최우선 | → Domain Constraint.HARD 그대로 복사 |
| ⑧ 검증 시나리오 | Feedback Loop Harness | 테스트 코드 생성 기준 | → test_scenarios로 전개 |
| ⑨ 의존 도메인 | Context Harness | Import·호출 대상 판단 | → dependency_domains, sequence |
| ⑩ 데이터 불변식 | Data Contract Harness | 데이터 정합성 보장 | → invariants, state_transition |
| (기본) 수용 기준 | Requirements Validation Harness | 입출력 검증 기준 | → Request/Response 교차검증 |
| (기본) 비기능 | Domain Constraint (하위) | 성능·보안·멱등성 | → 비기능 요구사항 섹션 |

### 전파 규칙 (요구사항 → API 정의서)

```
요구사항 정의서 (WHAT)              API 정의서 (HOW)
━━━━━━━━━━━━━━━━                ━━━━━━━━━━━━
⑦ HARD Constraint ──────────→  Domain Constraint.HARD (복사)
⑧ 검증 시나리오   ──────────→  Feedback Loop.test_scenarios (API별 분배)
⑨ 의존 도메인     ──────────→  Context.dependency_domains (상속)
⑩ 데이터 불변식   ──────────→  Data Contract.invariants (상속)

AC (수용 기준)     ──────────→  Request/Response (필드 상세 전개)
비기능             ──────────→  비기능 요구사항 (그대로)

※ Output Schema, Endpoint, Sequence는 API 정의서에서만 작성 (요구사항에 없음)
```

**중복 제거 원칙**:
- 요구사항 정의서: **규칙(WHAT)** 만 기술
- API 정의서: **구현 상세(HOW)** 만 기술
- 겹치는 것: HARD Constraint, 의존 도메인 → 요구사항이 원본, API는 참조

## 4. 작성 범위 판단 기준

모든 요구사항에 ⑦~⑩ 전부를 채울 필요는 없다.

| 요구사항 유형 | 필수 보강 | 선택 보강 | 비고 |
|--------------|----------|----------|------|
| 단순 CRUD (조회·등록) | 없음 | ⑩ 불변식 | AC만으로 충분 |
| 복합 비즈니스 로직 | ⑦⑧ | ⑨⑩ | AI 오류율 높은 영역 |
| 도메인 간 연동 | ⑦⑧⑨ | ⑩ | 의존 관계 명시 필수 |
| 상태 전이 (주문·클레임) | ⑦⑧⑩ | ⑨ | 상태 머신이 핵심 |
| 배치·이벤트 처리 | ⑦⑧⑨ | ⑩ | 이벤트 발행/수신 필수 |

> 판단 기준: **AI가 AC만 보고 정확히 구현할 수 있으면** 보강 불필요.
> AI가 틀릴 가능성이 높으면(복합 규칙, 도메인 간 연동, 상태 전이) 보강 필수.

## 5. Type별 보강 가이드

| Type | 설명 | 핵심 보강 항목 | 이유 |
|------|------|---------------|------|
| A (표준/운영) | 배치·동기화·CRUD | ⑩ 데이터 불변식 | 단순하지만 데이터 정합성 중요 |
| B (협상·클레임) | 귀책 판단·정산 이의 | ⑦ HARD + ⑧ 시나리오 | 비즈니스 규칙 복잡, AI 오류율 최고 |
| C (개발 주도) | 결제 연동·재고 선점 | ⑨ 의존 + ⑧ 시나리오 | 기술 제약·연동 순서가 핵심 |
| D (사업 주도) | 회원 등급·프로모션 | ⑦ HARD (변경 빈번 대비) | 정책 변경 시 AI 재구현 근거 |

## 6. 실 적용 예시: FR-ORD-001 장바구니

### 기본 섹션 (일반 방법론)

```
요구사항 ID   : FR-ORD-001
요구사항명    : 장바구니
분류          : 기능(FR)
우선순위      : P1
도메인        : Order
상태          : CONFIRMED
관련 화면     : CUS-040
관련 업무흐름  : BPM-ORD-001

[설명]
장바구니에 상품을 담고, 수량 변경·삭제할 수 있다.
비로그인 상태에서도 장바구니를 이용할 수 있으며, 로그인 시 기존 장바구니와 머지된다.

[상세 규칙]
• 입점사별 그룹핑 표시
• 할인 혜택 안내 (쿠폰·포인트·장바구니할인)
• 비로그인 장바구니 지원 (로그인 시 머지)
• 수량 변경·삭제·전체 삭제
• 최대 50개 (SKU 기준)

[수용 기준]
AC-1: 상품을 장바구니에 담으면 입점사별로 그룹핑되어 표시된다
AC-2: 동일 SKU 재담기 시 수량이 합산된다
AC-3: 비로그인 상태에서 담은 상품은 로그인 시 머지된다
AC-4: 50개 초과 시 담기가 거부된다
AC-5: 품절 상품은 비활성 상태로 표시된다

[비기능]
• 장바구니 조회 응답 1초 이내
• 타 회원 장바구니 접근 불가
```

### AI 코딩 보강 섹션

```
[⑦ HARD Constraint]
HC-ORD-CART-001 | 최대 50개(SKU) | wrong: 무제한 추가 허용
HC-ORD-CART-002 | 로그인 시 머지(교체 아님) | wrong: 덮어쓰기
HC-ORD-CART-003 | 동일 SKU 재담기=수량 합산 | wrong: 별도 행 추가

[⑧ 검증 시나리오]
1. 정상 담기 → 장바구니 추가, 입점사 그룹핑
2. 중복 담기 → 수량 합산
3. 품절 담기 → 에러, 변경 없음
4. 50개 초과 → 에러, 안내 메시지
5. 비로그인→로그인 → 머지 + 재고·행사 재검사

[⑨ 의존 도메인]
Upstream: Catalog(재고), Promotion(행사가)
Downstream: Order(주문서)
이벤트: 없음

[⑩ 데이터 불변식]
• quantity >= 1
• member_id + sku_id UNIQUE
• soft_delete 적용
• 상태전이: 없음
```

## 7. 작성 체크리스트

### 기본 섹션 (필수)
- [ ] 요구사항 ID·분류·우선순위 기재
- [ ] 설명이 비개발자도 이해 가능한 수준인가
- [ ] 수용 기준(AC)이 검증 가능한 형태인가
- [ ] 관련 화면·업무흐름 참조가 있는가

### AI 코딩 보강 (조건부)
- [ ] 복합 비즈니스 로직이면 → ⑦ HARD Constraint 작성했는가
- [ ] HARD마다 wrong_pattern을 기술했는가
- [ ] 도메인 간 연동이면 → ⑨ 의존 도메인 명시했는가
- [ ] 상태 전이가 있으면 → ⑩ 허용 전이 나열했는가
- [ ] ⑧ 검증 시나리오에 실패 케이스가 포함되어 있는가

## 8. 기존 요구사항 정의서 vs AI 보강 요구사항 정의서

| 항목 | 기존 방법론 | AI 보강 |
|------|-----------|---------|
| 대상 독자 | 현업·PMO·QA | + AI 에이전트 |
| 구조 | 동일 | 동일 (⑦~⑩ 부록 추가) |
| AC 상세도 | "~한다" 수준 | 동일 (상세는 ⑧로 분리) |
| 비즈니스 규칙 | 설명에 포함 | HARD/SOFT 분리 + wrong_pattern |
| 검증 방법 | QA가 TC 별도 작성 | ⑧ G-W-T가 TC 초안 역할 |
| 설계 정보 | 포함 안 함 | 포함 안 함 (API 정의서에 위임) |
| 유지보수 | 요구사항만 관리 | + HARD 변경 시 AI 재구현 트리거 |
