# ① 요구사항 정의서 — Harness 표준양식

- **매핑 Harness**: Domain Constraint Harness, Feedback Loop Harness
- **원천 작성 항목**: HARD Constraint (wrong_pattern 포함), 검증 시나리오
- **AI-H**: AI-H1 (HARD Constraint), AI-H2 (검증 시나리오)

---

```

  SOFT 규칙(권고·정책)은 ② 정책서 [AI-H3]에서 rule_expression으로 작성한다.

## 작성 기준

| 항목 | 기준 |
|------|------|
| HARD 기준 | AC 중 위반 시 시스템 오류·데이터 오염이 되는 것 |
| SOFT 기준 | 정책서에서 원천 작성, 여기서는 참조만 |
| wrong_pattern | AI(LLM)이 학습 편향으로 흔히 저지르는 구현 실수 |
| 검증 시나리오 | AC보다 구체적·실행 가능하게 (테스트 코드 생성 기준) |
| 작성 생략 가능 | 단순 CRUD이고 비즈니스 규칙이 없는 경우 |
| 출처 | 요구사항이 처음 등장한 문서·사건 (RFP / 인터뷰-Q번호 / 내부기획 / 법규·컴플라이언스) |
| 도출방식 | 명시적요청: 클라이언트가 직접 기술 / AI역추론: 인터뷰 답변에서 논리적 도출 / 기술파생: 아키텍처·설계 필요성에서 도출 |

  └─ API:  {DOM}-{SEQ}              (⑧ API정의서에서 최종 종합)
```
