# 화면 구조 재사용 지침

Commerce Admin UI에서 화면 구조를 재사용할 때 지켜야 할 기준과 패턴입니다.
이 문서는 `admin`의 메인 화면, 현황 화면, 상세 화면 구조를 통일하고, 중복 구현을 줄이며 개발의 일관성 유지를 위해 작성되었습니다.

---

## 1. 목적

- 화면 구조 재사용을 통해 일관된 UX를 유지합니다.
- 새 화면 개발 시 기존 레이아웃과 컴포넌트 패턴을 우선 활용합니다.
- 화면 타입별 역할과 공통 구성 요소를 명확히 정의합니다.

## 2. 화면 유형과 재사용 기준

### 2.1 메인 화면

- 역할: 첫 번째 고정(pinned) 탭으로 항상 존재하는 대시보드. 닫기 불가.
- 재사용 대상: KPI, 운영 현황, 요약 카드 중심 화면.
- 핵심 패턴:
  - `.dashboard` 최외곽 컨테이너
  - `.dashboard__head`, `.dashboard__grid`, `.dash-card`
  - 요약 카드, 지표, 상태 뱃지 구조
- 재사용 방식:
  - 새로운 대시보드는 기존 `dashboard` 구조를 그대로 가져온 후 카드 구성만 교체.
  - 동일한 카드 UI가 필요하면 공통 `MetricCard`, `SummaryCard` 컴포넌트를 분리.

### 2.2 현황 화면 (기본 목록형)

- 역할: 목록 조회, 필터링, 페이징 중심의 데이터 조회 화면.
- 재사용 대상: 주문 목록, 상품 목록, 이벤트 목록 등.
- 핵심 패턴:
  - `.page`, `.page-title`, `.filter-bar`, `.table-wrap`
  - `.pgm-toolbar`, `.summary-bar`, `.pagination`

#### 기본 목록 화면 구성 규칙

| 순서 | 영역 | CSS 클래스 | 노출 조건 |
|------|------|-----------|---------|
| 1 | 타이틀 | `.page-title-row` | 항상 |
| 2 | 필터 바 | `.filter-bar` | 항상 (검색 + 필터 + 조회 버튼) |
| 3 | 요약 카드 | `.summary-bar` | **조회 후** 노출 |
| 4 | 툴바 (등록 버튼) | `.pgm-toolbar` | **조회 후** 노출 |
| 5 | 데이터 테이블 | `.table-wrap` | **조회 후** 노출 (미조회 시 안내 메시지) |
| 6 | 페이지네이션 | `.pagination` | **조회 후** 노출 |

#### 진입 시 동작

```
화면 진입
  → 타이틀 + 필터 바만 표시
  → "조회 버튼을 눌러 목록을 불러오세요" 안내 메시지
  → [조회] 클릭 시:
      요약 카드 + 등록 버튼 + 테이블 + 페이지네이션 동시 노출
```

#### 필터 바 구성 기준

| 요소 | 설명 | 비고 |
|------|------|------|
| 키워드 입력 | 텍스트 검색 (ID, 이름 등) | Enter 키 조회 지원 |
| 상태 드롭다운 | 전체/활성/비활성 등 | 도메인별 상태값 |
| 조회 버튼 | `.btn-search` | 파란색 |

#### 요약 카드 (SummaryBar) 구성

| 카드 | 스타일 | 용도 |
|------|--------|------|
| 전체 N개 | `.summary-card` (기본) | 조회 결과 전체 수 |
| 활성 N개 | `.summary-card--info` (파란 테두리) | 활성 상태 수 |
| 비활성 N개 | `.summary-card--muted` (회색) | 비활성 상태 수 |
| 경고 N개 | `.summary-card--warn` (주황 테두리) | 주의 필요 수 |

#### 테이블 구성 기준

| 항목 | 규칙 |
|------|------|
| 행 클릭 | 상세 모달(detail-modal) 오픈 |
| ID 셀 | `.link-cell` (파란색, 클릭 가능 표시) |
| 금액 셀 | `.amount-cell` (우측 정렬, tabular-nums) |
| 상태 셀 | `.badge` + `data-*` 속성으로 색상 매핑 |
| 색상 셀 | 컬러칩(14×14) inline 표시 |

#### 참조 화면: 섹션종류 관리 (ADM-020-010)

```
타이틀: "섹션종류 관리"
필터: 타입ID/라벨명 검색 + 전체 상태 드롭다운 + 조회
요약: 전체 9개 | 활성 8개 | 비활성 1개
툴바: + 섹션종류 추가
테이블: 순서 | 타입ID | 라벨 | 설명 | 색상 | 활성 | 필드수 | 최종수정
행 클릭 → SectionTypeDetail 모달
```
- 재사용 방식:
  - 필터 행과 테이블 레이아웃은 공통 컴포넌트로 재사용.
  - 도메인 고유의 컬럼만 채우고, 공통 검색/정렬/페이지네이션 로직을 유지.

### 2.3 상세 화면

- 역할: 현황 화면에서 행 클릭 시 오버레이로 여는 단건 상세/편집 모달.
- 재사용 대상: 주문 상세, 상품 상세, 작업 상세, 등록/수정 화면 등.
- **규칙: admin/partner의 모든 상세·등록·수정 화면은 모달(detail-modal)로 구현한다. 탭으로 열지 않는다.**
- **모달 내부 기본 구조: InnerTabs (탭 방식). 명시적으로 단계별(step) UI를 요청한 경우에만 stepper 사용.**
- 핵심 패턴:
  - `.detail-modal-overlay`, `.detail-modal`, `.detail-modal__header`
  - `InnerTabs`, `.tab-panel-content`
  - `.detail-section`, `.info-grid`, `.add-form`
- 재사용 방식:
  - 기본 모달 프레임과 탭 구조는 그대로 유지.
  - 탭 콘텐츠만 도메인에 맞게 추가.

#### 상세 모달 구성 규칙

| 순서 | 영역 | 설명 |
|------|------|------|
| 1 | 헤더 | 타이틀(`{화면명} ? - {데이터명}`) + 부가정보(코드, 배지, 칩) + 닫기(✕) |
| 2 | 본문 | InnerTabs (탭별 content) |
| 3 | — | Footer 없음 (저장은 각 탭 내부에서 처리) |

#### 탭 내부 규칙

| 탭 유형 | 구조 | 동작 |
|---------|------|------|
| 기본정보 탭 | 읽기(info-grid) ↔ 편집(add-form) | 편집 버튼 → 폼 전환, 저장/취소로 복귀 |
| CRUD 탭 | 테이블 + 추가/편집/삭제/순서변경 | 로컬 state 관리, AddModal로 추가/편집 |

#### overlay 클릭 동작

| 모달 레벨 | overlay 클릭 |
|-----------|-------------|
| 상세/등록 모달 (최상위) | 닫기 허용 |
| 서브 모달 (AddFieldModal 등) | 닫기 차단 (데이터 유실 방지) |

### 2.4 등록 모달

- 역할: 새 데이터를 생성하는 입력 모달.
- **규칙: 상세화면의 편집 모드와 동일한 구조(InnerTabs)로 구성한다.**
- 핵심 패턴:
  - 상세 모달과 동일한 `.detail-modal` 프레임
  - InnerTabs (기본정보 + 하위 CRUD 탭)
  - 모달 하단 공통 Footer (취소 + 저장)

#### 등록 모달 구성 규칙

| 순서 | 영역 | 설명 |
|------|------|------|
| 1 | 헤더 | 타이틀(`{화면명} ?`) + 부가 설명 + 닫기(✕) |
| 2 | 본문 | InnerTabs (상세 편집모드와 동일 구조) |
| 3 | Footer | 취소 + 저장 버튼 |

#### 상세와 등록의 차이

| 항목 | 상세 (편집) | 등록 |
|------|-------------|------|
| ID 필드 | disabled | 입력 가능 |
| 초기값 | 기존 데이터 | 빈값/기본값 |
| 저장 위치 | 탭 내부 | 모달 하단 Footer |
| 유효성 | 수정된 필드만 | 필수 필드 전체 |

### 2.5 서브 모달

- 역할: 상세/등록 모달 내부에서 추가 입력을 받는 소형 모달.
- **규칙: overlay 클릭 시 닫히지 않는다. ✕ 또는 취소 버튼으로만 닫기.**
- 핵심 패턴:
  - `.modal-overlay` + `.modal` (detail-modal보다 작은 크기)
  - 추가/편집 모드 구분 (initialData prop)
  - onSave 콜백으로 부모 state 업데이트

#### 서브 모달 구성 규칙

| 순서 | 영역 | 설명 |
|------|------|------|
| 1 | 헤더 | 타이틀(`{추가/편집} ?`) + 닫기(✕) |
| 2 | 본문 | add-form (2열 구성) |
| 3 | Footer | 취소 + 저장/수정 |

#### 데이터 관리 원칙

- 서브 모달의 저장 결과는 부모 모달의 로컬 state에 즉시 반영
- 개별 추가/편집마다 API 호출하지 않음
- 부모 모달의 최종 저장 시 전체 데이터를 API로 일괄 전송

## 3. 공통 레이아웃 재사용 원칙

### 3.1 공통 컴포넌트 우선 사용

- `src/shell/shared/`에 공통 레이아웃 컴포넌트가 존재하면 반드시 우선 사용합니다.
- 공통 컴포넌트 예:
  - `Pagination`
  - `InnerTabs`
- 새 화면을 만들 때는 기존 컴포넌트를 복제하지 말고, 필요한 경우 props로 확장합니다.

### 3.2 CSS 클래스 재사용

- 공통 의미를 가진 UI는 동일한 CSS 클래스 이름을 사용해 스타일을 공유합니다.
- 비슷한 역할의 클래스도 새로운 이름 대신 기존 클래스를 확장하여 정의합니다.
- 예시:
  - 목록 화면: `.page`, `.filter-bar`, `.table-wrap`, `.link-cell`, `.amount-cell`
  - 상세 화면: `.detail-modal`, `.inner-tabs__bar`, `.tab-panel-content`
  - 대시보드: `.dashboard__grid`, `.dash-card`, `.dash-metric`

### 3.3 레이아웃만 재사용

- 기능이 다른 화면이라면 레이아웃만 재사용하고 데이터/비즈니스 로직은 분리합니다.
- 화면 유형이 동일할 때만 상태 관리 패턴과 이벤트 흐름까지 재사용합니다.

## 4. 파일/폴더 구조 기준

새 화면을 추가할 때는 다음 구조를 따릅니다.

```
{domain}/{ScreenName}/
  {ScreenName}Page.tsx              ← 목록 화면
  {ScreenName}Page.spec.md          ← 목록 화면 정의서 (? 버튼으로 모달 표시)
  {ScreenName}Detail.tsx            ← 상세 모달
  {ScreenName}Detail.spec.md        ← 상세 화면 정의서
  Add{ScreenName}Modal.tsx          ← 등록 모달
  Add{ScreenName}Modal.spec.md      ← 등록 화면 정의서
  mockData.ts                       ← Mock 데이터
  tabs/                             ← 탭 컴포넌트 (InnerTabs 사용 시)
    BasicInfoTab.tsx                ← 기본정보 탭
    BasicInfoTab.spec.md            ← 기본정보 탭 정의서
    FieldsTab.tsx                   ← 필드관리 등 탭
    FieldsTab.spec.md               ← 필드관리 탭 정의서
    AddFieldModal.tsx               ← 서브 모달
    AddFieldModal.spec.md           ← 서브 모달 정의서
```

### 스펙 확인 (? 버튼) 규칙

- 모든 화면/탭 타이틀 옆에 `?` 원형 버튼 표시 (18×18, #e2e8f0, bold)
- 목록/상세/등록 타이틀: 페이지 타이틀 옆
- InnerTabs: 탭 버튼 텍스트 옆
- 클릭 시: `/api/spec?file={src 기준 상대경로}` → SpecModal에서 .spec.md 내용 표시
- .spec.md 파일은 소스와 같은 폴더에 위치 (별도 .ts 래퍼 불필요)

### 화면ID 네이밍 규칙

| 화면 유형 | ID 패턴 | 예시 |
|---------|---------|------|
| 목록 | `ADM-{그룹}-{순번}` | ADM-020-010 |
| 상세 | `ADM-{그룹}-{순번}-DETAIL` | ADM-020-010-DETAIL |
| 등록 | `ADM-{그룹}-{순번}-ADD` | ADM-020-010-ADD |

## 5. 개발 시 재사용 체크리스트

### 5.1 화면 시작 전

- [ ] 이 화면이 `메인`, `현황`, `상세` 중 어느 유형인지 분류했는가?
- [ ] 기존 화면 중 유사한 구조가 있는지 확인했는가?
- [ ] 공통 컴포넌트(`Pagination`, `InnerTabs`, `FilterBar`)를 재사용할 수 있는가?
- [ ] 새로운 스타일 클래스 대신 기존 클래스를 활용할 수 있는가?

### 5.2 레이아웃 구현 중

- [ ] 최상위 wrapper에 유형별 기본 클래스(`.dashboard`, `.page`, `.detail-modal`)를 적용했는가?
- [ ] 목록 화면의 경우 `filter-bar`, `table-wrap`, `pagination`을 기본 구조로 사용했는가?
- [ ] 상세 화면의 경우 `tab-panel-content`를 모든 탭 콘텐츠 최외곽에 넣었는가?
- [ ] 모달은 오버레이 + 중앙 정렬 구조로 구현했는가?

### 5.3 코드 재사용

- [ ] 동일한 카드/행/리스트 레이아웃을 새로 만들지 않고 기존 컴포넌트를 확장했는가?
- [ ] 레이아웃 관련 UI는 props 전달로 분리하여 재사용성을 높였는가?
- [ ] 상태 관리(`loading`, `page`, `filters`)는 화면별로 유지하되, 공통 패턴을 따랐는가?

## 6. 재사용 예시

### 6.1 현황 화면 재사용 예

- `FilterBar`를 그대로 두고, `columns`와 `actions`만 도메인에 맞게 교체.
- `SummaryBar`는 도메인별 상태 카드만 교체하고, 레이아웃은 유지.
- `Table`은 공통 `.table-wrap` 안에 들어가며, `link-cell`/`amount-cell` 클래스를 재사용.

### 6.2 상세 화면 재사용 예

- `InnerTabs`는 공통 탭 구조로 사용한다.
- 탭 콘텐츠 내부는 반드시 `.tab-panel-content`로 감싼다.
- 편집 모드는 기존 `editing` 상태 패턴을 따라 `읽기전용 ⇄ 편집`으로 구현.

## 7. 유지보수 팁

- 새로 추가한 화면이 공통 패턴과 다른 경우, 먼저 왜 다른지 문서화합니다.
- 공통 구조가 여러 화면에서 반복되면 `src/shared/`로 추출합니다.
- 화면 작성 문서는 이 파일과 함께 최신 상태로 유지합니다.
- 스타일 가이드는 각 앱의 `/guide` 페이지에서 실행 가능한 형태로 확인합니다.
  - Admin: http://localhost:3001/guide
  - Partner: http://localhost:3002/guide

이 문서는 `admin` 화면을 일관되게 만들고, 새 화면 개발 시 기존 구조를 보다 쉽게 재사용하는 데 목적이 있습니다.
