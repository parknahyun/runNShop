# 화면정의서 — 도메인별 와이어프레임 보완 인덱스

## 배경

`runNshop_screen_definition_v1_0.md` → `v1_1.md`로 전환하는 과정에서 각 화면의 **와이어프레임(ASCII)이 삭제**되었다(v1.1은 메뉴 트리·API 목록·정책표 중심으로 축약됨). 이 작업은 `apps/` 폴더의 실제 구현 소스(admin/partner/mobile)를 대조해 삭제된 와이어프레임과 상세 화면 설명을 12개 업무도메인별 문서로 복원한 결과물이다.

- **표준안 참조**: `docs/참고자료/화면정의서_샘플/화면정의서_작성_표준안.md`(메타정보 + 영역(R)·속성(P)·기능(F)·UI상태(S) 4요소 방식)
- **원본 문서**: `runNshop_screen_definition_v1_0.md`(와이어프레임 있음, 참고용), `runNshop_screen_definition_v1_1.md`(현재 메뉴트리·API 기준, 이 작업의 1차 근거), `runNshop_admin_screen_guide_v1_0.md`
- **작성 원칙**:
  1. `docs_archive` 폴더는 원래 "참조용, 수정하지 않음" 규칙이 있으나 이 작업에 대해서는 사용자가 예외를 승인해 신규 파일 추가를 진행했다(기존 원본 파일 3개는 수정하지 않고 그대로 보존).
  2. `apps/` 소스가 있는 화면은 소스(코드·자체 `*.spec.md`)를 근거로 작성. 소스가 없는 화면은 원본 화면정의서의 URL·API·정책을 근거로 B2C 커머스 일반기능 수준에서 재구성(문서 내 "일반기능 기준"으로 표기).
  3. 화면별로 와이어프레임(ASCII)과 상세 디스크립션(메타정보/구성요소/기능/상태/Human Review)을 하나의 md 파일 안에 통합.
  4. 12개 업무도메인(order/catalog/member/payment/promotion/settlement/vendor/notification/community/search/config/audit 워크스페이스 규칙 기준, 본 작업에서는 config→platform으로 명명)별로 파일을 분리.
- **작성일**: 2026-08-26 · **버전**: 각 파일 v1.0(초판)

## 도메인 경계 결정 사항 (문서 간 참조 시 주의)

작업 과정에서 원본 메뉴 트리의 챕터 구분과 12개 업무도메인 분류가 정확히 1:1로 대응하지 않는 지점이 여러 곳 있었다. 아래는 화면이 "왜 이 문서에 있는지"를 확인할 때 참고할 경계 결정 목록이다.

| 화면/기능 | 원본 소속처럼 보이는 곳 | 실제 배치한 문서 | 이유 |
|---|---|---|---|
| 기획전(Exhibition, CUS-020/021, ADM-030-001) | Promotion(프로모션 관리 챕터) | `02-Catalog.md` | 전시(진열) 성격이 강해 Catalog로 분류 |
| 쿠폰함(CUS-058, 고객이 보유 쿠폰을 보는 화면) | Promotion | `03-Member.md` | 마이페이지 하위 화면이라 수신자 관점으로 분류. 쿠폰 발급/관리(admin·partner)는 `05-Promotion.md` |
| 알림 설정 — 고객(CUS-066) | Notification | `03-Member.md` | 수신자 관점 |
| 알림 설정 — 입점사(VND-080-003) | Notification 또는 Vendor | `11-Platform.md` | 계정 설정 묶음(계정관리·배송설정과 함께)으로 통일 |
| 알림 템플릿(ADM-090-005) | 운영 설정(§3.3) | `08-Notification.md` | 발송자 관점의 콘텐츠 관리라 Notification 도메인 자체로 독립 |
| 입점사 로그인·2FA·계정관리(VND-000-*, VND-080-*) | Vendor(입점사 관리) | `11-Platform.md` | admin이 입점사를 "관리"하는 관점(07-Vendor.md)과 입점사 "자신"의 인증·계정 관점을 분리. 다른 채널(admin) 인증 체계와 통일 목적 |
| 리뷰 관리(고객 "내가 쓴 리뷰", CUS-060) | Community | `03-Member.md` | 수신자/작성자 본인 관점 |
| 리뷰 관리(admin, ADM-080-001) / QnA(ADM-080-002) | Community | `09-Community.md` | 운영 관점 |
| 배치 관리(ADM-100-001) / Outbox·DLQ(ADM-100-002) | 시스템 관리(§3.3, Audit과 같은 챕터) | `11-Platform.md` | 조치(등록/재시도/무시) 기능이 있는 **인프라 운영** 화면이라 조회 전용 로그 화면(Audit)과 분리 |
| 감사 로그(ADM-100-003) / 개인정보 접근이력(ADM-090-010) | 시스템 관리·운영 설정(서로 다른 챕터) | `12-Audit.md` | 둘 다 등록/수정/삭제 없는 **조회 전용** 화면이라는 공통점으로 하나의 도메인으로 통합 |
| 결제(Payment) | 원본에 독립 챕터 없음 | `04-Payment.md` | 소스 조사 결과 독립 화면이 없음을 확인 — 다른 화면(주문서·주문상세·공통코드)에서 발췌하는 보완 문서로 작성 |

## 소스 상태 표기 범례

각 문서의 목차 표에서 사용하는 "소스 상태" 값의 의미:

| 표기 | 의미 |
|---|---|
| 소스 있음 | `apps/` 하위에 해당 화면의 실제 구현 컴포넌트가 존재하고, 이를 열람해 와이어프레임·기능을 작성 |
| 소스 있음(spec.md) | 구현 컴포넌트뿐 아니라 화면 자체의 UI 정의 문서(`*.spec.md`)가 이미 존재해 그 내용을 그대로 인용 |
| 소스 없음(일반기능 기준) | `apps/`에 해당 라우트·컴포넌트가 없음. 원본 화면정의서의 URL·API·정책을 근거로 B2C 커머스 일반기능 수준에서 추정 재구성 |
| 소스 있음 — 명시적 미구현 | 소스 코드 자체에 "아직 구현되지 않았습니다" 등의 placeholder 텍스트가 있어, 미구현임이 코드로 직접 증명되는 경우(예: `10-Search.md`의 CUS-030, `09-Community.md`의 CUS-070/071) |

## 공통적으로 반복 확인된 Human Review 패턴

12개 문서에 걸쳐 개별적으로 기록했지만 여러 도메인에서 동일하게 나타난 결함·이슈는 다음과 같다. 실 서비스 전환 시 공통 컴포넌트/정책 차원에서 한 번에 해결하는 것을 권장한다.

- **삭제 확인 팝업 부재**: admin 설정류 CRUD 화면(배너·공지·금지어·알림템플릿 등, `08-Notification.md`·`11-Platform.md`)에서 공통적으로 확인 팝업 없이 즉시 삭제된다.
- **admin/partner 데이터 모델 불일치**: 동일 기능이라도 admin과 partner 쪽 mock 데이터 모델(필드 구성, 상태값 enum)이 서로 다르게 설계된 경우가 다수 발견됐다(`05-Promotion.md`의 쿠폰, `06-Settlement.md`의 정산 요약, `07-Vendor.md`의 배송사 데이터 등).
- **소스 없는 mobile 화면의 존재**: 고객(mobile) 채널의 상당수 화면(회원가입, 로그인, 배송지 관리, 취소/반품/교환 신청 등)이 실제 라우트로 구현되어 있지 않아 원본 정책 기준으로만 작성했다. 프로토타입의 우선순위가 admin/partner 운영 화면에 맞춰져 있었던 것으로 추정된다.
- **partner 앱 로그인 게이트 부재**: `11-Platform.md`에서 확인된 대로 partner 앱은 로그인 화면 컴포넌트 자체가 없고 세션 체크 없이 바로 앱 셸이 렌더링된다(admin은 완비).

각 항목의 상세 내용과 근거는 해당 도메인 문서의 "종합 Human Review 목록" 절을 참조한다.
