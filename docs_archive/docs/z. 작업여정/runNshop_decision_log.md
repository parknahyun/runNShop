## 2026-06-30

### UI 용어 변경: "활성 여부" → "상태"
- **이유**: "활성 여부"는 boolean 느낌이 강해 확장성이 부족. "상태"로 통일하면 향후 상태값 추가(심사중, 대기 등)에 유연
- **적용**: 목록 컬럼 헤더, 상세/등록 모달 폼 라벨

### UI 용어 변경: "필수 여부" → "입력조건"
- **이유**: "필수/선택" 외에 "조건부 필수" 등 확장 가능성. "입력조건"이 더 포괄적
- **적용**: 필드관리 테이블 헤더, 필드 추가/편집 모달

### spec.ts 래퍼 제거 → API Route 방식으로 전환
- **이유**: .spec.md와 .spec.ts 이중관리 문제. Next.js Turbopack에서 .md import 불가했으나, API Route로 fs.readFile하면 .md 하나로 해결
- **적용**: `/api/spec?file={path}` → SpecModal에서 fetch

### 서브 모달 overlay 클릭 시 닫기 차단
- **이유**: 필드 추가/편집 중 데이터 유실 방지. 상위 모달(상세/등록)은 닫기 허용
- **적용**: AddFieldModal의 overlay onClick에 stopPropagation

### 등록 모달 = 상세 편집모드와 동일 구조
- **이유**: 별도 UI 학습 비용 제거. InnerTabs(기본정보+필드관리)로 통일
- **적용**: AddSectionTypeModal

### 스펙 버튼 통일: 타이틀 옆 "?" 원형 버튼
- **이유**: "스펙" 텍스트 버튼은 공간 차지 + 위치 비일관. "?" 18×18 원형으로 통일하면 어디든 일관적
- **적용**: 모든 화면/탭 타이틀, InnerTabs 탭 버튼 텍스트 옆

### 필드 추가/수정 데이터는 화면(로컬 state)에서 관리
- **이유**: 개별 필드 변경마다 API 호출하면 UX 저하. 최종 저장 시 일괄 전송이 효율적
- **적용**: FieldsTab, AddSectionTypeModal 내 FieldsForm

### GuidePage 탭별 파일 분리
- **이유**: 단일 파일 600줄 이상 → 유지보수 어려움. 탭별 독립 수정 가능
- **적용**: `src/guide/tabs/` 하위 5개 파일

### 코드성 속성 입력방식 규칙
- **이유**: 코드 수에 따라 적합한 UI가 다름. 적은 수는 한눈에 보이는 라디오/체크, 많은 수는 스크롤 가능한 셀렉트
- **규칙**: 코드 4개 미만 → 라디오(단일선택) 또는 체크박스(다중선택) / 코드 4개 이상 → select 드롭다운
- **적용 예**: 상태(3개: 활성/비활성/폐기) → 라디오, 템플릿유형(6개) → select
- **(steering 반영 필요)**

### 메뉴명 변경: "전시 템플릿" → "페이지 템플릿"
- **이유**: 템플릿은 전시 페이지뿐 아니라 다양한 페이지에 적용 가능. "페이지 템플릿"이 범용적
- **적용**: AppShell 메뉴, TemplatePage 타이틀, 화면정의서

### 페이지 템플릿에 유형(templateType) + 상태(status) 속성 추가
- **이유**: 메인/기획전메인/카테고리/기획전/이벤트메인/이벤트 등 페이지 용도별 분류 필요. 상태는 활성/비활성 외에 "폐기" 추가로 라이프사이클 관리
- **유형**: HOME, EXHIBITION_MAIN, CATEGORY, EXHIBITION, EVENT_MAIN, EVENT
- **상태**: ACTIVE(활성), INACTIVE(비활성), DEPRECATED(폐기)
- **적용**: mockData, FilterBar(유형+상태 드롭다운), 테이블 컬럼 추가

### 페이지의 게시예정일은 필수값
- **이유**: 모든 페이지는 게시일정이 있어야 운영 계획 수립 가능. 미게시 상태라도 예정일 필수
- **적용**: 페이지 목록의 게시일시 컬럼에 항상 값 표시 (게시중: 실제일시, 예약/미게시: 예정일 + "(예정)" 표기)

### 페이지 템플릿 미리보기 탭 — 검토중 (숨김)
- **배경**: 영역 배치 순서를 시각적으로 보여주는 탭. 프론트 wireframe UI 기준으로 적용 방향 검토중
- **현재 상태**: PreviewTab 코드는 존재하나 InnerTabs에서 제외 (숨김)
- **향후**: 고객웹 wireframe 확정 시 반영 여부 결정

### 적용 페이지 있으면 템플릿 정보/영역 수정 불가
- **이유**: 게시중인 페이지에 영향을 주는 변경을 방지. 운영 안정성 확보
- **조건**: `usedPageCount > 0 && status === 'ACTIVE'`
- **적용**: 기본정보 편집 버튼 disabled + 영역목록 추가/편집/삭제/순서변경 버튼 disabled + 안내 메시지 표시

### "전시 페이지" → "페이지 관리"로 명칭 변경
- **이유**: "전시 페이지"가 기획전/이벤트/카테고리/메인을 통칭하는데 "기획전"(ADM-030-001)과 혼동 발생. "페이지 관리"로 심플하게 변경하고, 유형(메인/기획전/이벤트/카테고리)은 필터로 구분
- **적용**: AppShell 메뉴, EventPage 타이틀, 상세 모달 타이틀

### 전시 도메인 4단계 계층 구조 확정
- **구조**:
  1. **필드 정의** → 섹션종류의 필드 (입력 항목 단위, 예: imageUrl, link, altText)
  2. **섹션 정의** → 섹션종류 관리 (필드 조합 = 영역 타입, 예: BANNER = 4개 필드)
  3. **템플릿 정의** → 페이지 템플릿 관리 (섹션 조합 = 레이아웃, 예: 배너+상품그리드+텍스트)
  4. **페이지 생성** → 페이지 관리 (템플릿 선택 + 영역별 데이터 입력/맵핑)
- **페이지 관리 핵심**: 템플릿을 복사해서 영역 수정 가능 + 각 영역의 필드에 실제 데이터 입력
- **적용**: 페이지 상세에 "데이터 맵핑" 탭 추가

### 기획전 = 정형이벤트, 이벤트 = 비정형이벤트 (용어 확정)
- **기획전**: 정형 이벤트. 템플릿 기반, 반복/정기, 고객 참여 없음 → 페이지 관리(4단계)에서 처리
- **이벤트**: 비정형 이벤트. 커스텀 레이아웃, 단발/비정기, 고객 참여(응모/출석/미션 등) → 추후 정의
- **페이지 유형에서 EVENT 제거**: 현재는 HOME / CATEGORY / EXHIBITION만 사용
- **적용**: mockData, 필터 옵션, 템플릿 유형에서 EVENT_MAIN/EVENT는 추후 정의 시 추가

### 프로모션 > 기획전 메뉴 삭제
- **이유**: 기획전은 페이지 관리(유형=EXHIBITION)에서 처리. 별도 메뉴 불필요, 중복 제거
- **적용**: AppShell에서 promotion/exhibition 메뉴 항목 삭제, ExhibitionPage import 제거
