# runNshop 프로젝트 관리 방법론

> 작성 주체: 3TOP 2본부  
> 문서 버전: v1.0  
> 작성일: 2026.06.25  
> 목적: 계약 완료 후 오픈까지 프로젝트 병렬 진행 체계 정의

## 문서 목적

회사(3TOP)의 프로젝트 수행 경험과 자산을 체계화하여, 신규 프로젝트 착수 시 즉시 적용 가능한 **프로젝트 관리 방법론**을 정의합니다.

### 적용 방법론

| 영역 | 적용 방법론 | 회사 경험·자산 적용 |
|------|-----------|-----------------|
| 개발 방법론 | AI-DLC (AI 기반 소프트웨어 개발 생명주기) | Claude·Kiro를 활용한 설계→코드 생성 체인, Spec 기반 개발 프로세스 |
| 프로젝트 관리 | 병렬 트랙 기반 Agile (Sprint 단위) | 업무 유형(A·B·C·D) 분류 체계, 6개 트랙 동시 진행 경험 |
| 품질 관리 | CI/CD 게이트 + PBT (Property-Based Testing) | Harness 파이프라인, 배포 게이트 자동화 |
| 인프라 | Docker → Kubernetes 단계 전환 | Modular Monolith → MSA 점진 전환 경험 |
| 문서 관리 | Spec-Driven + Steering 기반 | docs 폴더 구조, steering 파일 체계, scaffolding 가이드 |

## 대상 독자

- PM/PL: 프로젝트 계획·트랙 운영 시 참조
- 개발업체: 업무 유형별 역할·권한·진행 방법 확인
- 고객사: 협의 필요 사항·의사결정 기준 확인

## 적용 방법

1. **업무 유형 분류(A·B·C·D)** → 모든 업무를 4유형으로 분류하여 주도 주체·의사결정 방식 확정
2. **병렬 트랙 구성** → 6개 트랙 동시 진행. 트랙 간 의존성은 최소화
3. **유형별 수행 여정** → 각 유형에 맞는 프로세스(단독결정/협의/통보)로 진행
4. **타 프로젝트 적용** → 프로젝트명·기간·도메인만 교체하면 동일 체계 재사용

## 1. 프로젝트 진행 유형 정의

커머스 프로젝트 업무는 4가지 진행 유형으로 나뉜다.

| 유형 | 의사결정자 | 개발업체 역할 | 대표 업무 |
|------|----------|-------------|---------|
| **A. 표준** | 개발업체 결정 | 결정 사항 + 적절성 근거 안내. 설정 기능을 제공하여 의사결정이 즉시 반영되도록 구현 | 시스템 공통·인프라·코딩 표준·운영 설정 |
| **B. 협의** | 고객사 + 개발업체 공동 | 방안 A/B/C 제시 + 협의 주도 | 클레임 귀책·정산 주기·행사 정책 |
| **C. 개발주도** | 현업 결정 | 의사결정 요소 + 근거자료(기술스택·프로세스) 제시 | 성능·주문결제·아키텍처 |
| **D. 현업주도** | 현업 결정·실행 | 도구 제공 + 오류 지원만 | 상품 등록·카테고리·전시 기획 |

> **A vs C**: A는 개발업체가 직접 결정하고 안내. C는 현업이 결정하되 개발업체가 근거자료를 준비해서 의사결정을 리드.
> **C vs D**: C는 기술적 판단이 필요해서 개발업체가 리드. D는 내용·데이터를 현업이 직접 결정·실행하며 개발업체는 도구만 제공.

### 진행 유형별 업무 도메인 분류

| 도메인 | 주 유형 | 보조 유형 | 근거 |
|--------|---------|---------|------|
| Order | C. 개발주도 | B. 협의 | 재고 선점·보상 처리는 기술 판단(C), 클레임 귀책 기준은 협의(B) |
| Catalog | D. 현업주도 | A. 표준 | 상품 등록·카테고리는 현업(D), 재고-상태 연동은 표준(A) |
| Member | B. 협의 | A. 표준 | 등급 기준·혜택·포인트 적립률은 협의(B), 가입·로그인·세션은 표준(A) |
| Payment | C. 개발주도 | | PG 연동·결제 보상·FDS는 기술 판단(C) |
| Promotion | B. 협의 | D. 현업주도 | 쿠폰·할인 정책은 협의(B), 기획전 설정·실행은 현업(D) |
| Settlement | B. 협의 | A. 표준 | 수수료율·정산 주기는 협의(B), 배치 계산·지급은 표준(A) |
| Vendor | B. 협의 | A. 표준 | 계약 조건·퇴점 기준은 협의(B), 심사 프로세스는 표준(A) |
| Notification | A. 표준 | | 채널·템플릿·발송 규칙은 설정 제공(A) |
| Community | A. 표준 | | 리뷰·QnA 기본 기능은 표준(A) |
| Search | C. 개발주도 | D. 현업주도 | ES 인덱스·정렬은 기술(C), 인기검색어·MD추천은 현업(D) |
| Config | A. 표준 | | 권한·코드·공지·약관은 설정 제공(A) |
| Audit | A. 표준 | | 로그·Trace·감사는 표준(A) |

### 표준(A유형) 도메인 의사결정 요소

개발업체가 결정하고, 설정 기능을 제공하여 즉시 반영되도록 하는 항목.

#### Notification (알림)

| 의사결정 요소 | 결정 내용 | 설정 반영 |
|-------------|---------|---------|
| 채널 우선순위 | 알림톡 → SMS → 이메일 (Fallback 구조) | 어드민 설정으로 변경 가능 |
| 야간 차단 시간 | 22시~08시 마케팅 알림 차단 | 어드민 설정 |
| 재시도 정책 | 최대 3회, 즉시→30초→1분 | 시스템 설정 |
| 취합 배치 시각 | 09:00 / 13:00 / 18:00 | 배치 스케줄 설정 |
| 긴급 즉시 발송 조건 | 판매금지·출고기한초과·중재결정 | 코드 레벨 정의 |
| 수신거부 구분 | 거래(필수) vs 마케팅(거부 가능) | 유형별 자동 분류 |

#### Community (커뮤니티)

| 의사결정 요소 | 결정 내용 | 설정 반영 |
|-------------|---------|---------|
| 리뷰 작성 조건 | 구매확정 후 가능 | 시스템 로직 |
| 금지어 처리 | BLOCK(차단) / MASK(마스킹) | 어드민 금지어 관리 |
| 이미지 제한 | 최대 3장, 1MB, JPG/PNG/WEBP | 시스템 설정 |
| 활동지수 산정 | 리뷰+2, 러닝기록+1, 크루+1, 챌린지+3, QnA채택+2 | 어드민 설정 |
| 리뷰 포인트 | 구매확정 → 리뷰 작성 → 포인트 지급 | 시스템 자동 |

#### Config (운영설정)

| 의사결정 요소 | 결정 내용 | 설정 반영 |
|-------------|---------|---------|
| 운영자 롤 체계 | 슈퍼관리자·MD·CS·정산담당·입점관리 | 어드민 권한 관리 |
| 롤별 메뉴 접근 | 롤×프로그램 매핑 | 어드민 설정 |
| 공통코드 관리 | 그룹·코드·표시명·정렬순서 | 어드민 CRUD |
| 약관 버전 관리 | 유형·버전·시행일·갱신 시 추가동의 | 어드민 설정 |
| 공지사항 관리 | 등록·수정·노출 기간 | 어드민 CRUD |
| 배너 관리 | 위치·이미지·링크·노출기간 | 어드민 CRUD |

#### Audit (감사·로그)

| 의사결정 요소 | 결정 내용 | 설정 반영 |
|-------------|---------|---------|
| 로그 레벨 기준 | 운영:INFO / 스테이징:DEBUG | 프로파일별 설정 |
| 보존 기간 | ERROR·WARN·INFO: 1년 / DEBUG: 30일 | 시스템 정책 |
| Trace ID 형식 | TRC-{YYYYMMDD}-{8자리} | 코드 레벨 |
| 감사 대상 | 주문·결제·재고·가격·상품상태 변경 | 코드 레벨 (자동 수집) |
| 모니터링 임계치 | ERROR 10분 내 2회 → 관리자 알림 | 시스템 설정 |
| 소프트 삭제 기록 | 삭제 대상·PK·시각·주체·TraceID | 자동 기록 |

#### Catalog — 표준 영역 (재고-상태 연동)

| 의사결정 요소 | 결정 내용 | 설정 반영 |
|-------------|---------|---------|
| 재고 0 자동 전환 | 주문 시 재고=0 → SOLD_OUT 자동 | 시스템 로직 |
| 취소 시 자동 복구 | 주문취소 재고+1 → SOLD_OUT→ON_SALE 자동 | 시스템 로직 |
| 반품 시 상태 유지 | 재고+1 하되 SOLD_OUT 유지 (담당자 수동 전환) | 시스템 로직 |
| 상품 상태 전이 규칙 | DRAFT→REVIEW→ON_SALE→SOLD_OUT→DISCONTINUED | 코드 레벨 |
| 전시 페이지 예약 | 페이지당 1개, 배치 5분 주기 자동 전환 | 시스템 설정 |

#### Member — 표준 영역 (가입·로그인·세션)

| 의사결정 요소 | 결정 내용 | 설정 반영 |
|-------------|---------|---------|
| 세션 유지 시간 | 고객 1시간 / 입점사 30분 / 어드민 8시간 | 시스템 설정 |
| 동시 로그인 | 고객: 최대 3디바이스 / 입점사: 단일 | 시스템 설정 |
| 로그인 실패 잠금 | 5회 실패 → 30분 잠금 | 시스템 설정 |
| 비밀번호 정책 | 8자+영문+숫자(+특수문자 BO) | 프론트 검증 |
| JWT 구조 | Access(30분) + Refresh(1시간) + Redis 블랙리스트 | 시스템 설정 |
| 포인트 소멸 | 적립일 3년, 선적립 선소멸(FIFO), 30일 전 안내 | 시스템 로직 + 배치 |

#### Settlement — 표준 영역 (배치 계산·지급)

| 의사결정 요소 | 결정 내용 | 설정 반영 |
|-------------|---------|---------|
| 정산 대상 확정 | 매월 5일 구매확정 기준 자동 집계 | 배치 스케줄 |
| 정산금 지급일 | 매월 15일 (비영업일 시 직전 영업일) | 시스템 설정 |
| 최소 지급 금액 | 10,000원 미만 이월, 3회 연속 시 강제 지급 | 시스템 설정 |
| 재정산 방식 | 익월 차감/가산 | 시스템 로직 |
| 이의제기 기간 | 확정일 + 5영업일 | 시스템 설정 |

#### Vendor — 표준 영역 (심사 프로세스)

| 의사결정 요소 | 결정 내용 | 설정 반영 |
|-------------|---------|---------|
| 심사 SLA | 영업일 7일 이내 | 시스템 모니터링 |
| 재신청 제한 | 거절 후 30일 이후 | 시스템 로직 |
| 등급 산정 주기 | 매월 1일 자동 | 배치 스케줄 |
| 등급 하향 유예 | 1개월 | 시스템 로직 |
| 계좌 인증 | 1원 송금, 3회 실패 시 수동 | 시스템 로직 |
| 계약 만료 알림 | 30일·7일 전 | 배치 + 알림 |

## 2. 병렬 진행 트랙 구조

계약 완료 후 5개 트랙이 동시에 진행된다.

```
계약 완료
    │
    ├─ Track 1: 사업 준비     (고객사 주도)
    ├─ Track 2: 분석·설계     (공동)
    ├─ Track 3: 개발·구현     (개발업체 주도)
    ├─ Track 4: 환경·인프라   (개발업체 주도)
    ├─ Track 5: 표준화·품질   (개발업체 주도)
    └─ Track 6: 현업 준비     (현업 MD 주도)
                │
                ▼
            오픈 (Go-Live)
```

## 3. 트랙별 상세 내용

### Track 1. 사업 준비 (고객사 주도)

**목적**: 서비스 오픈 전 비즈니스 준비 완료

```
[ 협의 업무 (B유형) — 반드시 고객사가 결정 ]

정책 확정
    □ 수수료율 (카테고리별)
    □ 정산 주기·지급일
    □ 반품·교환 귀책 기준
    □ 클레임 처리 SLA (응답 시간)
    □ 행사·이벤트 운영 정책
    □ 회원 등급 혜택 수치 (무료배송·적립률)

입점사 확보
    □ 사전 입점 계약 체결
    □ 입점사 온보딩 일정
    □ 직매입 상품 선정

운영 조직
    □ CS팀 구성
    □ MD 역할 담당자
    □ 정산 담당자
    □ 운영 매뉴얼 작성 (개발업체 지원)
```

### Track 3. 개발·구현 (개발업체 주도)

**목적**: 도메인별 순차·병렬 구현

```
[ 개발 주도 업무 (C유형) — 개발업체 단독 결정 ]

구현 도구
    → Kiro: 코드 생성
    → Claude: 코드 리뷰·설계 검토
    → GitHub: PR·코드 리뷰

구현 순서 (의존성 기준)

Phase 1 (Week 3~5) — 기반
    □ Config·Common (공통·권한·코드)
    □ Vendor 기초 (입점사 계정·인증)
    □ Member 기초 (회원가입·로그인·등급)

Phase 2 (Week 5~8) — 핵심
    □ Catalog (상품·재고·전시)
    □ Order·Payment (주문·결제·재고선점)  ← C유형 집중
    □ Promotion (쿠폰·행사가·수량할인)

Phase 3 (Week 8~11) — 확장
    □ Claim (취소·반품·교환)             ← B유형 협의 후
```

## 5. 유형별 의사결정 프로세스

### A유형 (일반화) — 개발업체 단독 결정

```
결정 → 실행 → 결과 보고
    □ 아키텍처 결정
    □ 기술 스택 선택
    □ 성능 최적화 방법
    □ 인프라 구성

보고 방식: 주간 보고에 완료 사항 포함
```

### B유형 (협의) — 에스컬레이션 프로세스

```
이슈 발생
    ↓
개발업체 1차 분석 + 방안 A/B/C 제시
    ↓
고객사 검토 (기한: 영업일 3일)
    ↓
결정 없으면 에스컬레이션 (PM → 의사결정권자)
    ↓
확정 → 문서화 → 개발 반영

협의 이슈 트래킹
    □ 이슈명·발생일·담당자·결정기한·상태
    □ 미결 이슈 주간 리뷰
    □ 결정 지연 시 개발 일정 영향 즉시 공유
```

### D유형 (현업 주도) — 현업이 결정·실행, 개발은 도구 제공

```
현업(MD)이 결정
    → 카테고리 구성·상품 속성·전시 배치
    → 개발업체 개입 없음

개발업체 역할
    → 등록 도구·어드민 화면 제공
    → 일괄 등록·수정 도구 지원
    → 오류 즉시 대응

주의사항
    → 현업 작업 일정이 오픈 일정에 직접 영향
    → "상품이 없으면 오픈 불가"
    → 현업 준비 지연 = 오픈 지연
    → 초기부터 현업 일정 강제 관리 필요
```

### C유형 (개발 주도) — 기술 결정 후 통보

```
기술 결정 (개발업체)
    ↓
기술 문서 작성
    ↓
고객사 통보 (검토 요청 아님)
    ↓
이의 없으면 확정

해당 영역
    □ 재고 선점 방식 (Redis TTL)
    □ 결제 보상 처리 (3회 재시도)
    □ 비동기 처리 구조 (Outbox Pattern)
    □ 성능 최적화 방법
    □ 배포 전략 (Canary·Rolling)
```

## 10. AI-DLC 병렬 진행의 핵심 원칙

```
1. 설계는 선행, 구현은 병렬
   → Track 2 설계 완료 즉시 Track 3·4·5 시작
   → 설계 미완료 도메인은 Mock으로 대체

2. B유형 협의는 일정에 포함
   → "협의 후 개발"이 아닌 "협의와 개발 병렬"
   → 협의 결과 반영 시간 별도 확보

3. Claude·Kiro·Harness로 병렬 생산성 극대화
   → Claude가 명세 완료하는 속도 ≈ Kiro 구현 속도
   → 도메인별로 Claude 명세 → Kiro 구현 체인 동시 다발

4. 표준화는 Day 1 완료
   → 표준 없는 코드는 나중에 고치기 어려움
   → Week 1에 모든 표준 확정·배포

5. 고객사는 결정만, 개발업체는 실행만
   → 경계 명확히 → 불필요한 대기 시간 제거

6. 현업 준비는 오픈의 선결 조건
   → 상품·전시 없는 오픈은 없다
   → Track 6은 개발 완료와 무관하게 독립 진행
   → 현업 일정 관리 = 오픈 일정 관리
```
