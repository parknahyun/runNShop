# ⑨ Task Spec(작업지시서) — Harness 표준양식

- **위치**: ⑧ API정의서(화면정의서) 확정 이후, 실구현(Phase D/9공정) 착수 직전 단계
- **목적**: 확정된 설계 산출물을 AI(Kiro 등)가 바로 실행할 수 있는 **작업 단위 지시서**로 변환하고,
  완료 여부를 사람이 짧게 확인할 수 있는 **검증 체크리스트**를 제공한다
- **매핑 Harness**: 신규 — AI-H25(AI 코딩 지시), AI-H26(작업결과물 확인)
- **개발 유형(dev_type) 3종**: FE(Frontend 화면) / BE(Backend API) / BATCH(배치·Consumer)
- **참조 항목**: ①~⑧ 전체 상속 (규칙 재작성 금지, ID만 표기)
- **직접 작성 항목**: 구현 순서, 생성 파일 목록, 참고 구현(레퍼런스), 완료 조건(DoD) 체크리스트

> **원칙**: Task Spec은 설계를 새로 만들지 않는다. API정의서(⑧)·화면정의서(⑤)·도메인정의서(③)·
> 기술정의서(⑦)에 이미 있는 규칙을 **"AI가 지금 당장 실행할 순서"**와 **"완료 후 무엇을 확인할지"**로
> 재배열한 문서다. 설계 내용이 바뀌면 Task Spec이 아니라 원천 문서를 고친다.

## 문서 헤더 (공통)

```yaml
task_id: TSK-{DOM}-{SEQ}-{TYPE}     # TYPE = FE / BE / BATCH
task_name:
dev_type: FE / BE / BATCH
domain:
app: runNshop-admin / runNshop-mobile / runNshop-partner / runNshop-api  # 해당 앱
decision_type: A / B / C / D        # 업무유형(표준/협의/개발주도/현업주도) — 검증 강도 참고용

source_api: {DOM}-{SEQ}             # ⑧ API정의서 (BE·BATCH 필수, FE는 연동 API 전체 목록)
source_screen: {APP}-{SEQ}          # ⑤ 화면정의서 (FE 필수)
source_req: FR-{DOM}-{SEQ}          # ① 원천 요구사항
source_domain: DOM-{DOM}            # ③ 도메인 정의
source_tech: TC-{SEQ}               # ⑦ 기술 제약

reference_impl:                     # "이거 참고해서 구현" — 기존 구현 패턴 지정 (없으면 최초 구현)
depends_on: [TSK-...]               # 선행 완료 필요 Task
assignee: AI(Kiro) / 개발자명
status: TODO / IN_PROGRESS / DONE / VERIFIED
```

- `decision_type`은 03공정(project_management)의 A/B/C/D 업무유형을 그대로 참조한다.
  B(협의)유형 도메인의 Task는 정책 확정본(POL-*) 재확인을 완료 조건에 반드시 포함한다.
- `reference_impl`이 있으면 AI 코딩 지시의 1순위는 "레퍼런스 구조 그대로 적용"이며,
  신규 구조 설계는 레퍼런스가 없는 경우에만 허용한다.

## 공통 섹션: 작업 개요 + 공통 완료 조건

```
[작업 개요]
(1~2문장: 무엇을 어떤 범위까지 만드는가)

[전제 조건]
• depends_on Task 전체 DONE
• source_* 문서 상태가 CONFIRMED인가 확인 (DRAFT 상태면 착수 금지)

[공통 완료 조건 — 3개 dev_type 모두 해당]
□ 빌드 통과 (Gradle build / tsc + next build)
□ Steering 규칙 준수 (coding-standards.md 등 관련 파일)
□ 설계 문서 정합성 — source_* 원천과 불일치 없음 (있으면 Task 완료 아님, 원천 문서부터 수정)
□ 프로토타입 단계 제약(AI-H20) 위반 없음 — 해당 시
```

## [dev_type: FE] AI 코딩 지시 Harness — ← ⑤ 화면정의 + ⑧ API정의서 상속

```
구현 순서:
  1. 화면정의서(source_screen) 레이아웃 기준 구성. 공통 컴포넌트 우선 재사용
     (FilterBar / SummaryBar / Toolbar / Table / Pagination / InnerTabs 등)
  2. reference_impl이 있으면 해당 화면의 구조·상태관리·이벤트 패턴을 그대로 이식
     → 임의 재설계 금지, 다른 점만 명시적으로 변경
  3. API 연동 (source_api 목록의 AI-H12 컴포넌트-API 매핑 그대로) — 하드코딩 금지
  4. 상태 관리 (AI-H14): 초기 상태 "조회 버튼을 눌러 목록을 불러오세요" → 로딩(300ms) → 결과/빈 상태
  5. 프론트 유효성 검증 (AI-H13 규칙 1:1 구현)
  6. 에러 처리 — API error_catalog 코드별 사용자 메시지 매핑 (message_key 그대로 노출 금지)

생성 대상 파일:
  - {app 구조}/{domain}/{screen}/page.tsx (또는 Tab.tsx, 앱별 구조는 AI-H19 참조)
  - 신규 공통 컴포넌트가 필요하면 별도 명시 (없으면 기존 컴포넌트 재사용이 기본값)

금지 사항:
  - reference_impl과 다른 구조를 임의로 설계 (사유 없이)
  - Mock 데이터 프론트 하드코딩 (TC-004)
  - 화면정의서에 없는 필드·버튼 추가
  - source_screen 상태가 CONFIRMED가 아닌데 착수
```

## [dev_type: FE] 작업결과물 확인 Harness

```
자동 확인:
  □ tsc 오류 없음
  □ next build 성공
  □ eslint 오류 없음 (설정된 경우)

수동 시나리오 확인 — API정의서 Feedback Loop(test_scenarios)를 화면 관점으로 재구성:
  □ 정상 조회/등록/수정/삭제 플로우 동작
  □ 목록 필터·페이지네이션 동작
  □ error_catalog 코드별 에러 메시지 노출 확인 (전체 케이스)
  □ 화면 전환(버튼 → 다음 화면) 정상 동작
  □ 뒤로가기/탭 재진입 시 상태 유지 확인

설계 정합성 확인:
  □ 화면정의서(AI-H12/13/14) 필드·검증규칙 누락 없음
  □ steering 파일(nextjs-guide.md, admin-guide.md 등) 위반 없음
```

## [dev_type: BE] AI 코딩 지시 Harness — ← ⑧ API정의서 Output Schema 상속

```
구현 순서 (API정의서 expected_classes 순서 그대로):
  1. Request/Response DTO — Requirements Validation Harness 필드 그대로 (제약조건 포함)
  2. Repository — Data Contract Harness(invariants/state_transition/soft_delete) 반영
  3. Service — Domain Constraint Harness의 HARD 전체 구현 필수, SOFT(정책) 반영
  4. Controller — Context Harness의 endpoint(method/path/auth/role) 그대로
  5. 예외 처리 — error_catalog 전체 1:1 매핑 (임의 축약·병합 금지)
  6. 이벤트 발행 — event_publishing이 있으면 Outbox 패턴, AFTER_COMMIT 준수
  7. 테스트 코드 — Feedback Loop Harness의 test_scenarios 전체 커버

생성 대상 파일: expected_classes 목록 그대로 (API정의서에서 상속, 재정의 금지)

금지 사항:
  - HARD 제약(HC-*) 누락·우회
  - error_catalog 코드 임의 축약
  - transaction_annotation 명시된 위치 외 @Transactional 부착
  - 도메인 경계 위반 (AI-H5 boundary_rules — 타 도메인 테이블 직접 접근)
```

## [dev_type: BE] 작업결과물 확인 Harness

```
자동 확인:
  □ Gradle build 성공
  □ ktlint 오류 없음
  □ 단위 테스트 전체 통과 (test_scenarios 1:1 대응, 개수 일치 확인)
  □ 커버리지 ≥ quality_gate.test_coverage
  □ p95_latency ≤ quality_gate.p95_latency (부하 테스트 대상 API만)

크로스 확인 (사람 또는 AI 자기 점검):
  □ HARD 제약(HC-*) 목록 전체 구현 여부 체크 (누락 0건)
  □ error_catalog 코드 전체 구현 여부 체크 (누락 0건)
  □ cross_field_rules 검증 로직 존재 확인
  □ 이벤트 발행 시점(AFTER_COMMIT) 코드상 확인
  □ 도메인 경계 위반 없음 (AI-H5/H7 forbidden_dependencies 대조)
```

## [dev_type: BATCH] AI 코딩 지시 Harness — ← ④ 업무흐름(AI-H9/H11) + ⑦ 기술정의 상속

```
구현 순서:
  1. 트리거 정의 — 스케줄(cron) 또는 Consumer 구독 이벤트(AI-H9 event_name)
  2. 멱등성 처리 — 동일 트리거 중복 실행/중복 메시지 방지 키 설계 (필수)
  3. 비즈니스 로직 — Domain Constraint Harness(HARD/SOFT) 상속
  4. 실패 처리 — 재시도 횟수·백오프 정의, 최종 실패 시 DLQ 또는 알림
  5. 로그·모니터링 — Trace ID 부여, 처리 건수/실패 건수 로그

생성 대상 파일: expected_classes(있는 경우) + Batch/Consumer 전용 클래스
  예: {Domain}{Purpose}Batch, {Domain}EventConsumer

금지 사항:
  - 멱등키 없는 배치·컨슈머 로직
  - 실패 시 무한 재시도 (최대 횟수 명시 필수)
  - BEFORE_COMMIT 타이밍의 이벤트 발행에 의존 (AI-H23 wrong_pattern)
```

## [dev_type: BATCH] 작업결과물 확인 Harness

```
자동 확인:
  □ 스케줄 등록 확인 (cron 표현식이 AI-H11 schedule과 일치)
  □ 단위 테스트 통과 (정상 / 중복 실행 / 실패 3케이스 최소)

자동+수동 확인:
  □ 멱등성 테스트 — 동일 입력 2회 실행 → 결과가 1회 실행분과 동일
  □ 실패 재시도 정책 동작 확인 — 최대 N회 후 최종 실패 처리(DLQ/알림) 확인
  □ 처리량 확인 — 기준 건수/시간이 있는 경우 충족 여부
  □ 로그에 Trace ID·처리 건수·실패 건수가 남는지 확인
```

## 작성 기준

| 항목 | 기준 |
|------|------|
| dev_type | 앱/레이어 기준 3분류만 사용 (FE/BE/BATCH). 혼합 작업이면 Task를 분리 |
| 참조 항목 | 원천 문서 ID만 표기, 규칙 재작성 금지 |
| 생성 대상 파일 | BE는 API정의서 expected_classes를 그대로 상속, FE/BATCH는 Task Spec에서 직접 지정 |
| 완료 조건 | "자동 확인"은 CI에서 기계적으로 판정 가능한 것만, "수동/크로스 확인"은 사람 또는 AI 자기 점검 항목 |
| status | DONE = 자동 확인 통과, VERIFIED = 수동/크로스 확인까지 완료 (사람 승인 포함) |
| decision_type=B | 완료 조건에 "정책서(POL-*) 최신 확정본 재확인" 항목 추가 |

```
TSK-{DOM}-{SEQ}-{TYPE}
  ├─ source_api  → {DOM}-{SEQ}       (⑧ API정의서, BE/BATCH)

```
