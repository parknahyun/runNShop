### AI 코딩 지시 (BE)

```
1. DTO: CreateOrderRequest(cartItemIds, couponId, pointAmount, deliveryAddressId),
   CreateOrderResponse(orderId, orderNo, finalAmount, orderStatus, paymentUrl)
   → ORD-001 request 테이블 제약조건 그대로 반영

2. Repository: OrderRepository (INSERT ord_order, ord_order_item, ord_platform_order),
   OutboxRepository (INSERT ord_outbox)
   → invariants: final_amount 계산 일치, 음수 방지 / state_transition 초기값: TEMP

3. Service: OrderService.createOrder()
   HARD 전체 구현 필수:
     - HC-ORD-001 재고 부족 상품 주문 금지
     - HC-ORD-002 보유 포인트 초과 사용 금지
     - HC-ORD-003 만료·사용된 쿠폰 적용 금지
     - HC-ORD-004 주문 수량 1 이상
   SOFT 반영: POL-ORD-001(배송비), POL-ORD-002(쿠폰 할인)
   cross_field_rules: pointAmount + couponDiscount <= subtotal

4. Controller: CustomerOrderController(POST /api/v1/orders, JWT 필수, role=[CUSTOMER]),
   AdminOrderController(TC-006 동일 로직 재사용)

5. 예외 처리: error_catalog 7건 전체 구현
   (OUT_OF_STOCK, COUPON_EXPIRED, COUPON_ALREADY_USED, COUPON_MIN_AMOUNT,
    POINT_INSUFFICIENT, CART_ITEMS_EMPTY, CART_ITEM_NOT_OWNED)

6. 이벤트: OutboxRepository.save() → AFTER_COMMIT, @Transactional(readOnly = false)
   on OrderService.createOrder()

7. 테스트: test_scenarios 7건 전체 (정상 1 + 실패 6)
```

### 작업결과물 확인 (BE)

```
자동 확인:
  □ Gradle build 성공
  □ ktlint 오류 없음
  □ 단위 테스트 7건 전체 통과 (test_scenarios와 1:1 대응)
  □ 커버리지 ≥ 80% (quality_gate.test_coverage)
  □ p95_latency ≤ 1000ms (quality_gate.p95_latency)

크로스 확인:
  □ HC-ORD-001~004 4건 전체 구현 여부 코드 대조
  □ error_catalog 7건 전체 구현 여부 코드 대조 (누락 0건)
  □ pointAmount + couponDiscount <= subtotal 검증 로직 존재
  □ Outbox INSERT가 @Transactional 내부에서 AFTER_COMMIT으로 발행되는지 확인
  □ Order 도메인이 cat_/mbr_ 테이블에 직접 접근하지 않는지 확인 (AI-H5)
```

## 샘플 3. TSK-ORD-EVT-001-BATCH — 주문 Outbox 이벤트 발행 배치

```yaml
task_id: TSK-ORD-EVT-001-BATCH
task_name: 주문 Outbox 이벤트 발행 배치 (OutboxPublisherBatch)
dev_type: BATCH
domain: Order
app: runNshop-api
decision_type: C

source_api: ORD-001                 # event_publishing 정의 참조
source_domain: DOM-ORDER
source_tech: TC-007

reference_impl: (없음 — Outbox 공통 배치, 이후 타 도메인 Outbox의 레퍼런스가 됨)
depends_on: [TSK-ORD-001-BE]
assignee: AI(Kiro)
status: TODO
```

### AI 코딩 지시 (BATCH)

```
1. 트리거: 스케줄 기반 (매 10초), ord_outbox 테이블 중 미발행(sent_at IS NULL) 행 폴링
2. 멱등성: outbox_id를 멱등키로 사용, 발행 성공 시 sent_at 즉시 UPDATE (재조회 시 재발행 방지)
3. 비즈니스 로직: ORDER_CREATED 이벤트를 Kafka로 발행 (consumer_domain: Payment, Notification)
4. 실패 처리: 발행 실패 시 최대 3회 재시도(즉시→30초→1분), 최종 실패 시 admin_alert 발송 + retry_count 기록
5. 로그: Trace ID(주문 생성 시 발급된 값 그대로 전파), 배치 1회 실행당 발행 건수/실패 건수 로그

생성 대상 파일:
  - OutboxPublisherBatch.kt
  - OutboxPublisherBatchTest.kt

금지 사항:
  - sent_at UPDATE 없이 재조회하여 중복 발행
  - 무한 재시도 (3회 초과 시 알림 없이 계속 재시도)
```

### 작업결과물 확인 (BATCH)

```
자동 확인:
  □ 스케줄 등록 확인 (10초 주기 cron/fixedDelay 일치)
  □ 단위 테스트 통과 (정상 발행 / 중복 폴링 시 재발행 안됨 / 3회 실패 후 알림 발송 3케이스)

자동+수동 확인:
  □ 멱등성 테스트 — 동일 outbox_id 2회 폴링 → Kafka 발행 1회만 발생
  □ 재시도 정책 동작 확인 — 3회 실패 후 admin_alert 발송 확인
  □ 처리량 확인 — 배치 1회당 미발행 건 100건 이상 시 지연 없이 처리되는지
  □ 로그에 Trace ID·발행 건수·실패 건수 기록 확인
```
