# runNshop AI-DLC 설계 순서 비교 분석

> 작성 주체: 3TOP 2본부  
> 문서 버전: v1.0  
> 작성일: 2026.06.25  
> 목적: AI 협업 기반 설계 순서 변경 이유 및 근거 정리

---

## 1. 개요

전통적인 e커머스 플랫폼 개발에서는 **화면 설계 → ERD** 순서가 일반적이었다.  
runNshop 프로젝트에서는 **정책서 → 도메인 → ERD → 화면** 순서로 진행하였다.  
이 문서는 순서 변경의 배경·이유·트레이드오프를 정리한다.

---

## 2. 기존 방식 (화면 → ERD)

### 2.1 진행 순서

```
요구사항 수집
    ↓
화면 설계 (와이어프레임·목업)
    ↓
화면에서 필요한 데이터 도출
    ↓
ERD 작성
    ↓
API 설계
    ↓
개발 구현
```

### 2.2 특징

| 항목 | 내용 |
|------|------|
| 설계 기준 | UI 직관·화면 중심 |
| 데이터 도출 방식 | 화면에서 필요한 필드를 역추적 |
| 적합한 환경 | 단순 도메인·소규모 시스템 |
| 장점 | 현업 담당자와 즉각적인 확인 가능 |
| 단점 | 화면이 바뀌면 ERD 변경 빈번 |

### 2.3 문제점

```
화면 → ERD 방식의 한계

1. 데이터 정합성 저하
   → 화면마다 데이터 구조가 달라짐
   → ERD 통합 시 충돌 발생 빈번
   → 설계 변경 비용 증가

2. 비즈니스 규칙 누락
   → 화면에 보이지 않는 규칙 (정산 분담·귀책 판단 등)
   → 개발 중 발견 → 재설계 필요

3. 도메인 복잡도 대응 한계
   → 복수 입점사·클레임 귀책·포인트 분담 등
   → 화면만으로 규칙 표현 불가
```

## 3. 이번 방식 (ERD → 화면)

### 3.1 AI-DLC 9대 공정 기반 진행 순서

```
1공정: 정책서 작성 (비즈니스 규칙 확정)
    ↓
2공정: Bounded Context 정의 (도메인 경계)
    ↓
3공정: Modular Monolith 설계 (아키텍처)
    ↓
4공정: ERD 작성 (데이터 구조 확정)
    ↓
5공정: 이벤트 흐름 정의 (도메인 간 통신)
    ↓
6공정: 업무 프로세스 정의 (흐름 확정)
    ↓
7공정: 화면 정의서·API 도출
    ↓
8공정: 요구사항 정의서·질의서 작성
    ↓
9공정: API 명세 → 코드 구현
```

### 3.2 특징

| 항목 | 내용 |
|------|------|
| 설계 기준 | 비즈니스 규칙·도메인 중심 (DDD) |
| 데이터 도출 방식 | 정책서 → BC → ERD 순으로 도출 |
| 적합한 환경 | 복잡 도메인·AI 협업 환경 |
| 장점 | 데이터 정합성 보장·변경 영향 최소화 |
| 단점 | 초반 화면 부재로 현업 확인 어려움 |

## 4. 순서 변경의 핵심 이유

### 4.1 AI 협업 환경의 특성

```
기존 방식
    사람이 화면을 보면서 직관적으로 ERD 도출
    → 사람의 시각적 판단이 핵심

이번 방식
    AI가 정책서·BC를 읽고 ERD 생성
    → AI는 텍스트(정책·규칙) 기반 추론이 강점
    → 화면 이미지보다 정책 문서를 더 정확하게 해석
    → 비정형 요구사항보다 구조화된 정책서가 AI 입력에 최적
```

**AI 특성 활용 원칙**

| AI 강점 | 설계 순서 반영 |
|---------|-------------|
| 텍스트 기반 규칙 해석 | 정책서 먼저 작성 |
| 구조적 데이터 도출 | BC → ERD 순으로 도출 |
| 일관성 유지 | 정책 기반으로 전 산출물 연계 |
| 크로스 체크 | 산출물 간 정합성 자동 검증 |

---

### 4.2 도메인 복잡성 대응

runNshop은 단순 쇼핑몰이 아닌 복합 비즈니스 규칙을 가진다.

```
복잡한 비즈니스 규칙 예시

정산 분담
    매출 - 수수료 - 쿠폰분담(계약비율) - 포인트분담(30%)
    - 재정산 - 패널티 + 이월
    → 화면에서 도출 불가. 정책서에서 먼저 확정 필수

클레임 귀책 판단
    고객·입점사·플랫폼 귀책별 배송비 부담 차등
    → 화면 없이 프로세스로 먼저 정의

할인 적용 순서
    행사가 → 수량할인 → 쿠폰 → 장바구니할인 → 포인트
    → 정책 확정 없이 화면 설계 불가

2계층 주문 구조
    ord_platform_order + ord_order
    → 복수 입점사 처리 규칙이 ERD를 결정
```

**결론**: 이런 규칙들은 화면을 먼저 그려도 도출되지 않는다.  
정책서에서 규칙을 확정한 후 ERD를 설계해야 누락 없이 반영된다.

---

### 4.3 데이터 정합성 우선

```
기존 방식의 정합성 문제

화면 A에서 도출한 ERD
    → 주문 테이블: ord_order (단일)

화면 B에서 도출한 ERD
    → 입점사별 주문: vnd_order (별도)

통합 시 충돌
    → 어떤 테이블이 맞는가?
    → 재설계 필요

이번 방식
    → 정책서에서 "2계층 주문 구조" 먼저 확정
    → BC에서 Order 도메인 경계 정의
    → ERD에서 ord_platform_order + ord_order 설계
    → 화면은 이 구조를 그대로 반영
    → 충돌 없음
```

---

### 4.4 변경 영향 최소화

```
기존 방식 (화면 → ERD)
    화면 변경 → ERD 변경 → API 변경 → 개발 변경
    변경 영향: 전 계층

이번 방식 (정책서 → ERD → 화면)
    정책 변경 → ERD 변경 → 화면 변경
    화면만 변경 → 화면만 수정 (ERD·API 영향 없음)
    변경 영향: 제한적
```

## 5. 트레이드오프

### 5.1 이번 방식의 단점

| 단점 | 내용 | 보완 방법 |
|------|------|---------|
| 초반 화면 부재 | ERD 완성 전 현업 확인 어려움 | 업무 프로세스 다이어그램으로 대체 |
| 현업 친숙도 | 정책서·BC는 개발자 중심 언어 | 요구사항 질의서·답변서 별도 작성 |
| 역방향 사고 | ERD → 화면 역방향 설계 필요 | 화면 정의 후 ERD 크로스 체크 |
| 학습 비용 | DDD·BC 개념 이해 필요 | AI가 설명·가이드 제공 |

### 5.2 이번 방식의 보완 활동

```
runNshop 프로젝트에서 진행한 보완 활동

1. 업무 프로세스 다이어그램 (Mermaid)
   → 화면 없이도 흐름 시각화
   → 현업 담당자 검토 가능

2. 화면 정의서 작성 후 ERD 크로스 체크
   → 화면에서 필요한 데이터가 ERD에 있는지 확인
   → 누락 테이블·컬럼 보완

3. 정책서·BC·프로세스·ERD 상호 크로스 체크
   → 3개 이상 문서 간 불일치 항목 도출·해결

4. 요구사항 정의서·질의서 작성
   → 현업 언어로 번역
   → 확정 상태 관리
```

## 8. 결론

### AI-DLC 설계 순서 원칙

```
What (무엇을 만들 것인가)
    → 정책서: 비즈니스 규칙 확정

Structure (어떻게 구조화할 것인가)
    → BC·Modular Monolith·ERD: 도메인·데이터 구조 확정

How (어떻게 보여줄 것인가)
    → 화면 정의서·API: 사용자 인터페이스 확정

Why (왜 이렇게 작동하는가)
    → 프로세스·요구사항: 검증 및 문서화
```

**핵심 메시지**

> 화면은 비즈니스 규칙과 데이터 구조의 **결과물**이다.  
> 결과물을 먼저 그리면 원인(규칙·데이터)이 흔들린다.  
> AI 협업 환경에서는 **텍스트 기반 정책 → 구조 → 화면** 순서가  
> 정합성·효율성·변경 대응력 모두에서 우월하다.

## 9. 요구사항 정의 방식의 전환

### 9.1 전통적 방식 — "무엇을 해주세요"

```
요구사항 정의서 (전통)

FR-001: 회원가입 기능을 제공해야 한다.
FR-002: 로그인 실패 시 계정을 잠금 처리해야 한다.
FR-003: 장바구니에 상품을 담을 수 있어야 한다.
FR-004: 주문 후 결제가 가능해야 한다.
```

| 특징 | 내용 |
|------|------|
| 작성 시점 | 개발 전 (미확정 상태) |
| 기술 수준 | What (무엇을) |
| 목적 | 개발팀에게 요청·지시 |
| 문제점 | 개발자가 해석·결정 → 해석 차이 → 재작업 |

---

### 9.2 이번 방식 — "이렇게 합니다"

```
요구사항 정의서 (이번)

FR-MBR-001 회원가입
    - 가입 방식: 이메일·네이버·Apple
    - 본인인증: 가입 시 옵션널, 주문 시 필수
    - OTP 5회 실패 시 24시간 발송 제한
    - 웰컴 쿠폰 자동 발급
    - mbr_terms_agreement INSERT
```

| 특징 | 내용 |
|------|------|
| 작성 시점 | 설계 완료 후 (확정 상태) |
| 기술 수준 | What + How + Constraint |
| 목적 | 확정된 내용의 문서화·선언 |
| 효과 | 개발자 해석 여지 없음·바로 코드 전환 가능 |

---

### 9.3 왜 "이렇게 합니다"가 되었나

이번 방식에서 요구사항 정의서가 확정 선언문이 된 이유는  
**산출물 작성 순서** 때문이다.

```
정책서에서 규칙 확정
    "OTP 5회 실패 시 24시간 발송 제한"
    "포인트 적립: 구매확정 후 등급별 0.5~2%"
        ↓
BC에서 소유권 확정
    "포인트는 Member 도메인 소유"
    "적립은 PurchaseConfirmed 이벤트 수신 시"
        ↓
ERD에서 구조 확정
    "mbr_point 테이블, change_source 컬럼"
        ↓
프로세스에서 흐름 확정
    "구매확정 → MemberGradeBatch → 포인트 적립"
        ↓
요구사항 정의서 작성
    = 위 내용을 종합 정리
    = 이미 모든 것이 확정된 상태
    = 새로운 결정 사항 없음
```

요구사항 정의서를 작성하는 시점에는 이미  
정책·구조·흐름·데이터가 모두 확정되어 있기 때문에  
**요청이 아닌 확정 선언**이 자연스럽게 도출된다.

### 9.4 두 방식의 본질적 차이

| 구분 | 전통 방식 | 이번 방식 |
|------|---------|---------|
| 작성 시점 | 개발 전 (미확정) | 설계 완료 후 (확정) |
| 목적 | 개발팀에게 요청 | 확정 내용 문서화 |
| 기술 수준 | What | What + How + Constraint |
| 독자 | 개발자 | 개발자·현업·AI |
| 문서 역할 | 지시서 | 계약서·명세서 |
| 해석 여지 | 있음 | 없음 |
| 재작업 위험 | 높음 | 낮음 |

### 9.5 실무적 의미

```
전통 방식의 흐름
    고객 → 요구사항 작성 → 개발자에게 전달
    개발자가 해석하고 구현
    "이런 뜻이었나요?" 반복 확인
    재작업 발생

이번 방식의 흐름
    정책서·프로세스·ERD로 먼저 확정
    요구사항 = 확정된 내용의 요약본
    "이렇게 구현합니다" 선언
    Kiro가 요구사항 정의서 보고 바로 코드 생성
```

### 9.6 AI-DLC 요구사항 정의 핵심 원칙

> **요구사항은 요청이 아니라 확정이다.**
>
> 산출물(정책서·BC·ERD·프로세스)이 먼저 확정되면  
> 요구사항은 그 결과물로 자동 도출된다.
>
> "무엇을 해주세요" → 개발자가 해석  
> "이렇게 합니다" → 개발자가 구현

이것이 AI 협업 환경에서 **설계 선행·요구사항 후행** 순서가  
더 효율적인 근본적 이유다.
