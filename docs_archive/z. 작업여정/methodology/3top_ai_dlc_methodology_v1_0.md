## 1. 자산 정리의 당위성

### 1.1 현재 문제

```
유사업무를 수주할 때마다 매번 처음부터 시작하고 있다.

  - 정책서: 매번 백지에서 작성 (2~3주)
  - 설계: 같은 패턴인데 다시 그림 (2~4주)
  - 프로토타입: 비슷한 화면을 또 구현 (2~4주)
  - 현업 소통: 문서로 설명하면 이해 못함 → 재작업 (반복)

결과: 유사업무인데도 프로젝트마다 16~24주 소요.
     경험이 축적되지 않고, 사람에 의존.
```

### 1.2 자산을 정리해야 하는 이유

```
1. AI에게 줄 입력이 정리되어야 AI가 즉시 일한다
   → 자산이 없으면 AI도 매번 "뭘 만들어야 하나요?"부터 시작
   → 자산이 있으면 AI가 "이걸 기반으로 커스터마이징하겠습니다" 즉시 수행

2. 프로토타입이 빨라야 현업과 빨리 만난다
   → 자산이 있으면 1~2주 내 전체 화면 프로토타입 가능
   → 현업이 화면을 보면서 요구사항을 말하는 것이 문서보다 10배 정확

3. 사람이 바뀌어도 방법이 유지된다
   → PL이 바뀌어도, 팀원이 바뀌어도
   → 자산(초안+템플릿+steering)이 있으면 동일 품질로 착수 가능

4. 프로젝트 수주 경쟁력
   → "1~2주 내 동작하는 프로토타입을 보여드릴 수 있습니다"
   → 이 약속이 가능한 건 자산이 있을 때만

5. 누적될수록 빨라진다
   → 프로젝트 A의 산출물이 → 프로젝트 B의 초안이 됨
   → 반복할수록 커스터마이징만 하면 되는 범위가 넓어짐

6. 이해당사자의 의사결정을 유도해야 한다
   → 현업·기획자·BA는 의사결정을 위한 데이터가 부족하다
   → 데이터가 부족하니 결정을 미루고, 리딩하는 사람 없이 방관한다
   → 결과: "어떻게 할까요?" 회의만 반복. 아무것도 확정 안 됨

   자산이 이 문제를 해결하는 방식:
   → 초안(정책서·프로세스·화면)이 "이렇게 하면 됩니다"를 먼저 제시
   → 프로토타입이 "이걸 이렇게 만들었는데 맞나요?"를 보여줌
   → 이해당사자는 "결정"이 아닌 "확인"만 하면 됨
   → "백지에서 결정하라"가 아닌 "이거 맞나 아닌가만 말하라"로 전환

   즉, 자산 = 의사결정의 선택지를 먼저 제시하는 도구
   → 방관자를 "확인자"로 바꿈
```

### 1.3 자산 유무에 따른 차이

```
자산이 없으면                    자산이 있으면
━━━━━━━━━━━━━━━━━━━━━━━         ━━━━━━━━━━━━━━━━━━━━━━━
매번 백지 출발                   초안 기반 착수
AI에게 설명부터                  AI가 즉시 커스터마이징
현업에 문서로 설명               현업에 화면으로 시연
사람 바뀌면 처음부터             자산이 방법을 기억
방관자 양산                     확인자로 전환
프로젝트당 16~24주              프로젝트당 8~16주
```

## 2. 전제 조건: 보유 자산

```
설계 초안 5종
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    ├── 정책서 (비즈니스 규칙 초안)
    ├── 도메인 BC (경계·소유권 초안)
    ├── 업무플로우 (프로세스 다이어그램 초안)
    ├── ERD (엔티티 구조 초안) — 선택
    └── 화면정의서 (화면 목록·유형·API 목록 초안)

구현 자산 3종
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    ├── Scaffolding 가이드 (프로젝트 생성 절차)
    ├── Steering 파일 (AI 에이전트 코딩 규칙)
    └── 프로토타입 코드 템플릿 (전체 화면 Mock 기반)
```

| 구분 | 자산 | 필수/선택 | 없으면 |
|------|------|---------|--------|
| 설계 | 정책서 | 필수 | Phase A 착수 불가 |
| 설계 | 도메인 BC | 필수 | AI가 도메인 경계를 모름 |
| 설계 | 업무플로우 | 필수 | 프로세스 구현 방향 없음 |
| 설계 | ERD | 선택 | Phase C에서 AI가 도출 가능 |
| 설계 | 화면정의서 | 필수 | 프로토타입 화면 목록 없음 |
| 구현 | Scaffolding 가이드 | 필수 | 프로젝트 구조 매번 수동 세팅 |
| 구현 | Steering 파일 | 필수 | AI 코드 품질 불일치 |
| 구현 | 코드 템플릿 | 필수 | 프로토타입 속도 저하 |

## 3. 공정 체계: Phase A~D

```
Phase A: 프로토타입 생성 (AI 주도, 1~2주)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 입력: 초안 5종 + 구현 자산 3종
 수행:
    1. Scaffolding 가이드로 프로젝트 구조 생성
    2. 초안 5종을 신규 프로젝트에 맞게 커스터마이징
       - 정책서: 도메인명·수치·정책 치환
       - BC: 도메인 경계 조정
       - 화면정의: 화면 추가/제거
    3. Steering 파일 세팅 → AI(Kiro)에게 구현 위임
    4. 프로토타입 코드 템플릿 기반 전체 화면 Mock 구현
 산출물: 동작하는 프로토타입 (전 화면 Mock 기반)
 주체: AI(Kiro) + PL 1명
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Phase B: 현업 협의 → 요구사항 확정 (현업 주도, 2~4주)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 입력: 동작하는 프로토타입 + 초안 5종
 수행:
    1. 현업에게 프로토타입 시연
    2. 화면 단위로 피드백 수집
       - "이 화면 필요 없음" / "이 항목 추가"
       - "이 정책은 우리는 다르게"
    3. 피드백 → 요구사항 정의서 작성 (확정 선언)
    4. 요구사항 기반 프로토타입 즉시 수정 → 재시연 (반복)
 산출물: 확정 요구사항 정의서 + 수정된 프로토타입
 주체: 현업 + PL + AI
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Phase C: 설계 확정 (AI 주도, 1~2주)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 입력: 확정 요구사항 + 초안 5종 + 수정된 프로토타입
 수행:
    1. 확정 요구사항 기반 설계 문서 보완
       - 정책서 확정
       - BC 확정
       - ERD 확정 (프로토타입 Mock 구조 기반 + 요구사항 반영)
       - 프로세스 확정
       - 화면정의서 확정
    2. 크로스체크 (문서 간 정합성 검증)
    3. API 명세서 작성 (Swagger/OpenAPI) ※Phase A~B 병행 가능
 산출물: 확정 설계 산출물 전체 + API 명세
 주체: AI(Claude/Kiro) + PL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Phase D: 실구현 + 오픈 (팀 주도, 4~8주)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 입력: 확정 설계 + API 명세 + 프로토타입 코드
 수행:
    1. Mock → 실DB 연동 (JPA/R2DBC)
    2. 인증·인가 구현
    3. PG·외부 연동
    4. CI/CD 파이프라인
    5. 통합 테스트 + 성능 테스트
    6. 스테이징 → QA → 프로덕션 오픈
 산출물: 운영 가능한 시스템
 주체: 개발팀 + AI + PL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 5. 기대 효과

| 항목 | 전통 방식 | 이 방법론 |
|------|---------|---------|
| 요구사항 확정까지 | 4~8주 (문서 기반 회의) | 2~4주 (프로토타입 보면서) |
| 현업 이해도 | 낮음 (문서 읽기) | 높음 (화면 직접 조작) |
| 설계-구현 갭 | 큼 (설계 따로 구현 따로) | 없음 (프로토타입이 곧 코드 베이스) |
| 프로젝트 착수 ~ 오픈 | 16~24주 | 8~16주 |
| 재사용성 | 매번 처음부터 | 초안 + 템플릿 재활용 |
| 재작업 비용 | 높음 (요구사항 해석 차이) | 낮음 (보면서 확정) |
| 방관자 문제 | 지속 (결정 데이터 없음) | 해소 (화면이 선택지를 제시) |

## 6. 이슈 및 리스크

| # | 이슈 | 영향 | 대응 방안 |
|---|------|------|---------|
| 1 | **초안 품질 의존** — 초안이 부정확하면 프로토타입도 잘못된 방향 | Phase B에서 대규모 수정 → 일정 지연 | 초안 작성 시 유사업무 최소 2건 크로스 참조. Phase A에서 PL 사전 검증 |
| 2 | **현업 피드백 루프 지연** — 현업이 바빠서 Phase B가 길어짐 | 프로토타입 있는데 확정 안 됨 | 시연 일정 사전 확정 (주 1~2회). 미응답 시 "초안 기준 확정" 규칙 |
| 3 | **프로토타입 = 최종 착각** — 현업이 Mock을 완성품으로 오인 | Phase D 일정·비용 설명 어려움 | 시연 시 "Mock이고 실제 저장·결제·보안은 별도" 매번 명시 |
| 4 | **AI 컨텍스트 한계** — 규모 크면 AI가 전체를 한 번에 못 봄 | 세션 분리 시 산출물 불일치 가능 | Steering 파일 + 크로스체크 공정 필수 수행 |
| 5 | **초안 범용성** — 커머스 외 도메인에서 재사용률 낮음 | 커스터마이징이 거의 새로 쓰는 수준 | 도메인별 초안 풀 축적. 적용 범위를 "유사업무"로 한정 |
| 6 | **PL 의존도** — PL 1명이 방향 지시해야 AI가 움직임 | PL 부재 시 공정 정지 | PL 백업 체계 + decision_log.md 기록 |
| 7 | **프로토타입 → 실코드 전환 비용** — Mock → 실DB 전환 리팩토링 | Phase D 초기 일정 압박 | Controller-Service 분리. Service 레이어만 교체하도록 설계 |
| 8 | **Scope Creep** — 프로토타입 보면서 현업이 계속 추가 요청 | Phase B가 끝나지 않음 | 확정 기한 + "추가건은 Phase 2 범위"로 분리 |
| 9 | **고객 화면 디자인 컴펌** — Phase B에서 요구사항 확정과 동시에 서비스기획·디자인 컴펌 필요 | 현업이 두 트랙 동시 결정 → Phase B 지연 | 기획업체와 프로젝트 협의체 구성. 백오피스·고객화면 시연 분리 진행 |
| 10 | **프런트 기획 자산 이탈** — 기획이 자산의 화면 구조·플로우를 무시하고 새 구조 요구 | 프로토타입 코드 재사용 불가 → 방법론 효과 상실 | 디자인 시스템 자산화 + 협의체에서 "변경 가능 범위" 사전 합의. 자산 벗어나면 추가 비용·일정 산정 |

## 7. 자산이 없을 때: 진입점 비교

자산이 없는 상태에서 어디부터 시작하는가에 따라 4가지 방안이 있다.

### 방안 A: 정책서부터 (runNshop 방식)

```
정책서 → BC → 아키텍처 → ERD → 이벤트 → 화면 → 프로세스 → 요구사항 → 구현
```

| 장점 | 단점 |
|------|------|
| 비즈니스 규칙이 모든 산출물의 기준 | 화면 없이 출발 → 현업이 초반에 뭘 하는지 모름 |
| 정합성 높음 | PL에 정책 결정 역량 필요 |
| 변경 시 영향 범위 추적 가능 | 첫 프로토타입까지 4~6주 소요 |
| AI 입력에 최적 (텍스트 기반) | 현업 참여가 늦어짐 |

**적합**: 도메인 복잡도 높음. PL이 비즈니스를 잘 아는 경우.

### 방안 B: 화면부터

```
화면(와이어프레임) → 요구사항 → 정책서 → BC → ERD → 프로세스 → 구현
```

| 장점 | 단점 |
|------|------|
| 현업 즉시 참여 가능 | 데이터 구조 불일치 빈번 |
| 체감 속도 빠름 (1~2주) | 비즈니스 규칙 누락 |
| 현업 친화적 | 화면 바뀔 때마다 재설계 |
| 단순 도메인에 효율적 | 복잡 도메인에서 재작업 폭발 |

**적합**: 도메인 단순. 현업이 주도적이고 의견 명확.

### 방안 C: 요구사항부터 (전통 SDLC)

```
요구사항 수집 → 분석 → 설계 → 구현 → 테스트
```

| 장점 | 단점 |
|------|------|
| 업계 표준. 모두 익숙 | 모호하면 해석 차이 → 재작업 |
| 계약·범위 기준 활용 | 현업이 방관자 되기 쉬움 |
| 대규모 SI에서 검증됨 | AI 입력에 비효율 |

**적합**: 계약 기반 SI. 요구사항이 명확하게 도출된 경우.

### 방안 D: 프로토타입부터 (Lean/MVP)

```
프로토타입(MVP) → 피드백 → 요구사항 → 설계 → 실구현
```

| 장점 | 단점 |
|------|------|
| 가장 빠른 결과물 (1~2주) | 설계 없이 만들어서 구조 부실 |
| 현업 피드백 즉시 확보 | 프로토타입 → 실코드 전환 시 갈아엎기 |
| 방관자 참여 유도 | 정합성 보장 없음 |
| 스타트업·PoC에 최적 | 규모 큰 시스템에서 기술부채 폭발 |

**적합**: 요구사항 불명확. 빠른 방향 검증 필요.

### 비교 매트릭스

| 기준 | A 정책서 | B 화면 | C 요구사항 | D 프로토타입 |
|------|---------|--------|----------|------------|
| 첫 결과물 속도 | 느림 (4~6주) | 빠름 (1~2주) | 보통 (3~4주) | 매우 빠름 (1주) |
| 정합성 | 높음 | 낮음 | 보통 | 낮음 |
| 현업 참여 시점 | 늦음 | 즉시 | 초반 | 즉시 |
| 재작업 비용 | 낮음 | 높음 | 보통 | 매우 높음 |
| AI 협업 효율 | 최고 | 보통 | 낮음 | 보통 |
| 방관자 문제 해결 | 약함 | 강함 | 약함 | 강함 |
| 복잡 도메인 대응 | 강함 | 약함 | 보통 | 약함 |

### 3TOP 2본부의 선택: A + D 혼합

```
자산이 있을 때 (본 방법론)
    = A(정책서)의 정합성 + D(프로토타입)의 속도 + 방관자 해결

자산이 없을 때 첫 프로젝트
    = A 방식으로 자산을 만들면서 (runNshop이 이것)
    = 이후 유사업무는 A+D 혼합으로 진행

자산을 정리해야 하는 핵심 이유:
    A의 느린 속도를 D의 빠른 속도로 보완하려면,
    A의 산출물이 이미 자산으로 존재해야 가능하다.
```

## 8. 자산 현황: 한 것과 해야 할 것

### 설계 초안 5종

| 자산 | 한 것 (runNshop에서 완료) | 해야 할 것 (범용화) |
|------|------------------------|-------------------|
| 정책서 | v1_2 확정 (커머스 특화) | 챕터 구조를 고정하고 수치·정책만 교체하는 템플릿화 |
| 도메인 BC | 12개 도메인 경계 확정 | 도메인 목록을 변수화. 체크리스트 형태로 정리 |
| 업무플로우 | 12개 프로세스 다이어그램 | 공통 프로세스 vs 선택 프로세스 분류 |
| ERD | 107테이블 확정 | 도메인별 핵심 테이블만 추린 "기본 ERD 세트" 정리 |
| 화면정의서 | 158화면·470 API 정의 | 화면유형 단위 템플릿화. 도메인별 체크리스트 |

### 구현 자산 3종

| 자산 | 한 것 | 해야 할 것 |
|------|------|-----------|
| Scaffolding 가이드 | runNshop 전용 작성 완료 | 프로젝트명·도메인 치환 변수화 |
| Steering 파일 (7개) | runNshop 코딩 규칙 완성 | 공통 규칙과 프로젝트별 규칙 분리 |
| 코드 템플릿 | 3앱 + API 전체 화면 구현 중 | 도메인명·컬러·로고만 바꾸면 돌아가는 템플릿으로 추출 |

### 방법론 자산

| 자산 | 한 것 | 해야 할 것 |
|------|------|-----------|
| AI-DLC 9대 공정 | 공정 정의·순서·매핑 완료 | 공정별 체크리스트 작성 |
| 프로젝트 관리 방법론 | 업무 유형 A·B·C·D 분류 완료 | Phase A~D에 유형 매핑 |
| 협업 절차서 | 본 문서 작성 완료 | "현업 시연 프로토콜" 추가 (Phase B 운영 가이드) |
| 크로스체크 규칙 | 5회 수행 경험 기록 | 체크 항목 표준화 |

### 우선순위

```
즉시 (현재 Phase 3 진행 중)
    → Scaffolding 가이드 범용화 (프로젝트명 변수화)
    → Steering 파일 공통/프로젝트별 분리

Phase 5 완료 시점
    → 프로토타입 코드 템플릿 추출 (전체 화면 완성 후)
    → 화면정의서 템플릿화 (화면유형별 체크리스트)

방법론 확정 시점
    → Phase A~D 운영 가이드 문서화
    → 크로스체크 체크리스트 표준화
    → 초안 5종 범용 템플릿 완성
```

## 9. 핵심 원칙

```
1. 프로토타입이 커뮤니케이션 도구다
   → 문서가 아닌 동작하는 화면으로 현업과 소통

2. 요구사항은 만드는 것이 아니라 확인하는 것이다
   → 초안 + 프로토타입을 보여주고 "맞나요?"

3. AI는 반복 작업을 맡는다
   → 커스터마이징·코드 생성·크로스체크·문서 보완

4. 사람은 판단과 확정을 한다
   → PL: 기술 방향 / 현업: 비즈니스 확정

5. 자산은 축적된다
   → 매 프로젝트가 다음 프로젝트의 초안이 됨

6. 방관자를 확인자로 바꾼다
   → 선택지를 먼저 제시하여 의사결정을 유도
```
